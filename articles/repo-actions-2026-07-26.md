### 1. i18n Contribution Kit

**Type:** Community / DX
**Effort:** Small (hours)
**Impact:** The 10-community-PRs-by-Aug-1 hyperstition is at 5/10 with six days remaining. The fastest path to 3–5 additional PRs in that window isn't building a new feature — it's making the existing locale work so turnkey that any fork holder can contribute in under an hour without touching backend code. The i18n contribution kit creates exactly that pathway: a `LOCALES.md` guide, a scaffold script, a test harness, and a GitHub Discussions post template that recruits native speakers. The dictionary-only locale pattern requires zero knowledge of `.vue` files or Python. German and French both followed this pattern; the difference today is that no contributor guide exists for doing it — a fork holder who wants to add Spanish or Japanese has to reverse-engineer `locales/fr.js` manually. The kit removes that step. If three fork holders see the Discussion post and open a locale PR each, the hyperstition closes. The kit is also a permanent community onramp — every future locale contributor uses it.

**How:**
1. Create `frontend/src/locales/LOCALES.md` (~80 lines). Sections: **Overview** (current coverage: EN, ZH-CN, DE, FR; status on KO/JA/PT/ES as local commits pending push), **How to add a locale** (6-step walkthrough: copy `locales/fr.js` → rename → translate → update `i18n.js` import + locale array + `isLang` computed + `toggleLocale()` cycle + label map → update `LocaleToggle.vue` → add `README.{lang}.md` → run unit tests), **Translation guidance** (formal register for EU languages; standard developer register for East Asian; technical loan words keep common forms; JSON key ordering must match `locales/en.js` exactly — the test harness verifies this), **Key decisions reference** (table of the 20 most-used terms with EN → FR/DE examples as register guides), **Test command** (`cd frontend && npm run test -- locales`), **PR checklist** (6 items: LOCALES.md read, key count matches en.js, cycle updated, README.{lang}.md written, tests pass, PR title format `feat(i18n): add {language} locale`). Create `scripts/scaffold-locale.sh` (~30 LoC): takes a locale code argument, copies `locales/fr.js` to `locales/{code}.js`, replaces the header comment, outputs a step-by-step checklist to stdout with the exact files to edit and the exact lines to change in `i18n.js` and `LocaleToggle.vue`. The scaffold handles structure; the contributor handles only translation. Update the main `README.md` Contributing section to add a "Contributing a Locale" line with a link to `frontend/src/locales/LOCALES.md`.
2. Post a GitHub Discussions thread in the Show & Tell or Ideas category titled "Help add your language to MiroShark — contributor guide inside." Body (~300 words): intro (MiroShark in 100+ countries; 4 languages merged; 5th closes a September goal), what's needed (translate one JavaScript dictionary — no backend knowledge required), incentives (name in README contributor list, locale credit in file header), languages prioritized (PT, JA, ES, AR — with "KO/JA/ES already built as draft, needs native review" note), link to LOCALES.md, `@` mention 3–5 known fork holders. Update `docs/CONTRIBUTING.md` (create if absent) to add a "Locales" section mirroring LOCALES.md in condensed form.
3. Add 4 unit tests to the frontend test suite: (a) all keys in `locales/en.js` exist in `locales/fr.js` (key-parity gate), (b) `toggleLocale()` cycles through all supported locales without repeating, (c) `t('simulate', 'fr')` returns the expected French string, (d) scaffold script produces a file with the correct header comment. These tests serve as the CI gate that any new locale PR must pass — they run automatically and block merges where a locale file is missing keys or the cycle is broken. Document the test command in LOCALES.md and the PR checklist.

### 3. Simulation OG Image API

**Type:** Feature / Growth
**Effort:** Medium (1-2 days)
**Impact:** Twenty consecutive days of social silence. The mechanism isn't that people stopped talking about MiroShark — it's that sharing a simulation URL on X or Discord produces a blank link preview with nothing to retweet or screenshot. An OG image endpoint generates a social card automatically: simulation topic (first 80 chars), consensus direction chip (BULLISH/BEARISH/NEUTRAL), confidence percentage bar, platform icons, simulation metadata. When someone shares `miroshark.io/simulation/{id}`, a rich card appears. The card becomes retweetable on its own, without any caption required. Even a single share by one of 1,415 stargazers generates a visual that others can forward. The OG image is also the missing piece for the "5 external tutorials by Aug 15" path — a tutorial creator who shows the card preview in their thumbnail has a visual format viewers understand at a glance. The backend is a Python SVG template rendered on-the-fly and cached — no external image library required. This idea appeared in the Jul 18 candidate list but has not yet been built.

**How:**
1. Add `backend/app/services/og_image_service.py` (~150 LoC, pure stdlib). Function `generate_og_image(sim_id: str) -> bytes`. Reads `signal.json` (topic, consensus_direction, confidence_pct, agent_count, rounds, platforms, cost_usd). Generates an SVG string using Python string templating (no Pillow or cairosvg dependency). Dimensions: 1200×630px (standard OG size). Layout: black background (`#0a0a0a`), white headline (topic first 80 chars, max 2 lines, 36px sans-serif), consensus chip (BULLISH = `#22c55e`, BEARISH = `#ef4444`, NEUTRAL = `#eab308`, SPLIT = `#3b82f6` — 14px uppercase label, 8px radius), confidence bar (grey track with colored fill, percentage label, 180×6px), simulation metadata row (N agents · N rounds · platforms, 14px `#6b7280`), MiroShark wordmark bottom-left (16px `#9ca3af`), simulation URL bottom-right (14px `#6b7280`). SVG is purely text-based — no rasterization, no embedded fonts. Return SVG bytes with `Content-Type: image/svg+xml` by default; if `?format=png` is passed and Inkscape is available, rasterize via `subprocess.run(['inkscape', '--export-type=png', ...])`, otherwise fall back to SVG. Cache to `.og-cache/{sim_id}.svg` with 1-hour mtime TTL. Unpublished sim returns 404. Add 8 unit tests: SVG contains topic text, BULLISH produces `#22c55e` fill, confidence_pct=73 produces 73% bar width, platform list appears in metadata row, unpublished sim returns 404, second call returns cached file, 1200×630 viewBox in SVG, cost_usd appears if non-null.
2. Add `GET /api/simulation/{id}/og-image` to `backend/app/api/simulation.py` (~15 LoC). Returns SVG/PNG bytes with appropriate Content-Type. Publish-gated. Cache-Control: `public, max-age=3600`. Add `?format=png` param support. For server-side rendered simulation pages: inject `<meta property="og:image" content="/api/simulation/{id}/og-image">`, `<meta property="og:title" content="{topic_80chars}">`, `<meta property="og:description" content="{direction} consensus at {confidence}% — simulated by MiroShark">`, `<meta name="twitter:card" content="summary_large_image">`. If frontend is SPA (no SSR), document in `docs/API.md` that direct sharing of `/api/simulation/{id}/og-image` works as a standalone image URL, and that SSR (nginx `sub_filter` or Cloudflare Workers) is required for automatic crawler meta-tag injection. Add to `docs/API.md` under a "Social / OG" section with curl example and the `<meta>` tag block.
3. Add a "Copy OG image URL" option to Step3Simulation.vue's share menu: copies `{baseUrl}/api/simulation/{id}/og-image` to clipboard. Add an inline preview thumbnail (300×158px, scaled 1:4) in the share panel — an `<img>` pointing to the og-image endpoint so the card is visible before the user shares it. Update `surfaces_catalog.py` to add the og-image endpoint (type: social). Update `README.md` Features section: "Social cards: rich link previews for Twitter/X, Discord, and Slack — auto-generated for every published simulation."

### 5. Air-Gapped HuggingFace Cache Polish

**Type:** DX / Performance
**Effort:** Small (hours)
**Impact:** Issue #240 has been open for 20 days without movement. Every open issue without a response signals to 298 fork holders how the project handles user needs. The air-gapped HuggingFace feature is substantively important: enterprise teams and researchers in network-restricted environments (corporate VPNs, HPC clusters, government deployments) can't use MiroShark because it pulls HuggingFace models at runtime. A one-time offline cache setup unlocks the entire enterprise and academic institution deployment segment — exactly the audience most likely to produce the "academic citation by Sep 1" hyperstition. The implementation is a download script + documentation + environment variable gate: `MIROSHARK_HF_CACHE_DIR` points to a pre-populated directory; the application uses it instead of the live HuggingFace API. Additive, zero changes for non-air-gapped users. This idea has appeared in four consecutive candidate lists (Jul 8, Jul 10, Jul 18, Jul 20) without being built. With issue #240 now 20 days stale, the case for closing it outweighs any competing priority.

**How:**
1. Create `scripts/prefetch-hf-models.sh` (~50 LoC). Checks for `HF_CACHE_DIR` environment variable (defaults to `~/.miroshark-hf-cache/`). For each model ID referenced in the backend (locate by grepping `from_pretrained(` calls across `backend/app/`): calls `huggingface-cli download {model_id} --local-dir {HF_CACHE_DIR}/{model_id}`. Prints a progress summary after each download (model name, size, cache path). Prints a final summary (total models, total size, cache directory). Add a `--dry-run` flag that prints the model list without downloading. Add a `--list` flag that outputs a JSON array of model IDs for documentation and CI use. Design intent: run once on a network-connected machine; copy the resulting directory to the air-gapped target. Document in the `## Offline / Air-Gapped Setup` section of `docs/INSTALL.md`.
2. Update backend model loading to honor `MIROSHARK_HF_CACHE_DIR`. In each file that calls `from_pretrained()` (found via `grep -r "from_pretrained" backend/app/`): add `cache_dir = os.environ.get('MIROSHARK_HF_CACHE_DIR')` before the call; if set, pass `cache_dir=os.path.join(cache_dir, model_name)` (HuggingFace loads from local path, no network calls). If unset, use default online behavior (no change for connected users). Add `MIROSHARK_HF_CACHE_DIR=` to `backend/.env.example` with comment: `# Path to pre-downloaded HuggingFace models for offline/air-gapped environments. Run scripts/prefetch-hf-models.sh to populate.` If a `docker-compose.yml` is present, add a commented volume mount showing how to bind a local HF cache directory into the container.
3. Create `docs/AIRGAP.md` (~80 lines). Sections: **Who this is for** (corporate VPNs, HPC clusters, government deployments, offline demo environments), **Prerequisites** (one internet-connected machine, HuggingFace account for gated models), **Step-by-step** (5 steps: clone on networked machine → run `scripts/prefetch-hf-models.sh` → copy cache directory to air-gapped machine → set `MIROSHARK_HF_CACHE_DIR` in `.env` → `docker compose up`), **What gets downloaded** (model list with approximate sizes, generated from `--list`), **Docker** (volume mount snippet), **Verification** (how to confirm offline operation), **Troubleshooting** (model ID mismatch — run `--list` to compare against cached). Close issue #240 with a PR comment: "This PR implements the air-gapped HuggingFace cache requested in #240. See docs/AIRGAP.md for setup instructions." Update `README.md` to add: "Air-gapped deployment: pre-download HuggingFace models for offline environments — [docs/AIRGAP.md](docs/AIRGAP.md)."

## Selection Rationale

All five ideas address the active crises (20-day social silence, 6-day community-PR deadline, 20-day tutorial deadline) with minimal build time relative to impact.

- **i18n Contribution Kit (#1)** — The Aug 1 community-PR deadline is in six days at 5/10. Building a new feature won't generate five PRs from the community in that window; making locale contribution mechanically easy might. The kit creates a zero-background-required PR pathway — copy a file, translate strings, run four tests, open PR. If three fork holders convert, the hyperstition closes. The scaffold script does the structural work; contributors only translate.

- **Portuguese (PT) UI Locale (#2)** — The highest-population unbuilt locale after KO (suggested Jul 24). Brazil is the 5th-largest GitHub contributor market, with a developer community that produces a disproportionate share of open-source tutorials and tooling reviews. The dictionary-only pattern is validated at scale. One PR closes the 5-language hyperstition 37 days early and opens MiroShark to the largest Latin American developer audience.

- **Simulation OG Image API (#3)** — Twenty days of silence doesn't require a new community channel — it requires a visual worth sharing when one person shares a simulation link. An OG card turns a URL into an image. The SVG approach requires no external dependencies and generates a cache-friendly, shareable artifact automatically. Every shared simulation URL becomes a potential amplification event without the operator doing anything.

- **GitHub Discussions + Show & Tell Template (#4)** — The community-call hyperstition (3 speakers, Sep 1) has zero infrastructure. A Discussions thread asking "would you join?" is the minimum viable organizing mechanism. If three fork holders comment yes, the call gets scheduled. The Show & Tell category also gives 1,415 stargazers a place to share results without Twitter — the only community channel that currently requires an external account.

- **Air-Gapped HuggingFace Cache (#5)** — Issue #240 is 20 days stale. Closing it demonstrates responsiveness to the one documented user need in the tracker. The feature unlocks enterprise and academic institution deployment — the segment most likely to generate the "academic citation by Sep 1" hyperstition. Four consecutive candidate lists without being built; today the open-issue pressure makes the case decisive.
