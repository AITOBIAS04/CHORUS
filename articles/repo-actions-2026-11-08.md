### 1. Simulation Controversy Index

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Direction and confidence tell operators *what* a simulation concluded. They say nothing about *how contentious the debate was*. A simulation where 90% of agents agreed by round 3 is very different from one where 55% ended BULLISH after 24 rounds of heated argument — but both could share the same `direction: BULLISH`. A `controversy_score` (0–100) captures this: 100 = maximum polarization, sustained debate throughout; 0 = instant, unanimous consensus. Computed from two inputs: stance distribution distance (how far from 50/50 the final split was) and debate intensity (average posts per round × mention density). Operators can sort the gallery by controversy to find "the most contentious scenario I've run", researchers can distinguish weak-consensus results from strong ones, and the compare endpoint gains a richer signal than confidence alone. Zero new data sources — derived entirely from existing `signal.json` (stance splits) and `actions.jsonl` (post counts, mentions).

**How:**
1. Create `backend/app/services/controversy_service.py` (~120 LoC, pure stdlib). Accept `sim_id: str`. Load `signal.json` → extract `{bullish_pct, neutral_pct, bearish_pct, total_rounds}`. Load `actions.jsonl` → aggregate posts per round (a dict `{round: post_count}`). Compute `stance_distance = 1.0 - abs(bullish_pct - bearish_pct) / 100.0` (0.0 when unanimous, 1.0 when 50/50 split). Compute `intensity = mean(posts_per_round) / max_posts_per_round` (0.0–1.0; falls back to 0.0 if `actions.jsonl` absent). `controversy_score = round(0.6 * stance_distance * 100 + 0.4 * intensity * 100)` (weighted: stance distribution is more informative than raw intensity). Cache to `storage/simulations/{id}/controversy.json` (immutable after sim completes — no TTL). Merge `controversy_score: int` into `signal.json` during the signal-writing step. Add 5 unit tests: 50/50 bullish/bearish split → `stance_distance = 1.0`; 100% BULLISH → `stance_distance = 0.0`; `controversy_score` is in range [0, 100]; cached result returned on second call without re-computing; missing `actions.jsonl` falls back gracefully with `intensity = 0.0`.
2. Add `GET /api/simulation/:id/controversy` to `backend/app/api/controversy.py`. Publish-gated. Session-auth. Response: `Content-Type: application/json`, `Cache-Control: max-age=3600, private`. Return `{controversy_score: int, stance_distance: float, debate_intensity: float, posts_per_round: {round: int}, label: str}` where `label` is `"Highly Contested"` (≥70), `"Moderately Contested"` (40–69), or `"Strong Consensus"` (<40). Add `controversy_score` to the OpenAPI `Signal` schema. Add to `surfaces_catalog.py` (type: `analytics`). Add to `docs/API.md` under "Analytics". During simulation completion (wherever `signal.json` is written), call `controversy_service.compute(sim_id)` and merge `controversy_score`. Add 2 integration tests: endpoint returns 200 with `controversy_score` for a completed published sim; `controversy_score` is present in `signal.json` after sim completion.
3. Add a "Controversy" column to the gallery sort controls (alongside stars, confidence, date). Gallery card gains a small controversy badge below the confidence display: a flame icon with the numeric score, colored red (≥70), orange (40–69), or gray (<40). The signal card in Step 3 adds a "Controversy Index" row: score + label + a one-line tooltip ("How hotly contested was this simulation? 100 = maximum polarization."). Add `controversy_score` as a sortable column in the gallery URL param (`?sort=controversy_score`). Add 2 frontend unit tests: gallery card renders controversy badge when `controversy_score` is present; sort by controversy fires gallery fetch with `?sort=controversy_score`.

### 2. Agent Pool Pre-Filter by Profession

**Type:** Feature / DX
**Effort:** Small (hours)
**Impact:** Every MiroShark simulation builds a fresh roster of 100+ grounded agents with demographic attributes: age, profession, risk tolerance, platform. When an operator asks "How will retail investors react to the Fed cut?", they want the roster skewed toward retail investors — not a uniform cross-section that dilutes the target audience's signal with institutional and crypto-native perspectives. Right now there is no way to influence roster composition before the sim starts. Adding an optional `agent_filter` to the simulation start payload — `{profession_tags: ["retail investor", "day trader"]}` — lets the graph builder weight agent selection toward matching professions. The backend applies a 2× weight multiplier to agents matching the filter during graph construction; non-matching agents still appear (minimum 20% coverage for cross-perspective validity) but are under-represented. This is not a whitelist — it is a weighted bias. Operators who consistently run audience-specific scenarios (financial services, policy research, ad testing) get dramatically more targeted simulations without changing any other parameter.

**How:**
1. Modify the simulation start payload schema: add an optional `agent_filter: {profession_tags: list[str], weight_multiplier: float}` field (default: `null`, no filter; `weight_multiplier` defaults to 2.0, clamped 1.5–5.0 to prevent complete exclusion of non-matching agents). Validate `profession_tags`: each tag must be a non-empty string under 50 chars, max 5 tags. Update `backend/app/api/simulations.py` (the POST start endpoint) to accept and pass `agent_filter` to the simulation runner. Update the graph builder's agent selection step (wherever the roster is assembled from the demographic seed): when `agent_filter` is set, sort the candidate pool descending by `profession_match_score` (1.0 if any tag in `agent_filter.profession_tags` is a case-insensitive substring of the agent's profession string; 0.0 otherwise). Apply weighted sampling: assign sampling weights `[weight_multiplier if match else 1.0]` and use reservoir sampling to select the target agent count. Enforce minimum 20% non-matching agents: if the weighted sample would yield <20% non-match, re-sample to enforce the floor. Persist `agent_filter` in the simulation's `config.json` for audit. Add 5 unit tests: null `agent_filter` → uniform agent selection unchanged; `weight_multiplier` above 5.0 → clamped to 5.0; non-matching agents always ≥20% of final roster; profession matching is case-insensitive; more than 5 profession tags returns 400.
2. Add `agent_filter` to the OpenAPI simulation start request schema. Add `{applied_filter: {profession_tags: [str], weight_multiplier: float, matching_agents: int, total_agents: int} | null}` to the simulation start response (so the caller knows how many agents matched). Add to `docs/API.md` under "Running Simulations" with a note: "agent_filter biases roster composition — it does not exclude non-matching agents entirely. Use this to tilt perspectives, not to run a mono-profession simulation." Add 2 integration tests: simulation started with `agent_filter` stores filter in `config.json`; `matching_agents` in start response is non-zero when a valid profession tag matches the agent pool.
3. Add an "Agent Filter" collapsible section to Step 2 (EnvSetup) in the frontend, below the Scenario selector. The section shows: a text input for profession tags (comma-separated, with auto-complete from a static list of common professions: "retail investor", "institutional investor", "crypto trader", "policy analyst", "tech worker", "journalist", "academic", "day trader", "market maker", "regulator"). A weight slider (1.5× to 5.0×, labeled "Lean toward these agents"). A live preview line: "Filter active: 2 tags — expect ~60% matching agents at 2.0× weight." The preview is computed client-side (approximate: `min(0.8, (matching_pct * weight / (matching_pct * weight + (1 - matching_pct))))` where `matching_pct` is estimated based on how common the tags are). Add 2 frontend unit tests: collapsible section renders in Step 2 with no interaction breaking existing scenario selector; selecting a profession tag adds it to the comma-separated input.

### 3. "Run This Scenario" Embed Button

**Type:** Growth / Community
**Effort:** Small (hours)
**Impact:** GitHub repos, Notion wikis, and research blogs that document scenarios have no way to let readers instantly re-run the same simulation. Currently, sharing a MiroShark simulation sends people to a completed result — a frozen artifact. Adding a "Run this scenario" embed button gives readers a one-click path to spawn a fresh run with the same topic and scenario parameters, landing on the MiroShark new-simulation page pre-filled. `GET /api/simulation/:id/run-button.svg` returns a Shields.io-style flat SVG: "▶ Run on MiroShark" in purple with a hover-state alt text. Open-source projects documenting their community stress tests, researchers publishing repeatable methodologies, and operators who want community members to explore their scenarios all benefit. The `<a href>` wraps the entire SVG, pointing to `{base_url}/new?topic={urllib.parse.quote(topic)}&scenario={urllib.parse.quote(scenario_title or '')}`. Escape `<`, `>`, `&` in the topic and scenario title fields. Keyless (no auth) for published sims; 404 for unpublished. `Cache-Control: max-age=86400, public` (SVG content is immutable for a given sim; the link target topic rarely changes). ### 4. Email Digest Export

**Type:** Feature / Community
**Effort:** Small (hours)
**Impact:** Operators who run weekly simulations and share them in newsletters (Substack, Beehiiv, Ghost, Mailchimp) currently need to manually extract the topic, direction, confidence, and key agent quotes from the simulation detail page. The existing article generator produces a long-form Substack piece — too long for a newsletter section that devotes one paragraph per simulation. `POST /api/simulation/:id/digest` returns a compact, email-ready HTML fragment: a header row (topic + direction badge + confidence), the top 3 agent quotes (one per platform, filtered by influence quartile), the trajectory chart as a base64 inline `<img>` (for email clients that block external images), and a one-line CTA footer linking to the full result. The response is `text/html` — operators paste it into their newsletter editor. No server-side email sending, no subscriptions, no SMTP — just an HTML fragment export. This fills the gap between "long article" and "one-line badge" for the newsletter use case at the exact right granularity.

**How:**
1. Create `backend/app/services/digest_service.py` (~180 LoC, pure stdlib). Accept `sim_id: str`. Load `signal.json` → `{topic, direction, confidence_pct, share_url}`. Load `actions.jsonl` → extract top 3 agent posts by platform (one per platform: X, Reddit, Markets; prioritize high-influence agents using `influence_score` from `stance_flips.json` if available, else use post_count as proxy; filter to posts from the final 3 rounds for recency). Load trajectory chart: check if `storage/simulations/{id}/trajectory.svg` or `trajectory.png` exists; if PNG: base64-encode using `base64.b64encode(open(path,'rb').read()).decode()`; if SVG: inline as a `<svg>` block; if absent: skip the chart section. Direction-to-color map: `{"BULLISH": "#22c55e", "BEARISH": "#ef4444", "NEUTRAL": "#6b7280"}`. Build the HTML string using an f-string template: (a) a header row with `<b>{topic}</b>` and an inline span badge `<span style="background:{color};color:white;padding:2px 8px;border-radius:4px;font-weight:bold;">{direction} · {confidence_pct}%</span>`; (b) a "Top voices:" unordered list with 3 `<li>` items — `<b>{agent_name} ({platform}):</b> "{post_text_truncated_to_200_chars}"`; (c) the trajectory chart as `<img src="data:image/png;base64,{b64}" width="600" alt="Belief trajectory" />` or inline SVG (if SVG); (d) a footer `<p><a href="{share_url}">View full simulation →</a></p>`. Sanitize all user-sourced strings (topic, agent names, post text) with `html.escape()` to prevent XSS in the exported HTML. Cache to `storage/simulations/{id}/digest.html` with 15-min mtime TTL. Add 5 unit tests: `html.escape()` applied to topic containing `<script>` tags; direction badge uses correct color for BEARISH; top quotes list has at most 3 items; trajectory chart section absent when chart file missing; cached digest returned on second call without re-computing.
2. Add `POST /api/simulation/:id/digest` to `backend/app/api/digest.py`. Publish-gated. Session-auth. No request body. Response: `Content-Type: text/html; charset=utf-8`, `Cache-Control: max-age=900, private`. Return the full HTML fragment (not a full HTML document — no `<html>`, `<head>`, `<body>` wrappers). Add to `surfaces_catalog.py` (type: `export`). Add to `docs/API.md` under "Exporting Results" with a note: "Returns an HTML fragment (not a full page) suitable for pasting into Substack, Beehiiv, Ghost, or Mailchimp's HTML editor. All images are base64-inlined for email-client compatibility." OpenAPI schema: `DigestResponse` (or document as a free-form HTML response). Add 2 integration tests: returns 200 `text/html` for a completed published sim; response contains the simulation topic in the HTML.
3. Add "Email Digest" to the Step 3 share panel (EmbedDialog), alongside the article generator and existing share surfaces. Panel shows: a live HTML preview in a sandboxed `<iframe>` (using `srcdoc` attribute, no external navigation risk); a "Copy HTML" button; and a brief note: "Paste this HTML block directly into your newsletter editor — Substack, Beehiiv, Ghost, Mailchimp. All images are embedded." The preview refreshes once on panel open (single POST call with a 15-min cache on the backend). Add a "Regenerate" button for operators who want to re-fetch after the sim data changes. Add 2 frontend unit tests: digest preview renders in a sandboxed iframe without error for a completed published simulation; "Copy HTML" button copies the full HTML fragment to clipboard.

### 5. Cross-Platform Divergence Alert

**Type:** Feature / Analytics
**Effort:** Small (hours)
**Impact:** The existing `platform_sentiment_service.py` (built June 2026) computes per-platform bullish/neutral/bearish splits and surfaces them in a Step 3 "Platforms" overlay. It does not check whether platforms agree with each other. A simulation where X users are 75% BULLISH while Reddit users are 65% BEARISH is an entirely different signal from one where all three platforms converge at 70% BULLISH — but both appear as "BULLISH" in `signal.json`. Adding a `platform_divergence` field to `signal.json` and a `TOKEN_REPORT_LP_ALERT`-style alert gate in the platform sentiment flow gives operators an automatic "this sim's platforms disagree" flag. The alert fires when any two platforms' BULLISH percentages differ by more than 30 points. Downstream uses: the article generator can include "notably, X users were bullish while Reddit was bearish" framing; the compare endpoint can flag when two simulations' divergence patterns differ; and the gallery can filter to "high-divergence simulations only" for research into echo-chamber vs. cross-platform consensus scenarios.

**How:**
1. Extend `backend/app/services/platform_sentiment_service.py`: after computing per-platform splits, add a `compute_divergence(platform_sentiments: list[dict]) -> dict` function (~40 LoC). Input: list of `{platform, bullish_pct, neutral_pct, bearish_pct}` dicts. Compute all pairwise BULLISH deltas: `{(p_a, p_b): abs(p_a.bullish_pct - p_b.bullish_pct)}` for every pair. `max_divergence_pair`: the pair with the largest delta. `divergence_score`: the max delta (0–100). `alert`: `divergence_score >= 30`. `direction_consensus`: `True` if all platforms share the same direction (BULLISH/BEARISH/NEUTRAL majority). Build the output: `{divergence_score: float, alert: bool, max_divergence_pair: {platforms: [str, str], delta: float, directions: [str, str]}, direction_consensus: bool}`. Merge this into the existing `GET /api/simulation/:id/platform-sentiment` response as a top-level `divergence` key. Also write `platform_divergence: {score: float, alert: bool, max_pair: [str, str]}` into `signal.json` during the signal-writing step. Add 5 unit tests: all platforms at same BULLISH% → `divergence_score = 0.0, alert = False`; X=80% BULLISH, Reddit=40% BULLISH → `divergence_score = 40.0, alert = True`; `direction_consensus=True` when all platforms' majority direction matches; `direction_consensus=False` when platforms split majority direction; single-platform simulation → `divergence_score = 0.0, alert = False` (no pairs to compare).
2. Update `GET /api/simulation/:id/platform-sentiment` to include the `divergence` block in the response. Update the OpenAPI `PlatformSentimentResponse` schema to add `divergence: PlatformDivergenceBlock`. Add `platform_divergence` to the OpenAPI `Signal` schema. Update `docs/API.md` under "Analytics" (the platform-sentiment entry): add a note — "When `divergence.alert = true`, the simulation's platforms disagreed by more than 30 points on the BULLISH direction. This may indicate echo-chamber effects or cross-platform narrative divergence." Add 2 integration tests: `platform_divergence.alert = true` appears in `signal.json` for a sim where platforms diverged by ≥30 points; `platform_divergence.alert = false` for a sim where all platforms agreed within 30 points.
3. Update the Step 3 "Platforms" overlay in the frontend: when `divergence.alert = true`, prepend an amber warning banner at the top of the overlay — "⚠ Platforms diverged: {platform_a} ({pct_a}% bullish) vs {platform_b} ({pct_b}% bullish) — {delta} point gap." Update the signal card (Step 3 header) to include a small platform icon row: when all platforms agree, show three matching-color stance chips; when `divergence.alert = true`, show mismatched chips with an amber border. Add a "Divergence" sort option to the gallery: `?sort=platform_divergence_score` for operators who want to surface their most cross-platform contentious simulations. Add 2 frontend unit tests: amber divergence banner renders only when `divergence.alert = true`; signal card shows mismatched platform chips when divergence alert is active.
