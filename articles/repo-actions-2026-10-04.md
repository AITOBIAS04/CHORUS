### 1. Simulation Replay GIF Export

**Type:** Feature / Growth
**Effort:** Small (hours)
**Impact:** Every simulation has a belief drift story — `round 1: 42% bullish → round 3: 67% bullish → round 5: 88% bullish`. Currently there is no way to share that story as a self-contained visual artifact. `GET /api/simulation/{id}/animation.gif` returns a looping GIF: each frame is one round of the belief bar (a full-width horizontal strip, color-split bullish/neutral/bearish), with the round number and confidence_pct overlaid in white text. The final frame lingers 3× longer to show the resolution. The GIF is cached permanently to `.gif-cache/{simulation_id}.gif` on first generation. Because GIFs play automatically in Discord, Telegram, Twitter/X, Slack, and iMessage — no browser click required — a shared simulation URL that auto-embeds the animated GIF communicates the entire arc of the simulation without opening a link. During 88 days of silence, every artifact that travels without a human actively composing it matters. Distinct from: Replay Visualizer (Sep 28 — an interactive frontend component requiring a browser), Social Card PNG (Oct 2 — a single static frame optimized for og:image). This is the **shareable animation layer** — the belief drift arc as a standalone visual file that works in any messaging context.

**How:**
1. Create `backend/app/api/gif_export.py` (~110 LoC). `GET /api/simulation/{id}/animation.gif`. Publish-gated (returns 404 for unpublished). Cache: check `.gif-cache/{simulation_id}.gif` — if exists, serve directly with `Content-Type: image/gif`. If cache miss, generate. Reads `trajectory.json` for the simulation to get the per-round belief data: `[{round, bullish_pct, neutral_pct, bearish_pct, confidence_pct}]`. Image generation using `Pillow` (PIL) library (already in `backend/requirements.txt` per Social Card work). Frame spec: 800×120px, `#0f0f12` background. Per-round frame: (1) Draw a full-width horizontal belief bar at y=40, height=36px — bullish section `#7c3aed` (bullish_pct × 800 wide), neutral section `#6b7280`, bearish section `#ef4444`. Sections are proportional to their percentage. (2) Overlay text left: "Round {n}/{total_rounds}" in 18px white. (3) Overlay text right: "{direction} {confidence_pct}%" in 18px, direction-colored. Frame duration: 600ms per round frame, 1800ms for the final frame. Use `images[0].save(..., save_all=True, append_images=images[1:], loop=0, duration=[600]*n_frames)`. Write to `.gif-cache/` directory. Return bytes with `Content-Type: image/gif`, `Cache-Control: public, max-age=86400`. Create `.gif-cache/` directory in the startup check alongside other cache dirs. Add 3 unit tests: 404 for unpublished sim; valid GIF magic bytes (`GIF89a`) for published sim; frame count equals total_rounds + 1 (for extended final frame).

2. Add `GET /api/simulation/{id}/animation.gif` to `surfaces_catalog.py` (type: `media`) and OpenAPI schema noting it returns `image/gif` and is permanently cached once generated. Inject into the Step 3 page meta tags as an additional sharing resource: add `<meta name="twitter:player" content="{BASE_URL}/api/simulation/{id}/animation.gif">` (this triggers Twitter's GIF embed behavior when the URL is pasted). Also add a direct download link in the Step 3 share panel: a `🎞 Download GIF` button alongside the existing share controls that calls `GET /api/simulation/{id}/animation.gif` and triggers a browser download. Add a `curl` example in `EmbedDialog.vue`: `curl "{BASE_URL}/api/simulation/{id}/animation.gif" -o simulation.gif`. Register route in `backend/app/main.py`. Add to `docs/API.md` under "Media Endpoints" and `docs/FEATURES.md`. Add to the README "API" section: "Download any simulation as an animated GIF at `GET /api/simulation/{id}/animation.gif`."

3. Add a `?fps=N` query param (default: 1.67fps, computed from 600ms frame duration). Clamp to [0.5, 5]. At 5fps a 5-round simulation is 1 second; at 0.5fps a 5-round simulation is 10 seconds. This lets embed consumers control the playback speed without needing to post-process the GIF. Implement as a `duration_ms = int(1000 / fps)` override fed into the Pillow save call — no architectural change. Add 1 unit test: `?fps=5` produces frames with 200ms duration. Also add a `?style=compact` variant (default: normal) that renders at 400×60px instead of 800×120px for inline embedding in narrow contexts (Telegram bot messages, Discord embeds with multiple fields). The compact variant uses the same Pillow logic with halved dimensions and 14px font. Add 1 unit test for compact dimensions. Document both params in `docs/API.md`.

### 2. Topic Autocomplete API

**Type:** DX / Feature
**Effort:** Small (hours)
**Impact:** New users arriving at MiroShark's Step 1 input face a blank text field with no hint of what others have simulated. The most common abandonment point for generative tools is the blank first input. `GET /api/topics/autocomplete?q=btc&limit=8` returns up to 8 previously simulated topic strings that start with or contain the query token — sorted by simulation frequency (most-simulated topics first). Step 1 shows these as a dropdown as the user types, with each suggestion including a tiny direction badge (the dominant direction for that topic across all its simulations). Clicking a suggestion pre-fills the topic field. This converts a blank-page anxiety problem into a discovery problem: the user sees "BTC Q4 2026" appeared 14 times with 71% bullish rate — and decides either to re-run it for their own timestamp or to try "BTC Q1 2027" as a variation. Session starts that begin from a suggestion have meaningfully lower abandonment than cold-start typings. Distinct from: Full-Text Search (Jun 14 — returns full simulation objects given a user query), Hot Topics Feed (Sep 30 — aggregated topic-level stats with no prefix matching), Similar Simulations Discovery (Sep 30 — topical adjacency based on a *completed* simulation ID). This is the **suggestion layer for the creation flow** — pre-run, not post-run.

**How:**
1. Create `backend/app/services/autocomplete_service.py` (~120 LoC, pure stdlib). Class `AutocompleteService`. Index structure: a dict `{normalized_topic: {simulation_count, dominant_direction, avg_confidence_pct}}`. Normalization: lowercase, strip whitespace, collapse internal runs of whitespace to single space. Index build: scan all published simulation directories, read `signal.json` for each, group by normalized topic, compute per-topic `simulation_count` (len of group), `dominant_direction` (mode of `direction` across group, ties broken: BULLISH > NEUTRAL > BEARISH), `avg_confidence_pct` (mean, rounded to 1 decimal). Cache to `.autocomplete-cache/index.json` with 10-minute mtime TTL. Function `autocomplete(q: str, limit: int = 8) -> list[dict]`: (1) Strip and lowercase `q`. If `len(q) < 2`, return `[]`. (2) Scan all keys in the index: include if `q in key` (substring match, case-insensitive). Sort by `simulation_count` descending, then by `avg_confidence_pct` descending. Return top `limit` as `[{topic, simulation_count, dominant_direction, avg_confidence_pct}]`. Add 4 unit tests: returns empty for q shorter than 2 chars; substring match works mid-string ("btc" matches "ETH vs BTC" via lowercase); results sorted by simulation_count desc; result count capped at limit.

2. Add `GET /api/topics/autocomplete` to `backend/app/api/`. Query params: `q` (str, required, min 2 chars), `limit` (int, clamp [1, 20], default 8). Returns `{suggestions: [{topic, simulation_count, dominant_direction, avg_confidence_pct}]}`. Cache-Control: `max-age=60` (1 minute — stale suggestions are low-cost). Add to `surfaces_catalog.py` (type: `discovery`) and OpenAPI schema with `AutocompleteResponse` and `AutocompleteSuggestion`. Add 2 integration tests: response shape is correct; empty `suggestions` array (not null) when no matches. Register route in `backend/app/main.py`. Add to `docs/API.md` under "Discovery Endpoints" with a note: "Designed for live type-ahead inputs — debounce at 200ms to avoid per-keystroke requests." Add to `docs/FEATURES.md`.

3. Wire into the Step 1 topic input in `frontend/src/views/Step1TopicEntry.vue`. On each keystroke (debounced 200ms), if `q.length >= 2`, call `GET /api/topics/autocomplete?q={encodeURIComponent(q)}&limit=8`. Render a dropdown below the input using a `<ul>` absolutely positioned relative to the `<input>`. Each `<li>` shows: topic text (bold-highlights the matched characters), a direction badge chip (`↑ BULLISH` / `→ NEUTRAL` / `↓ BEARISH` in direction color), and a muted simulation count (`12 sims`). Clicking or pressing Enter on a suggestion: (a) fills the topic input, (b) closes the dropdown, (c) moves focus to the next step. Dismiss on Escape or click-outside via `useEventListener('click', outsideClickHandler)`. Show a "No prior simulations found — run the first one" empty state when `suggestions.length === 0` and `q.length >= 2` (this is not an error state — it's an invitation). Bilingual (EN/ZH-CN). This is the highest-traffic endpoint in terms of calls-per-session (every user types in Step 1) — the 10-minute cache and 1-minute `Cache-Control` prevent thundering-herd on first launch.

### 4. Simulation Digest Markdown Export

**Type:** DX / Integration
**Effort:** Small (hours)
**Impact:** MiroShark has three export surfaces: `signal.json` (raw machine-readable aggregate), `signed-result.json` (cryptographic envelope), and the Jupyter notebook (full data + analysis cells). None of them produce a human-readable Markdown block that can be pasted directly into a GitHub README, a newsletter, a GitHub Discussion body, or a Notion page. `GET /api/simulation/{id}/digest.md` returns a compact, paste-ready Markdown summary: a `## MiroShark: {topic}` header, a direction + confidence line, a belief bar using Unicode block characters (`▓▓▓▓▓▒▒░░░░` — no images required), a 3-column agent platform table, the top 3 most influential agents (name, stance, influence score), and the simulation URL. The whole block is 15–20 lines — compact enough to include in a README section without overwhelming it. A user who wants to cite a MiroShark simulation in their project's README currently has to manually copy-paste from the UI, format it themselves, and keep it manually updated. `digest.md` makes the citation one `curl` command. Distinct from Jupyter Notebook Export (Oct 2 — full analytical notebook with code cells and charts), Signed Result JSON (Jun 8 — cryptographic provenance, not human-readable), Social Card PNG (Oct 2 — visual image for og:image).

**How:**
1. Create `backend/app/api/digest.py` (~90 LoC, pure stdlib). `GET /api/simulation/{id}/digest.md`. Publish-gated (returns 404 for unpublished). Reads `signal.json`, `trajectory.json` (for final-round data), and `actions.jsonl` (for per-agent data). Builds the Markdown string in memory: (1) **Header**: `## MiroShark Simulation: {topic}`. (2) **Result line**: `**{DIRECTION}** · {confidence_pct}% confidence · {agent_count} agents · {total_rounds} rounds`. (3) **Belief bar**: Unicode block-character bar showing bullish/neutral/bearish split at the final round. Bar is 20 characters wide. Bullish portion: `█` × `int(bullish_pct/100 * 20)`, neutral: `▒`, bearish: `░`. Label below: `{bullish_pct}% bullish / {neutral_pct}% neutral / {bearish_pct}% bearish`. (4) **Platform table** (if platform data available): `| Platform | Bullish | Bearish |` Markdown table, 3 rows max (top 3 platforms by agent count). (5) **Top agents** (if `actions.jsonl` available): `### Top Agents` — a 3-row Markdown table `| Agent | Stance | Influence |` showing the top 3 agents by `influence_score` from `signal.json`'s `top_agents` field. (6) **Footer**: `[View simulation]({BASE_URL}/simulation/{simulation_id}) · Generated by [MiroShark](https://github.com/aaronjmars/MiroShark) · {published_at[:10]}`. Return with `Content-Type: text/markdown; charset=utf-8`, `Content-Disposition: attachment; filename="miroshark-{simulation_id}.md"`. Add 3 unit tests: 404 for unpublished; valid Markdown string (contains `##` header and `**` bold); belief bar is exactly 20 chars of Unicode block characters.

2. Add `GET /api/simulation/{id}/digest.md` to `surfaces_catalog.py` (type: `export`) and OpenAPI schema noting `text/markdown` content type. Add a "Copy Markdown" button to the Step 3 share panel — alongside "Copy Link" and the GIF/Notebook export buttons. Also include in `EmbedDialog.vue` under "Export" as a `curl` example: `curl "{BASE_URL}/api/simulation/{id}/digest.md"`. Add to `docs/API.md` under "Export Endpoints" with a note: "Returns paste-ready Markdown — useful for READMEs, newsletters, or GitHub Discussion bodies." Add to `docs/FEATURES.md`. Register route in `backend/app/main.py`.

### 5. Confidence Distribution Analytics

**Type:** Feature / Analytics
**Effort:** Small (hours)
**Impact:** MiroShark surfaces individual simulation confidence scores but has never published an aggregate distribution: "what does a MiroShark confidence_pct number actually mean across 8,000+ simulations?" `GET /api/analytics/confidence-distribution` computes a histogram of confidence_pct across all published simulations — 10-point buckets from [0–10] to [90–100] — plus summary statistics: median, mean, p75, p90, and the percentage of simulations in each direction band. This data serves three audiences: (1) **Researchers** calibrating models built on MiroShark data — knowing that 62% of simulations score above 70% confidence tells them this isn't a flat distribution. (2) **Journalists / analysts** writing "MiroShark predicts X" — "78% confidence" is context-free without knowing whether 78% is high, average, or low for this platform. The distribution answers that. (3) **The MiroShark narrative** — if the median confidence is 74%, the platform can truthfully claim "when we say bullish, we mean it at 74% confidence, on average." Distinct from: Consensus Heatmap API (Oct 2 — topic-grouped direction analysis), Per-Round Confidence Trajectory (Jun 11 — temporal per-sim trajectory), token-report (MIROSHARK token price analytics, not simulation confidence).

**How:**
1. Create `backend/app/services/confidence_distribution_service.py` (~100 LoC, pure stdlib). Function `get_confidence_distribution() -> dict`. Logic: (1) Scan all published simulation directories. Read `signal.json` for each (skip unpublished). Collect `confidence_pct` (float) and `direction` (str) for each sim. Cache the raw list to `.confidence-dist-cache/raw.json` with 30-minute mtime TTL — this avoids re-scanning 8,000+ directories on every call. (2) Compute histogram: 10 buckets `[0,10), [10,20), …, [90,100]` — count sims in each bucket. Bucket key format: `"0-10"`, `"10-20"`, etc.; `"90-100"` bucket is inclusive on 100. (3) Compute summary stats using pure stdlib: `sorted_scores = sorted(all_confidence_pcts)`. Median: `sorted_scores[len//2]` (or average of two middle values for even count). Mean: `sum / len`. P75: `sorted_scores[int(len * 0.75)]`. P90: `sorted_scores[int(len * 0.90)]`. (4) Compute direction split counts: `{BULLISH: n, NEUTRAL: n, BEARISH: n}` and pcts. (5) Return: `{total_simulations, buckets: [{range, count, pct}], stats: {mean, median, p75, p90}, direction_split: {BULLISH: {count, pct}, ...}}`. Cache full result to `.confidence-dist-cache/distribution.json` with same 30-minute TTL. Add 4 unit tests: empty corpus returns valid structure with zero counts; all-100% confidence sims land in 90-100 bucket only; mean is correct; direction_split pcts sum to 100.

2. Add `GET /api/analytics/confidence-distribution` to `backend/app/api/`. No query params on the base form (the distribution is always over all published sims). Returns the dict from Step 1. Cache-Control: `max-age=1800` (30 min, matching the disk cache). Add to `surfaces_catalog.py` (type: `analytics`) and OpenAPI schema with `ConfidenceDistributionResponse`, `ConfidenceBucket`, `DistributionStats`, and `DirectionSplit`. Add 2 integration tests: response has correct shape; `buckets` array has exactly 10 entries. Register route in `backend/app/main.py`. Add to `docs/API.md` under "Analytics Endpoints" with a note on the 30-minute cache and a sample use case: "Use this to calibrate what a confidence_pct score means relative to the full simulation corpus." Add to `docs/FEATURES.md`. Add `GET /api/analytics/confidence-distribution` to the CHORUS agent's next token-report article as a sidebar data point ("MiroShark simulations average X% confidence") once the endpoint is live.

3. Surface in the frontend as a chart at `/analytics/confidence` (a sub-route of `/analytics`). Fetches `GET /api/analytics/confidence-distribution` on mount. Renders: (1) A bar chart of the 10 histogram buckets — bars are violet (`#7c3aed`), width proportional to count, heights proportional to pct. X-axis: bucket ranges. Y-axis: % of simulations. (2) Three stat tiles below the chart: Median, P75, P90 confidence scores in dark-themed number tiles (same style as token-report tiles). (3) A direction split bar: a single full-width stacked bar (bullish/neutral/bearish) with percentage labels — shows "across all simulations, {bullish_pct}% resolved bullish." Add a `<title>` and meta description for SEO: "MiroShark Confidence Distribution — how confident is the swarm across 8,000+ simulations?" Add `/analytics/confidence` to `frontend/src/router/index.js`. Add "Confidence Stats" link under an "Analytics" nav section. Bilingual (EN/ZH-CN). The `/analytics/confidence` page URL is linkable — include it in the next CHORUS article as a citation when reporting on simulation confidence levels.

## Selection Rationale

Five ideas for Day 4 of Hacktoberfest, 88-day silence, and the GH_GLOBAL-blocked reality where all features are design artifacts until push access is restored.

- **Simulation Replay GIF (#1)** — The first export surface that works natively in messaging apps without browser interaction. A GIF in a Telegram or Discord message auto-plays and communicates the full belief arc. No curl, no browser, no click. During 88 days of silence, every artifact that travels without a human composing a caption is worth building. The per-round framing also tells a better story than the static Social Card (Oct 2): not just "what did it conclude" but "how did it get there."

- **Topic Autocomplete API (#2)** — Addresses the highest-friction moment in the user flow: the blank Step 1 input. Prior ideas focused on post-simulation export and discovery. This is pre-simulation discovery — before a user even commits to running a sim. Suggestions pre-populated with direction badges and simulation counts convert a cold-start problem into a browsing problem. Zero external dependencies; the corpus of 8,000+ topic strings is the entire data source.

- **GitHub Discussions Auto-Publisher (#3)** — The only idea this batch that uses `GITHUB_TOKEN` instead of GH_GLOBAL. Every other community/growth idea is blocked until push access returns. Discussions require only read-write to the target repo's Discussions API — `GITHUB_TOKEN` from the `aeon.yml` workflow covers this. The 302-fork ghost town gets a live activity layer on GitHub.com itself. Every published simulation becomes a permanent, Google-indexed, commentable thread.

- **Simulation Digest Markdown (#4)** — Fills a gap between the machine-readable `signal.json` and the research-grade Jupyter notebook. The `digest.md` endpoint is the "paste this" export for humans: README sections, newsletter callouts, GitHub Discussion bodies, Notion embeds. A 15-line Markdown block that works in any text context — no image renderer, no runtime, no schema knowledge required. The Unicode belief bar is the bit that travels furthest in low-bandwidth contexts (Telegram, plain email).

- **Confidence Distribution Analytics (#5)** — The "meta-calibration" layer that gives all prior signal data context. 8,000+ simulations with confidence scores and no aggregate distribution to interpret them against. This endpoint answers "is 78% confidence high for MiroShark?" without human analysis. It's the foundation for every future claim about signal reliability — and the `/analytics/confidence` page URL becomes a citation asset for CHORUS articles writing about simulation quality.
