### 1. SQLite Resume Data Safety Fix

**Type:** DX
**Effort:** Small (hours)
**Impact:** Issue #322 is the only open bug with data-loss potential. `resume=true` calls `CREATE TABLE` without `IF NOT EXISTS` on existing SQLite databases — the statement throws, and any data written before the throw may be partially committed. A retry on a failed resume then hits the same crash in a different state. For users who paid for a simulation and try to resume it after a network drop, the result is a silent data corruption they discover only when fetching results. Fixing the schema guard + adding a pre-flight integrity check converts a destructive failure into a clean, retryable error.

**How:**
1. Find every `CREATE TABLE` statement in the SQLite resume path (likely in `backend/app/services/` or `backend/app/db/`). Change all to `CREATE TABLE IF NOT EXISTS`. Add a pre-flight check: before executing any mutation, run `PRAGMA integrity_check` and `PRAGMA foreign_key_check`. If either returns non-`ok`, abort immediately and return `{"error": "existing_db_corrupted", "action": "use force_new=true to start fresh"}` — never overwrite a partially-written database without explicit user intent. Add `force_new=true` query param to `POST /api/simulation/{id}/resume`: when set, drops and recreates the SQLite DB rather than resuming. Document the param in `docs/API.md`. Add 3 unit tests: resume on existing DB succeeds without schema error; `PRAGMA integrity_check` failure aborts with correct error code; `force_new=true` recreates DB from scratch.

2. Wrap the entire resume transaction in a single `BEGIN IMMEDIATE` / `COMMIT` block with an explicit `ROLLBACK` on exception. `BEGIN IMMEDIATE` acquires a write lock upfront, preventing concurrent readers from seeing a partially-resumed state. Add a `resume_lock_{simulation_id}.lock` file created at resume start and deleted at commit — if the lock file exists on next resume, log `RESUME_INTERRUPTED` and offer the `force_new=true` prompt. This prevents the "failed resume leaves inconsistent data → retry crashes again" loop described in the issue. Add 2 unit tests: interrupted resume (lock file present) returns `RESUME_INTERRUPTED` with actionable message; successful resume deletes lock file.

3. Update the resume endpoint's error response schema in `docs/API.md`: add a table of error codes (`schema_conflict`, `existing_db_corrupted`, `resume_interrupted`, `force_new_required`) with a description and recommended action for each. Add `resume_safe: true` to the `GET /api/simulation/{id}` response body — set to `true` if the simulation can be safely resumed (no lock file, DB integrity OK), `false` otherwise with a `resume_blocked_reason` field. This gives polling clients a clean pre-flight check before attempting resume. Add 2 unit tests: `resume_safe: false` when lock file present; `resume_safe: true` when DB clean.

### 2. Report API Race Condition Fix

**Type:** Performance / DX
**Effort:** Small (hours)
**Impact:** Issue #323: `GET /api/simulation/{id}/report/status` and `GET /api/simulation/{id}/report/generate` return HTTP 400 on valid simulation IDs while generation is in progress. Any client polling for completion — a frontend UI, a CLI user running `watch curl`, an integration test waiting for a result — sees 400 and either crashes, retries in a tight loop, or gives up. The fix is a single-digit line change to the status check: return 202 with `{"status": "generating", "retry_after": 5}` instead of 400 while the job is running. The `force_regenerate` pollers race because the old completed report's status record isn't cleared before the new job writes — fix the write order.

**How:**
1. Locate the report generation handler (likely `backend/app/api/report.py` or `backend/app/services/report_service.py`). Find where `generate` is called and where `status` is checked. The 400 is returned because the status query runs before the new job's record is written — add a transition state: when `force_regenerate=true` is called, immediately write `{"status": "generating", "started_at": now(), "report_id": new_uuid}` to the status store before starting the job. All subsequent `GET .../status` calls see `generating` and return 202 until the job commits `completed`. Add 3 unit tests: `status` returns 202 (not 400) during generation; `status` returns 200 after completion; `force_regenerate` while already generating returns 202 (not 400 or 409).

2. Add a `Retry-After: 5` response header to all 202 responses from the report status and generate endpoints. `Retry-After` is an HTTP standard header; cURL, browser `fetch`, and most HTTP clients will honor it automatically, preventing tight polling loops without requiring client-side changes. Add a `progress_pct` field (0–100) to the 202 body — updated at major generation milestones (agent init: 10%, first round complete: 30%, all rounds complete: 80%, writing output: 95%, done: 100%). If progress tracking is not feasible without deeper instrumentation, stub it at `progress_pct: null` and document it as "not yet instrumented." Add 2 unit tests: 202 response includes `Retry-After` header; `progress_pct` is either an int 0–100 or null.

3. Fix the `force_regenerate` race specifically: when `force_regenerate=true`, the old completed report record must be **atomically** replaced — not deleted and then re-created, which leaves a window where `status` returns 404. Use a rename/swap pattern: write the new "generating" record to a temp key, then swap it in one atomic operation. In SQLite: use `INSERT OR REPLACE`. In file-based storage: write to `report_status.tmp.json`, then `os.replace("report_status.tmp.json", "report_status.json")` — `os.replace` is atomic on POSIX. Add 2 unit tests: a `GET /status` request racing a `force_regenerate` call never returns 404; two concurrent `force_regenerate` calls result in exactly one `generating` state (not two).

### 3. Provider Capability Matrix

**Type:** Feature / DX
**Effort:** Small (hours)
**Impact:** Issue #321 reveals a silent failure mode: the claude-code provider crashes on NER with an unexpected `repair_truncated` kwarg, then reports success with 0 nodes. Users have no way to know which providers support which features before running a $1 simulation. `GET /api/providers/capabilities` returns a machine-readable matrix of what each configured provider supports — NER, belief parsing, stance detection, graph build, multi-platform, locale support. Operators can show this in the UI before run setup. API integrators can query it to route simulation requests to the right provider. Distinct from: provider selection UI (not yet built), Pre-Run Estimate (Jun 20, predicts cost not capability). This is a **static capability reference** derived from the provider implementations themselves — no test-time probing, no live calls.

**How:**
1. Create `backend/app/services/provider_capabilities_service.py` (~100 LoC, pure stdlib). For each provider defined in the system (read from `aeon.yml` or the provider registry — wherever `claude-code`, `openai`, `ollama`, etc. are declared), emit a capability dict: `{"name": str, "features": {"ner": bool, "belief_parsing": bool, "stance_detection": bool, "graph_build": bool, "multi_platform": bool, "resume": bool}, "known_issues": [str], "last_verified": ISO8601 | null}`. Source the capability flags from inline annotations in each provider class: add a class-level `CAPABILITIES = {...}` dict to every provider implementation, which the service reads via `importlib`. For `known_issues`, add a free-text list: for claude-code, emit `"NER: repair_truncated kwarg not supported (issue #321)"` — fixes the silent failure by surfacing the known incompatibility to callers. Add 3 unit tests: all configured providers appear in output; `features` dict has all required keys; `known_issues` is a list (may be empty).

2. Add `GET /api/providers/capabilities` endpoint in `backend/app/api/providers.py`. Public, no auth. Response: `{"providers": [...capability dicts...], "generated_at": ISO8601}`. Cache-Control: `max-age=3600` (capabilities don't change at runtime). Add to `surfaces_catalog.py` (type: `meta`) and OpenAPI with `ProviderCapabilitiesResponse` and `ProviderCapability` schemas. Register route in `main.py`. Add to `docs/API.md` under a new "Providers" section: include a feature matrix table, the `known_issues` semantics, and a note that `last_verified` is set when the provider class is updated and not by live probing. Add 2 integration tests: endpoint returns 200; all providers have `features.ner` as a boolean.

3. Surface in the Step 2 (EnvSetup) frontend: when the user selects a provider, fetch `GET /api/providers/capabilities` and show a compact capability badge row — green checkmarks for supported features, yellow triangles for features with `known_issues`, gray dashes for unsupported. If the selected provider has any `known_issues`, show them as an inline warning below the badge row. This converts the silent #321 crash into a visible pre-run warning: "claude-code: NER has a known issue — simulation may produce empty graphs." No new page required — capability data surfaces exactly where provider selection happens. Add 1 frontend unit test: provider with `known_issues` renders a warning element.

### 4. Agent Diversity Score

**Type:** Feature / Analytics
**Effort:** Small (hours)
**Impact:** MiroShark's confidence score measures how strongly agents agreed on a direction. It doesn't measure whether the agents were diverse enough for that agreement to be meaningful. A simulation where 48 of 50 agents are `Finance_Analyst` archetype reaching 91% BULLISH is statistically weaker than one where 50 distinct archetypes across 3 platforms reach 91% BULLISH. `GET /api/simulation/{id}/diversity` returns a composite diversity score (0.0–1.0) and its three component metrics: stance entropy (Shannon entropy of BULLISH/NEUTRAL/BEARISH distribution at round 1), archetype variety (count of distinct archetypes / total agents), and platform spread (count of distinct platforms / max configured platforms). Distinct from: Archetype Atlas aggregate stats (cross-sim, not per-sim), Confidence Distribution Analytics (Oct 4 — distribution of confidence across corpus), Agent Mention Network (Jun 12 — who @-mentioned whom, not ensemble diversity). This is **how heterogeneous was this specific ensemble**, as a single number a researcher can cite.

**How:**
1. Create `backend/app/services/diversity_service.py` (~120 LoC, pure stdlib). Reads `trajectory.json` (round 1 beliefs for stance distribution) and `signal.json` (`top_agents` for archetype list) and `actions.jsonl` (platform column for platform spread). Computes: (a) **Stance entropy**: `H = -sum(p * log2(p) for p in [bullish_frac, neutral_frac, bearish_frac] if p > 0)`. Max entropy is `log2(3) ≈ 1.585`. Normalize to [0, 1]. (b) **Archetype variety**: `distinct_archetypes / total_agents`. Clamp to [0, 1]. (c) **Platform spread**: `distinct_platforms / max(1, configured_platform_count)`. Read configured platform count from `signal.json` if available. (d) **Composite diversity score**: `(stance_entropy_norm * 0.5) + (archetype_variety * 0.3) + (platform_spread * 0.2)`. Weights encode that stance diversity is the most signal-bearing component. Cache to `.diversity-cache/{simulation_id}.json` permanently — diversity is immutable once computed. Add 5 unit tests: uniform stance distribution returns max entropy; single-archetype sim returns archetype_variety=0; single-platform sim returns platform_spread=0; composite score is in [0, 1]; cache file written after first call.

2. Add `GET /api/simulation/{id}/diversity` endpoint in `backend/app/api/diversity.py`. Publish-gated (returns 404 for unpublished). Query params: none. Response: `{"simulation_id": str, "diversity_score": float, "grade": "A"|"B"|"C"|"D" (A: ≥0.75, B: ≥0.5, C: ≥0.25, D: <0.25), "components": {"stance_entropy_norm": float, "archetype_variety": float, "platform_spread": float}, "interpretation": str}`. The `interpretation` field is a one-sentence plain-text reading: `"High diversity: 47 distinct archetypes across 3 platforms with near-even initial stance distribution."` Built as a template string from the component values — no LLM call. Cache-Control: `max-age=86400`. Add to `surfaces_catalog.py` (type: `analytics`) and OpenAPI with `DiversityResponse` and `DiversityComponents` schemas. Add to `docs/API.md` under "Analytics" with the grading rubric and weight rationale. Add 3 integration tests: 200 for published sim; 404 for unpublished; `diversity_score` in `[0.0, 1.0]`.

3. Surface the diversity score on the Step 3 result page. Add a `Diversity` stat tile below the confidence tile: show `diversity_score` as a ring gauge (0–1 scale, 80px diameter SVG, filled arc in `#7c3aed` violet) with the letter grade centered. On hover: expand to a popover showing all three component bars (stance entropy, archetype variety, platform spread) each as a labeled horizontal bar. In `EmbedDialog.vue` under "Data," add `diversity_score` and `grade` as fields in the cURL example for `GET /api/simulation/{id}/diversity`. Add `diversity_score` to the comparison view if a Comparison API is ever built (reference the field name in `docs/API.md` under "Analytics" with a "see also: future comparison endpoint" note). Bilingual (EN/ZH-CN) for grade labels and interpretation text. Add 1 frontend unit test: diversity tile renders when `diversity_score` is present.

### 5. Simulation Embedding API

**Type:** Feature / Analytics
**Effort:** Small (hours)
**Impact:** 1,464 stars, 303 forks, 8,000+ simulations in the corpus — and no way to ask "which past simulations are semantically similar to this one?" The Archetype Atlas, Full-Text Search (Jun 14), and Similar Simulations Discovery (Sep 30 — still queued as a local commit) all operate on keyword overlap or archetype identity. None of them capture semantic meaning: "BTC Q4 2026 BULLISH" and "Bitcoin price forecast end of year BULLISH" are the same question but won't keyword-match. `GET /api/simulation/{id}/embedding` returns a fixed-length vector (e.g., 384-dim) of the simulation's semantic content — topic, direction, agent stances, round narrative summary — computed via a lightweight sentence-transformer (`all-MiniLM-L6-v2`, 22MB, pure CPU inference). The embedding is the building block for semantic search, clustering, and recommendation — features that become trivially composable once embeddings exist. Distinct from: Full-Text Search (keyword regex, not semantic), Similar Simulations Discovery (Sep 30 — unbuilt, but planned to use this embedding once it exists).

**How:**
1. Add `sentence-transformers` as an optional dependency in `backend/requirements.txt` (or `pyproject.toml`), version-pinned. Add a lazy-load guard: the embedding service only imports `sentence_transformers` on first call — if not installed, the endpoint returns `503 {"error": "embedding_model_not_installed", "install": "pip install sentence-transformers"}`. Model: `all-MiniLM-L6-v2` — 22MB, Apache-2.0 licensed, runs on CPU, 384-dim output. Create `backend/app/services/embedding_service.py` (~100 LoC). Input text construction: concatenate `topic` + `direction` + `confidence_pct` + a 200-char truncation of the `signal.json` narrative summary (or top-3 agent stances if no narrative). Feed through `SentenceTransformer.encode(text, normalize_embeddings=True)`. Cache embedding to `.embedding-cache/{simulation_id}.npy` (numpy binary, 1.5KB each). Load model once at service init via `functools.lru_cache` — no per-request model reload. Add 4 unit tests: returns a list of 384 floats; all values in `[-1, 1]` (normalized); cache file written; second call reads from cache (no model re-encode).

2. Add `GET /api/simulation/{id}/embedding` endpoint in `backend/app/api/embeddings.py`. Publish-gated (returns 404 for unpublished). Query params: `format=json` (default — JSON array of 384 floats) or `format=base64` (base64-encoded float32 LE bytes — 1.5KB vs ~11KB for JSON; preferable for bulk fetch). Response: `{"simulation_id": str, "model": "all-MiniLM-L6-v2", "dimensions": 384, "embedding": [float...] | str, "format": "json"|"base64"}`. Cache-Control: `max-age=86400`. Add to `surfaces_catalog.py` (type: `analytics`) and OpenAPI with `EmbeddingResponse` schema. Register route in `main.py`. Add to `docs/API.md` under "Analytics" with a note on use cases: semantic search (`GET /api/simulation/search` with a `semantic=true` param — hint at future upgrade path), clustering via cosine similarity, downstream recommendation. Add 3 integration tests: 200 for published sim; 404 for unpublished; `dimensions == 384`.

3. Add a `GET /api/simulations/similar?to={simulation_id}&limit=N` endpoint (`backend/app/api/semantic_search.py`) that leverages the embedding cache to return the top-N most semantically similar published simulations. Algorithm: load embeddings for all published simulations that have a cached `.npy` file (skip uncached — no on-demand batch encoding); compute cosine similarity between the query embedding and each cached vector using pure Python dot product (no numpy dependency in the endpoint itself — read the `.npy` bytes as raw float32 and compute in a list comprehension if numpy is unavailable, or use numpy if available); return top-N sorted by similarity descending. Response: `{"source_simulation_id": str, "similar": [{simulation_id, topic, direction, confidence_pct, similarity_score}]}`. Default `limit=5`, clamp `[1, 20]`. If fewer than 5 published simulations have cached embeddings, return what's available with `"coverage_note": "N simulations indexed"`. This completes the Similar Simulations Discovery feature (Sep 30 candidate) without a separate service layer — the embedding cache is the index. Add to `surfaces_catalog.py`, OpenAPI, `docs/API.md`. Add 3 unit tests: returns correct number of results; excludes source simulation from results; `similarity_score` in `[0.0, 1.0]`.
