### 1. Simulation Volatility Score

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Every existing analytics metric describes either endpoint state (direction, confidence, controversy) or cross-sectional behavior (platform divergence, lead-lag). None captures *how much beliefs oscillated* on the way to the final answer. A simulation where bullish_pct went 40% → 65% → 42% → 68% → 70% (four reversals) is structurally different from one that climbed monotonically from 40% to 70% — but both resolve to the same `direction: BULLISH, confidence: 70%`. A `volatility_score` (0–100) based on the standard deviation of per-round bullish_pct changes fills this gap. High volatility signals "the crowd changed its mind repeatedly"; low volatility signals "this was a straight-line conviction story." For market researchers: high-volatility simulations model "noisy signal" scenarios; low-volatility simulations model early-consensus scenarios. For operators building content: "the crowd swung wildly before settling" is a more compelling article hook than "as expected, the crowd agreed." Zero new data sources — derived entirely from `trajectory.json`.

**How:**
1. Create `backend/app/services/volatility_service.py` (~100 LoC, pure stdlib). Accept `sim_id: str`. Load `trajectory.json` → extract `bullish_pct` as a list ordered by `round_number`. If fewer than 3 rounds, return `{available: false, reason: "insufficient_data"}`. Compute round-to-round deltas: `deltas = [abs(bullish_pct[i] - bullish_pct[i-1]) for i in range(1, len(bullish_pct))]`. Compute `mean_delta = sum(deltas) / len(deltas)` and `std_delta = statistics.stdev(deltas)` (stdlib: `statistics.stdev`). `raw_volatility = mean_delta + std_delta` (mean shift + spread; captures both how much and how erratically). Normalize to 0–100: empirical range is [0, ~40] for typical simulations (bullish_pct rarely swings more than 40 points per round). `volatility_score = min(100, round(raw_volatility * 2.5))`. `volatility_label`: "High" (≥65), "Moderate" (35–64), "Low" (<35). `reversal_count`: number of rounds where the direction of bullish_pct change reversed sign (delta[i] > 0 and delta[i-1] < 0, or vice versa). Cache to `storage/simulations/{id}/volatility.json` (mtime-based, immutable after sim completes). Merge `volatility_score`, `volatility_label`, `reversal_count` into `signal.json` during signal-writing step. Add 6 unit tests: perfectly monotone trajectory → `reversal_count = 0, volatility_score` near 0; alternating +10/-10 trajectory → high reversal count; `volatility_score` clamped at 100; fewer than 3 rounds → `available: false`; `trajectory.json` absent → `available: false`; two-element bullish_pct (exactly 2 rounds) → `available: false` (stdev requires ≥2 deltas, need ≥3 rounds).
2. Add `GET /api/simulation/:id/volatility` to `backend/app/api/volatility.py`. Publish-gated. Session-auth. Response: `Content-Type: application/json`, `Cache-Control: max-age=3600, private`. Return `{available: bool, volatility_score: int, volatility_label: str, reversal_count: int, mean_delta: float, std_delta: float, per_round_deltas: list[float]}`. Add `volatility_score`, `volatility_label`, `reversal_count` to the OpenAPI `Signal` schema. Add to `surfaces_catalog.py` (type: `analytics`). Add to `docs/API.md` under "Analytics". During simulation completion (wherever `signal.json` is written), call `volatility_service.compute(sim_id)` and merge results. Add 2 integration tests: endpoint returns 200 with `volatility_score` for a completed published sim; `volatility_score` is present in `signal.json` after sim completion.
3. Add a "Volatility" row to the signal card in Step 3 (below direction and confidence): `{volatility_label} · {reversal_count} reversals`. Add a `?sort=volatility_score` gallery sort option ("Most Volatile First" / "Most Stable First"). The timeline chart in Step 3 gains a background shading layer: for each round where a reversal occurred, draw a thin vertical stripe in amber to visually highlight "the crowd changed direction here." Add 2 frontend unit tests: signal card renders "0 reversals" for a non-volatile simulation; volatility sort fires gallery fetch with `?sort=volatility_score&dir=desc`.

### 2. Agent Biography Auto-Generator

**Type:** Feature
**Effort:** Medium (1-2 days)
**Impact:** MiroShark simulations produce a cast of 100+ agents whose behavior shaped the outcome, but they remain abstract data rows. The article generator writes a macro-level narrative of the simulation. No feature creates a *micro-level narrative* about the specific agents who drove the result. For the top 5 most-influential agents (by influence_score from `stance_flips.json` or mention count from `mentions.json`), `GET /api/simulation/:id/agent-biographies` triggers a compact LLM generation pass that writes a 3-sentence narrative biography for each agent: who they are, how their views evolved, and what made them notable in this specific simulation. Example output: "A 41-year-old institutional investor from Singapore with a moderate risk appetite. Entered the simulation NEUTRAL and shifted BULLISH in round 7 after citing macro liquidity data in three consecutive posts. The most-cited agent in the Reddit platform, referenced by 14 other agents across the final 8 rounds." These biographies give articles, newsletters, and embeds a human-readable cast list — turning abstract agent IDs into characters. The competitor simswarm has no equivalent feature.

**How:**
1. Create `backend/app/services/agent_biography_service.py` (~200 LoC). Accept `sim_id: str`, `top_n: int = 5`. Load `agents.json` → agent roster (demographic attributes: age, profession, platform, risk_tolerance, region if available). Load `stance_flips.json` → rank agents by `flip_count` and `influence_score`; take top N. Load `mentions.json` → cross-reference mention counts for the top N agents. Load `trajectory.json` → for each top agent, extract their per-round stance (from per-agent entries in trajectory). Build a structured prompt per agent: `{agent_id, demographic_seed: {age, profession, platform, region}, initial_stance, final_stance, flip_round: int | null, mention_count, influence_score, posts_per_round_summary: str}`. Call the LLM (use existing OpenRouter client, `claude-haiku-5-5` or `gpt-4o-mini` as configured — single call with all 5 agents in one request to minimize cost): "Write a 2-3 sentence factual biography for each of these agents in a MiroShark simulation. Use present tense, avoid marketing language, describe who they are, how their stance evolved, and what made them notable. Output as JSON array `[{agent_id, biography}]`." Parse the JSON response. If the LLM call fails or returns malformed JSON, fall back to a template biography: `"A {age}-year-old {profession} on {platform}. {Entered | Remained} {initial_stance} throughout the simulation{, shifting to {final_stance} in round {flip_round} | }. {Most-cited agent | Cited {mention_count} times} by other agents."` Cache result to `storage/simulations/{id}/agent_biographies.json` (immutable after sim completes; no TTL — LLM-generated content is expensive to regenerate). Add 5 unit tests: template fallback activates on LLM JSON parse error; `top_n` clamped to range [1, 10]; agent with zero flips shows "remained" phrasing; cache hit returns stored result without re-calling LLM; missing `stance_flips.json` falls back to ranking by mention count from `mentions.json`.
2. Add `GET /api/simulation/:id/agent-biographies` to `backend/app/api/agent_biographies.py`. Publish-gated. Session-auth. Query params: `?top_n=5` (default 5, max 10). Response: `Content-Type: application/json`, `Cache-Control: max-age=86400, private`. Return `{available: bool, biographies: [{agent_id, biography: str, influence_score: float, mention_count: int, initial_stance: str, final_stance: str}], generated_at: str, model_used: str | null}`. Add to `surfaces_catalog.py` (type: `analytics`). Add to `docs/API.md` under "Analytics" with note: "First call generates biographies via LLM (adds ~2-5 seconds). Subsequent calls are cached and instant." Add 2 integration tests: endpoint returns 200 with `biographies` array for a completed published sim; `len(biographies) <= top_n` is always true.
3. Add a "Cast" collapsible panel to Step 3 (below the main signal card and above the platform overlay). The panel shows 5 agent cards in a horizontal scroll: each card has the agent's demographic label (profession, age, platform), a colored stance-shift indicator (initial → final with an arrow), and the biography text. Card header shows influence rank badge (1st–5th). An expand button on each card shows full detail (mention count, flip round, raw stats). Add "Agent Biographies" as an optional section in the article generator: when `available: true`, append a "Who drove this simulation?" section after the main article body, listing all 5 biographies. Add 2 frontend unit tests: Cast panel renders loading state while biography endpoint responds; collapsed by default, expands on click without breaking signal card layout.

### 3. Simulation Network Graph Export

**Type:** Feature / Integration
**Effort:** Small (hours)
**Impact:** The existing `GET /api/simulation/:id/mentions` returns a directed @-mention graph as JSON. Researchers who want to analyze the network using Gephi, Cytoscape, NetworkX, or Gephi Lite — the standard tools for network science — currently need to write custom parsers. Adding `GET /api/simulation/:id/network.graphml` and `GET /api/simulation/:id/network.gexf` as standard export formats turns a MiroShark simulation into a first-class network science dataset with zero friction. Each node is an agent with attributes: `id`, `profession`, `platform`, `initial_stance`, `final_stance`, `influence_score`. Each directed edge is a @-mention with attributes: `source`, `target`, `weight` (mention count), `round_range` (first/last round the mention occurred). The GEXF format supports time-varying graphs — including `round` as a time dimension lets tools like Gephi Timeline animate the network's evolution. This directly serves the researcher audience that cites MiroShark as a methodology (the `houseofethics.lu` critique and SwarmWorld papers reference network-level analysis as the gold standard for validating swarm simulation outputs). No new data collection required.

**How:**
1. Create `backend/app/services/network_export_service.py` (~160 LoC, pure stdlib). Accept `sim_id: str`, `format: str = "graphml"`. Load `agents.json` → build node list `[{id, profession, platform, stance_initial, stance_final, influence_score}]` (influence_score from `stance_flips.json` if available, else 1.0). Load `mentions.json` → build edge list `[{source, target, weight, first_round, last_round}]`. GraphML export: use string concatenation (no lxml/xml.etree needed beyond stdlib `xml.etree.ElementTree`): emit `<graphml>` root with `<key>` elements for node/edge attributes, then `<graph id="G" edgedefault="directed">`, then `<node>` elements with `<data key=...>` children, then `<edge>` elements. GEXF export: emit `<gexf>` root with `<meta>` (creator: MiroShark, description: f"Agent interaction network for simulation {sim_id}"), `<graph defaultedgetype="directed" timeformat="integer">`, `<attributes class="node">` with attribute declarations, `<nodes>` and `<edges>` with time-slice data (`<spells>` per edge using `first_round`/`last_round` as start/end). JSON export (always available as the base format): `{nodes: [...], edges: [...], meta: {sim_id, generated_at, total_nodes, total_edges, density: edges/nodes^2}}`. Compute `network_density = len(edges) / (len(nodes) * (len(nodes) - 1))` if >1 node else 0. Cache all three formats to `storage/simulations/{id}/network.{graphml,gexf,json}` (immutable). Add 5 unit tests: GraphML output is valid XML parseable by `xml.etree.ElementTree.fromstring`; edge weight equals mention count from `mentions.json`; zero-edge network produces valid XML with no `<edge>` children; node attributes include `platform` and `influence_score`; GEXF has `<meta>` block with sim_id.
2. Add three routes to `backend/app/api/network_export.py`: `GET /api/simulation/:id/network.graphml` (`Content-Type: application/xml`, `Content-Disposition: attachment; filename="sim-{id}-network.graphml"`), `GET /api/simulation/:id/network.gexf` (`Content-Type: application/xml`), `GET /api/simulation/:id/network.json` (JSON fallback for JS/Python scripts). All publish-gated (keyless for published sims), `Cache-Control: max-age=86400, public`. Add to `surfaces_catalog.py` (type: `export`). Add `network_graphml_url`, `network_gexf_url` to the `Signal` OpenAPI schema. Add to `docs/API.md` under "Exporting Results" with a "Network Analysis" subsection: include a code snippet showing how to open the GraphML in NetworkX (`nx.read_graphml(url)`) and Gephi (File → Open → `.graphml`). Add 2 integration tests: `network.graphml` download returns `application/xml` content type for a published sim with mentions data; `network.json` returns a `nodes` array with length matching the agent roster size.
3. Add a "Network Export" section to the Step 3 share panel (EmbedDialog), beneath existing export formats. Three download buttons: "Download GraphML", "Download GEXF", "Download JSON". Each button downloads the file with the correct filename. Below the buttons, a 2-line context note: "Open GraphML or GEXF files in Gephi or Cytoscape for network analysis. Import the JSON into NetworkX or D3 for custom visualizations." Add network export URLs to the transcript export ZIP (`network.graphml` + `network.json` included automatically for sims with mention data). Add 2 frontend unit tests: network export section renders only for completed published sims with `mentions` data available; GraphML download button triggers file download with `.graphml` extension.

### 4. Webhook Event Testing Playground

**Type:** DX
**Effort:** Small (hours)
**Impact:** Integrating MiroShark webhooks requires setting up an endpoint, starting a simulation, waiting for it to complete, and inspecting the payload — a 10-minute feedback loop for every configuration change. The existing webhook flow has no test harness: no way to send a sample payload to a URL without running a full simulation. `POST /api/webhooks/test` fills this gap: the operator provides a `target_url` and an optional `event_type` ("simulation.completed" | "simulation.started" | "director.injected"), and the endpoint sends a realistic sample payload to that URL with live response reporting — `{delivered: bool, http_status: int, latency_ms: int, error: str | null}`. This reduces webhook integration time from 10 minutes to 10 seconds. It also serves as a health-check tool for existing integrations: an operator who changed their endpoint URL can verify the new URL before re-enabling it. The feature is entirely self-contained and stateless — no simulation data is involved, only sample payloads. This distinguishes it from "Webhook Retry & Redelivery" (re-sending real events) or "Webhook Delivery History Log" (auditing past deliveries).

**How:**
1. Create `backend/app/services/webhook_test_service.py` (~120 LoC, pure stdlib). Define `SAMPLE_PAYLOADS: dict[str, dict]` with realistic but static sample payloads for each event type. `simulation.completed`: `{event: "simulation.completed", simulation_id: "test-sim-abc123", topic: "Will the Fed cut rates in December?", direction: "BULLISH", confidence_pct: 73.2, total_rounds: 24, completed_at: "2026-11-12T12:00:00Z", share_url: "https://miroshark.example.com/simulation/test-sim-abc123"}`. `simulation.started`: `{event: "simulation.started", simulation_id: "test-sim-abc123", topic: "...", started_at: "..."}`. `director.injected`: `{event: "director.injected", simulation_id: "test-sim-abc123", event_description: "Breaking: Fed announces emergency rate cut", injected_at: "...", current_round: 12}`. Add a `_test` boolean flag to all sample payloads to prevent test events from being processed as real events by the receiver. Function `send_test(target_url: str, event_type: str, timeout_seconds: int = 5) -> dict`: use `urllib.request.urlopen` (stdlib) with a `urllib.request.Request` object (POST, `Content-Type: application/json`, `User-Agent: MiroShark-Webhook/1.0`). Catch `urllib.error.URLError`, `socket.timeout`, and `http.client.HTTPException`. Return `{delivered: bool, http_status: int | null, latency_ms: int, error: str | null}`. Security: validate `target_url` starts with `https://` (reject `http://`, `localhost`, private IPs via regex: reject `10\.`, `192\.168\.`, `172\.(1[6-9]|2[0-9]|3[0-1])\.`, `127\.`, `0\.0\.0\.0` to prevent SSRF). Add 6 unit tests: private IP rejected (10.0.0.1 → error before network call); `localhost` rejected; sample payload contains `_test: true`; successful 200 response → `delivered: true`; connection refused → `delivered: false, error: "Connection refused"`; unknown `event_type` → 400 without making network call.
2. Add `POST /api/webhooks/test` to `backend/app/api/webhook_test.py`. Session-auth (requires a valid session — prevents public abuse). Request body: `{target_url: str, event_type: str = "simulation.completed"}`. Validate: `target_url` is a string, max 2048 chars; `event_type` is one of the three known event types. Rate limit: max 10 test sends per session per hour (use a simple in-memory counter keyed by session ID; acceptable for DX tooling). Response: `Content-Type: application/json`, no cache. Return the `{delivered, http_status, latency_ms, error}` object from `webhook_test_service.send_test`. Add `webhook_test_url` to the OpenAPI spec under "Webhooks". Add to `docs/API.md` under "Webhooks" with a note: "Only sends to HTTPS endpoints. Private network addresses (localhost, 192.168.x.x, etc.) are rejected." Add 2 integration tests: valid HTTPS `target_url` with correct event_type returns 200 response with `{delivered, http_status, latency_ms}`; private IP in target_url returns 400 with error message.
3. Add a "Test Webhook" button to the webhook configuration UI (wherever the webhook URL input lives — Step 3 share settings or operator settings panel). The button is active only when a webhook URL is entered. Clicking sends a `POST /api/webhooks/test` with the current input URL and `event_type: "simulation.completed"`. Show inline result: a green checkmark + `HTTP {status} in {latency_ms}ms` for success; a red X + error message for failure. The test result auto-clears after 30 seconds. Add an "Event type" dropdown next to the test button (default: "simulation.completed"; also shows "simulation.started" and "director.injected"). Add 2 frontend unit tests: test button disabled when webhook URL input is empty; success response shows green status chip with HTTP code and latency.

### 5. Operator Simulation Stats API

**Type:** Feature
**Effort:** Small (hours)
**Impact:** An operator who has run 50 simulations across two months has no aggregated view of their history. What's their average confidence? Which topic clusters do they simulate most? What's the typical cost and duration? `GET /api/users/:operator_id/stats` returns a compact analytics object for any operator's published simulations — no auth required for published data. This serves three audiences: the operator themselves (self-analysis, billing estimation), researchers (methodology transparency — "this author ran 23 simulations with average 73% confidence"), and ecosystem partners (capability signaling). The endpoint piggybacks on existing `signal.json` and `config.json` data — no new writes. The competitor simswarm has no equivalent cross-simulation analytics layer. This distinguishes MiroShark as the platform for *repeated, rigorous* simulation work rather than one-off curiosity runs. It also creates a natural social proof signal: an operator with 50 published simulations at 70%+ average confidence is a credible source.

**How:**
1. Create `backend/app/services/operator_stats_service.py` (~180 LoC, pure stdlib). Accept `operator_id: str`. Scan `storage/simulations/*/config.json` for sims where `operator_id` matches and `published: true` and `status: "completed"`. For each matching sim, load `signal.json` → extract `{direction, confidence_pct, total_rounds, controversy_score (if present), volatility_score (if present)}`. Load `config.json` → extract `{topic, created_at, estimated_cost_usd (if present)}`. Compute aggregate stats: `total_simulations: int`, `direction_distribution: {BULLISH: int, BEARISH: int, NEUTRAL: int}`, `mean_confidence_pct: float` (rounded to 1dp), `median_confidence_pct: float`, `confidence_range: {min: float, max: float}`, `mean_total_rounds: float`, `avg_estimated_cost_usd: float | null` (null if no cost data), `first_simulation_at: str`, `last_simulation_at: str`, `active_days: int` (days between first and last sim). Topic analysis: extract first 3 words of each topic → build a frequency dict → `top_topic_keywords: list[{keyword: str, count: int}]` (top 10). `high_confidence_simulations: int` (confidence_pct ≥ 70). `streak: {current_active_days: int, longest_active_days: int}` (days with at least one published sim, using `created_at` dates). Cache to `storage/operator_stats/{operator_id}.json` (mtime 1h TTL — operator publishes new sims). Add 5 unit tests: single sim → `mean_confidence_pct` equals that sim's confidence; zero published sims → `total_simulations = 0` with empty stats (not 404); direction_distribution sums to `total_simulations`; `high_confidence_simulations <= total_simulations`; `avg_estimated_cost_usd` is null when no sims have cost data.
2. Add `GET /api/users/:operator_id/stats` to `backend/app/api/operator_stats.py`. Keyless (public endpoint — only published sims included). `Cache-Control: max-age=3600, public`. Return `{operator_id, total_simulations, direction_distribution, mean_confidence_pct, median_confidence_pct, confidence_range, mean_total_rounds, avg_estimated_cost_usd, first_simulation_at, last_simulation_at, active_days, high_confidence_simulations, top_topic_keywords, streak}`. Return 200 with `total_simulations: 0` and empty stats when no published sims exist (not 404 — the operator exists, they just haven't published). Add to `surfaces_catalog.py` (type: `discovery`). Add to `docs/API.md` under "Operators" (new subsection) with a note: "Returns aggregate stats for published, completed simulations only. Unpublished runs are excluded." OpenAPI schema: `OperatorStatsResponse`. Add 2 integration tests: returns 200 with `total_simulations > 0` for an operator with published sims; `direction_distribution` values sum to `total_simulations`.
3. Add a compact stats bar to operator-scoped gallery pages (if a gallery filter by `operator_id` exists, add it there; if not, add it to the gallery header when `?operator=:id` query param is present). Stats bar shows: `{total_simulations} simulations · avg {mean_confidence_pct}% confidence · {high_confidence_simulations} high-confidence runs`. Add a "Share Profile Stats" link that generates a plain-text copyable summary: "I've run {total_simulations} MiroShark simulations with {mean_confidence_pct}% average confidence across {active_days} days. Top topics: {top_3_keywords}. {link to gallery filtered by operator}." Add a `stats_url` field to the `GET /api/users/:operator_id/profile` endpoint response (or create this endpoint if it doesn't exist, returning `{operator_id, stats_url, gallery_url}`). Add 2 frontend unit tests: stats bar renders only when operator stats endpoint returns `total_simulations > 0`; "Share Profile Stats" copies the correct plaintext format to clipboard.
