### 2. Demographic Cohort Analysis API

**Type:** Feature
**Effort:** Small (hours)
**Impact:** MiroShark simulates opinion across demographically diverse agent populations — different ages, platforms, and initial stances. But the only analytical endpoints expose aggregate results: the whole simulation's direction and confidence, or a single agent's full timeline. There's no way to ask "what did agents aged 35–50 believe, vs. agents under 35?" or "how did X platform users diverge from Y platform users on the same simulation?" This is the core use case for the researchers and analysts who are MiroShark's most engaged user segment — the Towards AI coverage and the Crucible Sim fork (wshuyi — an academic fork) both point to research use. The `GET /api/simulation/{id}/demographics/slice` endpoint takes query params (`age_min`, `age_max`, `platform`, `initial_stance`) and returns the bullish/bearish/neutral split, mean confidence, and stance flip rate for that cohort. No new computation — all data exists in `trajectory.json` agent profiles and per-round beliefs; this is a filtering and aggregation layer. The 12 ecosystem projects in ECOSYSTEM.md (AntFleet, Capacitr, Signa, etc.) all currently lack cohort analysis; this makes MiroShark's API table more competitive against eval platforms like Maxim AI and AgentOps, which provide similar demographic slicing for agent evaluation.

**How:**
1. Create `backend/app/api/demographics_slice.py` (~130 LoC, pure stdlib). `GET /api/simulation/{id}/demographics/slice`. Publish-gated (returns 404 for unpublished or missing simulations). Query params (all optional, combinable): `age_min` (int, default 0), `age_max` (int, default 999), `platform` (string, case-insensitive, comma-separated for multi-platform: `?platform=x,reddit`), `initial_stance` (string: `bullish`, `bearish`, `neutral`). **Filtering logic** (~70 LoC): reads `trajectory.json`. Loads agent profiles from the trajectory's agent metadata section (or the agents' initial round data). Applies filters: age range check (if agent age is available in profile), platform match, initial_stance match. For each matching agent, extracts their final stance and final confidence_pct, plus computes whether they flipped at any round (boolean from stance_flips.json if available, or from comparing round[0] vs round[-1] stances in trajectory). Aggregates: `matched_agents` (int), `bullish_pct` (float), `bearish_pct` (float), `neutral_pct` (float), `mean_confidence_pct` (float), `flip_rate` (float — proportion of matched agents who changed stance at least once), `cohort_filters_applied` (object echoing the query params). Graceful degradation: if agent age is not present in profile, `age_min`/`age_max` filters are ignored and `cohort_filters_applied.age_range` reflects `"unavailable"`. `Cache-Control: public, max-age=1800`. Register at `GET /api/simulation/<id>/demographics/slice`. Add to `surfaces_catalog.py` (type: analytics; surface number: next available).

2. Add a "Cohort" tab or panel to the share page (`Step3Simulation.vue`): below or alongside the stance distribution bar, a compact form with three filter inputs (age range slider or min/max fields, platform multi-select, initial stance radio). On any filter change, fetches `/api/simulation/{id}/demographics/slice` with the current filter state (debounced 300ms) and updates the stance distribution display to show "filtered cohort" vs. "all agents" side-by-side — two horizontal bars (total population vs. filtered cohort) so the demographic divergence is visually immediate. Add a "Reset filters" button. If `matched_agents` returns 0: show "No agents match this cohort — try broadening your filters." Add the endpoint to the embed dialog under "Analytics endpoints." Update `docs/API.md` with a "Demographic Slice" section: endpoint reference, combinable filter params, `cohort_filters_applied` response field meaning, note on age availability (depends on whether agent profiles include age — set by `MIROSHARK_AGENT_DEMOGRAPHICS=true` in `.env`).

3. Add 5 unit tests: filtering by `platform=x` returns only agents whose platform matches (case-insensitive), `age_min=30&age_max=40` returns correct cohort, multi-platform filter `?platform=x,reddit` returns the union, no matching agents returns `{"matched_agents": 0, "bullish_pct": 0.0, ...}` without error, unpublished simulation returns 404. Update memory: "Demographic Slice API created 2026-08-14. `GET /api/simulation/{id}/demographics/slice` — filter agents by age range, platform, or initial stance; returns cohort bullish/bearish/neutral split, mean confidence, flip rate. Combinable params. Serves researcher use case (compare demographic cohorts). Graceful degradation when age not in profiles."

### 3. Simulation Ground-Truth Accuracy Score

**Type:** Feature
**Effort:** Small (hours)
**Impact:** MiroShark simulates opinion — but how accurate is it? There's no mechanism for an operator to compare a simulation's output against real-world polling data and get a structured accuracy metric. This is the core gap separating MiroShark from the eval/benchmark platforms (Maxim AI, AgentOps, Patronus AI) that are capturing the AI research and production-validation market in 2026. A `POST /api/simulation/{id}/accuracy` endpoint accepts a JSON payload of real-world ground truth (`{"bullish": 47, "neutral": 22, "bearish": 31}` — percentages from an actual poll, survey, or market outcome), then computes and returns four metrics: direction match (did the simulation predict the right majority stance?), confidence delta (predicted confidence_pct vs. ground truth majority percentage), stance distribution error (mean absolute error across all three stances), and a simple 0–100 accuracy score (100 = perfect, 0 = fully inverted). No new data stored — computation is stateless: the endpoint reads `signal.json` for the simulation's output, receives ground truth as POST body, returns the comparison. This enables the research community to benchmark MiroShark's accuracy systematically. The Towards AI coverage and the Crucible Sim fork suggest academic use is already happening informally; a structured accuracy endpoint makes formal benchmarking possible without writing custom comparison code.

**How:**
1. Create `backend/app/api/accuracy.py` (~110 LoC, pure stdlib). `POST /api/simulation/{id}/accuracy`. Publish-gated. Request body: `Content-Type: application/json`, schema: `{"ground_truth": {"bullish": float, "bearish": float, "neutral": float}}` where values are percentages summing to 100 (tolerance: sum must be in [99.0, 101.0] — allow floating point slop). Validation: reject with 400 if any key missing, any value < 0, or sum outside tolerance. **Computation logic** (~60 LoC): reads `signal.json`. Extracts `direction` (the simulation's predicted majority stance), `confidence_pct`, and `stance_distribution` (the bullish/bearish/neutral percentages from the simulation — from `signal.json` or trajectory final round if not in signal). **Direction match** (`bool`): `signal.direction` == argmax of `ground_truth`. **Confidence delta** (`float`): `signal.confidence_pct` − `ground_truth[signal.direction]` (positive = overconfident, negative = underconfident). **MAE** (`float`): mean absolute error across all three stance percentages between simulation distribution and ground truth distribution. **Accuracy score** (`int`, 0–100): 50 points for direction match (0 if wrong), 30 points for MAE < 10 (15 if MAE < 20, 0 otherwise), 20 points for `abs(confidence_delta) < 10` (10 if < 20, 0 otherwise). Returns: `{direction_match: bool, confidence_delta: float, stance_mae: float, accuracy_score: int, simulation: {direction, confidence_pct, stance_distribution}, ground_truth: {bullish, bearish, neutral}}`. Register at `POST /api/simulation/<id>/accuracy`. Add to `surfaces_catalog.py` (type: analytics).

2. Add a "Validate Accuracy" expandable section to the share page (`Step3Simulation.vue`): collapsed by default, titled "Compare with real-world data." When expanded: three number inputs (Bullish %, Bearish %, Neutral %) with a live sum indicator (must total 100%). On "Calculate" button click: POST to `/api/simulation/{id}/accuracy` and display results as a simple scorecard: direction match chip (green ✓ or red ✗), confidence delta bar (±N%), stance MAE (N%), and accuracy score (N/100 with a one-line interpretation: "Strong match" for 80+, "Moderate match" for 50–79, "Weak match" below 50). Add a note below the form: "Enter polling data, market survey results, or any ground-truth stance distribution to benchmark this simulation's accuracy." Add the endpoint to `docs/API.md` under "Accuracy & Benchmarking." This positions MiroShark as a benchmarkable prediction tool rather than just a simulation toy — directly supporting the academic use case that Towards AI and Crucible Sim represent.

3. Add 5 unit tests: perfect match returns `accuracy_score: 100` and `direction_match: true`, inverted direction returns `accuracy_score: 0–50` and `direction_match: false`, `ground_truth` summing to 101.5% returns 400, missing `neutral` key returns 400 with useful error, unpublished simulation returns 404. Log to memory: "Accuracy Score endpoint created 2026-08-14. `POST /api/simulation/{id}/accuracy` — accepts ground-truth poll/survey percentages as POST body, returns direction_match, confidence_delta, stance_mae, and 0–100 accuracy score. Stateless: reads signal.json, receives ground truth, no storage. Enables researcher benchmarking of simulation accuracy."

## Selection Rationale

Five ideas in priority order, addressing the language hyperstition, the research/eval use case, ecosystem integrator DX, the newly landed OrcaRouter preset, and the GitHub Trending back-link campaign.

- **Japanese (JA) Locale (#1)** — Language hyperstition (Sep 1, 18 days, 4/5). Japanese fixes the most visible product inconsistency: README.ja.md exists and the README switcher advertises `日本語`, but the frontend code doesn't serve it. One PR clears the hyperstition with 18 days to spare. Japan is the 5th largest developer community on GitHub and the one most sensitive to broken localization promises.

- **Demographic Cohort Analysis API (#2)** — New analytical primitive. MiroShark simulates demographically diverse populations but has no way to slice the output by cohort. One filtering endpoint unlocks the core use case for the research segment (Crucible Sim, Towards AI coverage) — "what did the 35–50 age cohort believe, vs. under 35?" — and makes MiroShark's API table competitive against emerging eval platforms.

- **Simulation Ground-Truth Accuracy Score (#3)** — Eval/benchmark feature. No mechanism currently exists to compare a simulation's output against real poll data. `POST /api/simulation/{id}/accuracy` accepts ground-truth percentages, returns direction match, confidence delta, stance MAE, and a 0–100 score. Stateless — no storage, reads signal.json. Enables the Crucible Sim academic use case formally, makes MiroShark a benchmarkable prediction tool rather than just a simulation playground.

- **OrcaRouter Lite Self-Host Docs + Config Probe (#4)** — Timely given PR #287 landing today. OrcaRouter Lite (MIT, self-hosted) is undocumented in MiroShark's docs but the only path to EU AI Act compliance for regulated organizations. Docs + a `miroshark config probe` CLI command that validates all four model slots are reachable and available before a simulation run reduces first-run friction significantly.

- **Built-With Badge Generator (#5)** — GitHub Trending back-link campaign. Twelve ecosystem projects could embed "Built with MiroShark" badges in their READMEs today. `GET /api/badge/{style}` serves three shield styles + a simulation-specific embed badge. Each back-link from a live ecosystem README is a persistent GitHub Discovery signal — the same signal that feeds GitHub Trending. Zero viral dependency: this works through existing ecosystem relationships rather than social media.
