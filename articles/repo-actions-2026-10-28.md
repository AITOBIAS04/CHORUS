### 1. Custom Agent Roster Upload

**Type:** Feature
**Effort:** Small (hours)
**Impact:** The demographic generator produces statistically representative agents but gives callers no control over *who* is in the room. Researchers, protocol analysts, and teams running structured A/B experiments need deterministic seeding — "50% permabull analysts, 50% freshly-turned bears", or a named panel with pre-set influence weights. Adding an optional `custom_agents` array to `POST /api/simulation` (each entry: `{name, profession, initial_stance, influence_weight_multiplier}`) overrides the generator for those slots and fills the remainder demographically. No changes to the simulation execution path — the roster composition step already happens before round 1; this just allows caller-specified entries to be injected there. The practical effect: reproducible experiments (same roster → same starting conditions), bias testing (what does consensus look like with a skewed panel?), and educational demos (named personas the audience can track).

**How:**
1. Extend the simulation creation schema in `backend/app/api/simulation.py` to accept `custom_agents: list[CustomAgentEntry] | null` (default null). `CustomAgentEntry`: `{name: str (max 60 chars), profession: str (max 80 chars), initial_stance: Literal["BULLISH", "BEARISH", "NEUTRAL"], influence_weight_multiplier: float (range 0.1–5.0, default 1.0)}`. Validate: `len(custom_agents) <= agent_count` (you can't supply more named agents than the total count); names must be unique within the list; `initial_stance` must be one of the three valid values. Store `custom_agents` in the simulation config JSON. Add 5 unit tests: duplicate names return 400; `len > agent_count` returns 400; `influence_weight_multiplier=0.05` returns 400 (below 0.1 floor); valid custom_agents list returns 201 with simulation_id; null custom_agents produces same behavior as before (backward compat).
2. In the agent roster composition step (wherever the demographic generator produces the initial agent list — likely in `backend/app/services/` or `backend/app/simulation/`), merge custom entries: for each `CustomAgentEntry`, construct an agent record with the specified fields (name, profession, initial_stance, influence_weight). Fill remaining slots (`agent_count - len(custom_agents)`) via the demographic generator as before. Persist the merged roster to the simulation's `agents.json`. Add `custom_agent_count: int` to the simulation metadata (`config.json` or similar) so the timeline, stance-flip report, and mentions network can optionally tag custom agents differently. Add 3 unit tests: roster has exactly `agent_count` agents after merge; custom agent appears with the specified `initial_stance`; remaining agents are demographically generated.
3. Add a "Custom Agents" section to `docs/DEMOGRAPHICS.md` (one paragraph + a JSON example showing a 3-entry custom roster combined with `agent_count: 50`). Add `custom_agents` to the OpenAPI simulation creation schema (`CustomAgentEntry` component). Surface custom agents in the Step 2 config form (`Step2EnvSetup.vue` or equivalent): a collapsible "Advanced: Seed specific agents" panel with an "Add Agent" button that appends a row (name field, profession field, stance selector, influence slider). Initially collapsed — doesn't interrupt the default flow. Add 1 frontend unit test: adding a custom agent row appends it to the `custom_agents` form array and enables the "Remove" button.

### 2. Webhook Payload Filter Expressions

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Webhooks currently fire on every completed simulation. Operators building monitoring products — daily sentiment trackers, alert systems, crypto signal bots — receive hundreds of low-confidence runs for every one that's actionable. A `WEBHOOK_FILTER` env var (a simple JSON-Logic expression evaluated against the signal payload before the HTTP call) gates delivery to only the signals that matter: `{"and": [{">=": [{"var": "confidence_pct"}, 70]}, {"==": [{"var": "direction"}, "BULLISH"]}]}`. No new endpoints. No changes to the signal format. Just a pre-dispatch evaluation step in the existing webhook service. Operators who only want high-conviction BULLISH signals stop receiving noise without having to filter client-side. Builds on existing webhook infrastructure with zero new data dependencies.

**How:**
1. Add `WEBHOOK_FILTER` to `.env.example` (comment: "Optional JSON Logic expression to filter webhook deliveries. Leave unset to fire on every completed simulation. Example: {\">=\" : [{\"var\": \"confidence_pct\"}, 70]}"). In the webhook dispatch layer (wherever `WEBHOOK_URL` is read and the POST is made), after signal JSON is assembled: if `WEBHOOK_FILTER` is set, load it as JSON, evaluate it against the signal payload using a minimal pure-Python JSON Logic evaluator (~60 LoC — implement only the operators needed for filtering: `>=`, `<=`, `>`, `<`, `==`, `!=`, `and`, `or`, `not`, `var`). If evaluation returns falsy, skip the HTTP call and log `webhook_filter_skipped: true` alongside the simulation ID and evaluated expression result. If `WEBHOOK_FILTER` is set but not valid JSON, log a warning and fire the webhook anyway (fail-open to prevent silent data loss on misconfiguration). Add 5 unit tests: expression `{">=": [{"var": "confidence_pct"}, 70]}` returns true for `confidence_pct=75`; same returns false for `confidence_pct=60`; compound `and` expression evaluates correctly; invalid JSON in `WEBHOOK_FILTER` triggers fail-open (webhook fires, warning logged); `WEBHOOK_FILTER` unset fires webhook unconditionally.
2. Add a validation endpoint `POST /api/admin/webhooks/filter/test` (same `ADMIN_TOKEN` auth as other admin routes). Body: `{"filter_expression": str, "sample_payload": dict}`. Evaluates the expression against the sample payload and returns `{"matched": bool, "error": str|null}`. Lets operators test filter expressions without waiting for a real simulation to complete. The `sample_payload` defaults to the standard signal JSON shape if not provided (`confidence_pct`, `direction`, `agent_count`, `round_count`, `topic`). Add to `docs/WEBHOOKS.md` under a new "Filtering deliveries" section with 3 examples: direction-only filter, confidence threshold filter, compound AND filter. Add 3 unit tests: valid expression + matching payload → `{"matched": true, "error": null}`; valid expression + non-matching payload → `{"matched": false, "error": null}`; malformed expression → `{"matched": false, "error": "invalid JSON Logic expression"}`.
3. Add `WEBHOOK_FILTER_EXPRESSION` to the Settings page in the frontend (alongside `WEBHOOK_URL`): a monospace textarea pre-populated with a commented example. On blur, call `POST /api/admin/webhooks/filter/test` with the typed expression and a synthetic signal payload, and show a real-time "Matched ✓" / "No match ✗" / "Error ✗" indicator beside the field. This makes filter configuration self-service without requiring operators to craft curl commands. Add to `docs/CONFIGURATION.md` under "Webhooks". Add 2 frontend unit tests: "Matched ✓" renders when the test endpoint returns `matched: true`; textarea is disabled when `ADMIN_TOKEN` is not configured.

### 3. CLI Tab Completion

**Type:** DX
**Effort:** Small (hours)
**Impact:** The CLI (`cli.py`) is the primary interface for self-hosted operators running simulations in CI, cron jobs, and terminal workflows. Right now every subcommand, flag, and argument value has to be typed from memory or looked up in `docs/CLI.md`. A `miroshark completions [bash|zsh|fish]` subcommand outputs a shell completion script that pipes directly into config: `eval "$(miroshark completions bash)"`. Tab-completing `miroshark simulate --platform <TAB>` to `Twitter LinkedIn Reddit` removes the #1 source of first-time user errors (invalid platform names). Completion output for all subcommands, all flags, and enum argument values is under 200 lines; Click's built-in completion support reduces it further if the CLI uses Click. Zero runtime dependencies added.

**How:**
1. Add a `completions` subcommand to `cli.py`. If the CLI uses Click: register `_MIROSHARK_COMPLETE` env var support via Click's shell completion framework (`click.shell_completion`), and add a `miroshark completions [bash|zsh|fish]` command that runs `click.shell_completion.add_completion_class()` and emits the appropriate script to stdout. If the CLI uses argparse: manually write static completion scripts for bash, zsh, and fish in `scripts/completions/` and have the `completions` subcommand `cat` the appropriate one. Cover all top-level subcommands (`simulate`, `status`, `results`, `list`, `export`, and any others that exist in `cli.py`), all flags (`--platform`, `--agents`, `--rounds`, `--topic`, `--output`, etc.), and enum values for `--platform` (the full list from the platform config or a hardcoded list from `docs/CLI.md`). Add 3 unit tests: `miroshark completions bash` exits 0 and outputs non-empty text; output contains at least one known flag (`--platform`); output contains at least one known subcommand.
2. Add a `make completions-install` target: detects the user's shell (`$SHELL`), outputs the appropriate completion script, and appends `eval "$(miroshark completions <shell>)"` to the detected rc file (`~/.bashrc`, `~/.zshrc`, `~/.config/fish/completions/miroshark.fish`). Prompt for confirmation before writing: `Install completions for bash? (y/N)`. Add a dry-run `make completions-preview` that shows what would be written without modifying any files. Add `Makefile` targets and test with `make completions-preview` in CI to ensure the output is non-empty and well-formed.
3. Add a "Tab Completion" section to `docs/CLI.md` (directly after the Installation section): one-liner install commands for bash, zsh, and fish, plus a note on manual installation. Add completion support to `docs/INSTALL.md` quick-start under "Step 4: Install shell completions (optional)". Update `README_DEPLOYMENT.md` "Post-install checklist" to include completions as an optional enhancement. This is the kind of polish detail that gets mentioned in community posts ("by the way, tab completion works") and reduces the friction delta for non-power users evaluating MiroShark against alternatives.

### 4. Simulation Fine-Tuning Dataset Export

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Each completed simulation contains hundreds of structured agent posts: persona, round context, stance, belief drift, and the actual message text. That's exactly the data format teams use to build instruction fine-tuning datasets. `GET /api/simulation/:id/export/finetune.jsonl` serializes the simulation as JSONL where each line is a fine-tuning example (system: agent persona + initial stance; user: topic + round number + preceding posts as context; assistant: the agent's actual post). Compatible with OpenAI fine-tuning API, Anthropic model training, and Hugging Face `datasets`. No new data sources — pure re-serialization of existing `actions.jsonl` and `trajectory.json`. This positions MiroShark as a synthetic dialogue data generator — a distinct second distribution story alongside "run a market simulation." New user segment: ML engineers, researchers, and fine-tuning studios who generate datasets at scale.

**How:**
1. Create `backend/app/services/finetune_service.py` (~120 LoC, pure stdlib). Accept `simulation_id`. Load `actions.jsonl` and `trajectory.json`. For each agent post, build a training example: `{"messages": [{"role": "system", "content": f"You are {name}, a {profession}. Your initial stance on {topic} is {initial_stance}."}, {"role": "user", "content": f"Topic: {topic}. Round {round_n} of {total_rounds}. Context from prior round: {last_3_posts_from_other_agents_this_round_truncated_to_500_chars}. What do you post?"}, {"role": "assistant", "content": agent_post_text}]}`. Filter out posts where `post_text` is empty or under 20 chars. Cap context at the last 3 posts from other agents in the same round (not the same agent) to prevent context bleed. Return a list of dicts ready for JSONL serialization. Also compute a metadata header as the first line: `{"_meta": {"simulation_id": str, "topic": str, "agent_count": int, "round_count": int, "example_count": int, "generated_at": ISO8601}}`. Add 5 unit tests: output is valid JSONL (each line parses as JSON); each example has `messages` with exactly 3 entries (`system`, `user`, `assistant`); system message contains the agent's name and profession; empty-post entries are filtered out; metadata header is the first line.
2. Add `GET /api/simulation/:id/export/finetune.jsonl` to `backend/app/api/simulation.py`. Publish-gated (same ownership check). Response: `Content-Type: application/x-ndjson`, `Content-Disposition: attachment; filename="miroshark-{id}-finetune.jsonl"`. Stream the output (yield lines from `finetune_service.generate(simulation_id)`) rather than loading all into memory — a 100-agent × 20-round simulation can produce 2,000 examples. Add to `surfaces_catalog.py` (type: `export`) and OpenAPI (note: response is JSONL). Add to `docs/API.md` under "Exports" (alongside `signed-result.json` and trajectory exports): include a note that the format is compatible with `openai.fine_tuning.jobs.create(training_file=...)` and Hugging Face `datasets.load_dataset("json", data_files="*.jsonl")`. Add 2 integration tests: response Content-Type is `application/x-ndjson`; response body has at least 1 line when the simulation has completed rounds.
3. Add a "Export for Fine-tuning" button to the Step 3 result header (alongside "Share" and any other export actions). Clicking it navigates to `GET /api/simulation/:id/export/finetune.jsonl` which triggers a download. Add a tooltip: "Download this simulation as a JSONL dataset compatible with OpenAI fine-tuning, Anthropic model training, and Hugging Face datasets." Also add a `GET /api/export/batch/finetune.jsonl?topic_contains=X&limit=N` endpoint (max N=10, no auth beyond the existing session cookie — only returns sims the session owns): concatenates JSONL from up to 10 simulations into a single file for multi-sim training sets. Add `batch_finetune` to `surfaces_catalog.py`. Add 1 frontend unit test: "Export for Fine-tuning" button triggers navigation to the correct URL.

### 5. Simulation Round-by-Round Summary API

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Every per-round analytics surface (confidence trajectory, stance flips, mentions network) is a separate endpoint requiring separate client integration. Clients building replay UIs, longitudinal charts, or debugging tools currently have to call 3–4 endpoints and join the data themselves. `GET /api/simulation/:id/rounds` returns a structured summary of every completed round in one call: round number, aggregate direction at that round, average confidence across agents, stance distribution snapshot (% BULLISH/BEARISH/NEUTRAL), top-3 posts by influence score, and a `convergence_delta` (how much the aggregate direction changed vs. the prior round). This is the primitive for replay scrubbers, convergence charts, and per-round debugging without requiring clients to parse raw `trajectory.json` and `actions.jsonl`. The endpoint pre-computes and caches the summary alongside the simulation; clients get a clean JSON array instead of raw log files.

**How:**
1. Create `backend/app/services/round_summary_service.py` (~150 LoC, pure stdlib). Accept `simulation_id`. Load `trajectory.json` (per-agent per-round stances and confidence) and `actions.jsonl` (per-agent per-round posts with influence scores). For each round number from 1 to `total_rounds`: compute `{round: int, direction: str (majority BULLISH/BEARISH/NEUTRAL at this round), avg_confidence_pct: float, stance_dist: {bullish_pct, bearish_pct, neutral_pct}, top_posts: [{agent_name, post_text (truncated 120 chars), platform, influence_score, stance}], convergence_delta: float (abs(direction_pct_this_round - direction_pct_prior_round); 0.0 for round 1)}`. Write to `round_summary.json` in the simulation directory (mtime-cached: if file exists and is newer than `actions.jsonl`, return cached version). Return sorted by `round` ascending. Add 5 unit tests: returns exactly `total_rounds` entries; `round_1.direction` is the majority stance among round 1 agent states; `convergence_delta` for round 1 is 0.0; `top_posts` has at most 3 entries; result is mtime-cached on second call (no disk re-read).
2. Add `GET /api/simulation/:id/rounds` to `backend/app/api/simulation.py`. Publish-gated. Cache-Control: `max-age=3600` (round data is immutable once the simulation completes). Optional query param `?include_posts=false` to omit `top_posts` from each round entry (reduces payload size for lightweight chart use cases). Response: `{"simulation_id": str, "total_rounds": int, "rounds": [RoundSummaryEntry]}`. Add to `surfaces_catalog.py` (type: `analytics`) and OpenAPI with `RoundSummaryEntry` and `RoundSummaryResponse` schemas. Add to `docs/API.md` under "Simulation Analytics" with a note: "Use `?include_posts=false` for lightweight chart data (omits post text, ~70% smaller payload)." Add 3 integration tests: returns 200 for a completed simulation; `total_rounds` matches the simulation config; `?include_posts=false` omits `top_posts` from each entry.
3. Add a "Rounds" sparkline to the simulation result card in the gallery view (`frontend/src/`): a 120×28px SVG inline chart drawn from `GET /api/simulation/:id/rounds?include_posts=false`. The line tracks `avg_confidence_pct` across rounds; a color fill (violet above 50%, gray below) shows whether the simulation converged. Load lazily on card entry into the viewport (`IntersectionObserver`). Clicking the sparkline navigates to the Step 3 detail view with the rounds panel expanded. Add a "Rounds" tab to the Step 3 analytics panel (alongside Stance Shifts, Mentions) that renders the full round summary table: one row per round, with direction chip, confidence %, stance distribution bars, and the top post snippet. Add 2 frontend unit tests: sparkline SVG path element is present when rounds data has ≥ 2 entries; "Rounds" tab renders the correct number of table rows matching `total_rounds`.
