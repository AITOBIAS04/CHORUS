### 1. Real-World Outcome Annotation + Calibration Score

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Every simulation makes a prediction. Right now there's no way to close the loop — operators who ran "Will the Fed hold rates?" and now know the answer have nowhere to record it. `POST /api/simulation/:id/outcome` accepts `{actual_direction: "BULLISH"|"BEARISH"|"NEUTRAL", notes: str|null}` and stores the annotation alongside the simulation. `GET /api/simulation/:id/outcome` retrieves it. `GET /api/accuracy/summary` aggregates all annotated simulations owned by the session and returns `{total_annotated, correct, accuracy_pct, by_direction: {...}}` — the operator's personal calibration score. This turns MiroShark from a one-shot oracle into a tracked prediction record. Researchers who share their calibration score ("74% accuracy across 23 annotated predictions") have a concrete credibility signal; ecosystem partners building market-intelligence products can use the accuracy API to surface their platform's track record. Zero changes to the simulation execution path — pure annotation layer on top of completed simulations.

**How:**
1. Create `backend/app/services/outcome_service.py` (~100 LoC, pure stdlib). Data model: `{simulation_id: str, actual_direction: str, notes: str|null, annotated_at: ISO8601, session_token: str}`. Persist to `storage/outcomes/{simulation_id}.json`. Operations: `annotate(simulation_id, actual_direction, notes, session_token)` — validates `actual_direction` is one of the three values, checks the simulation exists and is published, writes to disk; `get(simulation_id)` — reads the file, returns `None` if missing; `accuracy_summary(session_token)` — scans `storage/outcomes/`, loads each file owned by the session, compares `actual_direction` to the simulation's `signal.json` direction field, computes `{total_annotated, correct, accuracy_pct, by_direction: {BULLISH: {total, correct, pct}, BEARISH: {...}, NEUTRAL: {...}}}`. Add 6 unit tests: invalid direction returns `ValueError`; annotation is persisted to disk; `get` returns `None` for unknown simulation; `accuracy_summary` counts correctly for all three directions; accuracy_pct is 0.0 when all wrong, 100.0 when all correct; only own-session outcomes are counted.
2. Add three routes to `backend/app/api/simulation.py`: `POST /api/simulation/:id/outcome` (publish-gated, same session ownership as signal endpoint); body `{actual_direction, notes}`; returns `{simulation_id, actual_direction, annotated_at}`; 400 for invalid direction; 409 if already annotated (update not allowed — prevents post-hoc result washing). `GET /api/simulation/:id/outcome` — returns annotation or 404 if not yet annotated. `GET /api/accuracy/summary` — session-scoped, returns the accuracy struct (requires at least 1 annotated sim; returns 200 with empty fields if none). Add to `surfaces_catalog.py` (type: `annotation`) and OpenAPI with `OutcomeAnnotation`, `AccuracySummary` schemas. Add to `docs/API.md` under a new "Prediction Accuracy" section with a note: "Annotations are immutable — you can record an outcome once per simulation, preventing retroactive result adjustment." Add 3 integration tests: POST outcome stores annotation; GET returns it; GET /accuracy/summary counts it correctly.
3. Add an "Accuracy" panel to the Step 3 result header (alongside Share, Export): a small chip showing whether this simulation has been annotated (if yes: green check + "Correct" or red X + "Incorrect"; if no: gray "Annotate outcome" button). Clicking "Annotate outcome" opens a 3-button selector (BULLISH / BEARISH / NEUTRAL) plus an optional notes field — POST on confirm, chip updates immediately. Add a user-level "My Calibration" link in the nav header (visible only when the user has ≥1 published simulation) that opens `GET /api/accuracy/summary` as a stats card: accuracy %, total count, breakdown by direction with small bar chart. Add 2 frontend unit tests: "Annotate outcome" button is hidden after annotation; accuracy % chip shows "74%" when summary returns `accuracy_pct: 74.3`.

### 2. QR Code Share Surface

**Type:** Feature
**Effort:** Small (hours)
**Impact:** MiroShark's 13-surface distribution architecture (share card, GIF, badge, transcript, …) reaches everywhere pixels travel digitally — but not physical media. Conferences, printed reports, whiteboards, and physical merchandise (stickers, posters for crypto events) all need a QR code. `GET /api/simulation/:id/qrcode.png` returns a 512×512 PNG QR code encoding the simulation's public share URL. No new dependencies — pure Python's `qrcode` package is 4KB and ships as a stdlib-complete fallback; the alternative is a 40-LoC pure-Python QR matrix renderer targeting version 3 codes (alphanumeric mode covers all URL characters and is supported by every smartphone scanner since 2012). The endpoint follows the same publish-gate pattern as every other share surface. A researcher presenting at ICSE or ETHDenver can embed the QR code in their final slide; every attendee with a phone can run the same simulation or check the result immediately. Fourteen surfaces.

**How:**
1. Create `backend/app/services/qr_service.py` (~120 LoC, pure stdlib + optional `qrcode` import). Accept `share_url: str`, `size: int` (default 512, clamp 256–1024). Primary path: `import qrcode` (if available) → generate with error-correction level M, box_size derived from `size // 21`, border 4. Render to PNG bytes via `io.BytesIO`. Fallback path (if qrcode not installed): generate a version 3 QR matrix manually using the ISO 18004 data encoding for alphanumeric mode — encode the URL characters, generate the 29×29 module matrix, render it as a PNG using `struct.pack` to write raw DEFLATE-compressed bitmap pixels without Pillow. Cache the result to `storage/qrcodes/{simulation_id}.png` (content-hash filename for cache busting on URL changes). Add 5 unit tests: output is valid PNG (starts with `\x89PNG`); output dimensions match the requested size; same URL produces identical bytes (deterministic); URL longer than 32 chars (version 3 alphanumeric limit) auto-upgrades to version 4 or falls back gracefully; cached result is returned on second call without re-computation.
2. Add `GET /api/simulation/:id/qrcode.png` to `backend/app/api/share.py` (alongside the existing share-card, GIF, and badge routes — same module, same publish-gate). Params: `?size=512` (optional). Response: `Content-Type: image/png`, `Cache-Control: max-age=86400, public`, `Content-Disposition: inline; filename="miroshark-{id}-qrcode.png"`. The URL encoded into the QR is the same share URL returned by `GET /api/simulation/:id/share` — derived from `MIROSHARK_PUBLIC_URL` env var with the simulation's share token. Add to `surfaces_catalog.py` (14th visual surface, type: `share`) and OpenAPI. Add to `docs/API.md` under "Sharing" alongside the badge surface. Add 2 integration tests: returns 200 PNG for a published simulation; returns 404 for an unpublished simulation.
3. Add a "QR Code" button to the Step 3 share sheet (`Step3Simulation.vue` Share panel, alongside the existing "Copy Link", "Share Card", "Badge" options). Clicking it shows a modal with the 256×256 QR code rendered from `GET /api/simulation/:id/qrcode.png?size=256`, a "Download 512px" button that triggers download of the 512px version, and a copy-URL link below. Add a "Print QR" button inside the modal that opens the browser's print dialog with just the QR + simulation title in a minimal print layout (no nav chrome). Add to the embed dialog's "share surfaces" list. Add 2 frontend unit tests: QR modal opens on button click; "Download 512px" button triggers navigation to the correct size URL.

### 3. Simulation Podcast Script Export

**Type:** Content / Feature
**Effort:** Small (hours)
**Impact:** The existing share surfaces (share card, GIF, thread formatter, transcript) cover visual, animated, and written formats. Podcast is the one audio-native format with no equivalent surface. `GET /api/simulation/:id/podcast-script` generates a 400–600 word conversational dialogue between two named hosts — a skeptic and a believer — discussing the simulation's signal: the topic, what the agents decided, the confidence level, the most surprising stance flip, and what would change the consensus. The script is generated by the existing LLM client (cached to disk after first generation). Operators running crypto or macro commentary podcasts can feed it directly into a text-to-speech pipeline (ElevenLabs, Play.ht, Murf) or read from it live. No new data sources — the signal, trajectory, and stance-flip data are all already computed. Fifteenth share surface. Creates a distinct content marketing angle: "AI agents debate X" is inherently talkable and shareable.

**How:**
1. Create `backend/app/services/podcast_script_service.py` (~180 LoC). Accept `simulation_id`. Load `signal.json` (direction, confidence_pct, topic, agent_count, round_count), `stance_flips.json` (top flip agent name + flip description if the service exists; skip gracefully if not), and `trajectory.json` (final round stance distribution). Construct a system prompt establishing two personas: `Alex` (balanced moderator, introduces the topic and final signal) and `Jordan` (challenges the consensus, probes why). Construct a user prompt: "Write a 400–600 word podcast script as Alex and Jordan discussing a swarm simulation on '{topic}'. The simulation ran {agent_count} agents for {round_count} rounds. Final signal: {direction} at {confidence_pct}% confidence ({bullish_pct}% bullish / {bearish_pct}% bearish / {neutral_pct}% neutral). {if top_flip: 'Notable: {agent_name} flipped from {from_stance} to {to_stance} during the simulation.'}. End with the one event that would most change the consensus." Call `LLMClient.chat_text()` with these prompts. Cache the result to `storage/podcast_scripts/{simulation_id}.md`. Return the cached file on subsequent calls (mtime check — only regenerate if signal.json is newer than the cached script). Add 5 unit tests: output is non-empty text; output contains both "Alex" and "Jordan"; output is cached on second call; cache invalidates if signal.json mtime is newer; missing stance_flips.json is handled gracefully (skip that sentence).
2. Add `GET /api/simulation/:id/podcast-script` to `backend/app/api/share.py`. Publish-gated. Response: `Content-Type: text/markdown; charset=utf-8`, `Cache-Control: max-age=3600, public`, `Content-Disposition: inline; filename="miroshark-{id}-podcast.md"`. Optional `?format=txt` param to return plain text without Markdown formatting (strips `**Alex:**` bold markers). Add to `surfaces_catalog.py` (type: `content`, 15th visual/content surface) and OpenAPI. Add to `docs/API.md` under "Share Surfaces" with a note: "Use ?format=txt to get plain text suitable for text-to-speech pipelines. The script is cached — first generation may take 5–10 seconds as the LLM writes it; subsequent requests return instantly." Add 2 integration tests: returns 200 Markdown for published sim; `?format=txt` strips bold markers.
3. Add a "Podcast Script" option to the Step 3 Share panel (alongside Share Card, GIF, Badge, QR). Clicking it opens a modal with the script rendered as a formatted dialogue (speaker names in bold, lines alternating left/right with a subtle avatar placeholder). Include a "Copy as Text" button (strips Markdown, copies plain text to clipboard) and a "Download .md" button. Add a small tip below the script: "Paste into ElevenLabs, Play.ht, or any text-to-speech tool. The two voices are named Alex and Jordan." Add 2 frontend unit tests: script modal renders with formatted dialogue; "Copy as Text" button calls clipboard API with plain text.

### 4. Trending Topics Discovery Feed

**Type:** Feature / Growth
**Effort:** Small (hours)
**Impact:** New users face a cold-start problem: they arrive at MiroShark with no idea what to simulate. The full-text search endpoint requires knowing what you want. `GET /api/feed/trending` solves discovery from the other direction — it aggregates all published simulations from the last 30 days, groups them by a normalized topic string, and returns a ranked list of topics with their latest signal direction and the aggregate confidence across runs. "Fed rate cut: 3 runs, BULLISH, avg 78% confidence" tells a new user immediately that this is an active topic and that the swarm is leaning one way. Zero new data sources — purely aggregates existing published `signal.json` files. The endpoint is keyless (same as `/api/estimate`) so it can be embedded on landing pages, linked from README, and consumed by ecosystem partners building monitoring dashboards. Practically: a "What's the market thinking?" widget on the MiroShark landing page built from this endpoint is the kind of live data display that turns a cold repo into an active oracle.

**How:**
1. Create `backend/app/services/trending_service.py` (~150 LoC, pure stdlib). Scan `storage/simulations/*/signal.json` for all published sims (check `publish_token` or `published: true` flag — same publish-gate predicate used by the search service). Filter to sims with `created_at` within the last 30 days (configurable via `TRENDING_WINDOW_DAYS` env var, default 30). For each, read `{topic, direction, confidence_pct, created_at}`. Group by a normalized topic key: lowercase, strip punctuation, collapse whitespace (e.g., "Will the Fed cut rates?" → "will the fed cut rates"). For each group, compute: `{topic_display: str (the most common raw topic string in the group), sim_count: int, latest_direction: str, avg_confidence_pct: float, directions_breakdown: {BULLISH: int, BEARISH: int, NEUTRAL: int}, latest_created_at: ISO8601}`. Sort by `sim_count` descending, then `latest_created_at` descending for ties. Mtime-cached: write result to `storage/trending_cache.json`; regenerate if any signal.json in the set is newer than the cache (check max mtime). Add 5 unit tests: topics normalize correctly; sims older than WINDOW_DAYS are excluded; breakdown counts correct for mixed-direction groups; sort is sim_count desc; cache returns same result without re-scan if no new sims.
2. Add `GET /api/feed/trending` to a new `backend/app/api/feed.py` (or the existing `feed.py` if it exists). Keyless (no auth). Query params: `?limit=N` (default 10, max 50), `?window=30` (override TRENDING_WINDOW_DAYS for this request, clamp 7–90). Response: `{"topics": [TrendingTopicEntry], "window_days": int, "generated_at": ISO8601}`. Cache-Control: `max-age=300, public` (5 min freshness). Add to `surfaces_catalog.py` (type: `discovery`) and OpenAPI with `TrendingFeedResponse`, `TrendingTopicEntry` schemas. Add to `docs/API.md` under "Discovery" (alongside the search endpoint). The endpoint is documented as suitable for embedding: "Keyless — safe to call from client-side JavaScript, widget scripts, and README embed badges without exposing secrets." Add 3 integration tests: returns 200 with `topics` array; `?limit=3` returns at most 3 topics; topic without any published sim in the window is excluded.
3. Add a "Trending" section to the main gallery page (`frontend/src/`): a horizontal scrolling chip row above the simulation list showing the top-5 trending topics from `GET /api/feed/trending?limit=5`. Each chip shows the topic display text + a direction color dot (violet=BULLISH, red=BEARISH, gray=NEUTRAL) + the sim count. Clicking a chip pre-fills the simulation creation topic field (Step 1) with that topic text. Load on page mount; cache the result in `sessionStorage` for 5 minutes to avoid re-fetching on navigation. Also add the trending feed as an embeddable snippet in the README's "Live data" section: a 3-row table rendered from the API, updated on each README deploy via a GitHub Actions step. Add 2 frontend unit tests: trending chips render with direction dot; clicking a chip sets the topic field value.

### 5. Simulation Confidence Leaderboard

**Type:** Community / Growth
**Effort:** Small (hours)
**Impact:** The public gallery shows simulations in chronological order. There's no way to discover the most decisive runs — the ones where 90%+ of agents converged on a direction, or the rarest cases where consensus split almost exactly 50/50. `GET /api/leaderboard` returns two ranked lists from all published simulations: `highest_confidence` (top-20 by `confidence_pct` descending) and `most_contested` (top-20 by proximity of `bullish_pct` to 50 — the most uncertain runs). Each entry includes topic, direction, confidence_pct, agent_count, and the operator's display name if they've set one via `GET /api/settings`. This is a quality-ranked showcase, not a chronological list. A "Leaderboard" tab in the gallery makes the most extreme consensus events permanently discoverable — "94% of agents agreed Bitcoin would consolidate" is the kind of data point that gets cited in research and shared on social. The endpoint also gives the project a natural content hook: the weekly top confidence runs are tweetable data.

**How:**
1. Create `backend/app/services/leaderboard_service.py` (~140 LoC, pure stdlib). Scan all published `signal.json` files. For each, read `{simulation_id, topic, direction, confidence_pct, bullish_pct, agent_count, round_count, created_at, publish_token}`. Compute `contest_score = abs(bullish_pct - 50.0)` (lower = more contested; 0.0 = perfect 50/50 split). Sort by `confidence_pct` descending for the high-confidence list; sort by `contest_score` ascending for the contested list. Take top-20 for each. For operator attribution: look up the `display_name` field from `storage/settings.json` if it exists (the same settings store used by `GET /api/settings`); if missing, omit the field (no PII risk — only operators who explicitly set a display name appear). Cache to `storage/leaderboard_cache.json` with the same mtime-invalidation pattern as trending_service. Add 5 unit tests: `contest_score` is 0.0 for 50/50 split; `highest_confidence` list is sorted desc; `most_contested` list is sorted by contest_score asc; top-20 cap is enforced; display_name is omitted when settings.json is missing.
2. Add `GET /api/leaderboard` to `backend/app/api/feed.py` (or `surfaces.py`). Keyless. Response: `{"highest_confidence": [LeaderboardEntry], "most_contested": [LeaderboardEntry], "generated_at": ISO8601}`. Cache-Control: `max-age=600, public` (10 min). Optional `?list=highest_confidence` or `?list=most_contested` to return only one list. `LeaderboardEntry`: `{rank: int, simulation_id: str, topic: str, direction: str, confidence_pct: float, bullish_pct: float, agent_count: int, created_at: ISO8601, display_name: str|null, share_url: str}`. Add `share_url` by constructing from `MIROSHARK_PUBLIC_URL` + the simulation's publish token (same pattern as the badge endpoint). Add to `surfaces_catalog.py` (type: `discovery`) and OpenAPI with `LeaderboardResponse`, `LeaderboardEntry` schemas. Add to `docs/API.md` under "Discovery". Add 3 integration tests: returns both lists; `?list=most_contested` returns only that list; entries include `share_url`.
3. Add a "Leaderboard" tab to the gallery page (alongside "My Simulations" and "Public") — loads `GET /api/leaderboard` and renders two sections: "Most Decisive" (highest confidence) and "Most Contested" (closest to 50/50 split). Each row: rank badge, topic text, direction chip, confidence % bar, agent count, time ago, and operator display name (if set). The direction chip uses the existing violet/red/gray palette. Row click navigates to the simulation's share URL. Lazy-load on tab activation (not on page mount). Add a shareable permalink: `/gallery?tab=leaderboard` deep-links to the tab. Add a static table of the current top-5 to the README under "Community Simulations" (built as a step in the existing GitHub Actions deploy workflow, populated from `GET /api/leaderboard?list=highest_confidence&limit=5`). Add 2 frontend unit tests: leaderboard tab renders "Most Decisive" and "Most Contested" sections; row click navigates to the simulation share URL.
