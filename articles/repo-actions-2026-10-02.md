### 1. RSS/Atom Feed for Published Simulations

**Type:** Integration
**Effort:** Small (hours)
**Impact:** MiroShark has 8,000+ published simulations with no standards-compliant feed that external aggregators can subscribe to. `GET /api/feed.xml` returns an Atom 1.0 feed — each `<entry>` has `<title>` (simulation topic), `<summary>` (direction + confidence_pct + agent count), `<link>` (simulation URL), `<published>` (published_at), and `<id>` (simulation ID as a URN). RSS readers (Feedly, NetNewsWire), Discord RSS bots, Telegram RSS channels, Zapier, Make.com, and IFTTT can all subscribe without any API key or integration work. The protocol is 25 years old — every automation tool on Earth speaks it. During 87 days of social silence, every distribution channel that operates without human action is worth building. Distinct from Activity Feed (internal JSON event stream for system events), Hot Topics Feed (aggregated topic JSON — off-limits Sep 30), and Trending Simulations Feed (JSON sorted by views — off-limits Aug 22). This is the universal pull-subscription surface — whatever tool a user already uses to follow updates will work with it.

**How:**
1. Create `backend/app/api/feed.py` (~80 LoC, pure stdlib). `GET /api/feed.xml`. Logic: (1) Scan all published simulation directories, read `signal.json` from each, sort by `published_at` descending, take the 50 most recent. (2) Build an Atom 1.0 XML document using `xml.etree.ElementTree` (stdlib). Root: `<feed xmlns="http://www.w3.org/2005/Atom">`. Feed-level elements: `<title>MiroShark Simulations</title>`, `<link rel="alternate" href="{BASE_URL}"/>`, `<link rel="self" href="{BASE_URL}/api/feed.xml"/>`, `<id>urn:miroshark:feed:simulations</id>`, `<updated>` (most recent entry's `published_at`), `<author><name>MiroShark</name></author>`. Per entry: `<id>urn:miroshark:simulation:{simulation_id}</id>`, `<title>{topic}</title>`, `<link href="{BASE_URL}/simulation/{simulation_id}"/>`, `<published>{published_at}</published>`, `<summary type="text">{agent_count} agents · {total_rounds} rounds · {direction} · {confidence_pct}% confidence</summary>`. Return with `Content-Type: application/atom+xml; charset=utf-8` and `Cache-Control: public, max-age=300`. Add `<autodiscovery>` link tag to the Step 1 page HTML `<head>`: `<link rel="alternate" type="application/atom+xml" title="MiroShark Simulations" href="/api/feed.xml">` — this makes the feed auto-discoverable in Firefox and Safari. Add 3 unit tests: feed is valid Atom 1.0 (root tag and namespace); entries are sorted by published_at descending; empty feed returns a valid Atom document with zero entries (not 500).

2. Add `GET /api/feed.xml` to `surfaces_catalog.py` (type: `feed`) and OpenAPI schema with a note that this endpoint returns `application/atom+xml` rather than JSON. Add a `GET /api/feed.json` companion that returns the same 50 entries as JSON (array of `{simulation_id, topic, direction, confidence_pct, agent_count, published_at, url}`) — for callers that prefer JSON over XML. Both endpoints share the same scan/sort logic via a common `FeedService` class, so the `feed.json` endpoint adds ~10 LoC. Add `GET /api/feed.json` to `surfaces_catalog.py` and OpenAPI schema. Add 2 more unit tests: `feed.json` returns correctly shaped JSON; both endpoints return the same number of entries for the same data directory.

3. Add a "Subscribe" section to the README under the existing "API" section: a badge `[![RSS Feed](https://img.shields.io/badge/RSS-Feed-orange?logo=rss)](https://your-deployed-url/api/feed.xml)` and a one-line description: "Subscribe to the latest simulation results via RSS/Atom: `GET /api/feed.xml`." Add to `docs/API.md` under a new "Feed Endpoints" section with a note on `limit` query param behavior and the autodiscovery `<link>` tag. Document in `docs/FEATURES.md`. The RSS badge in the README is visible to every person who views the repo — during Hacktoberfest, it signals that the project has active output worth following.

### 2. x402 Pay-Per-Simulation Endpoint

**Type:** Integration
**Effort:** Medium (1-2 days)
**Impact:** PR #313 registered MiroShark in the x402aff ecosystem — the protocol has handled 150M+ transactions and ~$50M in agent payments on Base. x402 is a standard HTTP 402 payment protocol where clients attach a signed payment header; the server verifies it before processing the request. Adding `POST /api/simulate/pay` (accepts an x402 `X-PAYMENT` header + simulation parameters) makes MiroShark the first social simulation platform where an AI agent can autonomously commission and pay for a swarm simulation with no human in the loop. An AI agent building a trading strategy can call `POST /api/simulate/pay` with `{topic: "ETH Q4 2026", agents: 50, rounds: 5}` + a valid x402 payment, get back a `simulation_id`, and poll `GET /api/simulation/{id}/status` until complete. This is the core of the "agent economy" narrative that x402 enables — distinct from all prior feature ideas which were human-facing. Price: 0.01 USDC per simulation (configurable via `SIMULATION_PRICE_USDC` env var). Distinct from all prior ideas, all of which assumed human-initiated simulations.

**How:**
1. Create `backend/app/api/pay_simulate.py` (~120 LoC). `POST /api/simulate/pay`. Request body: `{topic: str, agents: int, rounds: int, platforms: list[str]}` (same schema as the existing simulation start endpoint). Additional header: `X-PAYMENT` (x402 payment payload — a base64-encoded JSON containing the signed payment transaction). Payment verification logic: (1) Decode the `X-PAYMENT` header. (2) Check `payment.network` is `"base"` or `"base-sepolia"`. (3) Verify `payment.amount >= SIMULATION_PRICE_USDC` (default 0.01 USDC = 10000 in 6-decimal units). (4) Verify the payment transaction hash has not been used before (store used hashes in `.x402-used/` directory, one file per hash). (5) If valid, proceed to enqueue the simulation identically to the standard `POST /api/simulate` endpoint. If invalid: return `402 Payment Required` with body `{"error": "payment_required", "price": {"amount": "10000", "currency": "USDC", "network": "base"}, "payment_pointer": "{BASE_URL}/api/simulate/pay"}`. Add `X402_ENABLED` env var (default `false`) — the endpoint returns `501 Not Implemented` when disabled. Add `X402_PRICE_USDC` env var. Use `scripts/prefetch-x402.sh` to pre-validate the Base RPC endpoint is reachable (sandbox fallback: write to `.x402-cache/rpc-status.json`). Add 4 unit tests: returns 402 when payment header missing; returns 402 when amount insufficient; returns 402 when tx hash already used; returns 200+simulation_id when payment valid (mock the verification).

2. Create `docs/X402.md` (~80 lines). Documents: (1) What x402 is and why MiroShark supports it. (2) The payment flow: get the 402 response, read the `price` fields, construct the payment transaction on Base, include `X-PAYMENT` header, retry. (3) Example using the `x402` TypeScript/Python client library. (4) The simulation price (`SIMULATION_PRICE_USDC` default). (5) How to verify the simulation result is authentic (link to `GET /api/simulation/{id}/signed-result.json` which was PR #152). Add a "Pay-per-simulation (x402)" section to `docs/API.md`. Add `X402_ENABLED` and `X402_PRICE_USDC` to `docs/INSTALL.md` under a new "x402 Payments" section. Add `GET /api/simulate/pay` to `surfaces_catalog.py` (type: `payment-gated`). Add the endpoint to OpenAPI schema with the `402` response documented explicitly. This is the first endpoint in MiroShark where a 402 is a *success path*, not an error — the OpenAPI note matters for SDK generators.

3. Post to the CHORUS repo's `memory/topics/x402.md` a note on the integration: endpoint path, price env var, disabled-by-default behavior, and how the tx hash dedup works. Add a `scripts/test-x402-payment.sh` script that sends a test simulation request to `POST /api/simulate/pay` on the local dev server with a mock payment header (using Base Sepolia testnet) — verifies the 402 response shape and the successful payment path. This script doubles as a dev smoke test and a demo script that can be shared in the x402aff registry listing to show live integration. Add MiroShark to the x402aff registry's "simulation" category (if it exists) by updating the `description` field of PR #313's registry entry to mention the `POST /api/simulate/pay` endpoint. Update the README to add a "x402 Payment API" badge: `[![x402](https://img.shields.io/badge/x402-pay--per--sim-blue)](docs/X402.md)`.

### 3. Simulation Jupyter Notebook Export

**Type:** DX / Research
**Effort:** Small (hours)
**Impact:** The HuggingFace badge (PR #311) and Bulk CSV Export (Sep 30, not yet built) both address data access. But a researcher who downloads raw CSV still has to write all their analysis boilerplate from scratch: load data, reshape trajectory.json, plot belief drift, compute per-agent stats. `GET /api/simulation/{id}/notebook` returns a downloadable Jupyter `.ipynb` file pre-populated with the simulation's actual data and a set of ready-to-run analysis cells: (1) a belief drift line chart (matplotlib), (2) per-agent stance summary (pandas DataFrame), (3) platform breakdown bar chart, (4) a correlation cell checking if high-influence agents drove the final consensus. The researcher opens the file and clicks "Run All" — everything works immediately. No data wrangling, no figuring out the schema. Distinct from Bulk CSV Export (raw tabular data without analysis) and the existing `signal.json` / `trajectory.json` endpoints (raw JSON, no analysis layer). This makes MiroShark data accessible to researchers who know Jupyter but don't know the MiroShark API schema.

**How:**
1. Create `backend/app/api/notebook.py` (~100 LoC, pure stdlib). `GET /api/simulation/{id}/notebook`. Publish-gated (returns 404 if simulation not published). Reads `signal.json`, `trajectory.json`, and `actions.jsonl` for the simulation. Builds a `.ipynb` JSON structure (Jupyter notebook format v4.4) using Python dicts — no external libraries needed, the notebook format is just nested JSON. Notebook structure: (1) **Cell 0 — Markdown**: title cell "# MiroShark Simulation: {topic}" + metadata block (simulation_id, published_at, agent_count, total_rounds, direction, confidence_pct, URL). (2) **Cell 1 — Code**: `import json, pandas as pd, matplotlib.pyplot as plt` + inline data assignment `signal = {signal_data}; trajectory = {trajectory_data}` (actual data inlined as Python dict literals). (3) **Cell 2 — Code**: belief drift chart — `pd.DataFrame([{r['round']: r['bullish_pct'], ...} for r in trajectory]).plot(...)`. (4) **Cell 3 — Code**: per-agent summary DataFrame from `actions.jsonl` data (inlined as a list of dicts). (5) **Cell 4 — Code**: platform breakdown pie chart. (6) **Cell 5 — Markdown**: "Next steps" section with links to the API docs, similar simulations endpoint, and bulk export endpoint. Return `Content-Type: application/x-ipynb+json`, `Content-Disposition: attachment; filename="miroshark-{simulation_id}.ipynb"`. Add 3 unit tests: returned JSON parses as valid notebook (has `nbformat`, `cells` keys); all cells are present; data in cell 1 matches input signal.

2. Add `GET /api/simulation/{id}/notebook` to `surfaces_catalog.py` (type: `export`) and OpenAPI schema. Add a download button to the Step 3 UI — alongside the existing share/embed buttons, add `📓 Download Notebook (.ipynb)`. The button calls `GET /api/simulation/{id}/notebook` and triggers a browser download. Also add a `curl` example in `EmbedDialog.vue` under a "Research Export" section: `curl "{BASE_URL}/api/simulation/{id}/notebook" -o simulation.ipynb`. Add to `docs/API.md` under an "Export" section and `docs/FEATURES.md`. Add a note in the README's "API" section: "For researchers: download any simulation as a runnable Jupyter notebook at `GET /api/simulation/{id}/notebook`." This note in the README gives MiroShark a tangible research-grade credential that appears in first impressions.

3. Add a `?template=minimal` query param variant that returns a stripped-down notebook with only the data cells (no analysis code) — for users who want to start from scratch with just the data pre-loaded. And a `?template=full` variant (default) that includes all analysis cells. The template selection is a single `if template == "minimal":` branch in the cell-building logic — minimal adds only Cell 0 (markdown header) and Cell 1 (data inlining), no charts. Add 2 more unit tests: `?template=minimal` returns fewer cells than `?template=full`; default (no param) behaves identically to `?template=full`. Document both templates in `docs/API.md`. The minimal template is the correct default for researchers who use specific analysis frameworks (R-bridge, Julia, Polars) and don't want matplotlib boilerplate they'll delete anyway.

### 4. Cross-Topic Consensus Heatmap API

**Type:** Feature / Analytics
**Effort:** Small (hours)
**Impact:** MiroShark has 8,000+ simulations but no aggregated view of how different topic categories historically resolve. `GET /api/analytics/consensus-map` returns a consensus profile per keyword cluster: all simulations whose topic contains "BTC" → 61% bullish / 14% neutral / 25% bearish (avg confidence 74%); all "ETH" simulations → 54% bullish / 22% neutral / 24% bearish; "inflation" → 38% bullish / 31% neutral / 31% bearish. This is the "meta-consensus" layer — the aggregate signal across the entire simulation corpus. Researchers use it to calibrate how biased the swarm's priors are by topic. Third-party apps can embed it as a "MiroShark Consensus by Asset" widget. Distinct from: Hot Topics Feed (recent activity count, not historical consensus — off-limits Sep 30), Similar Simulations (topology matching — off-limits Sep 30), Trending Simulations (views-based — off-limits Aug 22), Per-Platform Consensus Divergence (cross-platform within a single sim — off-limits Aug 30). This is **historical cross-topic aggregate analysis across all simulations**.

**How:**
1. Create `backend/app/services/consensus_map_service.py` (~150 LoC, pure stdlib). Function `get_consensus_map(keywords: list[str] | None = None, min_sims: int = 3) -> list[dict]`. Logic: (1) Scan all published simulation directories, read `signal.json` for each (skip unpublished). Build an in-memory list of `{topic, direction, confidence_pct}` records. Cache to `.consensus-map-cache/index.json` with 15-minute mtime TTL. (2) If `keywords` provided, filter topic strings for those keywords (case-insensitive `in` check). If not provided, auto-extract keywords from all topic strings: tokenize topics (lowercase, split on non-alphanumeric, drop stopwords), keep tokens that appear in 3+ different topic strings, sort by frequency descending, take top 20. (3) For each keyword, group matching simulations. If fewer than `min_sims`, skip. Compute: `bullish_pct` (len where direction=="BULLISH") / total), `neutral_pct`, `bearish_pct`, `avg_confidence_pct` (mean of all confidence_pct), `simulation_count`, `dominant_direction` (highest of the three), `dominant_confidence` (the pct corresponding to dominant_direction). (4) Sort output by `simulation_count` descending. Add 4 unit tests: keyword with all-bullish sims → bullish_pct 1.0; keyword below min_sims threshold is excluded; auto-keyword extraction returns only tokens appearing in 3+ topics; output sorted by simulation_count descending.

2. Add `GET /api/analytics/consensus-map` to `backend/app/api/`. Query params: `keywords` (comma-separated list, optional), `min_sims` (int, default 3, clamp [1, 50]). Returns JSON: `{generated_at: ISO, total_simulations_scanned: int, map: [{keyword, simulation_count, bullish_pct, neutral_pct, bearish_pct, avg_confidence_pct, dominant_direction}]}`. Cache-Control: `max-age=900` (15 min). Add to `surfaces_catalog.py` (type: `analytics`) and OpenAPI schema with `ConsensusMapResponse` and `ConsensusMapEntry`. Add 2 integration tests: endpoint returns correct shape; `?keywords=BTC,ETH` filters correctly. Add to `docs/API.md` under an "Analytics" section with an example: `curl "/api/analytics/consensus-map?keywords=bitcoin,ethereum,inflation"`. Register route in `backend/app/main.py`. Add to `docs/FEATURES.md`.

3. Surface in the frontend as a "Topic Consensus Atlas" page at `/analytics/consensus-map`. Fetches `GET /api/analytics/consensus-map` on mount (no query params = auto-keywords). Renders as a sortable table: columns are Keyword, Sims, Bullish %, Neutral %, Bearish %, Avg Confidence, Dominant Direction. Each row has a mini stacked bar (violet/gray/red) showing the three percentages side-by-side — same style as the per-platform sentiment bars. Sort options: by simulation_count (default), by bullish_pct, by avg_confidence_pct. Add a text input for `?keywords=` that re-fetches on debounce (500ms). Bilingual (EN/ZH-CN). Add "Consensus Atlas" to the main navigation. This page is a standalone data artifact — a researcher or journalist can screenshot the BTC row and post it as "MiroShark: 61% of BTC simulations historically resolved bullish." That screenshot is its own distribution event. Add route to `frontend/src/router/index.js`.

## Selection Rationale

Five ideas for Day 2 of Hacktoberfest, the 87-day silence reality, and the x402 ecosystem opportunity just opened by PR #313.

- **RSS/Atom Feed (#1)** — The most universally compatible distribution surface available. Every aggregator, bot, and automation tool speaks RSS. During 87 days of silence, passive distribution via subscriptions is the only category of sharing that doesn't require human action. The autodiscovery `<link>` tag makes it findable without documentation.

- **x402 Pay-Per-Simulation (#2)** — PR #313 just listed MiroShark in the x402aff registry ($50M in agent payments). The natural follow-through is an actual payment endpoint so AI agents can pay to run simulations — making MiroShark the first simulation platform where agents are first-class clients. The unsigned `POST /api/simulate/pay` path is the core; the x402 verification layer wraps it. Disabled by default (no breaking change).

- **Jupyter Notebook Export (#3)** — The HuggingFace dataset badge created a research audience. That audience's default tool is Jupyter. Pre-populated notebooks with actual simulation data + ready-to-run analysis cells removes the highest-friction step (schema spelunking) and turns a 15-minute data-wrangling task into a 30-second download. Research-grade credibility with negligible implementation cost: `.ipynb` is just nested JSON.

- **Cross-Topic Consensus Heatmap (#4)** — 8,000+ simulations, zero aggregate analysis. A `GET /api/analytics/consensus-map` endpoint answers "how does the swarm historically lean on BTC vs ETH vs inflation?" in one call. The `/analytics/consensus-map` frontend page is a standalone screenshot artifact — "MiroShark: 61% of all BTC simulations resolved bullish" is the kind of data point that gets cited in newsletters and Discord threads without the author having visited the site.

- **Social Card Image Generator (#5)** — Every simulation shared as a URL currently shows a blank preview. A 1200×630 card with the direction, confidence, and topic baked in turns every organic share into a data communication event. The install is surgical: one `og:image` tag per simulation page. The card generator itself runs once per simulation and caches permanently. With 8,000+ simulations already published, every one of them gets retroactive social card support on the first share.
