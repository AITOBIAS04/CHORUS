### 2. Live Simulation Progress Stream (SSE)

**Type:** Feature / DX
**Effort:** Small (hours)
**Impact:** Currently, a user who starts a simulation in Step 3 sees a spinner and waits, with no indication of what's happening internally. If the simulation takes 3–5 minutes (typical for 100 agents over 5 rounds), that's a black box. Server-Sent Events fix this permanently: `GET /api/simulation/{id}/progress` streams round-by-round updates as the simulation executes — when each round begins, when it completes, and the current belief distribution after every round. The Step 3 UI replaces the static spinner with a live belief chart that grows in real time, one round at a time. This is strictly different from the off-limits "Replay Stream SSE" (which replayed a *completed* simulation). This is live emission during *active* execution — a fundamentally different data flow requiring backend integration with the simulation runner. The UX effect is significant: watching a 74% BULLISH signal crystallize over 5 rounds (opening at 40%, climbing through 53%, 61%, 68%, and landing at 74%) creates a story. Users who share the link mid-run bring viewers to a live page. For the 48-day social silence: "I'm watching a live MiroShark simulation on [topic] right now" is the exact social hook that turns a private computation into a public event.

**How:**
1. Create `backend/app/api/progress.py` (~90 LoC, pure stdlib). `GET /api/simulation/{id}/progress`. Uses `text/event-stream` response with `Cache-Control: no-cache`. The simulation runner must write incremental state to a progress file (e.g., `{simulation_dir}/progress.json` or `{simulation_dir}/progress.jsonl`) as each round completes — inspect the backend simulation runner to determine where to hook in (likely after `run_round()` or equivalent). If no progress file exists, the endpoint falls back to polling `signal.json` every 5 seconds and emitting a synthetic `simulation_complete` event when it appears. SSE event types: `data: {"event": "round_started", "round": 2, "total_rounds": 5, "ts": ISO8601}`, `data: {"event": "round_completed", "round": 2, "bullish_pct": 58.3, "bearish_pct": 25.0, "neutral_pct": 16.7, "agents_responded": 87, "ts": ISO8601}`, `data: {"event": "simulation_complete", "direction": "BULLISH", "confidence_pct": 73.2, "ts": ISO8601}`. Every 15 seconds: `data: {"event": "heartbeat", "ts": ISO8601}` (keeps the connection alive through proxies). On `simulation_complete` or `signal.json` detection: emit the complete event and close the stream. On simulation not found (no directory): emit `data: {"event": "error", "code": "not_found"}` and close. Register at `GET /api/simulation/{id}/progress`. Add to `surfaces_catalog.py`.

2. Replace the static spinner in `Step3Simulation.vue` with a live belief chart driven by the progress SSE stream. On mount (before `signal.json` is available): open `new EventSource('/api/simulation/{id}/progress')`. On `round_completed` events: update a local `rounds_so_far` array and re-render the belief chart with the partial data. On `simulation_complete`: close the EventSource and trigger the normal signal.json fetch + full result render. The live belief chart uses the same component as the finished trajectory chart — the difference is that it receives data incrementally. Add a "round N of M" progress label below the chart (e.g., "Round 3 of 5 — agents responding"). Fallback for completed simulations: if `signal.json` exists on mount, skip the SSE stream and render normally (don't stream replay for completed sims — that's a separate concern). Add one integration test: component connects to EventSource when simulation is in progress; disconnects and renders full result on `simulation_complete` event.

3. Add 3 unit tests: `GET /api/simulation/{id}/progress` returns 200 with `Content-Type: text/event-stream`; emits at least one `round_completed` event for an active simulation; emits a `simulation_complete` event when `signal.json` appears. Log to memory: "Live Simulation Progress Stream created 2026-08-24. `GET /api/simulation/{id}/progress` — SSE endpoint, text/event-stream. Events: round_started, round_completed (bullish/neutral/bearish pct + agents_responded), simulation_complete, heartbeat (15s). Fallback: polls signal.json when no progress file. Step3: replaces spinner with live belief chart, round N of M label. Distinct from Replay Stream SSE (completed sim replay) — this is active execution streaming. Social hook: share a live link mid-run."

### 3. Agent Influence Score API

**Type:** Feature / DX
**Effort:** Small (hours)
**Impact:** MiroShark's Agent Mention Network (Jun 12) maps who @-mentioned whom. The Agent Stance Flip Report (Jun 13) identifies which agents changed their minds. Neither answers the most important swarm intelligence question: which agents actually caused other agents to change their beliefs? `GET /api/simulation/{id}/influence-scores` measures belief-change attribution — correlating the timing of each agent's posts with subsequent belief-distribution shifts in the following round. The core heuristic: when a round sees a large bullish_pct delta and a specific agent posted a high-engagement argument in that round, that agent gets proportional influence credit. Returns agents ranked by estimated influence, their dominant stance, which rounds they were most active, and a one-sentence description of their apparent role in the simulation outcome. This is the analytical primitive that separates MiroShark from a polling tool: it's not just "what did the swarm decide?" but "who moved the needle and how?" A paper that cites MiroShark needs this metric to say "the BULLISH outcome was driven primarily by agents in the finance/crypto archetype who posted in rounds 2–3." The paper citation hyperstition (Sep 30) is 37 days out; this endpoint gives researchers the statistical claim they need to justify the citation.

**How:**
1. Create `backend/app/api/influence_scores.py` (~120 LoC, pure stdlib). `GET /api/simulation/{id}/influence-scores`. Publish-gated. Reads three files: `trajectory.json` (per-round belief evolution), `actions.jsonl` or per-platform `actions.jsonl` files (agent posts per round — confirm actual field names: likely `round`, `agent_name`, `action_type`, `content`, `stance`). Algorithm: (1) Compute per-round deltas: `delta[r] = abs(bullish_pct[r] - bullish_pct[r-1])` for rounds 2..N. (2) For each round r with `delta[r] >= 5pp` (meaningful shift), identify which agents posted in round r. (3) Distribute influence credit proportionally: each posting agent in a "high-delta" round gets `delta[r] / agents_in_round[r]` influence points. (4) Aggregate across all rounds. (5) Normalize to a 0–100 scale (top agent = 100). Secondary signal: agents whose stance matched the final direction and who posted in the turning-point round get a 20% bonus. Response: `{"simulation_id": id, "total_rounds": N, "turning_point_round": R, "agents": [{"agent_name": str, "influence_score": float (0–100), "rank": int, "dominant_stance": "BULLISH"|"BEARISH"|"NEUTRAL", "active_rounds": [int], "posts_in_turning_point": bool}], "methodology_note": "Influence estimated from belief-delta correlation; not causal attribution."}`. Cap at top 20 agents in response. `Cache-Control: public, max-age=3600`. Register at `GET /api/simulation/{id}/influence-scores`. Add to `surfaces_catalog.py`. Update `docs/API.md`.

2. Add an "Influence" overlay to the simulation share page (`Step3Simulation.vue`): an "Influence ↑" toolbar button that opens a panel showing the top 10 agents by influence score with gold/silver/bronze rank badges, their dominant stance chip (BULLISH green / BEARISH red / NEUTRAL gray), a bar showing influence score (0–100), and whether they posted in the turning-point round. Add bilingual labels (EN/ZH-CN) following the same pattern as the Stance Flip Report panel. The panel also includes a one-line methodology note at the bottom: "Scores reflect correlation between post timing and belief-distribution shifts, not direct causation." No new unit tests for the UI component — test the backend algorithm only.

3. Add 5 unit tests: published simulation returns 200 with `agents` as a non-empty array; each agent entry has `agent_name`, `influence_score` (float), `rank` (int ≥ 1), `dominant_stance`; influence scores are normalized (max score = 100.0 ± 0.01); `turning_point_round` is an integer between 1 and `total_rounds`; unpublished simulation returns 404. Log to memory: "Agent Influence Score API created 2026-08-24. `GET /api/simulation/{id}/influence-scores` — belief-delta-weighted attribution. Algorithm: per-round bullish_pct delta ≥5pp identifies high-influence rounds; credit distributed proportionally across posting agents; turning-point-round bonus +20%; normalized 0–100. Caps at top 20 agents. Distinct from Agent Mention Network (@-mention graph) and Stance Flip Report (who changed mind). This answers: who caused the outcome. Step3: Influence toolbar panel with rank badges, stance chips, bar chart. Key for paper citation hyperstition (Sep 30): gives researchers a quantitative claim."

### 4. Recurring Simulation Scheduler

**Type:** Feature / Integration
**Effort:** Medium (1-2 days)
**Impact:** Longitudinal analysis is the highest-value MiroShark use case — tracking sentiment on the same topic weekly to observe how it evolves. Currently, operators who want to run the same topic every Monday have no tooling: they must manually trigger each simulation. `POST /api/schedule` creates a recurring simulation job: `{topic, agents, rounds, platforms, cron: "0 9 * * 1"}` (standard cron syntax). `GET /api/schedule/{id}` returns the schedule, its last 5 run IDs, and next-run timestamp. `DELETE /api/schedule/{id}` cancels. The backend uses Python's `sched` stdlib module (no external dependencies). In a Docker Compose environment, a lightweight scheduler process runs alongside the API server. Use cases: a crypto researcher running "$MIROSHARK sentiment" every Monday morning; a policy team running "EU AI Act compliance burden" weekly as enforcement matures; a fund tracking "tech layoffs Q3 2026" biweekly across the September earnings window. Each scheduled run creates a new simulation ID — the full history is queryable via existing endpoints. For the FDV $500K hyperstition (Sep 15, 22 days): scheduling a weekly simulation on "Will MIROSHARK FDV hit $500K?" gives operators a dated sequence of AI swarm predictions to compare with on-chain reality.

**How:**
1. Create `backend/app/api/schedule.py` (~130 LoC, pure stdlib). Three endpoints: **`POST /api/schedule`** — accepts `{"topic": str, "agents": int, "rounds": int, "platforms": [str], "cron": str, "label": str (optional, max 60 chars), "max_runs": int (optional, default null = indefinite)}`. Validate cron with a minimal parser (5 fields: minute, hour, day-of-month, month, day-of-week; reject 6-field and non-standard syntax). Compute next-run time (UTC) from the cron expression. Write schedule config to `{schedules_dir}/{schedule_id}.json`. Return `{"schedule_id": uuid, "topic": str, "cron": str, "next_run_utc": ISO8601, "created_at": ISO8601}`. **`GET /api/schedule/{id}`** — reads schedule config + scans simulation history for runs associated with this schedule_id (simulations store `schedule_id` in their `signal.json` when created by the scheduler). Returns config + `{"runs": [{"simulation_id": str, "ran_at": ISO8601, "direction": str, "confidence_pct": float}]}` (last 10 runs, newest first) + `next_run_utc`. **`GET /api/schedule`** — lists all active schedules (no auth; operator-level endpoint). **`DELETE /api/schedule/{id}`** — marks schedule as cancelled (sets `cancelled_at` in schedule JSON). 204 on success, 404 if not found. Create `backend/app/scheduler.py` — a lightweight background thread (stdlib `threading.Thread`) that wakes every 60 seconds, scans `{schedules_dir}/`, checks if any non-cancelled schedules have a `next_run_utc` in the past, and triggers a simulation run using the same internal run path as the existing API. After each triggered run: update `next_run_utc` based on the cron expression. Start the scheduler thread in the Flask app's `create_app()`. All endpoints registered with the Flask app. Add to `surfaces_catalog.py`. Update `docs/API.md` with a "Scheduling" section, cron syntax guide, and Docker Compose note.

2. Add a `docs/SCHEDULING.md` (~60 lines): what recurring simulations are and why they're useful, full cron syntax reference with MiroShark examples (weekly on Monday 09:00: `0 9 * * 1`; daily at midnight: `0 0 * * *`; weekdays at 08:00: `0 8 * * 1-5`), a section on "Longitudinal analysis" explaining how to compare simulation runs over time using `GET /api/digest/weekly` (from the Aug 22 article), a note on `max_runs` for bounded studies (e.g., track this topic for exactly 8 weeks), and a caution about LLM API costs for high-frequency schedules. Add a "Scheduled runs" badge chip to the simulation share page for simulations created by the scheduler: "Part of schedule: {label} · Run {N}" if `schedule_id` is present in `signal.json`.

3. Add 5 unit tests: `POST /api/schedule` with valid cron returns 201 with `schedule_id` and `next_run_utc` as a valid ISO8601 string; invalid cron (6-field or non-standard) returns 400 with `"error": "invalid_cron_expression"`; `GET /api/schedule/{id}` returns schedule config and empty `runs` array for a freshly created schedule; `DELETE /api/schedule/{id}` returns 204 and the schedule no longer fires (simulate by checking `cancelled_at` in the schedule JSON); `GET /api/schedule/{id}` returns 404 for a non-existent ID. Log to memory: "Recurring Simulation Scheduler created 2026-08-24. `POST /api/schedule` (cron string, topic, agents, rounds, platforms, optional max_runs). Background threading.Thread wakes every 60s, triggers runs when next_run_utc in past, updates next_run_utc. `GET /api/schedule/{id}` returns config + last 10 run history. `DELETE /api/schedule/{id}` cancels. Schedule IDs stored in signal.json of created simulations. docs/SCHEDULING.md with cron reference. Longitudinal analysis use case: weekly topic tracking, compare with digest endpoint."

### 5. Agent Debate Summary API

**Type:** Feature / DX
**Effort:** Small (hours)
**Impact:** MiroShark simulates swarm consensus, but the *arguments* — the specific reasons agents gave for their stances — are buried in per-platform `actions.jsonl` files. No current endpoint extracts the strongest arguments on each side. `GET /api/simulation/{id}/debate-summary` returns the top 3 bullish arguments and top 3 bearish arguments, extracted from agent post content using frequency/keyword analysis (no new LLM calls — pure computation over the existing `actions.jsonl` data). Each argument is a verbatim excerpt from an agent's post (truncated to 200 chars, preserving the strongest clause) with the agent's name, round, and platform. This is the "both sides in 30 seconds" artifact: a journalist covering the $MIROSHARK rally can paste it as a quote block; a policy researcher can cite it as evidence of the simulated discourse; a product team can paste the top bearish arguments directly into their risk log. During a 48-day social silence, every published simulation has un-extracted arguments sitting in `actions.jsonl` files — this endpoint surfaces them without requiring any API key, any LLM call, or any configuration. The Narration API (Aug 22, blocked) generated a paragraph from template strings; this API surfaces the *actual arguments* from the raw simulation data, which are more credible and more citable.

**How:**
1. Create `backend/app/api/debate_summary.py` (~100 LoC, pure stdlib). `GET /api/simulation/{id}/debate-summary`. Publish-gated. Reads `signal.json` (direction, confidence_pct, rounds) and all per-platform `actions.jsonl` files. For each agent action in the `actions.jsonl` files: parse `round`, `agent_name`, `platform`, `action_type`, `stance`, `content`. Filter to only actions where `action_type` is a post or reply (not trade/market actions — check actual action types in one real `actions.jsonl` file). Separate into BULLISH and BEARISH stance buckets. Extract "strongest" arguments using a simple heuristic: for each content string, score by length (longer posts tend to carry more substance), presence of numerical data (digits in the content, weight × 1.5), and absence of generic filler phrases (filter out posts that are only "I agree", "Same here", "Bullish on this"). Within each stance bucket: deduplicate near-identical posts (if content is >80% similar via character-level comparison, keep only the longest). Return the top 3 from each bucket, sorted by score descending. If fewer than 3 arguments exist for a stance, return as many as exist (minimum 1 to avoid empty buckets for very one-sided simulations). Response: `{"simulation_id": id, "topic": str, "direction": str, "confidence_pct": float, "bullish_arguments": [{"agent_name": str, "round": int, "platform": str, "excerpt": str (≤200 chars), "score": float}], "bearish_arguments": [{"agent_name": str, "round": int, "platform": str, "excerpt": str (≤200 chars), "score": float}], "generated_at": ISO8601}`. Truncation rule: find the strongest clause in the content string (the segment with the highest keyword density); return that segment followed by "..." if truncated. `Cache-Control: public, max-age=3600`. Register at `GET /api/simulation/{id}/debate-summary`. Add to `surfaces_catalog.py`. Update `docs/API.md`.

2. Add a "Debate" panel to the simulation share page (`Step3Simulation.vue`): a "Debate ↔" toolbar button that opens a two-column panel — left column "Bullish Case" (green header), right column "Bearish Case" (red header). Each column shows the top 3 excerpts as quote cards: agent name + platform badge + round badge + excerpt text in a light blockquote style. Mobile: stacked (Bullish above Bearish). Below the quotes: a one-line methodology note "Arguments are verbatim excerpts from agent posts, ranked by content richness." Also expose the debate summary in the embed dialog as a collapsible "Key Arguments" section, making it easy for operators to include the reasoning alongside the headline result. Add bilingual labels (EN/ZH-CN) for the panel header and column titles.

3. Add 5 unit tests: published simulation returns 200 with `bullish_arguments` and `bearish_arguments` as arrays; each argument entry has `agent_name`, `round`, `platform`, and `excerpt` (non-empty string); `bullish_arguments` contains at most 3 items; excerpt strings are ≤ 200 chars; unpublished simulation returns 404. Log to memory: "Agent Debate Summary API created 2026-08-24. `GET /api/simulation/{id}/debate-summary` returns top 3 bullish + top 3 bearish agent arguments extracted from actions.jsonl. Scoring: content length + numerical data weight (×1.5) + generic filler filter. Near-duplicate dedup at 80% char similarity. Excerpts ≤200 chars (strongest clause first). No LLM calls — pure computation. Step3: 'Debate ↔' toolbar panel, two-column quote cards. Embed dialog: collapsible 'Key Arguments' section. Distinct from Narration API (template prose) — this surfaces actual verbatim simulation arguments. Primary use: journalist/researcher quote extraction."
