### 1. German (DE) UI Locale

**Type:** Community / DX
**Effort:** Small (hours)

**How:**

Key term decisions: `simulation` → `Simulation`, `agent` → `Agent`, `round` → `Runde`, `consensus` → `Konsens`, `bullish` → `bullisch` (finance loan word, understood across DACH; not `steigernd`), `bearish` → `bärisch`, `confidence` → `Konfidenz` (technical; not `Vertrauen`), `platform` → `Plattform`, `scenario` → `Szenario`, `stance` → `Haltung`, `publish` → `veröffentlichen`, `topic` → `Thema`, `influence` → `Einfluss`, `belief` → `Überzeugung`. Technical loan words keep English form: `webhook`, `embed`, `endpoint`, `fork`, `API`, `token`, `wallet`, `DEX`, `deployment`. Accented characters use precomposed form (ü not u + combining diaeresis). `ß` vs `ss`: use `ß` after long vowels and diphthongs (Straße, Maßnahme), `ss` after short vowels (Fluss) — this follows the post-1996 reform rules and avoids Switzerland-mode (which eliminates ß entirely; acceptable to use ß since the target is international German, not exclusively CH). ### 2. TypeScript/JavaScript Client SDK

**Type:** Feature / DX
**Effort:** Medium (1–2 days)
**Impact:** The Python SDK (suggested Jul 28) targets data scientists and Jupyter-native tutorial creators. A TypeScript/JavaScript SDK targets a different and larger pool: the ~18M JavaScript developers on GitHub who write blog posts on Dev.to, build Codepen demos, create YouTube tutorials using the browser console, and ship integrations in Vercel/Cloudflare workers. The Aug 15 tutorial deadline (0/5, 16 days) has a bottleneck problem — zero easy path for JS developers to demonstrate MiroShark without writing a raw fetch wrapper. `npm install miroshark-js` followed by four lines of code makes MiroShark the obvious choice for any JS developer writing a "cool API of the week" piece. TypeScript types also open JetBrains/VS Code autocomplete, which is the single most powerful onboarding surface for developer-tools adoption. The SDK also unblocks frontend integrations: a Notion widget, a Raycast extension, a VS Code sidebar — all start with `npm install miroshark-js`.

**How:**
1. Create `sdk/javascript/` directory with standard npm package structure. `package.json` (package name `miroshark-js`, version `0.1.0`, `"type": "module"`, dependencies: none — zero external deps; devDependencies: `typescript`, `vitest`). `src/client.ts` (~150 LoC): `class MiroShark(baseUrl: string, options?: {apiKey?: string, timeout?: number})` with async methods: `.simulate(params: SimulateParams): Promise<Simulation>` (POST `/api/simulate`, polls `/api/simulation/{id}/status` with exponential backoff until `status === 'published'`); `.get(simId: string): Promise<Simulation>` (GET `/api/simulation/{id}/signal`); `.search(query: string, limit?: number): Promise<Simulation[]>` (GET `/api/simulation/search`); `.estimate(params: EstimateParams): Promise<EstimateResult>` (GET `/api/estimate`). `src/types.ts` (~60 LoC): `SimulateParams`, `Simulation`, `SimulationStatus`, `EstimateParams`, `EstimateResult`, `ConsensusDirection` (union: `'bullish' | 'bearish' | 'neutral'`), `MiroSharkError` (extends Error with `status: number`), `TimeoutError`. `src/index.ts`: re-exports `MiroShark`, all types, `SimulateParams`, `EstimateParams`. ### 3. Simulation RSS/Atom Feed

**Type:** Feature / Integration
**Effort:** Small (hours)
**Impact:** MiroShark has 40+ published public simulations and grows with each run. An RSS feed at `/api/feed.rss` and `/api/feed.atom` converts this corpus into a subscribable content stream that surfaces in: Feedly/Inoreader (millions of tech readers), RSS-consuming tools (Zapier, n8n, IFTTT), developer aggregators (lobste.rs, Planet Python/PHP), and GitHub's own "feed for releases" pattern that some OSS followers use. The feed requires zero promotion — auto-discovery via `<link rel="alternate" type="application/rss+xml">` in the simulation index HTML head means any feed reader that visits the site finds it automatically. It also provides a passive distribution channel during the 24-day social silence: a developer who subscribed to the feed months ago gets every new simulation in their reader without any social activity from the operator. Implementation is ~120 LoC of pure-stdlib Python XML generation — no new dependencies, no new frontend work. The RSS spec is stable (2000) and well-tested against all major feed readers.

**How:**
1. Create `backend/app/api/feed.py` (~120 LoC, pure stdlib — `xml.etree.ElementTree` for XML generation). `GET /api/feed.rss`: returns `Content-Type: application/rss+xml; charset=utf-8` with a valid RSS 2.0 document. Channel metadata: `<title>MiroShark Simulations</title>`, `<description>Live AI swarm intelligence simulation results</description>`, `<link>https://miroshark.io</link>`, `<lastBuildDate>` (RFC 822 format), `<ttl>60</ttl>`. Items: latest 20 published public simulations (query `simulations/` directory by mtime desc), each with `<title>` (simulation topic, truncated at 80 chars), `<description>` (CDATA-wrapped HTML: direction + confidence, agent count, platform list, cost estimate, simulation timestamp), `<link>` (`https://miroshark.io/simulation/{id}`), `<guid isPermaLink="true">` (same URL), `<pubDate>` (RFC 822 from created_at). Sanitize all simulation content before inserting into XML (escape `<>&"'` in topic strings). `GET /api/feed.atom`: same data, Atom 1.0 format (`application/atom+xml`). Atom offers better internationalization support — use `<content type="html">` for the description block, `<id>` (canonical URI), `<updated>` (ISO 8601). Both endpoints: 5-minute server-side cache (mtime-based, same pattern as other services); `Cache-Control: public, max-age=300`; no auth required (only public published simulations included). Register both routes in the main app router.
2. Inject auto-discovery links into the simulation index page HTML head (in the frontend, likely `index.html` or the head section of the main layout component): `<link rel="alternate" type="application/rss+xml" title="MiroShark Simulations" href="/api/feed.rss">` and `<link rel="alternate" type="application/atom+xml" title="MiroShark Simulations" href="/api/feed.atom">`. This allows feed readers to discover the feed by visiting the homepage without any manual URL entry. Add a "Subscribe" link to the footer or navigation: a feed icon (standard orange RSS icon, inline SVG or emoji) linking to `/api/feed.rss`.
3. Add 8 unit tests: RSS document is valid XML with correct Content-Type, Atom document is valid XML with correct Content-Type, both contain at most 20 items, each item includes title/link/pubDate, CDATA content does not contain unescaped angle brackets, cache returns same document within 5 minutes, unpublished simulations excluded, private simulations excluded. Add `GET /api/feed.rss` and `GET /api/feed.atom` to `surfaces_catalog.py` (type: discovery). Update `docs/API.md` under a new "Feed" section: endpoint docs, format notes, curl examples for both formats, suggested feed reader setup.

### 4. CLI Live Progress Display

**Type:** DX / Performance
**Effort:** Small (hours)
**Impact:** The CLI's `miro wait {id}` subcommand currently polls silently until the simulation completes, then prints the result. A live terminal display — spinner, round counter, per-round consensus percentage, running cost estimate, elapsed time — transforms `miro wait` from a blocking command into a compelling demo artifact. Tutorial creators who record terminal sessions (asciinema, Terminalizer, VS Code's built-in recorder) need interesting terminal output to make demos watchable. A 60-second terminal recording of `miro simulate "..." && miro wait {id}` with a live updating progress panel is shareable as a GIF, embeddable in blog posts, and postable to X/Twitter — exactly the kind of content that could break the 24-day social silence without requiring the operator to write copy. The `rich` library (or a pure-stdlib fallback using ANSI escape codes and `\r`) adds this in ~80 LoC. If `rich` is already a dev dependency, the implementation is purely additive; if not, the fallback ensures zero new production dependencies.

**How:**
1. In `cli/` (or wherever the CLI entry point lives), extend the `wait` subcommand's polling loop. Current behavior: poll `/api/simulation/{id}/status` every N seconds, print nothing, return result on completion. New behavior: on each poll response, clear the current terminal line and overwrite with a status string. Use `rich` if available (import guard: `try: from rich.progress import Progress, SpinnerColumn, TextColumn, TimeElapsedColumn; RICH_AVAILABLE = True except ImportError: RICH_AVAILABLE = False`). Rich path: render a `Progress` panel with three columns — `SpinnerColumn()`, `TextColumn("[bold]{task.description}")`, `TimeElapsedColumn()` — updated each poll with the current round, consensus direction and pct, and cost estimate if available. Pure-stdlib fallback: `print(f"\r[{elapsed:.0f}s] Round {round}/{total} · {direction} {confidence:.1f}% · ~${cost:.4f}  ", end="", flush=True)` using `\r` to overwrite the line. On completion: clear the progress line, print the full result block (same format as the existing `miro get` output). On Ctrl-C: clear the line, print "Cancelled." and exit with code 130.
2. Extend the `simulate` subcommand to pass `--watch` / `-w` flag: `miro simulate "topic" --watch` runs the simulation and immediately enters `wait` mode with the live display. This turns the two-step flow (simulate → wait) into a single command — the natural form for a demo recording. The flag is additive: without `--watch`, `simulate` behaves as before (prints the simulation ID and exits). Add `--watch` to the `simulate` subcommand's argparse definition.
3. Update `docs/CLI.md` (or `README.md` CLI section): add `--watch` flag documentation with an asciinema recording placeholder (`[![asciicast](https://asciinema.org/a/XXXX.svg)](https://asciinema.org/a/XXXX)` — the operator records and fills in the ID). Add a "Live Demo" section to the README listing `miro simulate "Will remote work remain the default for tech companies?" --watch` as the recommended first-run command. Add 4 unit tests: `--watch` flag is accepted by the CLI parser, live display clears each line on update, completion message prints after progress clears, `rich` import guard falls back to ANSI without raising.

### 5. Batch Simulation API

**Type:** Feature
**Effort:** Medium (1–2 days)
**Impact:** Researchers running parameter sweeps (varying agent counts, platform compositions, or topic framings across many simulations) currently have no mechanism to submit multiple simulations concurrently — they must POST `/api/simulate` repeatedly and track each ID manually. A `POST /api/simulate/batch` endpoint that accepts an array of simulation configurations, queues them, and returns a batch ID with a status endpoint is the architectural unlock for research-grade usage. This is the use case most likely to generate academic citations: a researcher who runs 20 simulations across 4 topic framings and 5 agent configurations, then writes a paper comparing outcomes, needs a batch tool for reproducibility. The batch API also surfaces MiroShark to Jupyter notebook users who would otherwise throttle themselves with sequential requests. Implementation reuses the existing simulation queue and status infrastructure with a thin coordination layer (~200 LoC). No frontend changes required — this is a pure backend feature.

**How:**
1. Create `backend/app/api/batch.py` (~200 LoC, pure stdlib). `POST /api/simulate/batch`: accepts `Content-Type: application/json` body `{simulations: [{topic, agents, rounds, platforms, ...}, ...], label?: string}`. Validation: array length 1–20 (reject with 400 if exceeded, message: "Batch size limit: 20 simulations per request"); each simulation item validated against the same schema as `POST /api/simulate`; any validation failure returns 400 with field-level error array. On success: generate a `batch_id` (UUID4); create `simulations/batches/{batch_id}/` directory; write `batch.json` with `{batch_id, label, count, submitted_at, simulations: [{id: sim_id, status: "queued", ...}, ...]}`. Queue each simulation via the existing simulation engine (same path as single `/api/simulate`). Return `{batch_id, count, simulations: [{id: sim_id, status: "queued"}, ...]}` with status 202. `GET /api/batch/{batch_id}`: reads `batches/{batch_id}/batch.json`, cross-references each `sim_id`'s current status from `simulations/{sim_id}/status.json`. Returns `{batch_id, label, count, submitted_at, completed_count, failed_count, pending_count, simulations: [{id, status, topic, direction?, confidence_pct?, cost_usd?}, ...]}`. No auth required for batch status if all simulations are public; if any is private, require matching API key. Add both routes to the main app router. Register as surfaces 42 and 43 in `surfaces_catalog.py` (type: batch).
2. Add batch support to the Python SDK (`sdk/python/miroshark/client.py`): `MiroShark.simulate_batch(simulations: list[dict], label=None) -> BatchResult` (POST `/api/simulate/batch`, returns `BatchResult`); `MiroShark.get_batch(batch_id: str) -> BatchResult` (GET `/api/batch/{batch_id}`); `BatchResult` class with `batch_id`, `count`, `completed`, `pending`, `failed`, `simulations` (list of `Simulation`), `.wait(poll_interval=5.0)` (blocks until all simulations complete or any fails, prints progress to stderr). Add `BatchResult` to `miroshark/__init__.py` exports. Add 6 unit tests: `simulate_batch()` sends the correct JSON body, `get_batch()` calls the right endpoint, `BatchResult.wait()` polls until `pending_count == 0`, array of 21 items raises `ValueError`, empty array raises `ValueError`, `BatchResult.simulations` returns typed `Simulation` list.
3. Add batch support to the TypeScript SDK (`sdk/javascript/src/client.ts`): `simulateBatch(simulations: SimulateParams[], label?: string): Promise<BatchResult>` (POST `/api/simulate/batch`); `getBatch(batchId: string): Promise<BatchResult>` (GET `/api/batch/{batchId}`); `BatchResult` type with `batchId`, `count`, `completedCount`, `pendingCount`, `failedCount`, `simulations: BatchSimulationItem[]`. Add 4 unit tests. Update `docs/API.md` with a "Batch Simulation" section: endpoint reference, JSON schema, curl examples (submit batch of 3, check status, wait for completion), research use case note. Update both SDK READMEs to document batch methods. File a GitHub issue `feat: batch simulation API` to track this as a research-grade feature.
