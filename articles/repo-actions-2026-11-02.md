### 1. Weekly Newsletter Digest Generator

**Type:** Content / Feature
**Effort:** Small (hours)
**Impact:** Operators running crypto or macro intelligence newsletters have no way to auto-generate a summary of the past week's simulation activity. `GET /api/newsletter/digest?days=7` returns a formatted Markdown document (also available as `?format=html`) covering: the top-3 most decisive simulations (by `confidence_pct`), the most contested topic (closest to 50/50), week-over-week consensus shift (did aggregate BULLISH % rise or fall vs. the prior period), and a "by the numbers" footer (total sims run, total agents deployed, avg confidence). No new data sources — pure aggregation of published `signal.json` files within the window. The digest is cached and regenerates at most once per hour. Operators who sell a weekly intelligence newsletter can paste this directly into Beehiiv, Substack, or Mirror.xyz. Journalists covering AI-driven market sentiment have a machine-generated weekly briefing. The endpoint is session-scoped (returns only the operator's published simulations) which makes it personal, not aggregate.

**How:**
1. Create `backend/app/services/newsletter_service.py` (~160 LoC, pure stdlib). Accept `days: int` (default 7, clamp 1–30) and `format: Literal["markdown", "html"]` (default markdown). Scan `storage/simulations/*/signal.json` for all sims owned by the requesting session and published within the window (`created_at >= now - days * 86400`). Compute: `top_decisive` (top-3 by `confidence_pct` desc); `most_contested` (one entry: min `abs(bullish_pct - 50.0)`); `direction_pct_this_week` = `(bullish_count / total_count) * 100`; look up last week's same metric from `storage/newsletter_cache_{session_token}_{prior_window_start}.json` if it exists — compute `direction_delta`. Totals: `{sim_count, agent_hours: sum(agent_count * round_count), avg_confidence_pct}`. Build the Markdown string: H2 title with date range, "This week's top calls" table (topic, direction chip text, confidence%), "Most contested" single row with split %, "Sentiment shift" line (e.g. "Aggregate BULLISH share moved from 62% → 71% vs. last week"), "By the numbers" stats footer. Write the rendered output to `storage/newsletter_cache_{session_token}_{window_start}.json`. Return the raw string. If HTML requested: wrap the Markdown in a minimal `<html>` + inline CSS (max-width 680px, system font stack, dark-mode `@media`) — no external dependencies. Add 5 unit tests: output starts with an H2 heading; top-3 entries are sorted by `confidence_pct` desc; `direction_delta` is 0.0 when no prior cache exists; HTML output contains `<html>` tag when `?format=html`; no sims in window returns a valid but empty digest rather than a 500.
2. Add `GET /api/newsletter/digest` to a new `backend/app/api/newsletter.py`. Session-auth (same cookie as other session-gated endpoints). Query params: `days` (int, default 7), `format` (string, default markdown). Response for markdown: `Content-Type: text/markdown; charset=utf-8`, `Cache-Control: max-age=3600, private` (per-session). Response for html: `Content-Type: text/html; charset=utf-8`. Add `Content-Disposition: inline; filename="miroshark-digest-{start_date}-{end_date}.md"`. Add to `surfaces_catalog.py` (type: `content`) and OpenAPI with `NewsletterDigestResponse` schema (or raw text, documented as such). Add to `docs/API.md` under a new "Newsletter & Digests" section. Add 2 integration tests: returns 200 Markdown for a session with ≥1 published sim in the window; returns valid HTML when `?format=html`.
3. Add a "Weekly Digest" entry to the Step 3 "Export" panel (alongside Share Card, GIF, Badge). Clicking opens a modal: a textarea pre-populated with the Markdown digest (editable before copy), a "Copy Markdown" button, and a "Download HTML" link. Include a small tip: "Paste into Beehiiv, Substack, Mirror.xyz, or any newsletter platform. The digest covers your last 7 days of published simulations." Add a date-range picker (default 7 days, selectable to 14 or 30). Add 2 frontend unit tests: "Weekly Digest" modal opens and textarea contains Markdown text; "Download HTML" button triggers navigation to `?format=html` URL.

### 2. Deployment Usage Stats API

**Type:** Feature / DX
**Effort:** Small (hours)
**Impact:** Operators running self-hosted MiroShark instances have no visibility into their deployment's usage patterns — how many simulations have run, which endpoints are hot, whether webhooks are succeeding, how much disk the simulation archive is consuming. `GET /api/admin/stats` (ADMIN_TOKEN auth, same as other admin routes) returns a structured usage summary: total simulations all-time + this week + this month, published vs. unpublished counts, average confidence across all published sims, top-5 topics by run count, webhook success rate (delivered / attempted — computed from the webhook delivery log if it exists, or from a lightweight counter appended to each webhook call), and storage consumption in MB (sum of file sizes under `storage/simulations/`). Zero new data dependencies — all figures derive from existing on-disk files. The endpoint lets operators track their ROI ("we ran 340 simulations this month, 78% published"), report usage to stakeholders, and set capacity budgets.

**How:**
1. Create `backend/app/services/usage_stats_service.py` (~140 LoC, pure stdlib). Scan `storage/simulations/` once per call (mtime-cached to `storage/usage_stats_cache.json` with a 5-min TTL — walk the directory once, write the cache, return from cache on subsequent calls within TTL). Compute: `{total_simulations: int, published: int, unpublished: int, this_week: int, this_month: int, avg_confidence_pct: float (mean of all published signal.json confidence_pct values), top_topics: [{topic, count}] (top-5 by count from all published sims, normalized topic strings), storage_mb: float (sum of os.path.getsize for all files under storage/simulations/, divided by 1_048_576), webhook_stats: {attempted: int, delivered: int, success_rate_pct: float} (read from storage/webhook_log.jsonl if it exists, summing 'attempted' and 'delivered' fields per-line; if file absent: omit the field), generated_at: ISO8601}`. `this_week` and `this_month` computed from `created_at` in each `signal.json`. Add 5 unit tests: `total_simulations` matches the directory entry count; `published` count is correct for mixed published/unpublished; `top_topics` is sorted by count desc and capped at 5; `storage_mb` is positive for a non-empty directory; cache is returned within TTL without re-scanning.
2. Add `GET /api/admin/stats` to `backend/app/api/admin.py` (or create it if admin routes are elsewhere). Requires `ADMIN_TOKEN` authentication via the same auth pattern as other admin routes. Response: `Content-Type: application/json`, `Cache-Control: max-age=300, private`. Return the full `UsageStatsResponse` object. Optional `?refresh=true` param forces cache invalidation (clears `storage/usage_stats_cache.json` before computing). Add to `surfaces_catalog.py` (type: `admin`) and OpenAPI with `UsageStatsResponse`, `WebhookStats`, `TopicRunCount` schemas. Add to `docs/API.md` under a new "Admin" section alongside any existing admin endpoints. Add 2 integration tests: returns 200 JSON with `total_simulations` for an instance with ≥1 simulation; `?refresh=true` returns fresh data and updates the cache timestamp.
3. Add a "Usage" card to the existing Settings page (or as a new tab if Settings is tabbed) — visible only when `ADMIN_TOKEN` is configured. The card shows a minimal stats grid: "Total Runs" (all-time + sparkline this week), "Published" (count + % of total), "Avg Confidence" (gauge-style number), "Storage" (MB with a soft warning if > 500MB), "Webhook Success" (% with a red indicator if < 90%). All values load from `GET /api/admin/stats` on page mount; a "Refresh" button calls `?refresh=true`. Add a small "Export CSV" link that serializes the stats object as a single-row CSV (for pasting into a spreadsheet tracker). Add 2 frontend unit tests: stats grid renders with all 5 fields when admin token is configured; "Refresh" button calls the API with `?refresh=true`.

### 3. Multi-Language Simulation Mode

**Type:** Feature
**Effort:** Medium (1-2 days)
**Impact:** Every simulation today produces English-language agent posts. The signal, trajectory, and analytics surfaces are all language-agnostic (they track `BULLISH`/`BEARISH`/`NEUTRAL` stances, not post text) — but the post text itself, the operator UX, and the platform ecosystem are English-only. Adding an optional `lang` parameter to `POST /api/simulate` instructs the LLM to generate all agent posts in the specified language (`es`, `ja`, `de`, `fr`, `zh`, `pt`, `ko`, `ar`). The demographic generator already produces multi-national agent archetypes; their posts in the target language would be consistent with their described backgrounds. Practical impact: a Spanish-speaking fintech operator can run "¿Subirá Bitcoin antes de fin de año?" and share results in their community; a Japanese crypto media outlet can embed a Japanese-language consensus widget. Non-English crypto communities represent more than half of global crypto activity. Zero new data dependencies — the LLM client handles multilingual generation natively; the existing analytics services read structured fields, not post text.

**How:**
1. Add `lang: str | null` (default null, meaning "en") to the simulation creation schema in `backend/app/api/simulation.py`. Validate against an allowlist: `["en", "es", "ja", "de", "fr", "zh", "pt", "ko", "ar"]`. Store in `config.json` alongside other simulation parameters. In the agent prompt construction layer (wherever the per-agent prompt is built), append a language instruction when `lang != "en"` and `lang is not null`: "All posts in this simulation must be written entirely in {language_name} (ISO 639-1 code: {lang}). Do not switch languages mid-simulation. Agent names and stances remain as-is (BULLISH/BEARISH/NEUTRAL in English); only post text uses {language_name}." Map ISO codes to full language names for the instruction: `{"es": "Spanish", "ja": "Japanese", "de": "German", "fr": "French", "zh": "Simplified Chinese", "pt": "Brazilian Portuguese", "ko": "Korean", "ar": "Modern Standard Arabic"}`. Add `lang` to the simulation metadata object returned by `GET /api/simulation/:id`. Add 5 unit tests: `lang="xx"` (invalid) returns 400; `lang=null` produces no language instruction in the prompt; `lang="ja"` appends the correct Japanese instruction string; `config.json` stores the `lang` value; `GET /api/simulation/:id` response includes `lang` field.
2. Propagate `lang` through the simulation output surfaces: add `"lang": str` to `signal.json` (after the simulation completes, write the lang field from `config.json` into the signal); update the share card generator to set the card's text direction (`dir="rtl"` for `ar`, `dir="ltr"` for all others) when rendering the share card image; update the transcript export (`GET /api/simulation/:id/transcript`) to include a `Language: {lang}` header line in the exported document; update `docs/API.md` to document `lang` in the simulation creation schema, signal.json fields, and share card endpoint. Add 3 unit tests: `signal.json` contains `lang` matching the simulation config; share card for `lang="ar"` has `rtl` layout flag set; transcript export includes language header.
3. Add a "Language" selector to the Step 1 simulation creation form (`Step1TopicSetup.vue` or similar): a dropdown with the 8 supported language flags + names (a native name in parentheses: "Spanish (Español)", "Japanese (日本語)", etc.) plus "English (Default)" at the top. Default to "English (Default)" — no visual complexity added for the common case. When a non-English language is selected, show a brief tooltip: "Agent posts will be written in {language}. The signal and analytics data remain in English." Pass the `lang` value in the `POST /api/simulate` body. In the Step 3 result header, show the language flag emoji next to the topic if `lang != "en"` (e.g. "🇯🇵 Will the Bank of Japan raise rates?"). Add 2 frontend unit tests: "English (Default)" is selected by default and passes `lang=null` in the body; selecting "Japanese (日本語)" shows the tooltip and passes `lang="ja"`.

### 4. Bulk Simulation Archive Export

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Researchers and ML practitioners who have run a month of simulations need to download their full dataset as a ZIP archive for offline analysis — not one simulation at a time, not a fine-tuning JSONL for a single run, but the complete raw data for a batch. `GET /api/export/archive?format=zip&ids=id1,id2,...` (or `?topic_contains=crypto&days=30` to select by filter) packages up to 20 simulations into a ZIP file. Each simulation gets its own directory (`{simulation_id}/`) containing `signal.json`, `trajectory.json`, `actions.jsonl`, and `config.json`. A top-level `README.md` inside the ZIP describes the schema. Compatible with direct consumption by pandas `pd.read_json`, polars `pl.read_ndjson`, and Hugging Face `datasets.load_dataset("json")`. Uses Python's stdlib `zipfile` module — zero new dependencies. This is the "get everything" complement to the per-simulation fine-tuning JSONL and signed-result exports.

**How:**
1. Create `backend/app/services/archive_service.py` (~120 LoC, pure stdlib). Accept `simulation_ids: list[str]` (max 20 — cap enforced with a 400 if exceeded) and `include_fields: list[str]` (default all: `["signal", "trajectory", "actions", "config"]`; allows callers to request a lighter archive by omitting actions.jsonl which dominates file size). For each simulation ID: validate the session owns it (same ownership check as all other export endpoints); verify the sim is published; check the four files exist on disk. Construct the ZIP in memory using `zipfile.ZipFile(io.BytesIO(), "w", zipfile.ZIP_DEFLATED)`. Directory structure: `{simulation_id}/signal.json`, `{simulation_id}/trajectory.json`, `{simulation_id}/actions.jsonl`, `{simulation_id}/config.json`. Add a top-level `README.md` describing the archive: schema of each file type, field reference table, example pandas/polars import commands. Add a `manifest.json` at the root listing `{simulation_id, topic, direction, confidence_pct, created_at}` for all included sims (the index without requiring consumers to unzip and read each signal.json). Return the ZIP bytes. Add 5 unit tests: output is a valid ZIP (passes `zipfile.is_zipfile`); each sim directory contains the expected files; `manifest.json` contains all simulation IDs; `include_fields=["signal"]` produces only signal.json files; `len(ids) > 20` returns `ValueError`.
2. Add `GET /api/export/archive` to `backend/app/api/export.py` (or create it). Session-auth. Query params: `ids` (comma-separated list, required unless `topic_contains` is given), `topic_contains` (substring match against topic; requires `days` param), `days` (int, 1–90, used only with `topic_contains`), `format` (only `zip` for now — future: `tar.gz`), `include` (comma-separated subset of `["signal","trajectory","actions","config"]`, default all). Response: `Content-Type: application/zip`, `Content-Disposition: attachment; filename="miroshark-archive-{date}.zip"`, no Cache-Control (generated on demand). Add to `surfaces_catalog.py` (type: `export`) and OpenAPI with `ArchiveRequest` parameters documented. Add to `docs/API.md` under "Exports" with a callout: "Max 20 simulations per request. Use `topic_contains` + `days` to filter by topic and time window without listing explicit IDs." Add 2 integration tests: response Content-Type is `application/zip`; ZIP contains a `manifest.json` at the root.
3. Add an "Export Archive" button to the gallery page (alongside per-simulation export options): a "Download selected as ZIP" button that appears when at least one simulation checkbox is checked. Multi-select via checkbox on each gallery row (or card). The button calls `GET /api/export/archive?ids={selected_ids_csv}` and triggers a download. Cap the UI selection at 20 checkboxes — if the user selects more, show a warning: "Maximum 20 simulations per archive. Deselect some to continue." Also expose the filter-based version: a "Bulk export by topic" modal where the operator types a topic substring and selects a time window (7/14/30/90 days), then downloads. Add 2 frontend unit tests: "Download selected as ZIP" button is disabled when no checkboxes are checked; it triggers navigation to the correct archive URL when IDs are selected.

### 5. Operator Public Profile Page

**Type:** Community / Growth
**Effort:** Small (hours)
**Impact:** Currently every simulation result is anonymous — there's no way to see all published simulations from a specific operator, no way for an operator to establish a public track record, and no way for visitors to discover who is running what. `GET /api/profile/:handle` returns a public JSON profile for an operator who has opted into a public presence: their display name, optional bio (max 200 chars), the count of their published simulations, their accuracy score (if any annotated outcomes exist), their top topics, and their 5 most recent published simulations. The `/p/:handle` frontend route renders this as a public profile card — shareable as "miroshark.app/p/cryptoresearcher" or self-hosted equivalent. Operators building a public track record ("I called 74% of these correctly") have a landing page to link from their Twitter/Substack bio. Downstream ecosystem partners building aggregation products have a stable identity layer. Zero changes to the simulation execution path — the profile reads only from existing published signals and the settings store.

**How:**
1. Add `handle`, `bio`, and `public_profile` fields to the operator settings schema (`storage/settings.json` or equivalent). `handle`: alphanumeric + hyphens, 3–30 chars, globally unique (enforced by a `storage/handles.json` registry mapping handle → session_token with a file-lock write). `bio`: max 200 chars, plain text. `public_profile`: boolean, default false — must be explicitly opted into. Add `PUT /api/settings/profile` accepting `{handle: str, bio: str | null, public_profile: bool}`. Validate: `handle` matches regex `^[a-z0-9-]{3,30}$`; uniqueness check against `storage/handles.json` (read the file, check if handle is already claimed by a different session); if taken, return 409. Write `handle` + `bio` + `public_profile` to `storage/settings.json`; update `storage/handles.json`. Add 5 unit tests: invalid handle (`handle@bad`) returns 400; handle already taken by another session returns 409; same session re-claiming their own handle returns 200 (idempotent); `public_profile=false` can be set after being true (opt-out); `bio` over 200 chars returns 400.
2. Create `backend/app/services/profile_service.py` (~130 LoC, pure stdlib). Accept `handle: str`. Look up session_token from `storage/handles.json`. Load `storage/settings.json` for that session — if `public_profile` is false or handle doesn't exist, return None (renders as 404). Scan all published sims owned by that session_token (same scan pattern as trending_service). Compute: `{handle, display_name, bio, sim_count, accuracy: {annotated, correct, accuracy_pct} | null (null if 0 annotated outcomes), top_topics: [{topic, count}] (top-5), recent_sims: [{simulation_id, topic, direction, confidence_pct, created_at, share_url}] (5 most recent by created_at)}`. Cache to `storage/profile_cache_{handle}.json` with a 10-min mtime TTL. Add `GET /api/profile/:handle` to `backend/app/api/profile.py` — keyless (public). Cache-Control: `max-age=600, public`. Return the profile or 404 if not found / not opted in. Add to `surfaces_catalog.py` (type: `community`) and OpenAPI with `PublicProfile` schema. Add to `docs/API.md` under "Community". Add 3 unit tests: profile with `public_profile=false` returns None from service; profile with 0 published sims returns `sim_count=0` (not 404); `recent_sims` is capped at 5 entries.
3. Add a `ProfileCard.vue` component and the `/p/:handle` route to the frontend. The card layout: avatar area (a deterministic color block generated from the handle hash — no image upload needed); display name and `@handle` in large type; bio text; "Simulations: N" + "Accuracy: X%" (if annotated, else hidden); top-topics chip row; and a list of recent simulation tiles (same card component as the gallery, reusing the existing tile). The page is public — no auth required to view. Add a "Your Public Profile" section to the Settings page: a "Create handle" form (validates uniqueness live via debounced `GET /api/profile/:handle` — returns 200 if exists, 404 if available), bio textarea, and a toggle for `public_profile`. When enabled, show a copyable link to `/p/:handle`. Add 2 frontend unit tests: profile card renders display name and `@handle`; "Create handle" form shows "available" indicator when `GET /api/profile/:handle` returns 404.
