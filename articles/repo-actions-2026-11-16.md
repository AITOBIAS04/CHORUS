### 1. Simulation Monte Carlo Mode

**Type:** Feature
**Effort:** Medium (1-2 days)
**Impact:** A single simulation is a point estimate. The same topic run 10 times with different random seeds produces a distribution: "BULLISH in 8/10 runs (80%)" is a fundamentally stronger signal than "BULLISH in 4/10 (40%)." No existing analytics metric measures outcome robustness — the `confidence_pct` field measures within-run consensus, not cross-run stability. Adding a Monte Carlo mode gives operators a `robustness_score` that research can cite (and investors can trust). The existing simulation engine is already deterministic given a seed; running it N times in parallel is a matter of parallelizing the launch step. Output: `{runs: int, bullish_count: int, bearish_count: int, neutral_count: int, modal_outcome: str, robustness_pct: float, robustness_label: "Strong"|"Moderate"|"Weak"}`. The robustness label sets a plain-English threshold: 70%+ modal agreement = Strong, 50–69% = Moderate, <50% = Weak (genuinely contested). This surfaces naturally in article generation as a lede: "10 agent simulations, 8 BULLISH — a strong consensus."

**How:**
1. Create `backend/app/services/montecarlo_service.py` (~180 LoC, pure stdlib). `run_monte_carlo(topic: str, config: dict, runs: int = 10) -> dict`: validate `runs` in [3, 20] (clamp). Generate `runs` unique random seeds (UUID4 hex prefix → int32). For each seed: clone `config`, set `config["seed"] = seed`. Launch a simulation via the existing `simulation_service.launch(config)` call — this returns a sim_id. Wait for each to complete (poll `status` field on each sim, 5s interval, 30-min timeout). Once all complete: load each sim's `signal.json` → extract `direction`. Tally counts. `modal_outcome` = most frequent direction. `robustness_pct = round(modal_count / runs * 100)`. `robustness_label`: ≥70% = "Strong", 50–69% = "Moderate", <50% = "Weak". Write to `storage/montecarlo/{batch_id}/result.json`: `{batch_id, topic, runs, seeds, sim_ids: list, bullish_count, bearish_count, neutral_count, modal_outcome, robustness_pct, robustness_label, created_at}`. Return `batch_id`. Add 5 unit tests: 10/10 bullish → "Strong" robustness; 5/10 bullish → "Weak"; tally function handles ties correctly (bearish wins tiebreaker by alphabetic sort for determinism); runs clamped to [3, 20]; result JSON has all required keys.
2. Add `POST /api/simulations/monte-carlo` to `backend/app/api/montecarlo.py`. Session-auth. Request body: `{topic: str, config: dict, runs: int = 10}`. Validates config using existing schema validators. Launches async via `BackgroundTasks` (FastAPI) — returns immediately with `{batch_id: str, runs: int, status: "running", status_url: "/api/simulations/monte-carlo/{batch_id}"}`. Add `GET /api/simulations/monte-carlo/{batch_id}` for polling: returns current status ("running" with per-sim progress, "complete" with full result, "error" with failed sim IDs). Add both routes to `surfaces_catalog.py` (type: `analytics`, `create`). Add to `docs/API.md` under "Simulation Lifecycle" with a "Robustness Testing" subsection. Add 3 integration tests: POST returns 202 with `batch_id`; GET returns "running" with progress before completion; GET returns `robustness_label` after all sims complete.
3. Add a "Monte Carlo" launch option to Step 2: a toggle "Run robustness check (×N)" with an N selector (3/5/10, default 5). When toggled, the launch button becomes "Run ×N simulations" and shows an estimated cost multiplier (`~$X.XX × N = ~$Y.YY`). The Step 3 results page shows the Monte Carlo batch result card when `source_batch_id` is present on a sim: "Part of a robustness batch — BULLISH in {N}/{total} runs" with a small distribution bar (green/red/gray proportional to bullish/bearish/neutral). The gallery shows Monte Carlo batch simulations grouped under a collapsible parent. Add 2 frontend unit tests: estimated cost multiplier displays correctly; distribution bar proportions match `robustness_pct`.

### 2. Outcome Resolution & Accuracy Tracking

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Simulations are predictions. Currently there is no mechanism to record whether a prediction was correct. An operator who has run 50 simulations and been right 72% of the time is a fundamentally different credibility signal than one who just started. `POST /api/simulation/:id/resolve` lets operators mark the actual outcome (`BULLISH`, `BEARISH`, `NEUTRAL`) after the real-world event resolves. The system computes a running calibration score per operator: `accuracy_pct`, broken down by confidence band (high-confidence sims at 80–100% — were they actually right more often?). This creates the foundation for "trusted operator" badges, leaderboards, and academic citation. It also closes the feedback loop that swarm intelligence research requires to validate — Surowiecki's "Wisdom of Crowds" conditions include that individual estimators can be evaluated. Zero new data sources; all computed from existing `signal.json` fields plus the new resolution records.

**How:**
1. Create `backend/app/services/resolution_service.py` (~150 LoC, pure stdlib). `resolve_simulation(sim_id: str, actual_outcome: str, operator_id: str) -> dict`: validate `actual_outcome` ∈ {"BULLISH", "BEARISH", "NEUTRAL"}. Load `config.json` for `sim_id` → verify `operator_id` matches session (or admin override). Load `signal.json` → extract `direction`, `confidence_pct`. Compute `correct: bool = (direction == actual_outcome)`. Write to `storage/simulations/{id}/resolution.json`: `{sim_id, operator_id, predicted_outcome: direction, actual_outcome, correct, confidence_pct, resolved_at: str}`. Merge `resolved: true, actual_outcome, resolution_correct` into `signal.json`. `get_operator_calibration(operator_id: str) -> dict`: scan all `resolution.json` files for this operator. Group into confidence bands: "50–64%", "65–79%", "80–100%". Per band: `{count, correct_count, accuracy_pct}`. Overall: `{resolved_count, accuracy_pct, by_confidence_band: list, well_calibrated: bool}`. `well_calibrated = True` when high-confidence band accuracy ≥ low-confidence band accuracy (correct directionality). Add 5 unit tests: resolve with wrong operator_id raises PermissionError; `correct: false` written when direction ≠ actual; `accuracy_pct` = 2/3 for 2 correct out of 3; `well_calibrated: true` when high-confidence accuracy > low; `by_confidence_band` missing a band when no sims in that range.
2. Add `POST /api/simulation/:id/resolve` to `backend/app/api/resolution.py`. Session-auth (operator must own the sim). Request body: `{actual_outcome: str}`. Returns updated `signal.json` fields plus `{calibration_updated: true}`. Add `GET /api/users/:id/calibration` (keyless for published profiles): returns full `get_operator_calibration` output. Add both to `surfaces_catalog.py` (type: `feedback`, `analytics`). Add to `docs/API.md` under "Operators" with note: "Resolution data is voluntary — only operators who mark outcomes contribute to calibration scores." Add 2 integration tests: resolve endpoint writes `resolution.json` and updates `signal.json`; calibration endpoint returns `resolved_count: 0` for operator with no resolutions.
3. Add a "Mark outcome" button to the Step 3 signal card (visible only to the sim's operator, 24h+ after completion — event must have had time to resolve). Three-option toggle: BULLISH / BEARISH / NEUTRAL. On submit: show "Marked as [X]" with a checkmark. If `correct: true`: show a subtle green "Prediction correct" indicator. If `correct: false`: show a neutral gray "Prediction missed." The operator gallery shows a calibration badge on profiles with ≥10 resolutions: "72% accurate (of 10 resolved)" with a color scale (green ≥65%, yellow 50–64%, red <50%). Add 2 frontend unit tests: "Mark outcome" button renders only when `is_owner: true` and sim is 24h+ old; calibration badge renders only when `resolved_count >= 10`.

### 3. Director Event Template Library

**Type:** DX improvement
**Effort:** Small (hours)
**Impact:** Every operator currently types director events freeform. This creates three problems: (1) inconsistent phrasing means similar events produce incomparable simulations; (2) new users don't know what constitutes a good event ("The Fed raised rates" vs. "The Federal Reserve announced an emergency 75bps rate hike, citing CPI at 9.1%"); (3) cross-simulation analytics on "simulations with a rate hike event" are impossible without consistent phrasing. A curated library of 50 director event templates, categorized and keyword-searchable, solves all three. Categories: Macro (20), Crypto (15), Geopolitics (8), Tech (7). Each template has: a short label, the full event text, and 2–3 topic tags. Frontend adds a "Use a template" popover in the director event input. `GET /api/director-events/templates?category=crypto&q=hack` returns matching templates. The library is a static JSON file — no LLM calls, no database, no auth. It ships as a pure stdlib service reading `data/director_event_templates.json`.

**How:**

### 4. Simulation Consensus Stability Index

**Type:** Feature
**Effort:** Small (hours)
**Impact:** The `confidence_pct` field in `signal.json` reports the final round's confidence — a snapshot. It says nothing about how the simulation *arrived* at that number. A confidence of 73% that was 72% at round 20 and 74% at round 24 is fundamentally more reliable than a 73% that was 45% at round 20, surged to 85% at round 22, then collapsed back to 73% at round 24. The second simulation's outcome is "unsettled" — it would likely change if run for 5 more rounds. A `stability_index` (0–1) derived from the standard deviation of `confidence_pct` across the final 5 rounds captures this directly. `stability_label`: "Stable" (σ < 3%), "Settling" (3–8%), "Volatile" (> 8%). Merged into `signal.json` alongside `confidence_pct`. Surfaces in the signal card as a small indicator. Gallery sort: "Most Volatile Outcomes First" — a useful research filter for finding simulations with contested, unresolved consensus. Zero new data sources; derived purely from the existing `trajectory.json` per-round `bullish_pct` values.

**How:**
1. Create `backend/app/services/stability_service.py` (~90 LoC, pure stdlib). `compute_stability(sim_id: str) -> dict`: Load `trajectory.json` → extract `bullish_pct` per round → sort by round number → take last 5 entries (or all if < 5 rounds). Compute mean and standard deviation using pure-stdlib math (`statistics.stdev` for sample std, or manual if fewer than 2 entries). `stability_index = max(0.0, round(1.0 - (stdev / 50.0), 3))` — a stdev of 0 → index 1.0 (perfectly stable), stdev of 50 → index 0.0 (maximum volatility; 50 is the realistic ceiling for a 0–100 percentage). `stability_label`: index ≥ 0.94 (σ < 3%) → "Stable", ≥ 0.84 (σ < 8%) → "Settling", else → "Volatile". If fewer than 3 rounds: `{available: false, reason: "insufficient_rounds"}`. Cache to `storage/simulations/{id}/stability.json` (immutable after completion). Merge `stability_index`, `stability_label` into `signal.json`. Add 5 unit tests: 5 identical `bullish_pct` values → index = 1.0, label "Stable"; high-variance values (40, 85, 30, 90, 45) → label "Volatile"; < 3 rounds → `available: false`; `stability_index` ∈ [0, 1] always; "Settling" label fires for a moderate-variance sequence.
2. Add `GET /api/simulation/:id/stability` to `backend/app/api/stability.py`. Keyless for published sims. `Cache-Control: max-age=86400, public`. Response: `{available: bool, stability_index: float, stability_label: str, final_rounds_variance: float, rounds_analyzed: int}`. Add `stability_index`, `stability_label` to the OpenAPI `Signal` schema. Add to `surfaces_catalog.py` (type: `analytics`). Add to `docs/API.md` under "Analytics." Add 2 integration tests: endpoint returns 200 with `stability_index` ∈ [0,1] for a completed published sim; `stability_index` present in `signal.json` after sim completion.
3. Add a "Stability" row to the signal card in Step 3 (below Confidence): `{stability_label} outcome · {stability_index*100:.0f}% stable`. Use a small color indicator: green dot for Stable, yellow for Settling, red for Volatile. Add `?sort=stability_index&order=asc` gallery sort option ("Most Volatile Outcomes First") — useful for finding contested predictions. Add `stability_label` to the article generator's confidence block: "With confidence at {confidence_pct}% — {stability_label.lower()} across the final five rounds." Add 2 frontend unit tests: signal card renders "Stable" label with green dot for a high-index sim; gallery sort option includes "Most Volatile Outcomes First."

### 5. Model Performance Leaderboard

**Type:** Integration
**Effort:** Small (hours)
**Impact:** MiroShark uses OpenRouter for LLM routing — multiple models can be used across simulations. Currently, model selection is opaque: operators pick a model at launch with no data on which models produce higher-confidence outcomes, more stable predictions, or lower cost per simulation. `GET /api/analytics/models` aggregates across all published simulations to build a model leaderboard: for each model that has run at least 5 simulations, return `{model_name, sim_count, avg_confidence_pct, avg_stability_index, avg_controversy_score, avg_cost_usd, avg_duration_secs}`. This turns the OpenRouter model catalog from an abstract list into a data-driven choice: "claude-haiku-5-5 runs 2.3× faster than opus-5-5 at 42% of the cost, with confidence within 3 points." For operators optimizing for speed vs. quality, this is the missing decision aid. Useful immediately with existing simulation data — no new data sources, no auth required, all computed from `config.json` and `signal.json` files already on disk.

**How:**
1. Create `backend/app/services/model_stats_service.py` (~140 LoC, pure stdlib). `build_model_leaderboard(min_sims: int = 5) -> list[dict]`: scan `storage/simulations/*/config.json` for all completed published sims. Extract `model_name` (from `config.json` → `llm_model` or equivalent field; fall back to parsing `llm_config`). Group by model. For each model with `sim_count >= min_sims`: load each sim's `signal.json` → accumulate `confidence_pct`, `stability_index` (if present), `controversy_score` (if present). Load `config.json` → accumulate `estimated_cost_usd`, `duration_secs`. Compute means. Build entry: `{model_name: str, sim_count: int, avg_confidence_pct: float, avg_stability_index: float | null, avg_controversy_score: float | null, avg_cost_usd: float | null, avg_duration_secs: float | null}`. Sort by `sim_count` descending (most-used first). Cache result to `storage/analytics/model_leaderboard.json` with 15-min mtime invalidation. Add 5 unit tests: model with 3 sims excluded when `min_sims=5`; means computed correctly; `avg_stability_index: null` when no sims in that model have `stability_index`; sort order is by `sim_count` descending; models with identical sim_count sorted alphabetically as tiebreaker.
2. Add `GET /api/analytics/models` to `backend/app/api/model_analytics.py`. Keyless. Query params: `?min_sims=5` (default 5, clamp [1, 50]), `?sort=confidence` (default `sim_count`; also accepts `confidence`, `cost`, `speed`). `Cache-Control: max-age=900, public` (15 min). Response: `{generated_at: str, model_count: int, models: list[ModelStats]}`. If fewer than 2 models have enough sims: return `{available: false, reason: "insufficient_data", minimum_sims_per_model: 5}` with HTTP 200. Add to `surfaces_catalog.py` (type: `analytics`). Add to `docs/API.md` under "Analytics" with a curl example and note: "Returns data only when ≥2 models have each run ≥5 published simulations." Add 2 integration tests: endpoint returns `available: false` when data insufficient; sort=cost returns models ordered by `avg_cost_usd` ascending.
3. Add a "Models" tab to the existing analytics page (or create `frontend/src/pages/ModelLeaderboardPage.vue` at `/analytics/models`). Table layout: columns `Model`, `Sims`, `Avg Confidence`, `Avg Stability`, `Avg Controversy`, `Avg Cost`, `Avg Duration`. Sortable by clicking column header. Each model name links to the OpenRouter model page (use `https://openrouter.ai/models/{model_name}` if model name matches OpenRouter slug format). Show a "Insufficient data" empty state when `available: false`. Add a "Model comparison" chip to the Step 2 model selector — clicking it opens the leaderboard table in a side drawer before the operator finalizes their selection. Add 2 frontend unit tests: table renders with correct column count when data is available; "Insufficient data" empty state renders when `available: false`.
