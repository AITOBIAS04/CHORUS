### 1. Webhook Delivery Log

**Type:** Feature
**Effort:** Small (hours)
**Impact:** WEBHOOKS.md shows a fully-functional outbound webhook system — HMAC-signed payloads, event filtering, Slack/Discord/n8n support. But there's no delivery history. When a webhook silently fails (consumer goes down, network blip, HMAC mismatch), the operator has no way to know. `GET /api/webhooks/deliveries` returns a log of recent delivery attempts: HTTP status code, latency, response body (first 500 chars), retry_count, succeeded_at/failed_at. Operators debugging why their Zapier zap isn't firing need this — today they're blind.

**How:**
1. Create `backend/app/services/webhook_delivery_service.py` (~100 LoC, pure stdlib). When the webhook dispatcher fires, append a delivery record to `uploads/webhook_deliveries.jsonl` (append-only, like the event log): `{"delivery_id": uuid4, "webhook_url": sha256_truncated(url)[:8] + "...", "event": "simulation.completed", "sim_id": str, "attempted_at": ISO8601, "http_status": int|null, "latency_ms": int|null, "response_preview": str, "retry_count": int, "succeeded": bool}`. Hash the webhook URL to avoid logging sensitive endpoints in plaintext. Retry logic: if http_status >= 500 or null (network error), mark for retry with backoff (5s, 30s, 2min, 10min); update `retry_count` and re-append the outcome. Add 4 unit tests: successful delivery logs `succeeded: true`; 5xx response triggers retry; URL is hashed in record; delivery record has all required fields.

2. Add `GET /api/webhooks/deliveries` endpoint in `backend/app/api/webhooks.py`. Auth-required (same session/API key that configured the webhook). Query params: `limit` (default 50, max 200), `since` (ISO8601 — filter deliveries after this time), `status` (all/succeeded/failed). Reads `uploads/webhook_deliveries.jsonl` in reverse (newest first) via a tail-read pattern (seek to end, scan backward for newlines — avoids loading entire log into memory). Response: `{"deliveries": [...], "total_in_window": int, "success_rate_24h": float, "generated_at": ISO8601}`. Add `success_rate_24h` as a quick health signal — operators can see "webhook is at 97% delivery over last 24h" at a glance. Add to `surfaces_catalog.py` (type: `integrations`) and OpenAPI with `WebhookDeliveryResponse` and `WebhookDeliveryEntry` schemas. Add to `docs/WEBHOOKS.md` under a new "Delivery history" section. Add 3 integration tests: returns 200; `success_rate_24h` is a float 0–1; `limit` clamp respected.

3. Surface in the Settings → Integrations frontend. Next to the webhook URL field, add a "Delivery History" expandable panel: table showing last 10 delivery attempts (date, HTTP status badge green/yellow/red, latency). A `Retry` button re-dispatches the most recent failed delivery. Add a `Copy delivery_id` icon on each row — delivery IDs are the canonical reference when filing a bug with an integration partner ("delivery abc12345 failed"). Add 1 frontend unit test: delivery with http_status=500 renders a red badge and Retry button.

### 2. Cross-Provider Performance Telemetry

**Type:** Observability / Feature
**Effort:** Small (hours)
**Impact:** OBSERVABILITY.md shows a rich per-simulation event stream with `llm_call` events carrying model, tokens, latency, and caller. All this data exists in `backend/logs/events.jsonl` across every simulation ever run. But there's no cross-simulation aggregate: no way to see "openai/gpt-4o is averaging 2.3s p95 latency across the last 200 simulations" vs "claude-haiku-5-5 is averaging 0.8s." Operators who run 50+ simulations/day and route to multiple providers have no fleet view. `GET /api/observability/providers` rolls up the per-simulation `llm_call` events into a provider performance report. Distinct from Provider Capability Matrix (Oct 8 — static feature flags, not runtime metrics) and `GET /api/observability/stats` (per-simulation scoped, not cross-provider aggregate).

**How:**
1. Create `backend/app/services/provider_telemetry_service.py` (~150 LoC, pure stdlib). Scans `uploads/simulations/*/events.jsonl` for all `llm_call` events (the same source the debug panel uses). Groups by `provider` (extracted from `model` field: prefix before `/`). Computes per-provider: `total_calls`, `error_rate` (status != success / total), `p50_latency_ms`, `p95_latency_ms` (sort array, index at 0.50/0.95), `avg_input_tokens`, `avg_output_tokens`, `avg_cost_usd` (read from the event's cost field if present). Rolling window: last 7 days only (filter `recorded_at` >= now − 7d). Cache result to `.provider-telemetry-cache.json` with 15-minute mtime invalidation — recomputing across thousands of events on every request would be too slow. Add 5 unit tests: provider with 0 events returns zero-state dict; p95 computed correctly on 20-item array; rolling window excludes events older than 7 days; cache file written after first call; error_rate is float 0–1.

2. Add `GET /api/observability/providers` endpoint in `backend/app/api/observability.py` (or extend the existing observability router). Auth-required (admin/operator view — telemetry may include cost data). Query params: `window` (default `7d`, options: `1d`, `7d`, `30d`). Response: `{"providers": [{"name": str, "total_calls": int, "error_rate": float, "p50_latency_ms": int, "p95_latency_ms": int, "avg_input_tokens": int, "avg_output_tokens": int, "avg_cost_usd": float, "sample_size": int}], "window": str, "generated_at": ISO8601, "coverage_note": str}`. Include `coverage_note` if sample_size < 10 for any provider: `"openai: only 3 calls in window — estimates may be unreliable."` Add to `surfaces_catalog.py` (type: `meta`) and OpenAPI with `ProviderTelemetryResponse` schema. Register route. Add to `docs/OBSERVABILITY.md` under a new "Provider fleet view" section with a table showing all response fields. Add 3 integration tests: returns 200; all providers in `providers` list have `p50_latency_ms` as int; window param changes result set.

3. Surface in the debug panel's **LLM Calls** tab. Add a "Fleet View" toggle at the top of the tab that switches from per-simulation view to the cross-provider aggregate. Show each provider as a card: name, p50/p95 latency as a paired bar (p50 in violet, p95 in gray), error rate as a percentage badge (green < 1%, yellow 1–5%, red > 5%), sample size in small text. Cards sorted by total_calls descending. This gives operators the "which provider should I route my next 100 simulations to?" answer from the UI without leaving the debug panel. No new page required. Add 1 frontend unit test: provider with error_rate > 0.05 renders a red badge.

### 3. Simulation Input Provenance

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Signed Result JSON (merged Jun 8) HMAC-signs the *output* of a simulation. But there's no signed record of the *inputs* — the exact topic text, agent count, round count, platform list, seed, provider, and model version used. Two simulations run on the same topic might produce different results due to different providers or seeds. Researchers citing MiroShark results ("we ran 50 simulations of X and got 87% BULLISH consensus") need to prove their corpus is reproducible and unaltered. `GET /api/simulation/{id}/provenance` returns a SHA-256 hash of all deterministic inputs so a reader can independently verify a published simulation was run with exactly the stated parameters. Distinct from Signed Result JSON (signs outputs), Pre-Run Time & Cost Estimate (Jun 20 — predicts runtime, not documents inputs).

**How:**
1. Create `backend/app/services/provenance_service.py` (~80 LoC, pure stdlib). Reads `signal.json` (contains `topic`, `agent_count`, `rounds`, `platforms`, `direction`, `confidence_pct` — proxies for inputs since the original run config may not be stored separately) and `backend/app/config.py` or equivalent for the model/provider used. Builds a canonical input dict: `{"topic": str, "agent_count": int, "rounds": int, "platforms": [str], "provider": str, "model": str, "seed": int|null, "schema_version": "1.0"}`. Sorts all keys canonically (sorted dict). Serializes to JSON with `ensure_ascii=False, separators=(',',':')` — no whitespace, deterministic output. Computes `hashlib.sha256(json_bytes).hexdigest()`. Writes provenance JSON to `uploads/simulations/{id}/provenance.json` on first call (permanent cache — inputs never change). Add 4 unit tests: same inputs always produce the same hash; different topic strings produce different hashes; serialization is deterministic across runs; provenance file is written to disk.

2. Add `GET /api/simulation/{id}/provenance` endpoint in `backend/app/api/provenance.py`. Public (no auth — provenance is meant for public citation). Response: `{"simulation_id": str, "input_hash": str, "inputs": {topic, agent_count, rounds, platforms, provider, model, seed}, "schema_version": "1.0", "signed_at": ISO8601, "verification_note": "SHA-256 of canonical inputs JSON — run provenance_verify.py to confirm"}`. Include a `verification_note` that tells readers exactly how to verify independently: point to a `scripts/verify_provenance.py` helper (a 15-line script that recomputes the hash from the JSON and checks it). Cache-Control: `max-age=86400`. Add to `surfaces_catalog.py` (type: `analytics`) and OpenAPI with `ProvenanceResponse` schema. Add to `docs/API.md` under "Analytics" with the canonical serialization spec (sorted keys, no whitespace, UTF-8). Add 2 integration tests: returns 200 for published sim; `input_hash` is 64-char hex.

3. Expose provenance in the result page and `EmbedDialog.vue`. On the Step 3 result page, add a `Cite` button that opens a modal: "This simulation's inputs are SHA-256 hashed for reproducibility. Hash: `abc123...`. To verify: `python verify_provenance.py {sim_id}`." Include a pre-formatted BibTeX-style citation block: `@misc{miroshark_{sim_id}, title={MiroShark Simulation}, note={Provenance hash: {input_hash}}, url={share_url}}`. Copy button copies the BibTeX block. In `EmbedDialog.vue`, add `provenance.input_hash` as a field in the cURL example. Add 1 frontend unit test: Cite modal renders input_hash. Write `scripts/verify_provenance.py` (15 LoC, stdlib only): reads `GET /api/simulation/{id}/provenance`, recomputes hash from the `inputs` dict using the canonical spec, prints VERIFIED or MISMATCH.

### 4. CLI Live Progress Stream

**Type:** DX
**Effort:** Small (hours)
**Impact:** The observability system already emits a live SSE event stream at `GET /api/observability/events/stream?simulation_id=sim_xxx` — every round boundary, LLM call, and agent decision appears in real time. The CLI (`miro run`) polls status by calling `GET /api/simulation/{id}/report/status` in a loop. This means CLI users either wait blind or run `watch curl`, staring at raw JSON. A `--live` flag connects directly to the existing SSE endpoint and renders a real-time progress bar and cost ticker in the terminal. No new backend code required — purely a CLI layer over existing infrastructure. Distinct from all prior batches (no prior idea touched the CLI progress display).

**How:**
1. Add `--live` flag to the `miro run` command in `scripts/` or wherever the CLI entrypoint is defined. When `--live` is set: after the simulation is started (POST /api/simulation), connect to `GET /api/observability/events/stream?simulation_id={id}` using Python's `urllib.request` with streaming (no new dependencies — stdlib `http.client` supports chunked transfer). Parse SSE lines (`data: {...}\n\n` format). Maintain state: `rounds_complete`, `rounds_total` (from `round_boundary` events with `phase=end`), `llm_calls_total`, `tokens_total`, `cost_so_far`. On each `round_boundary` event, redraw the progress line using `\r` carriage return (no `curses` — single-line redraw works in any terminal): `Round 3/10 ████████░░░░░░░░ 30%  LLM calls: 47  Tokens: 12,340  Cost: $0.08`. On `error` events, print the error class and message and continue. On stream close (simulation completed), print a final summary line. Add 4 unit tests: SSE parser correctly splits `data:` lines; round_boundary increments rounds_complete; error events print to stderr; final summary renders on stream close.

2. Add a `--live-format` option to control output verbosity: `compact` (default, single-line progress), `verbose` (one line per event type with timestamp), `json` (raw event JSON, one per line — for piping to jq). For `compact`: show only `round_boundary` events. For `verbose`: show `round_boundary`, `llm_call` (model name + latency), `graph_build` (phase), and `error` events — skip `agent_decision` (too high-volume for a terminal). For `json`: emit every raw SSE event as one JSON line to stdout. This makes `--live --live-format=json | jq '.type == "error"'` a valid debugging pattern — no need to open the debug panel in a browser. Add 3 unit tests: compact format produces one line per round; json format emits valid JSON per event; verbose format includes llm_call lines.

3. When `--live` is not set, make the default `miro run` behavior show a minimal heartbeat indicator rather than silence: print a spinner character that updates every 5 seconds with elapsed time (`⠸ Running… 00:02:15  ~$0.12 estimated`). The cost estimate comes from `GET /api/estimate` (the Pre-Run Estimate endpoint from Jun 20) called before the run starts — the spinner shows "~$0.12 estimated" until the run completes, then replaces it with the actual cost from the result. This brings the default experience closer to `--live` without requiring SSE, and works in environments where streaming is unreliable. Add 2 unit tests: spinner updates elapsed time string correctly; estimated cost from Pre-Run Estimate populates the spinner line.

### 5. Opinion Leader Influence Score

**Type:** Feature / Analytics
**Effort:** Medium (1-2 days)
**Impact:** The Agent Mention Network (merged Jun 12) counts @-mentions — raw citation frequency. The Stance Flip Report (merged Jun 13) logs which agents changed direction. Neither answers: "did agent A's @-mention actually cause agent B to flip?" Causal influence is the missing layer. `GET /api/simulation/{id}/opinion-leaders` correlates mentions with subsequent stance changes: if agent A @-mentioned agent B in round 3 and agent B flipped stance in round 4, that is an influence edge. Aggregated across rounds, this produces a per-agent influence score — the probability that a mention of that agent precedes a stance change in the next round. This is a per-simulation version of the Archetype Atlas's influence_score, but computed from actual causal chains rather than archetype-level aggregates. Researchers studying information cascades in agent swarms have a citable per-agent number.

**How:**
1. Create `backend/app/services/opinion_leader_service.py` (~200 LoC, pure stdlib). Inputs: `actions.jsonl` (post text, platform, round, agent_id) and `trajectory.json` (per-agent stance per round). Algorithm: for each round R, extract all @-mentions from `actions.jsonl` (same parser as mentions_service.py — reuse the `extract_mentions(text, roster)` function). For each mention edge (mentor → mentee), check if mentee flipped stance between round R and round R+1 (using `trajectory.json`). Compute per-agent influence score: `influence_score = mention_triggered_flips / max(1, total_times_mentioned)` — clamped to [0, 1]. Augment with `mention_count` (raw @-mention frequency from mentions_service) and `flip_count` (raw stance changes from stance_flip_service). Cache to `opinion_leaders.json` per simulation (mtime-based, same pattern as mentions.json). Add 5 unit tests: agent with 3 mentions and 3 subsequent flips scores 1.0; agent with 3 mentions and 0 flips scores 0.0; agent never mentioned scores 0.0; round R+1 flip threshold respected; cache file written after first call.

2. Add `GET /api/simulation/{id}/opinion-leaders` endpoint in `backend/app/api/opinion_leaders.py`. Publish-gated. Response: `{"simulation_id": str, "opinion_leaders": [{"agent_name": str, "platform": str, "influence_score": float, "mention_count": int, "mention_triggered_flips": int, "stance_flips_as_mentee": int}], "method": "mention-precedes-flip (round+1 window)", "total_agents": int, "generated_at": ISO8601}`. Sort `opinion_leaders` by `influence_score` desc, then `mention_count` desc for ties. Limit to agents with `mention_count >= 2` — single-mention agents have insufficient data for a meaningful influence score; include them in a `low_sample_agents` count in the response. Cache-Control: `max-age=3600`. Add to `surfaces_catalog.py` (type: `analytics`) and OpenAPI with `OpinionLeadersResponse` schema. Add to `docs/API.md` under "Analytics" with a note on the causal definition ("correlation within a round-window boundary, not structural causation"). Add 3 integration tests: returns 200 for published sim; `influence_score` in [0, 1]; agents with mention_count < 2 excluded from leaders list.

3. Surface in the Step 3 result page. Add an `★ Opinion Leaders` toolbar button (sibling to the existing `@ Mentions` and `↻ Stance Shifts` buttons). Opens a dark-themed overlay panel showing: top-5 opinion leaders as ranked cards (gold/silver/bronze badges, agent name, platform chip, influence score as a percentage, `mention_triggered_flips` / `mention_count` fraction). Below the top-5, a collapsible "Full influence matrix" table: rows = mentors, columns = mentees, cells = mention_triggered_flip_count (0 if no causal edge). Cells colored by value: 0 = transparent, 1 = faint violet, 2+ = full violet. Bilingual (EN/ZH-CN). In `EmbedDialog.vue` under "Data," add `GET /api/simulation/{id}/opinion-leaders` cURL example. Add 1 frontend unit test: agent with `influence_score = 1.0` renders a full-violet score bar.

## Selection Rationale

Zero open issues today — the Oct 8 bug batch was fixed within 48 hours. The codebase is healthy. The next productive work is closing the feedback gaps in the two fully-built but un-inspectable systems: webhooks have no delivery log (#1), and the observability event stream has no cross-simulation aggregate view (#2).

- **Webhook Delivery Log (#1)** — The webhook system is complete (HMAC, event filtering, Slack/Discord/n8n). But silent failures are invisible. A 50-line append to `webhook_deliveries.jsonl` on every dispatch closes the feedback loop. Operators go from blind to "webhook at 97% delivery over 24h."

- **Cross-Provider Performance Telemetry (#2)** — `llm_call` events already log model, tokens, and latency per simulation. Rolling them up into a fleet view is a read-pass over existing data. Distinct from Provider Capability Matrix (Oct 8 — static, not runtime), from per-simulation observability stats (scoped, not cross-provider). Operators routing to multiple providers need this.

- **Simulation Input Provenance (#3)** — Signed Result JSON (Jun 8) signs outputs. Nobody signs inputs. A SHA-256 hash of canonical inputs is the piece that makes MiroShark results scientifically citable — researchers can prove their corpus is unaltered. The `verify_provenance.py` helper makes this self-service.

- **CLI Live Progress Stream (#4)** — The SSE endpoint exists. The CLI polls blindly. Connecting them is a stdlib `http.client` read loop and a `\r` redraw. Zero backend work. This is the highest-leverage DX fix relative to implementation cost.

- **Opinion Leader Influence Score (#5)** — The mention network (Jun 12) and stance-flip report (Jun 13) are both built. Their data is in the same files. Correlating them to produce a causal influence score is the missing synthesis — and the first per-simulation metric that captures *why* stances shifted, not just *that* they shifted. Distinct from every prior batch.
