### 1. Simulation Lifecycle MCP Tools

**Type:** Integration
**Effort:** Small (hours)
**Impact:** `mcp_server.py` already exists and exposes knowledge graph tools to Claude Desktop, Cursor, and Windsurf. Adding `run_simulation`, `get_simulation_status`, and `get_simulation_result` as MCP tools to the same server lets any connected AI assistant launch and retrieve simulations mid-conversation — no API knowledge required, no context switch. The user workflow becomes: "Claude, run a 50-agent simulation on the Fed's September pivot and report back." A developer demoing this in a tweet or README GIF — AI assistant runs a real sim and summarizes the signal — is the kind of media that gets shares. Zero new backend infrastructure; pure extension of the existing MCP surface.

**How:**
1. In `backend/mcp_server.py`, add three tool registrations (alongside the existing `list_graphs`, `search_graph`, etc.). `run_simulation`: accepts `topic: str`, `agent_count: int` (default 50), `round_count: int` (default 10), `platforms: list[str]` (default `["Twitter"]`). Calls `POST /api/simulation` via `httpx` against `localhost:{PORT}` (same port MiroShark runs on — read `MIROSHARK_PORT` env var, default 8000). Returns `{"simulation_id": str, "status": "pending", "estimated_duration_seconds": int}`. `get_simulation_status`: accepts `simulation_id: str`. Calls `GET /api/simulation/:id/status`. Returns `{"status": str, "current_round": int, "total_rounds": int}`. `get_simulation_result`: accepts `simulation_id: str`. Calls `GET /api/simulation/:id/signal`. Returns the full signal JSON. Each tool uses `httpx.Client` (sync, already a transitive dependency); add 10s connect timeout, 30s read timeout. Add 6 unit tests: `run_simulation` calls the correct POST endpoint; `get_simulation_status` calls the correct GET; `get_simulation_result` calls signal endpoint; all three are listed in `GET /api/mcp/status` under `simulation_tools: true`; invalid `simulation_id` bubbles an MCP error (not a crash); tool returns `status: running` correctly without blocking.
2. Add a "Simulation" section to `docs/MCP.md` under "What's exposed" — extend the existing table with three rows: `run_simulation`, `get_simulation_status`, `get_simulation_result`. Include an example prompt: *"Run a 100-agent simulation on whether Ethereum will outperform Bitcoin this quarter, then summarize the consensus once it completes."* Add a note on polling: since simulations take minutes, advise users to call `get_simulation_status` in a follow-up message once they see `status: pending`. Add a sandbox note in a `<!-- dev note -->` comment in `mcp_server.py`: simulation calls require MiroShark to be running locally on `MIROSHARK_PORT` — remote deployments need a `MIROSHARK_API_BASE_URL` override.
3. Add `MIROSHARK_API_BASE_URL` to `.env.example` (comment: "Override for remote MiroShark deployments accessed from MCP clients — defaults to http://localhost:8000"). Add a smoke test under `scripts/test-mcp-sim.sh` that starts a dry-run simulation (1 agent, 1 round) via the MCP tool and checks that `simulation_id` is non-empty. Add a `make mcp-sim-test` target. Update the Settings panel's auto-generated MCP config snippet (`GET /api/mcp/status`) to include the simulation tools block.

### 2. Recurring Simulation Scheduler

**Type:** Feature
**Effort:** Medium (1–2 days)
**Impact:** Every ecosystem partner building a monitoring product (daily crypto sentiment, weekly macro pulse, recurring election forecasts) currently has to run their own cron job that calls `POST /api/simulation`. `POST /api/simulation/:id/schedule` accepts a cron expression and stores it in the simulation's config; the engine re-runs the simulation on that cadence, generating a new result record (indexed under `series_id`) each time. `GET /api/series/:id` returns all runs sorted by `created_at` with their signals. This is the primitive that turns MiroShark from a one-shot oracle into a continuous monitoring platform — the market pulse use case that most ecosystem partners are building around, now built into the engine itself. No external scheduler infrastructure needed.

**How:**
1. Create `backend/app/services/scheduler_service.py` (~150 LoC, pure stdlib). Data model: `ScheduledSeries` — `{series_id: UUID4, source_simulation_id: str, topic: str, config_snapshot: dict, cron_expression: str, next_run_at: ISO8601, created_at: ISO8601, owner_session: str}`. Persist series to `storage/series/{series_id}.json`. On each MiroShark startup, load all series and register them in a lightweight in-process cron runner: a background thread that wakes every 60 seconds, checks all series for `next_run_at <= now()`, creates a new simulation from `config_snapshot`, enqueues it, and updates `next_run_at` by advancing the cron expression (use a minimal pure-Python cron parser — implement just the subset: minute/hour/day fields with `*`, `*/N`, and comma-separated values; 20 LoC is enough for the common cases). Cap series at 50 runs to prevent unbounded storage growth; when the cap is hit, auto-delete the oldest run before writing the new one. Add 6 unit tests: cron parser produces correct `next_run_at` for `0 8 * * *` (daily 08:00 UTC); series is persisted to disk after creation; background thread does not trigger early (`next_run_at` not yet elapsed); run count increments on trigger; cap of 50 deletes oldest run; cron expression `*/6 * * * *` triggers at 6-minute intervals.
2. Add `POST /api/simulation/:id/schedule` to `backend/app/api/simulation.py`. Request body: `{"cron": str, "label": str|null}`. Validate `cron`: must be 5 fields, each field matches the supported syntax (minute/hour/day-of-month/month/day-of-week; reject `@reboot` style for safety); minimum interval is `*/10 * * * *` (10 min, to prevent abuse). Creates a `ScheduledSeries` via `scheduler_service`, returns `{"series_id": str, "next_run_at": ISO8601, "label": str|null}`. Add `DELETE /api/series/:id` to cancel a series (marks `active: false`, stops background thread from triggering it). Add `GET /api/series/:id` to list all runs (returns `{series_id, label, cron, runs: [{simulation_id, created_at, direction, confidence_pct, status}]}` sorted newest-first). Add to OpenAPI with `ScheduledSeriesResponse`, `SeriesRunEntry` schemas. Add to `surfaces_catalog.py` (type: `scheduling`). Add 4 integration tests: valid cron returns 200 with `series_id`; invalid cron (`bad-value * * * *`) returns 400; delete sets `active: false`; GET series lists completed runs.
3. Add a "Recurring Simulations" section to `docs/API.md` (under "Simulation Lifecycle"). Include: the schedule endpoint, the minimum 10-minute interval constraint, an example using `0 8 * * 1` (every Monday at 08:00 UTC for a weekly market pulse), a note that series are capped at 50 runs. Add `SCHEDULER_ENABLED=true` to `.env.example` (comment: "Set to false to disable the recurring simulation scheduler — useful for read-only replica deployments"). Add to `docs/FEATURES.md` under "Simulation Engine" — one paragraph: "Recurring simulations let you schedule a market scenario to run automatically on any cron cadence. Each run is indexed under a series, and GET /api/series/:id returns the complete result history."

### 3. Simulation Parameter Dry-Run Validator

**Type:** DX
**Effort:** Small (hours)
**Impact:** The most common support pattern for self-hosted MiroShark: someone runs a simulation that fails or produces garbage output because of a bad parameter combination — 0 agents, a `round_count` that would exceed the LLM token budget, a typo in `platforms`. `POST /api/simulation/validate` accepts the same body as `POST /api/simulation` but runs no agents and charges nothing — it returns a validation report: detected issues, budget estimate, agent roster preview (3 sample agent names from the demographic distribution), and a `valid: bool`. No new data sources — the estimator and demographic services are already available. The practical effect: new self-hosters stop wasting simulation budget on sanity-check runs, and ecosystem builders can add a "pre-flight check" step before submitting any production sim.

**How:**
1. Create `backend/app/services/validate_service.py` (~100 LoC, pure stdlib). Accept the full simulation creation params. Run each validation check and accumulate a warnings list: `agent_count < 5` → warning "Low agent count may produce noisy consensus"; `round_count > 30` → warning "High round count may exceed your LLM token budget"; `platforms` empty → error "At least one platform is required"; `topic` under 5 characters → error "Topic too short for meaningful simulation"; `agent_count × round_count > 5000` → warning "Large simulation — estimated cost may exceed $10". Call `estimate_service.estimate(agent_count, round_count, platforms)` to get `estimated_cost_usd` and `estimated_duration_seconds`. Generate 3 sample agent names from the demographic service (draw from the default demographic distribution — first names, professions, stances). Return `{"valid": bool (no errors), "errors": [str], "warnings": [str], "estimate": {cost_usd, duration_seconds, confidence}, "sample_agents": [{name, profession, initial_stance}]}`. Add 5 unit tests: empty topic → error; 0 agent_count → error (even before the low-count warning); valid params → `valid: true, errors: []`; `agent_count × round_count > 5000` → warning present; sample_agents has exactly 3 entries.
2. Add `POST /api/simulation/validate` to `backend/app/api/simulation.py` (register *before* `POST /api/simulation` to avoid routing ambiguity). No auth required (it runs nothing, costs nothing). Accept same body schema as simulation creation. Return 200 with the validation report JSON (even when `valid: false` — use 200 not 422, because the validation itself succeeded; the payload tells the caller what's wrong). Add to `surfaces_catalog.py` (type: `validation`) and OpenAPI with `ValidationResponse` schema. Add to `docs/API.md` under "Simulation Creation" with a note: "Call /validate before submitting large or expensive simulations." Add 2 integration tests: missing required field returns 422 (FastAPI schema validation, before our validator runs); valid body returns 200 with `valid: true`.
3. Add a "Pre-flight" step to the Step 2 (configuration) form in `frontend/src/`: when the user clicks "Run" for the first time on a new configuration, call `POST /api/simulation/validate` first, show the estimate chip (if the estimator wasn't already called), and display any warnings as muted amber inline callouts under the relevant fields. If there are errors, block submission and highlight the fields. If only warnings, show a "Proceed anyway" button. The validation call is a prerequisite — the "Run" button spinner shows "Checking…" for up to 2 seconds, then transitions to "Running" if validation passes. Add 2 frontend unit tests: warnings render as amber callouts; errors disable the "Run" button and render red callout.

### 4. Webhook Delivery History Log

**Type:** DX
**Effort:** Small (hours)
**Impact:** Webhooks are fully documented and deployed — but once a simulation completes, integrators have no visibility into whether their webhook endpoint received it, what HTTP status it returned, or whether a retry was attempted. `GET /api/admin/webhooks/deliveries` returns the last 100 delivery attempts with timestamp, HTTP status, request duration, and `succeeded: bool`. This is the single most common question from ecosystem integrators who are debugging why their Zapier trigger, Slack bot, or custom endpoint "never fires." Exposing the delivery log as an API endpoint (admin-token gated) closes the observability loop without requiring server log access. The Settings UI can surface a simple "Webhook Health" view for non-technical operators.

**How:**
1. Extend the webhook dispatch layer (wherever `WEBHOOK_URL` is read and the HTTP POST is made — likely in `backend/app/services/webhook_service.py` or similar) to write a delivery record to an append-only log file at `storage/webhook_deliveries.jsonl`. Each record: `{"attempt_id": UUID4, "simulation_id": str, "timestamp": ISO8601, "url": str (masked — only the host, no path), "http_status": int|null (null if network error), "duration_ms": int, "succeeded": bool, "error": str|null}`. Keep only the last 500 records (truncate on write when count exceeds 500 — read all lines, drop oldest to bring back to 499, append new). Masking the URL to host-only prevents secret webhook tokens in URLs from appearing in the log. Add 4 unit tests: successful delivery writes a record with `succeeded: true, http_status: 200`; network error writes `succeeded: false, http_status: null, error: "connection_refused"`; log truncates at 500 records; URL is masked to host only.
2. Add `GET /api/admin/webhooks/deliveries` to `backend/app/api/admin.py` (or create this module if the Oct 24 "Stuck Simulation Recovery" idea was not yet built — same auth pattern: `Authorization: Bearer {ADMIN_TOKEN}`). Query param: `?limit=N` (default 20, max 100). Reads `storage/webhook_deliveries.jsonl`, parses, returns newest-first. Response: `{"deliveries": [{attempt_id, simulation_id, timestamp, url_host, http_status, duration_ms, succeeded, error}], "total": int, "success_rate_pct": float (last 100 attempts)}`. Add `success_rate_pct` as a quick health gauge. Add to OpenAPI with `WebhookDeliveryResponse` schema. Add 3 integration tests: returns newest-first order; `?limit=5` returns 5 records; `success_rate_pct` is 100.0 when all deliveries succeeded.
3. Add a "Webhook Health" subsection to the Settings page (`frontend/src/`): a small panel showing the last 5 delivery attempts as a status list (green check / red X, simulation ID, time ago, duration). Fetch from `GET /api/admin/webhooks/deliveries?limit=5` on page load; poll every 30s while the page is open. Show `success_rate_pct` as a single percentage badge above the list. If `ADMIN_TOKEN` is not set, hide the panel silently. Add `GET /api/admin/webhooks/deliveries` and its usage pattern to `docs/WEBHOOKS.md` under a new "Monitoring deliveries" section. Add 2 frontend unit tests: success rate badge renders "100%" when all deliveries have `succeeded: true`; failed delivery renders with red X icon.

### 5. Named Simulation Series for Longitudinal Tracking

**Type:** Feature
**Effort:** Medium (1–2 days)
**Impact:** Power users — researchers, ecosystem partners, protocol analysts — run the same or similar simulations repeatedly over time. Right now those runs are disconnected: each one lives under a UUID with no organizing structure. `POST /api/series` creates a named series (e.g., "Fed Rate Sentiment — Weekly"). Any simulation can be added to a series via `PATCH /api/simulation/:id/series`. `GET /api/series/:id/timeline` returns all runs in the series sorted by date, with each run's `direction`, `confidence_pct`, and `bullish_pct` aligned for direct comparison — ready for a trend chart. This is the primitive that makes MiroShark a continuous monitoring platform rather than a one-shot oracle. It's also the organizing structure that makes the Recurring Simulation Scheduler (idea #2) easier to use, as scheduled runs are automatically added to their parent series. No changes to the simulation execution path.

**How:**
1. Create `backend/app/services/series_service.py` (~120 LoC, pure stdlib). Data model: `Series` — `{series_id: UUID4, label: str, description: str|null, owner_session: str, created_at: ISO8601, simulation_ids: [str]}`. Persist to `storage/series/{series_id}.json`. Operations: `create(label, description, owner_session)`, `add_simulation(series_id, simulation_id)`, `get_timeline(series_id)` (loads signal.json for each simulation_id, returns sorted array of `{simulation_id, created_at, direction, confidence_pct, bullish_pct, bearish_pct, neutral_pct, topic}`), `list(owner_session)`. Cap `simulation_ids` at 200 per series. Add 6 unit tests: create returns a new `series_id`; add_simulation appends to `simulation_ids`; timeline sorts by `created_at` ascending; timeline entry includes `direction` and `confidence_pct`; cap of 200 rejects additional adds with an error; get with unknown `series_id` returns `None`.
2. Add four endpoints to `backend/app/api/series.py`: `POST /api/series` (create; body: `{label, description}`; returns `{series_id, label, created_at}`), `GET /api/series` (list all series owned by session; returns `[{series_id, label, created_at, run_count}]`), `GET /api/series/:id/timeline` (full timeline with per-run signals), `PATCH /api/simulation/:id/series` (add to series; body: `{series_id}`; 404 if series not found, 403 if not owner of series). Register in `main.py`. Publish-gate: only the session that created the series can add simulations or read the timeline (consistent with per-sim ownership). Add to `surfaces_catalog.py` (type: `organization`) and OpenAPI with `SeriesResponse`, `SeriesTimelineEntry` schemas. Add to `docs/API.md` under a new "Series & Longitudinal Tracking" section. Add 4 integration tests: create + add simulation + get timeline returns 1 entry; PATCH with wrong session returns 403; timeline entry has `direction` field; list returns all series for the session.
3. Add a "Series" view to the gallery page (`frontend/src/`): a collapsible panel showing the user's saved series as cards (series label, run count, last direction, sparkline of `bullish_pct` over time — a 100×24px SVG line chart drawn from the timeline data). Clicking a series card expands it to show the full timeline table (one row per run: date, direction chip, confidence %, topic). Add a "New Series" button (top-right of the panel) that opens a name-entry dialog. Add "Add to Series" to the `Step3Simulation.vue` result header (next to "Share" and future "Fork & Rerun") — clicking it opens a dropdown of the user's series, or an "Add to new series" option. The sparkline uses the same violet/gray/red palette as the stance bars — a 1px stroke, no dots, no axes. Add 2 frontend unit tests: series card renders the last direction chip; sparkline SVG path element is present when timeline has ≥ 2 entries.
