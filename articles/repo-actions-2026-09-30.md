Returns JSON: `{issues: [{number, title, state, claimed: bool, merged_pr: int|null}], merged_count: int, contributor_count: int, contributors: [{login, merged_pr_count}]}`. ### 2. Simulation Bulk CSV Export

**Type:** Feature / DX
**Effort:** Small (hours)
**Impact:** The HuggingFace dataset badge (PR #311, Sep 26) links to 8,201 decisions across 16 sims uploaded as a static snapshot. Researchers who want fresh data — simulations published after the upload — have no programmatic path. `GET /api/simulations/export?format=csv&limit=100&since=2026-09-01` returns a ZIP archive containing one CSV per simulation: `{id}.csv` with columns `round, agent_id, platform, initial_stance, final_stance, stance_flips, influence_score, posts_count`. No new data collection — the CSV is compiled from `trajectory.json` and `actions.jsonl` files that already exist per simulation. This turns MiroShark into a real-time data feed for researchers, students, and ML practitioners who want to run their own analysis on fresh swarm data. Distinct from signed-result.json (single-sim aggregate JSON), activity.json (event stream), and the Full-Text Search endpoint (returns metadata, not raw data) — this is the raw bulk tabular export surface.

**How:**
1. Create `backend/app/api/export.py` (~110 LoC, pure stdlib). `GET /api/simulations/export` — accepts query params: `format` (only `csv` for now; 400 if other), `limit` (int, clamp [1, 50], default 10), `since` (ISO date string, optional), `until` (ISO date string, optional). Logic: (1) Scan simulation directories filtered by `published_at` within `[since, until]`, sorted descending, capped at `limit`. (2) For each simulation, read `trajectory.json` and `actions.jsonl`. Build a flat list of rows with columns: `simulation_id, round, agent_id, platform, stance, confidence_pct, posts_count`. (3) Use `io.StringIO` + `csv.writer` to build CSV text in memory. (4) Use `zipfile.ZipFile` with `io.BytesIO` to assemble all CSVs into a single ZIP. Set response `Content-Type: application/zip`, `Content-Disposition: attachment; filename="miroshark-export-{timestamp}.zip"`. Return 200 with ZIP bytes. Cache-Control: no-cache (each export is fresh by definition). Add `GET /api/simulations/export` to `surfaces_catalog.py` (type: `export`) and OpenAPI schema with `BulkExportResponse` describing the ZIP structure. Add 3 unit tests: empty result when no sims in window; CSV has correct column headers; ZIP contains correct number of files for a given limit. Add endpoint to `backend/app/main.py` router.

2. Add a "Download Dataset" section to the Step 3 simulation view. Below the existing share/embed buttons, add a `⬇ Download CSV` button that calls `GET /api/simulations/export?format=csv&limit=1&since={published_at}` for the current simulation only — this is a single-simulation CSV download (no ZIP wrapping needed for limit=1; unzip automatically when limit=1). Also add a `⬇ Bulk Export` link: `GET /api/simulations/export?format=csv&limit=50` with a tooltip "Downloads up to 50 most recent published simulations as a ZIP archive." Add both buttons to `EmbedDialog.vue` as a "Data Export" section with `curl` examples. Update `docs/API.md` under a new "Data Export" section: describe the query params, CSV column schema, ZIP structure, and rate-limit note (recommend max 1 request/minute for the bulk endpoint). Document in `docs/FEATURES.md`.

3. Add a metadata-only companion endpoint `GET /api/simulations/export?format=manifest` (extend Step 1) that returns JSON instead of ZIP: an array of objects `{simulation_id, topic, direction, confidence_pct, agent_count, total_rounds, published_at, csv_download_url}`. Limit 200 (higher than CSV because it's JSON, not binary). The manifest is what a HuggingFace dataset pipeline would consume to incrementally sync new simulations: fetch manifest, find sims newer than last sync, download only those CSVs. Add `ManifestEntry` to OpenAPI schema. This pairs with the HuggingFace Live Dataset Sync idea (Sep 26 batch) which would use the manifest as its polling source — the two ideas form a clean separation of concerns: manifest describes what's available, CSV export delivers the data.

### 3. Similar Simulations Discovery

**Type:** Feature
**Effort:** Small (hours)
**Impact:** MiroShark has 8,000+ published simulations and no way to discover related ones. When a user finishes a "BTC Q4 2026 price" simulation, there are likely dozens of similar "BTC", "Bitcoin", "crypto market" simulations to explore — but the user sees none of them. `GET /api/simulation/{id}/similar?limit=5` surfaces the 5 most topically similar published simulations using TF-IDF bag-of-words computed over simulation topics. No external ML API — pure stdlib `collections.Counter` over tokenized topic strings. The index is built on first call and cached to `similar_index.json` with a 30-minute mtime refresh. This drives session depth: a user following a "similar" link is deeper in the product and more likely to share a second simulation. Distinct from the Full-Text Search endpoint (Jun 14 — exact text matching on a user-supplied query string); this is **automatic topical adjacency** without requiring the user to type anything.

**How:**
1. Create `backend/app/services/similar_service.py` (~150 LoC, pure stdlib). Class `SimilarSimulationService`. Index structure: a dict `{simulation_id: Counter}` where the Counter is the TF-IDF-weighted token bag for that simulation's topic string. Tokenization: lowercase, split on non-alphanumeric, remove English stopwords (hardcoded set of ~20: "the", "a", "an", "in", "of", "for", "and", "or", "to", "is", "will", "be", "by", "as", "at", "on", "from", "with", "this", "that"). IDF: computed as `log(N / df)` where N = total docs and df = number of docs containing the token. TF: raw token frequency in the topic string. Similarity: cosine similarity between two TF-IDF vectors via `sum(min(a.get(t,0), b.get(t,0)) for t in a) / (sqrt(sum(a.values())**2) * sqrt(sum(b.values())**2))`. Cache: on first call (or when `similar_index.json` is >30min stale), scan all published simulation directories, extract topic strings, build the full index, write to `similar_index.json`. On subsequent calls, load from cache. `find_similar(sim_id, limit=5)` returns the top-N sim IDs by cosine similarity to the query, excluding the query itself, excluding unpublished sims. Add 4 unit tests: identical topics → similarity 1.0; completely different topics → similarity 0.0; stopwords stripped before comparison; results capped at limit and exclude self.

2. Add `GET /api/simulation/{id}/similar` to `backend/app/api/`. Returns JSON: `{similar: [{simulation_id, topic, direction, confidence_pct, similarity_score, url}]}`. Publish-gated: 404 if the query simulation is not published (consistent with all other publish-gated endpoints). Cache-Control: `max-age=1800` (30 min). Add to `surfaces_catalog.py` (type: `discovery`, 40th+ surface) and OpenAPI `SimilarSimulationsResponse` schema. Add 2 integration tests: response has correct shape; empty result when index has only one simulation. Register route in `backend/app/main.py`.

3. Surface in the Step 3 simulation view as a "Related Simulations" section below the main signal block. Fetches `GET /api/simulation/{current_id}/similar?limit=5` on mount. Renders as a horizontal scrollable row of cards (same card style as the simulation list view): topic, direction badge, confidence chip, similarity dot (a small colored circle: green >0.7, yellow 0.4–0.7, gray <0.4). Clicking a card navigates to `/simulation/{similar_id}`. Shows "No similar simulations found" (empty state) gracefully. Bilingual (EN/ZH-CN). Also inject the top similar simulation's URL into the embed response body `GET /api/simulation/{id}/embed` as a `related_url` field — a third-party embed consumer can optionally show a "Related:" link below the embed. Update `docs/FEATURES.md` with the Similar Simulations section.

### 4. Interactive OpenAPI Explorer

**Type:** DX / Growth
**Effort:** Small (hours)
**Impact:** MiroShark has 40+ documented API surfaces with full OpenAPI schemas — but there is no hosted interactive documentation. The only way to explore the API is to read `docs/API.md` (prose) or grep the source. Mounting Swagger UI at `GET /api/docs` turns the existing OpenAPI spec into a live API playground where developers can read endpoint descriptions, see example requests and responses, and click "Try it out" to fire real requests against the running backend — without writing a single line of code. During Hacktoberfest week, a contributor evaluating whether to build an integration sees a polished `/api/docs` page as a signal that this is a well-maintained project worth investing in. This is pure infrastructure — the API spec already exists; this surfaces it. No new API design, no new business logic, no new tests. Estimated 2-3 hours: install `fastapi[all]` (which bundles Swagger UI) or serve the static Swagger UI bundle from `backend/app/static/`.

**How:**
1. Check whether the backend uses FastAPI (likely, given the OpenAPI schemas already referenced throughout skills). If yes: FastAPI includes Swagger UI and ReDoc out of the box — they are already mounted at `/docs` and `/redoc` by default unless `docs_url=None` was set in the `FastAPI()` constructor. Check `backend/app/main.py`: if `docs_url=None` or `openapi_url=None` is set, remove those arguments. FastAPI then auto-generates `/openapi.json` from all registered routes and serves Swagger UI at `/docs`. The only code change needed is removing those disable flags (if present). If the backend is not FastAPI, create `backend/app/api/docs.py` (~30 LoC): serve `swagger-ui-dist` static assets from a CDN URL via a simple HTML redirect page at `GET /api/docs` — load the Swagger UI bundle from `https://unpkg.com/swagger-ui-dist@latest/swagger-ui-bundle.js` and point it at `GET /api/openapi.json`. Add a `GET /api/openapi.json` route that reads and serves `docs/openapi.yaml` (or generates it from the route registry).

2. Customize the Swagger UI instance. In the FastAPI constructor (or the HTML template from step 1), set: `title = "MiroShark API"`, `description = "Swarm intelligence simulation engine — 40+ surfaces for simulation, analysis, and data export. See [GitHub](https://github.com/aaronjmars/MiroShark) for setup."`, `version = "1.0"`, `contact = {"name": "MiroShark", "url": "https://github.com/aaronjmars/MiroShark"}`, `license_info = {"name": "MIT"}`. Group endpoints by tag: add `tags` parameters to all route decorators in `backend/app/api/` — use these tag values: `simulation` (run, status, signal, trajectory routes), `analysis` (agent archetypes, sentiment, stance flips, mentions, difficulty routes), `discovery` (search, similar, hot topics, activity feed), `export` (signed-result, bulk CSV, manifest), `admin` (quota, surfaces catalog). This makes the Swagger UI render as 5 collapsible sections rather than a flat list of 40+ endpoints. Update `docs/API.md` to add a one-line note at the top: "Interactive API explorer: `GET /api/docs` (Swagger UI) or `GET /api/redoc` (ReDoc)."

3. Add a `/api/docs` link to the Step 1 (setup) page as a "Developer API" footer link, and to the MiroShark README under a "API Reference" section: `[![API Docs](https://img.shields.io/badge/API-Swagger_UI-85EA2D?logo=swagger)](https://your-deployed-url/api/docs)`. The Swagger badge in the README signals to developers — especially Hacktoberfest contributors — that this project has first-class API documentation. A contributor who sees "40+ endpoints, all documented, interactive playground" is measurably more likely to build an integration or plugin than one who must grep through prose. Add an `openapi.json` export script `scripts/export-openapi.sh` that starts the backend, hits `GET /api/openapi.json`, writes the result to `docs/openapi.json`, and stops the backend. This allows the OpenAPI spec to be committed to the repo and consumed by external tooling (Postman, ReadMe.io, code generators) without needing a live instance.

### 5. Simulation Hot Topics Feed

**Type:** Feature / Growth
**Effort:** Small (hours)
**Impact:** Discord bots, Telegram bots, and third-party dashboards that want to embed MiroShark content currently have no aggregated signal to consume — only individual simulation endpoints. `GET /api/topics/hot?hours=24&limit=10` returns the top 10 most-simulated topics in the last 24 hours with: topic string, simulation count, dominant direction (bullish/neutral/bearish), average confidence_pct, and a representative simulation URL. A Discord bot operator polling this endpoint hourly can post: "*Today's top MiroShark topic:* BTC Q4 2026 → **BULLISH** (81% confidence, 12 sims)." With 85 days of social silence, every passive distribution surface matters — this endpoint enables a class of third-party distribution that currently can't exist. Distinct from the Trending Simulations Feed (Aug 22 — returns full sim objects sorted by views); this returns **topic-level aggregation** with aggregated direction + confidence statistics, not individual sim objects.

**How:**
1. Create `backend/app/services/hot_topics_service.py` (~120 LoC, pure stdlib). Function `get_hot_topics(hours: int = 24, limit: int = 10) -> list[dict]`. Logic: (1) Scan all published simulation directories. Filter to sims where `published_at >= now - timedelta(hours=hours)`. (2) Group by normalized topic string: lowercase, strip leading/trailing whitespace, collapse internal whitespace. (3) For each topic group, compute: `simulation_count` (len of group), `direction` (mode of `direction` values across sims in group: if tie, prefer "neutral"), `avg_confidence_pct` (mean of `confidence_pct` across group, rounded to 1 decimal), `representative_url` (URL of the sim with highest `confidence_pct` in the group). (4) Sort groups by `simulation_count` descending, break ties by `avg_confidence_pct` descending. (5) Return top `limit` groups. Clamp `hours` to [1, 168] (1 hour to 7 days). Clamp `limit` to [1, 50]. Cache to `.hot-topics-cache/hot.json` with a 5-minute mtime TTL. Add 4 unit tests: returns top-N groups sorted by count; direction is mode of group; avg_confidence_pct is mean; clamp applied to hours and limit. Register in `backend/app/main.py`.

2. Add `GET /api/topics/hot` to `backend/app/api/`. Query params: `hours` (int, default 24), `limit` (int, default 10). Returns JSON: `{generated_at: ISO string, window_hours: int, topics: [{rank, topic, simulation_count, direction, avg_confidence_pct, representative_simulation_url}]}`. Cache-Control: `max-age=300` (5 min). Add to `surfaces_catalog.py` (type: `aggregation`) and OpenAPI schema with `HotTopicsResponse` and `HotTopicEntry`. Add 2 integration tests: response shape is correct; returns empty `topics` array (not null) when no sims in window. Add `GET /api/topics/hot` to `docs/API.md` under a new "Aggregation" section, with a note: "Designed for third-party integrations and bots — returns topic-level aggregates, not individual simulation data." Add to `docs/FEATURES.md`.

3. Surface `GET /api/topics/hot` in the frontend as a "What's Being Simulated" widget on the Step 1 topic-entry page. Widget: a compact `<ul>` of 5 hot topics (refreshed on page load from `/api/topics/hot?hours=24&limit=5`) rendered as clickable chips. Clicking a chip pre-fills the Step 1 topic input with that topic string. Each chip shows: topic text, a small direction arrow (↑ bullish / → neutral / ↓ bearish), and confidence_pct. Label: "Trending today — click to use." This creates a virtuous loop: popular topics surface as suggestions → new users simulate similar topics → those simulations add to the count → topic rises in the feed. Zero friction for a new user who doesn't know what to simulate. Also include `/api/topics/hot` in the EmbedDialog `curl` examples section as a "programmatic feed" example alongside the individual simulation endpoints. This widget exists independently of GH_GLOBAL — it works the moment the endpoint is available in a deployed instance.

## Selection Rationale

Five ideas timed to the Hacktoberfest launch (tomorrow), the ongoing social silence, and the 90+ push-block reality where design quality matters more than shipping velocity.

- **Hacktoberfest Progress Dashboard (#1)** — Hacktoberfest opens tomorrow. The Issue Filer, Readiness Kit, and Welcome Automation are all prepped but invisible to the outside world. The scoreboard is the **public face** of the event — the one URL a maintainer can tweet, post to Discord, or link from the README. It creates social proof that the event is real and active. Uses built-in `GITHUB_TOKEN`; no GH_GLOBAL dependency.

- **Simulation Bulk CSV Export (#2)** — The HuggingFace badge (Sep 26) pointed to a static 8,201-decision snapshot. Researchers who want fresh simulations have no programmatic path. The bulk CSV export makes MiroShark a live data feed — queryable, filterable by date, downloadable in ZIP. Pairs naturally with the HuggingFace Live Dataset Sync (Sep 26) as the data delivery layer that sync would consume.

- **Similar Simulations Discovery (#3)** — Pure TF-IDF, no external API, pure stdlib. Every simulation already has a topic string. The 8,000-simulation corpus is a discovery problem waiting to be solved. A "Related Simulations" row at the bottom of Step 3 keeps users in the product and reduces single-session bounce. Session depth is the metric most correlated with organic sharing.

- **Interactive OpenAPI Explorer (#4)** — The API has 40+ documented surfaces and zero interactive documentation. Hacktoberfest contributors evaluating whether to build an integration make this judgment in seconds — and a polished Swagger UI page is the most credible signal available. For FastAPI backends, the implementation cost approaches zero: unmute `/docs`. The badge in the README is the distribution surface.

- **Simulation Hot Topics Feed (#5)** — The missing aggregation layer for third-party distribution. Discord bots, Telegram bots, and external dashboards can't currently build on MiroShark data at the topic level — only at the individual-simulation level. `/api/topics/hot` enables a class of passive distribution that doesn't require social posts or human attention. During 85 days of social silence, every channel that posts without human initiation is worth building.
