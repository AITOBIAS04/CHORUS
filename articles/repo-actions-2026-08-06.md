### 1. Demo Simulation Library

**Type:** Growth / Community
**Effort:** Small (hours)
**Impact:** Nine days until the tutorial hyperstition deadline (0/5). The core barrier for tutorial writers is the first step: getting a simulation result worth writing about. Running a simulation requires API keys, an environment, and waiting up to 10 minutes. A curated library of pre-run, published simulations with diverse topics and interesting results gives tutorial writers ready-made content to reference, screenshot, embed, and link without running their own. This is how tools like Postman, Observable, and Hugging Face onboard tutorial creators — a gallery of real results they can cite immediately. The library also serves as a `/demo` discovery page for visitors who want to understand what MiroShark produces before committing to a run. Each entry links to the live share URL, shows the direction/confidence, and suggests a tutorial angle — removing three friction points at once.

**How:**
1. Create `docs/DEMO_SIMULATIONS.md` (~120 lines). The file is a curated table of 10 published simulations spanning diverse use cases and consensus directions. Each row: `| Topic | Direction | Confidence | Share URL | Suggested Tutorial Angle |`. Use case categories: regulatory policy (EU AI Act, China agent regulation), crypto/token sentiment (a MIROSHARK rally scenario), product launch reaction (a tech product announcement), crisis communication (a public company scandal), political opinion (a contested policy vote), labor market (remote work permanence), scientific consensus (a contested research finding), consumer sentiment (a product recall). For each entry, include a one-paragraph "Why this simulation is interesting" note below the table explaining what made the consensus direction surprising or notable — this is the hook tutorial writers use to open their post. Add a "How to use this library" section: instructions for embedding any demo simulation (`<iframe src="https://miroshark.xyz/simulation/{id}/embed">`), for linking to the share page, for using the API to fetch the signal.json (`GET /api/simulation/{id}/signal.json`), and for including a reproduce.json citation in a blog post. Footer: "Want to add a simulation to this library? Open a PR to `docs/DEMO_SIMULATIONS.md` with your share URL."

2. Create `backend/app/api/demo.py` (~60 LoC, pure stdlib). `GET /api/demo`: returns a JSON array of the demo library entries. Reads the demo list from a config file `backend/app/data/demo_simulations.json` (10 entries, each: `{id, topic, direction, confidence_pct, share_url, use_case_category, tutorial_angle, note}`). For each entry, fetches the live `signal.json` from the local simulation storage (same path logic as existing signal service) to verify it's still published and to return the current confidence value. Entries where the simulation is no longer published are excluded from the response (with a `status: "archived"` flag logged but not returned). `Cache-Control: public, max-age=1800` (30-minute cache — demo entries don't change frequently, but we want live published status). Register the route in the main app router. Add to `surfaces_catalog.py` (type: discovery; next available surface number). Add 3 unit tests: endpoint returns 200 with an array, each entry has required fields, archived simulations are excluded from the response.

3. Add a `GET /demo` frontend route rendering a `/demo` page (`DemoGallery.vue`). The page: dark-themed grid of demo simulation cards (4 per row on desktop, 2 on tablet, 1 on mobile). Each card: topic text, direction badge (green/red/gray for bullish/bearish/neutral), confidence percentage bar, use-case category chip, "View Simulation →" link to the share page, and the tutorial angle as a subtitle. Page header: "Explore What MiroShark Can Do — 10 pre-run simulations, ready to reference." Footer CTA: "Ready to run your own? Try it for under $1 →" linking to the homepage. Add `/demo` to the frontend router. ### 2. CLI Shell Completion Scripts

**Type:** DX improvement
**Effort:** Small (hours)
**Impact:** The `miro` CLI is the primary interface for developers who self-host MiroShark, yet it has no shell autocompletion. Every professional CLI tool publishes completion scripts: `gh completion`, `docker completion`, `kubectl completion`. The absence of completion is a signal of immaturity to developers evaluating the tool. For the tutorial hyperstition (Aug 15, 9 days), the single most common CLI tutorial format is a terminal recording with tab-completion showing the full command surface — the viewer sees `miro sim<TAB>` complete to `miro simulate`, then `--to<TAB>` complete to `--topic`. Without completion, recordings look rough and commands get mistyped. Completion scripts are a 100-line feature with zero new dependencies that makes every subsequent tutorial look polished. Also serves the 298 fork holders who are building integrations and want to discover CLI flags without reading docs.

**How:**
1. Add a `completion` subcommand to the `miro` CLI entry point (wherever `cli/__main__.py` or equivalent lives). `miro completion bash` outputs a bash completion script to stdout. `miro completion zsh` outputs a zsh completion script. `miro completion fish` outputs a fish completion script. Each script covers: (a) all top-level subcommands (`simulate`, `completion`, `version`, and any others defined in the CLI); (b) for `miro simulate`: `--topic` (takes string), `--agents` (takes integer), `--rounds` (takes integer), `--platforms` (takes comma-separated list from a fixed set: `twitter,reddit,prediction_market,discord,telegram,weibo,tiktok` — enumerate these), `--output` (takes `json|markdown|csv`), `--watch` (flag), `--publish` (flag), `--quiet` (flag); (c) for `miro completion`: `bash`, `zsh`, `fish` as completions. The bash script uses `_miro_completions()` registered with `complete -F _miro_completions miro`. The zsh script uses `#compdef miro` with `_arguments` and `_values`. The fish script uses `complete -c miro` blocks with `-s`/`-l`/`-d` for short/long/description. Each script is generated statically (not dynamically from the CLI parser) — simpler and more portable. Approximately 30 lines per script.

2. Add `docs/SHELL_COMPLETION.md` (~60 lines). Installation instructions for each shell: bash (`miro completion bash >> ~/.bash_completion` or `miro completion bash > /etc/bash_completion.d/miro` on Linux), zsh (`miro completion zsh > "${fpath[1]}/_miro"` with a note to ensure `autoload -U compinit && compinit` is in `~/.zshrc`), fish (`miro completion fish > ~/.config/fish/completions/miro.fish`). Each section includes the one-liner command and a note on where to reload the shell config. Add a CI test that runs `miro completion bash | bash -n` (syntax check the bash output), `miro completion zsh | zsh -n`, and `miro completion fish --silent` (fish has a `--silent` linter mode). Add to `docs/CLI.md`: a "Shell Completion" section near the top, before the subcommand reference, with a one-liner pointing to `docs/SHELL_COMPLETION.md`. Add `miro completion zsh > ~/.zsh/_miro` as a line in the `CONTRIBUTING.md` setup checklist (after the install step) — makes completions standard for all contributors from first setup.

3. Add 4 unit tests: `miro completion bash` exits 0 and prints a non-empty string containing `_miro_completions`, `miro completion zsh` exits 0 and contains `#compdef miro`, `miro completion fish` exits 0 and contains `complete -c miro`, `miro completion invalid-shell` exits 1 with a helpful error message listing supported shells. Update `README.md` Quickstart to include `miro completion zsh > ~/.zsh/_miro` as an optional but recommended step. Add a "tab completion demo" note to `docs/DEMO_SIMULATIONS.md` (the library from idea #1): "Run `miro completion bash | bash` to enable tab completion before recording your terminal demo."

Apostrophes use U+2019 RIGHT SINGLE QUOTATION MARK for Dutch contractions (`'s`, `'n`) but U+0027 in JSON string values for machine safety. File structure mirrors `locales/fr.js` exactly. ### 5. Operator Metrics Endpoint

**Type:** Feature / DX improvement
**Effort:** Small (hours)
**Impact:** Self-hosted MiroShark operators — the 298 fork holders — have no way to understand how their instance is being used without reading raw logs. How many simulations has it run? What's the total cost incurred? Which platform gets used most? What's the average agent count? These are the first questions any operator asks after a week of production use. An auth-gated `GET /api/metrics` endpoint returning aggregate instance statistics makes MiroShark observable for operators without a dedicated monitoring stack. It also enables a lightweight admin UI: a single HTML page that fetches the endpoint and renders the stats as a table — no backend changes needed beyond the endpoint itself. The stats surface the story of the instance: an operator who has run 47 simulations at an average of $0.23 each knows exactly what they've committed to and what their next 100 simulations will cost. This is particularly valuable for the 11 ecosystem project operators (AntFleet bench, Capacitr integration) who need usage stats to justify infrastructure spend.

**How:**
1. Create `backend/app/api/metrics.py` (~120 LoC, pure stdlib). `GET /api/metrics`. Auth: reads `METRICS_TOKEN` from environment; if set, requires `Authorization: Bearer {METRICS_TOKEN}` header (returns 401 without it). If `METRICS_TOKEN` is not set, the endpoint is unreachable (returns 404 — not a 401, to avoid advertising the existence of the endpoint to unauthenticated callers). Computation: scans the simulation storage directory for all simulation directories (same path logic used by the search service). For each simulation, reads `signal.json` (if it exists) to extract: `direction`, `confidence_pct`, `cost_usd`, `agents`, `rounds`, `platforms` (list), `completed_at`. Builds the aggregate: `{total_simulations: int, published_simulations: int, total_cost_usd: float (sum of all cost_usd), avg_cost_usd: float, total_agents_spawned: int (sum of all agents × rounds — approximation), avg_agents_per_sim: float, avg_rounds_per_sim: float, avg_confidence_pct: float, direction_distribution: {bullish: int, bearish: int, neutral: int}, platform_usage: {twitter: int, reddit: int, ...} (count of simulations using each platform), most_active_day: str (YYYY-MM-DD of the date with the most completed_at timestamps), first_simulation_at: str (ISO 8601 of the earliest completed_at), last_simulation_at: str (ISO 8601 of the most recent completed_at), instance_uptime_days: int (days since first_simulation_at)}`. Mtime-cache the result to `metrics.json` for 1 hour (hourly precision is sufficient for operator dashboards). `Cache-Control: private, max-age=3600` (private because auth-gated). Add `METRICS_TOKEN` to `.env.example` with a comment: "# Set to any secret string to enable GET /api/metrics — leave empty to disable." Register route in the main app router. Add to `surfaces_catalog.py` (type: admin).

2. Add `docs/OPERATOR_GUIDE.md` (~80 lines, create if it doesn't exist; add a section if it does). Section: "Instance Metrics". Content: set `METRICS_TOKEN` in `.env`, run `curl -H "Authorization: Bearer {token}" https://your-instance/api/metrics | jq '.'`, description of each field, example output (a realistic JSON blob with plausible values). Add a "metrics dashboard" stub: a `scripts/metrics-dashboard.sh` (~20 lines) that fetches `GET /api/metrics`, parses the JSON with `jq`, and prints a formatted summary to the terminal — the `uptime_days`, `total_simulations`, `total_cost_usd`, `direction_distribution`, and `most_active_day`. This is the simplest possible "admin dashboard" that requires nothing but `curl` and `jq`. Include it in the operator guide as a "quick health check" script.

3. Add 5 unit tests: endpoint returns 404 when `METRICS_TOKEN` is not set, returns 401 with wrong token, returns 200 with correct token, response JSON contains all required fields, `total_cost_usd` equals the sum of individual `cost_usd` values across test simulations. Add `GET /api/metrics` to `docs/API.md` in a new "Operator" section at the bottom (after the Ecosystem section), noting the auth requirement and linking to `docs/OPERATOR_GUIDE.md`. Add a mention in `CONTRIBUTING.md`: "When running the dev server, set `METRICS_TOKEN=dev` in `.env` to access aggregate usage stats at `GET /api/metrics`." This makes the endpoint discoverable for contributor-operators during local development.
