### 1. Pre-Built Scenario Template Gallery

**Type:** Feature
**Effort:** Small (hours)
**Impact:** The biggest drop-off for first-time self-hosters is the blank Step 1 screen — "what topic should I simulate?" A library of 10–15 ready-to-run templates (Fed rate decision, crypto token launch, product announcement, geopolitical event, earnings beat/miss) reduces time-to-first-result from minutes of setup to a single click. Templates live in `backend/templates/` as JSON; a `GET /api/templates` endpoint lists them; a new "Templates" tab on Step 1 populates all setup fields from the chosen template. No new execution path — template data is applied client-side before the existing `POST /api/simulation` call. Pure acquisition improvement: a user who sees a working simulation in 90 seconds becomes a repeat user; one who stares at a blank form may not.

**How:**
1. Create `backend/templates/` with 12 JSON files. Each file follows the schema: `{"id": str, "title": str, "description": str (1 sentence), "topic": str, "agent_count": int, "round_count": int, "platforms": [str], "direction_hint": str|null, "tags": [str]}`. Cover the categories: macro-financial (3), crypto (3), product/tech (3), geopolitical (2), sports/culture (1). Add `GET /api/templates` to `backend/app/api/` — reads all JSON files from the templates directory, returns a list sorted by `title`. Cache-Control: `max-age=3600` (templates rarely change). Add to `surfaces_catalog.py` (type: `discovery`) and OpenAPI with `TemplateEntry` schema. Add 4 unit tests: all template files pass JSON schema validation; `GET /api/templates` returns 12 entries; `direction_hint` is null or one of `["BULLISH", "BEARISH", "NEUTRAL"]`; all `platform` values are from the known platform list.
2. Add a "Templates" button to Step 1 (`Step1Input.vue` or equivalent setup form). Clicking it opens a modal grid: templates displayed as cards (title, description, tag chips). Clicking a template populates the Step 1 form fields (topic, agent_count, round_count, platform toggles) and closes the modal — the user can tweak before running. Add a search/filter input to the modal that filters by `tags`. No network call until the modal opens (lazy-load via `GET /api/templates`). Add 2 frontend unit tests: clicking a template card populates the `topic` field in the parent form; filter input hides non-matching cards.
3. Add a `make add-template` convenience target (or a `scripts/add-template.sh NAME` helper) that scaffolds a new template JSON with all required fields as empty stubs, then opens it in `$EDITOR`. Document in `docs/INSTALL.md` under "Extending MiroShark" (one paragraph). This makes the template library forkable and community-extensible without requiring backend knowledge. Add the templates directory to `docs/FEATURES.md` feature list under "Simulation Setup."

### 2. Agent Quote Deeplink

**Type:** Feature
**Effort:** Small (hours)
**Impact:** The agent bio card (proposed Oct 20) surfaces aggregate statistics per agent. But researchers, journalists, and X/Twitter power users want to cite a *specific* statement — "Agent 'Maya Chen, ESG analyst' posted in round 4: 'The Fed's pivot timing looks miscalibrated — I'm flipping bearish.'" Right now that's only accessible by parsing raw `actions.jsonl`. `GET /api/simulation/:id/quote?agent=NAME&round=N` returns the agent's post text at that round, their stance at that moment, and a `deeplink_url` that opens the simulation UI with the agent pre-selected and the round indicator set to N. The deeplink format is `https://miroshark.xyz/sim/{id}?agent={name}&round={N}`. No new data stored — pure indexing of existing `actions.jsonl`. The practical output: tweet-sized citations from swarm intelligence runs, attributable to a specific persona and moment in time.

**How:**
1. Create `backend/app/services/quote_service.py` (~80 LoC, pure stdlib). Accept `simulation_id`, `agent_name`, `round_n`. Load `actions.jsonl` filtering by agent (case-insensitive) and round. Return the post with the highest `influence_at_round` (or simply the most recent post in that round if `influence_at_round` isn't stored). Alongside the post text, include: `agent_name`, `round`, `stance` (from trajectory.json at that round), `platform`, `simulation_topic` (from signal.json), `deeplink_url` (constructed from a configurable `BASE_URL` env var). If the agent posted multiple times in one round, return all posts. If the agent posted nothing in that round, return `{"posts": [], "note": "agent posted nothing in this round"}` — not a 404. Add 4 unit tests: returns the correct post for agent+round; empty result when agent posted nothing in the round; `deeplink_url` contains simulation ID and agent name; agent name match is case-insensitive.
2. Add `GET /api/simulation/:id/quote` to `backend/app/api/simulation.py`. Query params: `agent` (required), `round` (required, int ≥ 1). Publish-gated (same ownership check as other per-sim endpoints). Return 400 if either param missing, 404 if sim not found. Response: `{"simulation_id": str, "agent_name": str, "round": int, "posts": [{"text": str, "platform": str, "stance": str}], "deeplink_url": str, "simulation_topic": str, "generated_at": ISO8601}`. Cache-Control: `max-age=3600` (post text is immutable once the simulation completes). Add to `surfaces_catalog.py` (type: `analytics`) and OpenAPI with `QuoteResponse` schema. Document in `docs/API.md` under "Agent Analytics" with a curl example. Add 2 integration tests: valid agent+round returns 200; missing `agent` param returns 400.
3. Add a "Copy Quote Link" button to each agent row in the stance-shift panel and the mentions matrix (both already render per-agent data). Clicking it calls `GET /api/simulation/:id/quote?agent={name}&round={current_replay_round_or_last_round}`, then copies the `deeplink_url` to clipboard and shows a "Copied!" toast for 2 seconds. If no replay scrubber is active, defaults to the agent's most-opinionated round (the round with the largest single-step belief change, already computable from `trajectory.json`). Add 1 frontend unit test: clicking "Copy Quote Link" calls the quote endpoint and invokes `navigator.clipboard.writeText` with the returned `deeplink_url`.

### 3. Stuck Simulation Recovery Endpoint

**Type:** DX
**Effort:** Small (hours)
**Impact:** PR #326 (`fix(simulation): make resume work on existing DBs and keep progress on failure`) landed because simulations were getting stuck in `running` state after failures. The fix improved recovery *during* a run, but simulations that were already stuck before the fix — or that fail in edge cases the fix doesn't cover — still show up as `running` indefinitely in self-hosted deployments. `POST /api/admin/simulation/:id/recover` inspects the simulation's state, detects whether it is genuinely running (by checking process state) or orphaned, and if orphaned: sets the status to `failed`, generates a partial report from whatever round data exists, and returns the partial results to the caller. Admin-token gated (`ADMIN_TOKEN` env var, same pattern as other admin endpoints if they exist). Provides operators a break-glass tool without requiring database access or server restarts.

**How:**
1. Create `backend/app/services/recovery_service.py` (~100 LoC, pure stdlib). Accept `simulation_id`. Check the simulation's `status` field — if not `running` or `pending`, return early with `{"status": "not_stuck", "current_status": str}`. Check whether a live process owns the simulation: look for a `.lock` file or PID file in the simulation directory (if the codebase uses one); if no lock mechanism exists, use `last_heartbeat_ts` from the simulation metadata (any sim with `status: running` and no heartbeat update in >15 minutes is treated as orphaned). If orphaned: set `status: "failed"`, write `failed_at: now()`, write `failure_reason: "recovered_from_orphan_state"`. If partial round data exists in `trajectory.json` (any rounds completed), call the existing report generation service with a `partial=True` flag to produce a truncated report. Return `{"recovered": bool, "rounds_completed": int, "partial_report_available": bool}`. Add 5 unit tests: non-stuck sim returns `not_stuck`; orphaned sim (stale heartbeat) is marked failed; orphaned sim with trajectory data triggers partial report; recovery is idempotent (calling twice is safe); `ADMIN_TOKEN` mismatch returns 403.
2. Add `POST /api/admin/simulation/:id/recover` to a new `backend/app/api/admin.py` module. Auth: read `Authorization: Bearer {token}` header, compare against `ADMIN_TOKEN` env var (constant-time comparison via `hmac.compare_digest`). Return 403 if unset or mismatched. Return 404 if sim not found. Return 200 with the recovery result JSON. Register the router in `main.py` under `/api/admin`. Add `ADMIN_TOKEN` to `.env.example` (with comment: "Admin API token for management endpoints — generate with: openssl rand -hex 32"). Add 2 integration tests: valid token + orphaned sim returns 200 with `recovered: true`; invalid token returns 403.
3. Add a `POST /api/admin/cleanup` bulk companion (10 LoC, same auth). Query all simulations with `status: running` and last heartbeat >15 minutes ago; call `recovery_service.recover(sim_id)` for each; return `{"recovered_count": int, "simulation_ids": [str]}`. Add a cron-friendly flag `?dry_run=true` that returns the list of simulations that *would* be recovered without actually changing state. Document both endpoints in `docs/API.md` under a new "Admin" section. Add 1 unit test: dry-run returns the same simulation IDs as a real run without modifying any state.

### 4. Cost Cap Guard

**Type:** Feature
**Effort:** Small (hours)
**Impact:** The pre-run estimator (built Jun 20) gives a cost prediction before launch. But there's no enforcement mechanism — a simulation can run 10× over the estimate if the LLM provider charges unexpected token overages or if the agent count/round count interaction produces more posts than projected. A `max_cost_usd` field in the simulation creation request gives callers a hard ceiling: before each round begins, the backend checks cumulative cost against the cap; if the next round would exceed it, the simulation concludes at the current round with `completed_at_budget_cap: true` and the report is generated from partial data. This is the right primitive for self-hosted shared instances (team budget enforcement), API integrations (cost-controlled batch runs), and the hosted product (future pricing tier enforcement). Builds on the existing per-round cost tracking — no new accounting logic needed, just a check gate.

**How:**
1. Add `max_cost_usd: float | null` to the simulation creation schema in `backend/app/api/simulation.py` (nullable, default null = no cap). Validate: must be positive if provided; maximum allowed value is `100.0` (to prevent accidental `0.000001` caps that kill every simulation). Store in the simulation's config/metadata. Add 2 unit tests: `max_cost_usd=0` returns 400; `max_cost_usd=101.0` returns 400.
2. In the simulation execution loop (wherever rounds are ticked — likely `backend/app/simulation/` or the runner service), add a pre-round cost check: `if max_cost_usd is not None and cumulative_cost_usd >= max_cost_usd * 0.95: conclude_simulation(reason="budget_cap_reached")`. Use 95% of the cap as the trigger (not 100%) to leave headroom for the current round's cost accumulation before the gate runs. On conclusion, set `status: "completed"`, `completed_at_budget_cap: true`, `final_cost_usd: cumulative_cost_usd` in the simulation metadata, then proceed to the normal report generation path. The partial report is valid — treat rounds-completed-so-far as the full dataset. Add 3 unit tests: simulation with 1-round cost above cap concludes after round 1; simulation with cap above projected total cost runs to completion normally; `completed_at_budget_cap` field is `false` when cap is not hit.
3. Surface `completed_at_budget_cap` in the Step 3 UI: if `true`, show a muted amber banner below the simulation header: "Simulation concluded at budget cap ($N.NN). Results reflect N of M estimated rounds." — amber to distinguish from success (no banner) and failure (red). Include the cap value and rounds completed. Also surface it in `GET /api/simulation/:id/signal` as a top-level `budget_cap_reached: bool` field (alongside existing `direction`, `confidence_pct`). Add to `docs/API.md` under "Simulation Creation" with a note on the 95% trigger threshold. Add 1 frontend unit test: `completed_at_budget_cap: true` renders the amber banner with the correct dollar amount.

### 5. Simulation Gallery RSS Feed

**Type:** Growth
**Effort:** Small (hours)
**Impact:** The activity feed (`GET /api/activity.json`) is the only machine-readable discovery surface for completed simulations today, and it requires custom polling code. A standard RSS 2.0 feed at `GET /api/gallery/feed.xml` makes the simulation gallery subscribable with zero integration effort: RSS readers (Feedly, NetNewsWire, NewsBlur), automation tools (Zapier, n8n, Make), and content aggregators can subscribe without code. Every completed public simulation becomes a feed item: topic as title, direction + confidence as description, share URL as link. No new data sources — pure re-serialization of `activity.json` content into RSS XML. The distribution surface grows passively: anyone who subscribes gets new simulations in their reader, perpetually, with no ongoing effort from the operator.

**How:**
1. Create `backend/app/api/feed.py` (~60 LoC). `GET /api/gallery/feed.xml`: read the top 20 items from the activity feed service (re-use `activity_feed_service.get_recent(limit=20)`). For each, build an RSS `<item>`: `<title>` = simulation topic, `<description>` = `"{direction} · {confidence_pct}% confidence · {agent_count} agents · {round_count} rounds"`, `<link>` = share URL (construct from `BASE_URL` + `/sim/{id}`), `<pubDate>` = RFC 822 formatted `published_at`, `<guid isPermaLink="true">` = share URL. Wrap in a standard RSS 2.0 channel with `<title>MiroShark Simulations</title>`, `<description>Recent public simulations from MiroShark</description>`, `<link>{BASE_URL}/gallery</link>`, `<lastBuildDate>` = most recent item's `pubDate`. Set `Content-Type: application/rss+xml; charset=utf-8`. Cache-Control: `max-age=300`. Add to `surfaces_catalog.py` (type: `discovery`) and OpenAPI (note: response is XML, not JSON — document separately). Add 4 unit tests: response Content-Type is `application/rss+xml`; each item has non-empty `title`, `link`, and `pubDate`; `guid` matches `link`; feed contains at most 20 items even when more are available.
2. Add `<link rel="alternate" type="application/rss+xml" title="MiroShark Simulations" href="/api/gallery/feed.xml">` to the HTML `<head>` of the frontend's `index.html` — this enables browser auto-discovery of the feed (the RSS icon appears in some browsers and reader extensions automatically). Add a small RSS subscribe button (the standard orange RSS icon SVG, 16×16) to the gallery page header, linking to `/api/gallery/feed.xml`. Register the feed router in `main.py` under `/api/gallery`. Add to `docs/API.md` under a new "Feeds" section (3 lines: URL, format, update frequency). Add 1 frontend unit test: RSS link tag is present in `document.head` with correct `href`.
3. Add an Atom feed companion `GET /api/gallery/feed.atom` (15 LoC, same data, Atom 1.0 format: `<feed xmlns="http://www.w3.org/2005/Atom">`, `<entry>` instead of `<item>`, `<updated>` instead of `<pubDate>`, `<id>` instead of `<guid>`). Atom is preferred by some feed readers and required by some aggregators that reject RSS 2.0. Reuse the same channel metadata and item data — only the serialization differs. Document both feed URLs in `docs/API.md`. Add 2 unit tests: Atom response Content-Type is `application/atom+xml`; each `<entry>` contains `<id>`, `<title>`, and `<updated>` elements.
