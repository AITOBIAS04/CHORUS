### 1. Python SDK (`miroshark-client`)

**Type:** Integration / Growth
**Effort:** Medium (1-2 days)
**Impact:** MiroShark has 42+ documented API surfaces but no programmatic client — every integration starts from scratch reading `docs/API.md`. A pip-installable `miroshark-client` SDK wrapping the 5 most-used endpoints (`POST /api/simulate`, `GET /api/simulation/{id}/signal`, `GET /api/simulation/{id}/trajectory`, `GET /api/simulation/search`, `GET /api/taxonomy`) makes MiroShark callable in 3 lines of Python. The package itself is the mechanism that clears the "non-fork dependent repo" hyperstition: a PyPI-hosted package is by definition a non-fork downstream repository. A well-structured PyPI package also earns Google discoverability via the package index and opens a second inbound channel beyond GitHub stars. Distinct from the GitHub Actions Example (older ideas, workflow file only) and n8n integration (Aug 30 Hacktoberfest issue #5, single JSON workflow) — this is a reusable library for any Python environment.

**How:**
1. Create `sdk/python/` in the MiroShark repository. Structure: `miroshark_client/__init__.py`, `miroshark_client/client.py` (~120 LoC), `miroshark_client/models.py` (~60 LoC), `pyproject.toml`, `README.md`. The client class: `MiroSharkClient(base_url: str, api_key: str = None)`. Methods: `simulate(topic: str, agents: int = 50, rounds: int = 5, platforms: list[str] = None) -> SimulationResult` — posts to `POST /api/simulate`, polls `GET /api/simulation/{id}/signal` every 10s until complete or 10-minute timeout; `get_signal(simulation_id: str) -> Signal`; `get_trajectory(simulation_id: str) -> Trajectory`; `search(query: str, limit: int = 10) -> list[SearchResult]`; `get_taxonomy() -> Taxonomy`. All models are typed dataclasses (no Pydantic, pure stdlib + dataclasses). The `simulate()` method is the main entry point — it handles the full run-to-result cycle in one call. Error handling: raises `MiroSharkAPIError(status_code, message)` on non-2xx responses. Connection timeout defaults: 30s per request, 600s polling ceiling. Add `pyproject.toml` with `[project]` metadata: `name = "miroshark-client"`, `version = "0.1.0"`, `description = "Python client for the MiroShark simulation API"`, `python_requires = ">=3.9"`, no non-stdlib dependencies. ### 2. Simulation Calibration Ledger

**Type:** Feature / Research
**Effort:** Small (hours)
**Impact:** MiroShark currently has no mechanism to record whether a simulation's prediction came true. `POST /api/simulation/{id}/resolve` lets an operator mark a completed simulation as resolved (correct or incorrect), and `GET /api/calibration` aggregates all resolved simulations into a public accuracy ledger: overall accuracy by direction type (BULLISH/BEARISH/NEUTRAL), accuracy by domain (Finance: 71%, Policy: 58%, Technology: 63%), and a running Brier score. For the paper citation hyperstition (Sep 30, 8 days): a researcher who can write "MiroShark's BULLISH predictions were accurate in 73% of resolved simulations" has a quantitative finding worth citing. This is distinct from the Ground-Truth Accuracy Score (older list, which was a single-simulation score) — the Calibration Ledger is a cross-simulation accuracy track record visible to the public. No LLM calls, no external data — operators supply the ground truth via the `resolve` endpoint.

**How:**
1. Create `backend/app/api/calibration.py` (~100 LoC, pure stdlib). Two endpoints: **`POST /api/simulation/{id}/resolve`** — operator-authenticated (requires `X-API-Key` header matching `OPERATOR_API_KEY` env var; if unset, requires operator session). Accepts `{"outcome_correct": bool, "ground_truth_direction": "BULLISH"|"BEARISH"|"NEUTRAL", "resolution_note": str (optional, max 280 chars), "resolved_at": ISO8601 (defaults to now)}`. Validates that the simulation exists and is published. Writes `resolved.json` to the simulation directory: `{"simulation_id": id, "topic": str, "predicted_direction": str, "predicted_confidence": float, "outcome_correct": bool, "ground_truth_direction": str, "resolution_note": str, "resolved_at": ISO8601}`. Returns 200 with the written record. On second call: updates the existing `resolved.json` (idempotent). **`GET /api/calibration`** — public, no auth. Scans all simulation directories for `resolved.json` files. Aggregates: `{"total_resolved": int, "total_correct": int, "overall_accuracy": float, "brier_score": float, "by_direction": {"BULLISH": {"count": int, "correct": int, "accuracy": float}, ...}, "by_domain": {"Finance": {"count": int, "correct": int, "accuracy": float}, ...}, "recent_resolutions": [{"simulation_id": str, "topic": str, "predicted_direction": str, "outcome_correct": bool, "resolved_at": ISO8601}] (last 10), "generated_at": ISO8601}`. Domain classification uses the same 7-category keyword pattern as Taxonomy (if built) or a simplified version. Brier score: `(1/N) * Σ(confidence_pct/100 - outcome_correct)²` — measures calibration of confidence alongside direction. `Cache-Control: public, max-age=300`. Register both endpoints. Add to `surfaces_catalog.py`. Update `docs/API.md` with a "Calibration" section.

2. Add a "Resolved" indicator to the simulation result share page (`Step3Simulation.vue`). When `resolved.json` exists for a simulation: show a `✓ Resolved` chip in the result header (green if `outcome_correct: true`; red if false). On hover/click: show the `resolution_note` and `ground_truth_direction` in a tooltip. If not resolved: no chip, no indicator. Add bilingual labels (EN/ZH-CN). Also add a `GET /api/calibration` stats block to the main landing page or dashboard — a "Track Record" widget showing `overall_accuracy`, `total_resolved`, and `brier_score` in three stat tiles. One integration test: `POST /api/simulation/{id}/resolve` writes `resolved.json`, and the subsequent `GET /api/calibration` response includes the simulation in `recent_resolutions`.

3. Add 4 unit tests: `POST /api/simulation/{id}/resolve` with valid payload returns 200 and writes `resolved.json`; `POST` on a non-existent simulation returns 404; `GET /api/calibration` with 3 resolved simulations (2 correct, 1 incorrect) returns `overall_accuracy = 0.67`; `GET /api/calibration` with no resolved simulations returns `total_resolved = 0`, `overall_accuracy = null`. Log to memory: "Simulation Calibration Ledger created 2026-09-22. `POST /api/simulation/{id}/resolve` (operator-auth) — writes resolved.json: predicted direction vs. ground truth, outcome_correct bool, resolution_note, resolved_at. `GET /api/calibration` — scans all resolved.json files, computes overall_accuracy, Brier score, accuracy by direction and domain, last 10 resolutions. Step3: '✓ Resolved' chip. Dashboard: 'Track Record' stat tiles. Paper citation hook: 'MiroShark BULLISH predictions accurate in X% of N resolved simulations (Brier score Y).'"

### 4. Agent Population Pressure Gauge

**Type:** Feature
**Effort:** Small (hours)
**Impact:** The analytical stack for a single simulation now covers: what happened (signal.json, direction + confidence), when consensus formed (Time-to-Consensus, Aug 26), and how contested the path was (Swarm Diversity Index, Aug 30). One question remains unanswered: *what drove the consensus*? Was it early leaders who locked in direction by round 1 and the rest followed (convergence pressure)? Or did the swarm reverse course in the final rounds (reversal pressure)? `GET /api/simulation/{id}/pressure` computes stance-change velocity in early rounds (1–2) vs. late rounds (final 2) from trajectory.json and returns a `pressure_type`: **"immediate_consensus"** (direction fixed by round 1, < 5% shift throughout), **"convergence"** (high early volatility, stabilizes by final rounds — classic herd effect), **"reversal"** (low early volatility, large late shift — momentum change), **"sustained_debate"** (high volatility throughout). Pure trajectory.json computation, no LLM calls. Completes the analytical four-pillar framework: What / When / How contested / What drove it. For the paper citation hyperstition (Sep 30, 8 days): a researcher who can characterize each simulation's dynamics along all four dimensions has a quantitative typology of swarm deliberation worth submitting.

**How:**
1. Create `backend/app/api/pressure.py` (~90 LoC, pure stdlib). `GET /api/simulation/{id}/pressure`. Publish-gated. Reads `trajectory.json`. If absent, returns 404. Algorithm: (1) For each round, compute `stance_change = |bullish_pct[r] - bullish_pct[r-1]| + |bearish_pct[r] - bearish_pct[r-1]|` (total absolute percentage shift from the prior round). (2) Compute `early_volatility = mean(stance_change for rounds 1..min(2, total_rounds-1))`. (3) Compute `late_volatility = mean(stance_change for rounds (total_rounds-2)..total_rounds-1)`. (4) Compute `total_range = max(bullish_pct across all rounds) - min(bullish_pct across all rounds)` — overall swing. (5) Classify: if `total_range < 10` → "immediate_consensus" (barely moved); elif `early_volatility > late_volatility * 1.5` → "convergence" (volatile early, settles late); elif `late_volatility > early_volatility * 1.5` → "reversal" (surges late); else → "sustained_debate". (6) Compute `pressure_intensity`: 0–100 scale, `min(100, int((max(early_volatility, late_volatility) / 50) * 100))` — how strong the dominant pressure phase was. Response: `{"simulation_id": id, "topic": str, "direction": str, "total_rounds": int, "pressure_type": "immediate_consensus"|"convergence"|"reversal"|"sustained_debate", "pressure_intensity": int, "early_volatility": float, "late_volatility": float, "total_range": float, "pressure_note": str}`. The `pressure_note` is a one-line plain-English explanation: e.g. `"convergence"` → "Agents debated actively in early rounds before converging on {direction} consensus by round {N}."; `"reversal"` → "Late-round momentum shift flipped the swarm toward {direction} after initial {alt_direction} lean."; `"immediate_consensus"` → "The swarm locked onto {direction} from round 1 with minimal dissent."; `"sustained_debate"` → "Agents maintained active disagreement throughout all {N} rounds." `Cache-Control: public, max-age=3600`. Register at `GET /api/simulation/{id}/pressure`. Add to `surfaces_catalog.py`. Update `docs/API.md` with a "Simulation Analytics" section grouping the four pillars: signal (result), time-to-consensus (timing), diversity (contestedness), pressure (driver).

2. Add a "⚡ Pressure" toolbar button to the Step 3 simulation share page (`Step3Simulation.vue`). Panel layout: (1) A large `pressure_type` badge at the top — color-coded: immediate_consensus: gray; convergence: green; reversal: amber; sustained_debate: red. (2) A "Pressure Intensity" bar — horizontal bar 0–100, filled to `pressure_intensity`, label below. (3) A two-column stat row: "Early volatility: {early_volatility:.1f}pp/round" | "Late volatility: {late_volatility:.1f}pp/round". (4) The `pressure_note` in muted italic text. (5) A one-line "analytics context" label (only visible if the simulation also has diversity data): "Diversity: {classification} · Pressure: {pressure_type}" — the combined two-word characterization. Add bilingual labels (EN/ZH-CN). Add one integration test: "⚡ Pressure" toolbar button fetches `GET /api/simulation/{id}/pressure` and renders the `pressure_type` badge. Also surface `pressure_type` and `pressure_note` in the EmbedDialog metadata section.

3. Add 5 unit tests: published simulation returns 200 with `pressure_type` as one of the four valid strings; `pressure_intensity` is an integer in [0, 100]; `early_volatility` and `late_volatility` are floats ≥ 0; a trajectory where all rounds have the same direction percentages returns `pressure_type == "immediate_consensus"`; unpublished simulation returns 404. Log to memory: "Agent Population Pressure Gauge created 2026-09-22. `GET /api/simulation/{id}/pressure` — computes stance-change velocity per round from trajectory.json. early_volatility = mean of per-round abs shifts in rounds 1-2; late_volatility = mean in final 2 rounds. Classifications: immediate_consensus (total_range < 10pp), convergence (early > late × 1.5), reversal (late > early × 1.5), sustained_debate (else). pressure_intensity 0-100. pressure_note: plain-English one-liner. Step3: '⚡ Pressure' panel with type badge + intensity bar + stat row. Fourth analytical pillar: What / When / How contested / What drove it."

### 5. Simulation Leaderboard

**Type:** Feature / Community
**Effort:** Small (hours)

A public leaderboard makes the archive feel alive and competitive, surfacing which simulations generated the most debate, which resolved fastest, and which produced the highest-confidence results. `GET /api/leaderboard` returns 5 ranked lists from the published simulation archive: most-contested (highest diversity index, when built), fastest-to-consensus, highest-confidence, most-polarized, and most-recent-resolved (from calibration data). The `/leaderboard` page is a shareable URL — each row is a simulation that links to its full result page. Distinct from the Trending Simulations Feed (Aug 22, recency-sorted only) and Taxonomy Browser (Aug 30, domain classification, no ranking) — this is a multi-dimensional hall-of-records for the simulation archive. For Hacktoberfest (Oct 1): leaderboard entries are link-worthy targets for community showcase posts.

**How:**
1. Create `backend/app/api/leaderboard.py` (~110 LoC, pure stdlib). `GET /api/leaderboard`. Public, no auth. Scans all published simulation directories. For each, reads: `signal.json` (direction, confidence_pct, topic), `trajectory.json` (if present: rounds, per-round diversity), `resolved.json` (if present: outcome_correct, resolved_at), `created_at` from the directory's simulation config JSON. Computes and returns 5 ranked lists (max 10 entries each): (1) **`highest_confidence`** — top 10 by `confidence_pct` desc; each entry: `{simulation_id, topic, direction, confidence_pct, created_at}`; (2) **`most_contested`** — top 10 by avg diversity index (computed from trajectory per-round D, same formula as Swarm Diversity Index if built, else use `(bullish_pct/100)^2 + ...` directly from trajectory); if trajectory absent, skip; each entry: `{simulation_id, topic, direction, avg_diversity, total_rounds}`; (3) **`fastest_consensus`** — top 10 by fewest rounds to reach ≥ 60% majority (BULLISH or BEARISH ≥ 60); if no round reaches 60%, use total rounds; each entry: `{simulation_id, topic, direction, consensus_round, total_rounds}`; (4) **`most_polarized`** — top 10 by highest per-round polarization (max bullish_pct that is also NOT above 85%, i.e., contested but leaning — the swarm split without full consensus); each entry: `{simulation_id, topic, direction, peak_split_pct, total_rounds}`; (5) **`recently_resolved`** — top 10 most recently resolved simulations from `resolved.json` files, sorted by `resolved_at` desc; each entry: `{simulation_id, topic, predicted_direction, outcome_correct, resolved_at}`. Response: `{"leaderboard": {"highest_confidence": [...], "most_contested": [...], "fastest_consensus": [...], "most_polarized": [...], "recently_resolved": [...]}, "total_published": int, "generated_at": ISO8601}`. `Cache-Control: public, max-age=600`. Register at `GET /api/leaderboard`. Add to `surfaces_catalog.py`. Update `docs/API.md` with a "Leaderboard" section. Update `frontend/src/router/index.js` with a `/leaderboard` route.

(2) Five collapsible sections — one per ranked list, each with a title (`Most Confident`, `Most Contested`, `Fastest Consensus`, `Most Polarized`, `Recently Resolved`), all expanded by default. (3) Each section is a ranked table: gold/silver/bronze badge for positions 1–3, simulation topic (truncated at 60 chars with ellipsis), the key metric for that section (confidence_pct, avg_diversity, consensus_round, peak_split_pct, or resolved outcome chip), direction badge (BULLISH/BEARISH/NEUTRAL), and a "View →" link to `/sim/{simulation_id}`. (4) Mobile: stack the sections vertically (not tabs). Add a `Leaderboard` link to the main nav (the header nav bar already has tabs — add "Leaderboard" alongside existing nav items). Bilingual labels (EN/ZH-CN) for all section headers and column names following existing i18n patterns. One integration test: `/leaderboard` page renders at least one non-empty ranked list when published simulations exist.

## Selection Rationale

Five ideas targeting SDK distribution (direct mechanism for clearing the non-fork dependent repo line), calibration tracking (paper citation hook, 8 days out), LLM ecosystem integration (zero-maintenance discoverability via tool schema), analytical depth (pressure gauge completing the four-pillar framework), and archive showcasing (leaderboard differentiates the simulation archive from raw API data).

- **Python SDK (#1)** — PyPI package is the only idea that creates a non-fork downstream repository without requiring human community action. Medium effort but high structural value. The "Use from AI" README badge + SDK Python tab in EmbedDialog add two new surfaces on top of the package itself.

- **Calibration Ledger (#2)** — Eight days to Sep 30 paper citation deadline. `POST /api/simulation/{id}/resolve` + `GET /api/calibration` Brier score gives a researcher a quantitative accuracy claim. The `✓ Resolved` chip makes resolved simulations visually distinct in the Step 3 share page.

- **LLM Tool-Calling Schema (#3)** — A single static JSON file + endpoint enables any LLM to call MiroShark as a tool. The repo-root `llm-tools.json` is discoverable via GitHub code search by anyone building AI agent pipelines. Zero maintenance after initial write.

- **Pressure Gauge (#4)** — Completes the simulation analytics four-pillar framework (What / When / How contested / What drove it). Pure trajectory.json computation, no external dependencies. The `pressure_note` plain-English line is paste-ready for a thread or report, same UX pattern as the divergence `summary` (Aug 30 #5).

- **Simulation Leaderboard (#5)** — Makes the growing simulation archive navigable by merit, not just date. The `/leaderboard` page is a shareable URL with a concrete reason to return. Integrates with Calibration Ledger (#2) via the `recently_resolved` list and with Pressure Gauge (#4) via the `most_contested` sort dimension.
