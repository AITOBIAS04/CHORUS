### 1. Consensus Formation Speed Metric

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Every `signal.json` captures *where* beliefs ended — direction and confidence. None of the existing analytics capture *how fast* consensus formed. A simulation where 65% agreement emerged by round 3 and held for 21 rounds is structurally different from one where the same 65% only crystallized in round 22. The former is "quick consensus under pressure"; the latter is "grinding emergence." Adding `rounds_to_consensus: int | null` to `signal.json` fills this gap. The metric defines consensus as the first round in which a single direction holds >60% across all agents for two consecutive rounds and never reverses — `null` if that threshold is never crossed. Downstream uses: gallery sorting ("show fastest-forming consensus first"), the compare endpoint gains a temporal dimension, and operators running policy stress tests get a signal for "how contentious will this topic's consensus journey be."

**How:**
1. Create `backend/app/services/consensus_speed_service.py` (~110 LoC, pure stdlib). Accept `sim_id: str`. Load `trajectory.json` → extract per-round `{round_number, bullish_pct, bearish_pct, neutral_pct}` entries. Scan rounds sequentially: at each round, check if `max(bullish_pct, bearish_pct, neutral_pct) >= 60.0`. If yes, record as `candidate_round`. Check the next round for confirmation (also ≥60% same direction). If confirmed and no reversal before the final round, `rounds_to_consensus = candidate_round`. Reversal check: once a direction first hits ≥60%, scan remaining rounds for any round where that direction drops below 50% — if found, invalidate and restart scan. If `trajectory.json` is absent or has fewer than 2 rounds, return `{rounds_to_consensus: null, reason: "insufficient_data"}`. Cache to `storage/simulations/{id}/consensus_speed.json` (mtime-based, TTL 1h while sim runs, immutable on completion). Merge `rounds_to_consensus: int | null` and `consensus_speed_label: str` ("Fast" ≤25% of total rounds, "Moderate" 26–75%, "Slow" >75%, "No Consensus" null) into `signal.json` during the signal-writing step. Add 6 unit tests: consensus at round 2 of 24 → `rounds_to_consensus = 2, label = "Fast"`; consensus at round 20 of 24 → `label = "Slow"`; direction reverses at round 10 → restart search, final answer ≠ round 2; never reaches 60% → `rounds_to_consensus = null`; single-round trajectory → `null` (insufficient); `trajectory.json` absent → returns `{rounds_to_consensus: null, reason: "insufficient_data"}`.
2. Add `GET /api/simulation/:id/consensus-speed` to `backend/app/api/consensus_speed.py`. Publish-gated. Session-auth. Response: `Content-Type: application/json`, `Cache-Control: max-age=3600, private`. Return `{rounds_to_consensus: int | null, consensus_speed_label: str, total_rounds: int, consensus_pct_at_formation: float | null, reason: str | null}`. Add `rounds_to_consensus`, `consensus_speed_label` to the OpenAPI `Signal` schema. Add to `surfaces_catalog.py` (type: `analytics`). Add to `docs/API.md` under "Analytics". During simulation completion, call `consensus_speed_service.compute(sim_id)` and merge into `signal.json`. Add 2 integration tests: endpoint returns 200 with `rounds_to_consensus` for a completed published sim; `rounds_to_consensus` is present in `signal.json` after sim completion.
3. Add a "Consensus Speed" row to the signal card in Step 3 (below direction and confidence): `{label} · consensus by round {N} of {total_rounds}` (or "No consensus formed" when null). Add `?sort=rounds_to_consensus` as a gallery sort option ("Fastest Consensus First"). The timeline chart in Step 3 gains a vertical dashed line at the consensus formation round labeled "Consensus". Add 2 frontend unit tests: signal card renders "No consensus formed" when `rounds_to_consensus` is null; timeline chart renders the consensus line only when `rounds_to_consensus` is non-null.

### 2. Post-Run Cost Breakdown

**Type:** DX / Feature
**Effort:** Small (hours)
**Impact:** The existing `GET /api/estimate` endpoint predicts cost and time *before* a run using historical medians. After a run completes, operators have no way to see where the actual tokens were spent. A $1.23 simulation that took 18 minutes is a black box — was most of the cost in the report-writing phase? The agent LLM calls? The graph builder? Adding `GET /api/simulation/:id/cost-breakdown` surfaces per-phase actual token usage and estimated cost. This directly answers the top cost-optimization question ("where should I cut to make this cheaper?") and creates a feedback loop from actual runs back to the estimator. Zero new data sources — MiroShark already logs LLM call metadata (model, input tokens, output tokens) during each phase into `run_log.jsonl`. The service reads this log and aggregates by phase tag.

**How:**
1. Create `backend/app/services/cost_breakdown_service.py` (~150 LoC, pure stdlib). Accept `sim_id: str`. Load `storage/simulations/{id}/run_log.jsonl` (each line is a JSON object with at minimum `{phase: str, model: str, input_tokens: int, output_tokens: int, timestamp: str}`; skip lines missing these fields). Group by `phase` tag: standard phases are `ontology`, `graph_build`, `agent_setup`, `simulation_round_{N}`, `report`. For each phase: sum `input_tokens`, `output_tokens`, `total_tokens = input + output`. Estimate cost per phase using a static model→price map (store in a `COST_PER_1M_TOKENS` dict: map common OpenRouter model IDs to their published $/1M token rates; fall back to 0.0 for unknown models). Compute `estimated_cost_usd` per phase. Compute totals: `total_input_tokens`, `total_output_tokens`, `total_tokens`, `total_estimated_cost_usd`. Compute `simulation_round_summary`: group all `simulation_round_*` phases and report combined tokens and cost as `simulation_execution`. Cache to `storage/simulations/{id}/cost_breakdown.json` (mtime 15min while sim runs, immutable on completion). Add 5 unit tests: phases are correctly grouped and summed; unknown model falls back to 0.0 cost; missing `run_log.jsonl` returns `{available: false, reason: "log_not_found"}`; lines missing required fields are skipped without crashing; `total_tokens` matches sum of all phase tokens.
2. Add `GET /api/simulation/:id/cost-breakdown` to `backend/app/api/cost_breakdown.py`. Session-auth (no publish gate — cost data is private). Response: `Content-Type: application/json`, `Cache-Control: max-age=900, private`. Return `{available: bool, phases: [{phase: str, input_tokens: int, output_tokens: int, total_tokens: int, estimated_cost_usd: float}], simulation_execution_summary: {...}, totals: {...}, currency: "USD", note: str}` where `note` warns "Costs are estimates based on published model pricing and may differ from your actual OpenRouter invoice." Add to `surfaces_catalog.py` (type: `analytics`). Add to `docs/API.md` under "Simulation Results" with a note: "Cost breakdown requires `run_log.jsonl` to be present. Runs started before this feature was deployed will return `available: false`." Add 2 integration tests: returns 200 with `phases` list for a completed sim whose `run_log.jsonl` exists; returns `{available: false}` for a sim with no `run_log.jsonl`.
3. Add a "Cost Breakdown" collapsible section to Step 3 below the signal card. When `available: true`, show a horizontal bar chart (pure CSS, no chart library) — one row per phase, bar width proportional to `total_tokens`, label showing `{phase}: {total_tokens} tokens · ~${estimated_cost_usd}`. Bottom row: "Total: {total_tokens} tokens · ~${total_estimated_cost_usd}". When `available: false`, show a one-line note: "Cost breakdown not available for this simulation." Add 2 frontend unit tests: cost breakdown section renders only when endpoint returns `available: true`; total row matches sum of individual phase rows.

### 3. Agent Engagement Score

**Type:** Feature / Analytics
**Effort:** Small (hours)
**Impact:** `actions.jsonl` records every post, reaction, and trade by every agent in every round. No existing endpoint aggregates *participation rate* — the fraction of agents who posted at least once in a given round vs. total agents in the pool. A round with 30% participation reads very differently from one with 92% participation: low engagement might mean the topic is low-salience, the LLM quota was throttled, or agent diversity is too low for the scenario to resonate. Adding an `engagement_score` per round and a simulation-level `mean_engagement_pct` creates a new signal axis. Operators can quickly identify runs where agent participation dropped mid-simulation (indicating a scenario that "ran out of things to say") vs. runs with sustained high engagement. The `engagement` data can feed directly into the article generator's framing ("All 112 agents were actively posting through round 20" vs. "Participation fell sharply after round 8").

**How:**
1. Create `backend/app/services/engagement_service.py` (~130 LoC, pure stdlib). Accept `sim_id: str`. Load `agents.json` → `total_agents: int` (count of all agents in the roster). Load `actions.jsonl` → aggregate per round: for each line `{agent_id, round_number, action_type}`, count distinct `agent_id` values per `round_number` (use a `defaultdict(set)` keyed by round). Compute `per_round_engagement: list[{round: int, active_agents: int, total_agents: int, engagement_pct: float}]`. `engagement_pct = active_agents / total_agents * 100`, rounded to 1dp. `mean_engagement_pct`: mean across all rounds. `peak_engagement_round`: round with highest `engagement_pct`. `trough_engagement_round`: round with lowest `engagement_pct` (excluding round 1 which may be bootstrapped differently). `engagement_label`: "High" (mean ≥ 70%), "Moderate" (40–69%), "Low" (<40%). `engagement_trend`: compare first-third vs. last-third mean — "Rising", "Stable" (within 10pp), "Declining". Cache to `storage/simulations/{id}/engagement.json` (mtime 15min, immutable on completion). Merge `mean_engagement_pct`, `engagement_label`, `engagement_trend` into `signal.json` during signal-writing step. Add 6 unit tests: all agents active every round → `mean_engagement_pct = 100.0`; zero agents active in a round → `engagement_pct = 0.0`; `engagement_trend = "Declining"` when first-third mean ≫ last-third; `engagement_label = "Low"` when mean < 40%; `agents.json` absent → graceful fallback with `available: false`; `actions.jsonl` absent → `available: false`.
2. Add `GET /api/simulation/:id/engagement` to `backend/app/api/engagement.py`. Publish-gated. Session-auth. Response: `Content-Type: application/json`, `Cache-Control: max-age=1800, private`. Return full engagement object including `per_round_engagement` list. Add `mean_engagement_pct`, `engagement_label`, `engagement_trend` to OpenAPI `Signal` schema. Add to `surfaces_catalog.py` (type: `analytics`). Add to `docs/API.md` under "Analytics". Add 2 integration tests: endpoint returns 200 with `per_round_engagement` list for a completed published sim; `mean_engagement_pct` is present in `signal.json` after sim completion.
3. Add an "Engagement" row to the signal card in Step 3: `{mean_engagement_pct}% agent participation · {engagement_label} · {engagement_trend}`. The belief-drift chart in Step 3 gains a secondary translucent area overlay showing `engagement_pct` per round as a gray fill behind the main trajectory lines (right-axis, 0–100% scale). Add `?sort=mean_engagement_pct` gallery option ("Most Engaged Simulations"). Add 2 frontend unit tests: engagement overlay renders only when engagement data is available; signal card shows "Declining" trend label when `engagement_trend = "Declining"`.

### 4. Platform Lead-Lag Analysis

**Type:** Feature / Analytics
**Effort:** Small (hours)
**Impact:** The existing `platform_sentiment_service.py` computes per-platform splits as a final-state snapshot. When platform sentiment data exists across rounds, a natural follow-on question is: *which platform moved first?* A scenario where X users were the first to shift BULLISH, with Reddit and Markets following 3 rounds later, is a leading-indicator pattern of practical value to market researchers and narrative analysts. Adding lead-lag detection to the platform sentiment flow identifies whether one platform consistently leads sentiment shifts. The result is surfaced as a simple `{leading_platform: str, lag_rounds: int, confidence: str}` block — computed via cross-correlation of per-round bullish_pct sequences between platform pairs. This is entirely derived from already-computed trajectory data and costs zero new API calls.

**How:**
1. Create `backend/app/services/lead_lag_service.py` (~140 LoC, pure stdlib). Accept `sim_id: str`. Load `platform_sentiment.json` → verify `per_round_by_platform` exists (a dict of `{platform: list[{round, bullish_pct, ...}]}`). If fewer than 2 platforms or fewer than 4 rounds per platform, return `{available: false, reason: "insufficient_data"}`. For each platform pair `(A, B)`, compute cross-correlation of their `bullish_pct` sequences at lags `[-3, -2, -1, 0, 1, 2, 3]` rounds (using pearsonr from `statistics` module; approximate with covariance if scipy absent — pure stdlib: `cov(shift(A, lag), B) / (std(A) * std(B))`). `best_lag_AB` = lag that maximizes `abs(correlation)` for pair (A, B). Positive lag → A leads B. Negative lag → B leads A. `lag_significance`: "High" if `|correlation| > 0.7`, "Moderate" if 0.4–0.7, "Low" if <0.4. `leading_platform`: the platform that leads the most pairs with high/moderate significance. `lag_summary: list[{platform_a, platform_b, lag_rounds, correlation, interpretation: str}]` where `interpretation` is e.g. "X leads Reddit by 2 rounds (high confidence)". Cache to `storage/simulations/{id}/lead_lag.json` (mtime 1h). Merge `{leading_platform, mean_lag_rounds, lead_lag_confidence}` into `platform_sentiment.json`. Add 5 unit tests: identical sequences → `lag = 0`; A perfectly leads B by 2 rounds → `best_lag = 2`; fewer than 2 platforms → `available: false`; fewer than 4 rounds → `available: false`; lag summary contains one entry per platform pair.
2. Add `GET /api/simulation/:id/lead-lag` to `backend/app/api/lead_lag.py`. Publish-gated. Session-auth. Response: `Content-Type: application/json`, `Cache-Control: max-age=3600, private`. Return `{available: bool, leading_platform: str | null, lag_summary: [...], interpretation: str}` where `interpretation` is a human-readable summary: "X users shifted sentiment 2 rounds before Reddit (high confidence)." Add to `surfaces_catalog.py` (type: `analytics`). Update `GET /api/simulation/:id/platform-sentiment` to include a `lead_lag` summary block in the response (the full detail is at `/lead-lag`). Add to `docs/API.md` under "Analytics". Add 2 integration tests: endpoint returns 200 with `leading_platform` for a multi-platform sim with ≥4 rounds; returns `{available: false}` for a single-platform sim.
3. Update the Step 3 "Platforms" overlay: when `lead_lag.available = true` and `lead_lag_confidence` is "High" or "Moderate", show a "Lead-Lag" section below the platform bars — a simple timeline arrow diagram (pure CSS/SVG): three platform labels on a horizontal axis with arrow connecting the leading platform leftward and lagging platforms rightward, labeled "leads by {N} rounds." When only "Low" confidence, suppress the diagram and show a note: "Platform sequences too similar to determine lead-lag order." Add 2 frontend unit tests: lead-lag diagram renders only when `available: true` and confidence is high/moderate; diagram suppressed at "Low" confidence.

### 5. Scenario Template Gallery

**Type:** Community / Growth
**Effort:** Medium (1-2 days)
**Impact:** The current share layer sends people to a *completed result*. There is no path for an operator to share a *reusable scenario starting point* — a prompt template that others can clone and run on their own MiroShark instance. A community template gallery (filtered gallery of operator-published templates) gives the community a shared vocabulary of reproducible scenarios. Operators mark a completed simulation as a template via a toggle; the template appears in a public `/templates` gallery page with its topic, scenario title, example result, and a "Clone & Run" button pre-filling the new-sim form. Researchers with published methodologies, educators building case studies, and operators who run recurring topic families ("Fed meeting reactions", "token launch scenarios") all benefit. The key insight is that templates are just simulations with an extra boolean tag — zero new storage schema, no new execution path.

**How:**
1. Add `is_template: bool` and `template_description: str | null` (max 300 chars) to the simulation's `config.json` schema. Add `PATCH /api/simulation/:id/template` to `backend/app/api/template_toggle.py` — accepts `{is_template: bool, template_description: str | null}`, validates ownership (session auth, same user who created the sim), persists to `config.json`. Validation: sim must be published (`published: true`) and completed (`status: "completed"`) to be marked as a template. Add `is_template` and `template_description` to the `GET /api/simulation/:id` response. Create `backend/app/services/template_index_service.py` (~150 LoC, pure stdlib): scans all simulation directories for `config.json` where `is_template = true` and `published = true`, builds an index with `{sim_id, topic, scenario_title, template_description, direction, confidence_pct, created_at, operator_id}` sorted by `created_at` desc, mtime-cached (15min TTL) to `storage/template_index.json`. Add 5 unit tests: unpublished sim cannot be marked as template (returns 400); `template_description` over 300 chars is rejected; template index includes only published + completed + `is_template=true` sims; `PATCH` by non-owner returns 403; marking `is_template=false` removes sim from template index on next rebuild.
2. Add `GET /api/templates` to `backend/app/api/templates.py` — keyless (no auth required), returns template index with optional `?q=` text search (case-insensitive match on topic + template_description), `?limit=` (default 20, max 50), `?sort=recent|confidence` (default: recent). Response: `Content-Type: application/json`, `Cache-Control: max-age=300, public`. Return `{templates: [{sim_id, topic, scenario_title, template_description, direction, confidence_pct, clone_url: str}], total: int}` where `clone_url = "{base_url}/new?topic={encoded_topic}&scenario={encoded_scenario_title}&from_template={sim_id}"`. Add to `surfaces_catalog.py` (type: `discovery`). Add to `docs/API.md` under "Discovery". Add 2 integration tests: returns all published completed templates; `?q=` text search filters results correctly.

Each card has a "Clone & Run" button that navigates to `/new?topic=...&from_template={sim_id}`. The existing new-sim form (`Step1ScenarioInput`) reads `from_template` from query params and pre-fills topic + scenario.
