### 3. Simulation Comparison API

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Researchers and longitudinal operators who run repeated simulations on the same topic have no way to compare results programmatically. "I ran an EU climate policy simulation in June and again in August — how did the consensus shift?" currently requires reading two `signal.json` files manually. `GET /api/simulation/compare?id1=X&id2=Y` returns a structured comparison: direction match/mismatch, confidence delta, stance distribution shift (per-stance percentage change), agent and round count deltas, and a machine-readable verdict sentence. Stateless — reads `signal.json` for both IDs, computes and returns; no new data stored. The Towards AI coverage and the Crucible Sim academic fork (wshuyi) confirm that longitudinal research use is already happening informally — this formalizes it. The comparison endpoint is also the foundation for a future "trending topics" page: simulations where repeated runs show direction reversals signal meaningful opinion shifts. Last proposed ~Aug 2 (outside the 7-day window; returning with updated framing from Towards AI + OrcaRouter context).

**How:**
1. Create `backend/app/api/comparison.py` (~90 LoC, pure stdlib). `GET /api/simulation/compare?id1={id}&id2={id2}`. Both simulations must be published; returns 404 `{"error": "simulation_not_found", "missing_id": id}` if either is missing or unpublished. Computation (~55 LoC): reads `signal.json` for both. Extracts for each: `direction`, `confidence_pct`, `stance_distribution` (bullish/neutral/bearish percentages), `agent_count`, `round_count`, `topic`, `created_at`. Computes: **direction_match** (`bool`): `sim1.direction == sim2.direction`. **confidence_delta** (`float`): `sim2.confidence_pct − sim1.confidence_pct` (positive = sim2 more confident). **stance_shift** (object): `{bullish_delta, neutral_delta, bearish_delta}` — sim2 minus sim1 for each stance percentage. **scale_delta** (object): `{agent_delta, round_delta}` — sim2 minus sim1. **verdict** (string): machine-readable one-sentence summary — logic: if `direction_match and abs(confidence_delta) < 5` → "Direction and confidence held stable."; `direction_match and confidence_delta > 0` → "Direction held. Confidence strengthened by {N:.1f} points."; `direction_match and confidence_delta < 0` → "Direction held. Confidence declined by {N:.1f} points."; `not direction_match and abs(confidence_delta) > 15` → "Direction reversed with high confidence shift ({N:.1f} points)."; else → "Direction reversed. Confidence shifted by {N:.1f} points." Response: `{sim1: {id, topic, direction, confidence_pct, stance_distribution, created_at}, sim2: {...}, direction_match, confidence_delta, stance_shift, scale_delta, verdict}`. `Cache-Control: public, max-age=3600`. Register at `GET /api/simulation/compare`. Add to `surfaces_catalog.py`.

2. Add a "Compare" panel to the simulation share page (`Step3Simulation.vue`): a search-as-you-type input labeled "Compare with another simulation" (searches `/api/simulation/search?q=` or accepts a raw simulation ID). On selection, fetches `/api/simulation/compare?id1={current}&id2={selected}` and renders a comparison card: two side-by-side direction/confidence badges (with a directional arrow → for same, ↔ for reversed), a stance shift chart (three bars showing bullish/neutral/bearish delta — green for increase, red for decrease), and the verdict text. Add to `docs/API.md` under "Comparison & Longitudinal Analysis": endpoint reference, `stance_shift` field definitions, `verdict` logic, usage pattern: "Run the same topic at different dates and compare to track opinion drift over real-world events."

3. Add 5 unit tests: two identical simulations return `direction_match: true`, `confidence_delta: 0.0`, `stance_shift: {bullish_delta: 0.0, neutral_delta: 0.0, bearish_delta: 0.0}`; two simulations with opposite directions return `direction_match: false`; missing or unpublished ID returns 404 with `missing_id` field; `verdict` is a non-empty string in all non-error cases; both `sim1` and `sim2` objects contain `topic`, `direction`, `confidence_pct`, and `created_at` keys. Log to memory: "Simulation Comparison API created 2026-08-16. `GET /api/simulation/compare?id1=X&id2=Y`. Returns direction_match, confidence_delta, stance_shift (per-stance %), scale_delta, verdict (one sentence). Stateless — reads signal.json for both. Enables longitudinal research. Foundation for trending-topics page (simulations with direction reversals across runs)."

### 5. Simulation Completion Webhook

**Type:** Integration
**Effort:** Small (hours)
**Impact:** MiroShark integrations currently require polling: clients repeatedly hit `GET /api/simulation/{id}` to check whether a simulation has finished. For programmatic integrations (CI/CD pipelines, custom bots, Zapier/Make.com automations), polling is wasteful and fragile — a 10-minute simulation at 5-second polling intervals generates ~120 redundant requests. A completion webhook fires exactly once when a simulation transitions to "published" state, delivering the `signal.json` payload as a POST to a registered callback URL. `POST /api/simulation/{id}/webhook` registers the URL; `DELETE` deregisters. This is architecturally distinct from Per-Round Webhook Events (off-limits, Aug 4 — fires during each round of a live run for real-time monitoring). The completion webhook fires once, after the run is fully done — the standard integration primitive for every async job system (GitHub Actions, Stripe, Twilio). Without it, the GitHub Actions integration example (Aug 10) must poll; with it, the workflow reduces to a single webhook registration step. Zapier and Make.com both require webhooks, not polling — this is the missing primitive for no-code integrations.

**How:**
1. Create `backend/app/api/webhook.py` (~100 LoC, pure stdlib). Two endpoints. **`POST /api/simulation/{id}/webhook`** (register): accepts JSON body `{"callback_url": str, "secret": str (optional — for HMAC-SHA256 signature)}`. Validates `callback_url` is a valid HTTP/HTTPS URL: regex check that rejects `file://`, blocks RFC-1918 addresses (10.x.x.x, 192.168.x.x, 172.16.x.x ranges) and localhost — SSRF prevention. Persists to `{simulation_dir}/webhook.json`: `{callback_url, secret_hash (SHA-256 of secret if provided; never store plaintext), registered_at: ISO8601, fired: false}`. Returns `{"registered": true, "simulation_id": id, "callback_url": callback_url, "note": "Webhook fires once when simulation is published."}`. If webhook already registered: overwrites (last registration wins). If simulation is already published at registration time: fire immediately without queuing, return `{"registered": true, "fired_immediately": true}`. **`DELETE /api/simulation/{id}/webhook`** (deregister): deletes `webhook.json`. Returns 204. **Webhook firing trigger**: in the publication route (wherever the background task writes `signal.json` and marks the simulation published), after confirming publication succeeds, check for `{simulation_dir}/webhook.json` with `fired: false`. If found: assemble payload `{"simulation_id": id, "event": "simulation.published", "timestamp": ISO8601, "signal": <signal.json contents>}`. If `secret_hash` is set: compute `HMAC-SHA256(secret, json.dumps(payload, separators=(',', ':')))` and include as `X-MiroShark-Signature: sha256=<hex>` header (canonical: sort keys before HMAC to ensure deterministic payload). POST to `callback_url` with 5-second timeout. On 2xx response: set `fired: true`. On failure: set `last_error: {status_code_or_exception, timestamp}` — no automatic retry (re-registering is the caller's mechanism). Register both endpoints in the main app router. Add to `surfaces_catalog.py`.

2. Update `docs/API.md` with a "Webhooks" section: register/deregister endpoint docs, full webhook payload schema (`simulation_id`, `event`, `timestamp`, `signal`), HMAC signature verification instructions in Python (`hmac.new(secret.encode(), payload.encode(), 'sha256').hexdigest()`) and JavaScript (`crypto.createHmac('sha256', secret).update(payload).digest('hex')`), SSRF prevention note, and a minimal Express.js webhook receiver snippet (~10 lines). Update `examples/github-actions-simulate.yml` (proposed Aug 10) to add a commented "webhook alternative" section: instead of polling the status endpoint, register a webhook URL in a prior step using `curl -X POST /api/simulation/{id}/webhook -d '{"callback_url": "..."}'`. Add the webhook registration endpoint to the embed dialog's "Integration" section alongside `signal.json` and `reproduce.json` links.

3. Add 5 unit tests: registration of a valid HTTPS URL returns 200 with `registered: true`; registration of an RFC-1918 URL (`http://192.168.1.1/webhook`) returns 400 (SSRF prevention); `DELETE` returns 204; if simulation is already published at registration, response includes `fired_immediately: true`; the payload POSTed to the callback URL contains both `event: "simulation.published"` and `signal` keys. Log to memory: "Simulation Completion Webhook created 2026-08-16. `POST /api/simulation/{id}/webhook` registers callback_url + optional HMAC secret. Fires once on publish. SSRF prevention: rejects RFC-1918 + localhost. `DELETE` deregisters. No auto-retry. Enables CI/CD without polling and no-code integrations (Zapier/Make.com). Distinct from Per-Round Webhook (fires per round during live run)."
