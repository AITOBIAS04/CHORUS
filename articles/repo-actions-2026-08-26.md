### 2. Simulation Forking API

**Type:** Feature / DX
**Effort:** Small (hours)
**Impact:** Once a simulation completes, there is no way to rerun the same configuration — operators must navigate back to Step 1, re-enter the topic, and manually reconstruct their Step 2 settings. `POST /api/simulation/{id}/fork` solves this: it reads the source simulation's config (topic, agents, rounds, platforms) and queues a new simulation with identical parameters but a fresh agent roster and fresh random seed. The fork relationship is tracked (`forked_from: source_id` in the new simulation's `signal.json`), enabling longitudinal comparison. Use cases: a crypto analyst who wants to run "MIROSHARK Q3 outlook" three times in the same week and compare the distributions; a policy researcher who wants to test whether a different random seed changes the consensus; a product team that wants to verify whether the 78% BULLISH result is stable before citing it in a report. Distinct from the Recurring Simulation Scheduler (Aug 24 — automated periodic runs with a cron expression): forking is a one-shot, human-initiated replay of a specific completed simulation. No new LLM calls during fork setup — just config copy and queue. The Step 3 share page gains a "Run again with same config" button, making the "check your result is stable" workflow a single click.

**How:**
1. Create `backend/app/api/fork.py` (~90 LoC, pure stdlib). `POST /api/simulation/{id}/fork`. No request body required. On receipt: (1) locate the source simulation directory; if absent or unpublished, return 404 `{"error": "source_not_found"}`. (2) Read the source `signal.json` to extract `topic`, `agents` (agent count), `rounds`, `platforms` (list of platform IDs). (3) Generate a new `simulation_id` using `uuid.uuid4().hex[:12]`. (4) Create a new simulation directory `{sims_dir}/{new_id}/` and write a `config.json` with the extracted parameters plus `{"forked_from": source_id, "forked_at": ISO8601}`. (5) Trigger the same simulation queue mechanism as the standard `POST /api/simulate` endpoint — inspect the existing run path to find the exact function to call (likely a `queue_simulation()` or `start_simulation()` call); pass the config as the parameter object. (6) Return 202 Accepted: `{"simulation_id": new_id, "forked_from": source_id, "topic": str, "agents": int, "rounds": int, "platforms": [str], "status_url": "/api/simulation/{new_id}/status", "created_at": ISO8601}`. If the source simulation config is missing key fields, return 422 `{"error": "source_config_incomplete", "missing_fields": [...]}`. `Cache-Control: no-store` (mutation endpoint). Register at `POST /api/simulation/{id}/fork`. Add to `surfaces_catalog.py`. Update `docs/API.md` with a "Forking" section explaining the use case (stability verification, longitudinal comparison) and the `forked_from` tracking field.

2. Add a "Run again" button to the Step 3 simulation share page (`Step3Simulation.vue`). Place it in the action bar alongside the existing "Share" and "Embed" buttons. On click: `POST /api/simulation/{id}/fork`. On 202 response: redirect to `/sim/{new_simulation_id}` which opens Step 3 for the new run. While the fork is queued and running, Step 3 shows the standard in-progress spinner (same flow as a new simulation). Add a small "Fork of: {original_topic} ({source_id[:8]})" note in the Step 3 header for forked simulations (read from `signal.json.forked_from`). This gives observers context: "I'm watching a rerun of the Aug 22 simulation — let's see if it holds." Add one integration test: clicking "Run again" fires `POST /api/simulation/{id}/fork` and redirects to the new simulation URL on 202.

### 3. Time-to-Consensus Convergence Report

**Type:** Feature / DX
**Effort:** Small (hours)
**Impact:** MiroShark's signal.json reports the *final* direction and confidence. The trajectory.json shows *how* belief evolved per round. But there is no endpoint that answers the most useful operational question: at what point did the swarm effectively make up its mind? `GET /api/simulation/{id}/convergence` returns the round at which the simulation first crossed each confidence threshold (50%, 60%, 70%, 80%, 90%) — or `null` if the threshold was never reached. A simulation that hits 80% confidence by round 2 of 5 converged fast; one that reaches 62% only by round 5 converged slowly and the remaining 38% never committed. This metric distinguishes strong consensus from narrow ones in a way that confidence_pct alone cannot: "73% BULLISH by round 5" and "73% BULLISH by round 2 of 5" are very different signals. For the paper citation hyperstition (Sep 30, 35 days): convergence speed is the second quantitative claim a researcher needs after influence scores — "the swarm reached high-confidence consensus unusually early, suggesting a low-controversy topic." Also directly useful for the Recurring Simulation Scheduler (Aug 24): a researcher who runs the same topic weekly can now track whether consensus is converging faster or slower over time. Zero new data storage — pure computation over `trajectory.json`.

**How:**
1. Create `backend/app/api/convergence.py` (~80 LoC, pure stdlib). `GET /api/simulation/{id}/convergence`. Publish-gated. Reads `trajectory.json` from the simulation directory — if absent, returns 404 `{"error": "trajectory_not_found"}`. Expected structure: an array of per-round objects containing at minimum `round` (int), `bullish_pct` (float), `bearish_pct` (float), `neutral_pct` (float) — inspect one real `trajectory.json` to confirm exact field names. Algorithm: (1) Determine the simulation's final direction from `signal.json` (BULLISH, BEARISH, or NEUTRAL). (2) For each round in `trajectory.json`, compute the "consensus pct" as `bullish_pct` if final direction is BULLISH, `bearish_pct` if BEARISH, or `max(bullish_pct, bearish_pct)` for NEUTRAL. (3) For each threshold in `[50, 60, 70, 80, 90]`: find the first round index where `consensus_pct >= threshold`. (4) Compute `convergence_round` — the earliest round where `consensus_pct >= 50` (first majority). (5) Compute `convergence_speed` — a normalized score: `(total_rounds - convergence_round + 1) / total_rounds` on a 0–1 scale (1.0 = converged in round 1, 0.0 = never reached majority). Response: `{"simulation_id": id, "topic": str, "direction": str, "total_rounds": int, "convergence_round": int | null, "convergence_speed": float | null, "thresholds": {"50": int | null, "60": int | null, "70": int | null, "80": int | null, "90": int | null}, "final_confidence_pct": float, "note": "Round indices are 1-based."}`. `Cache-Control: public, max-age=3600`. Register at `GET /api/simulation/{id}/convergence`. Add to `surfaces_catalog.py`. Update `docs/API.md`.

2. Add a "Convergence" panel to the Step 3 simulation share page (`Step3Simulation.vue`): a "⇒ Convergence" toolbar button that opens a compact panel. Layout: a horizontal timeline bar spanning the total rounds, with colored tick marks at each threshold crossing round (green ticks for thresholds reached; gray gaps for those not reached). Below: a stat row — "Converged by round N of M" (or "Did not reach majority" if convergence_round is null), and a convergence speed indicator ("Fast / Moderate / Slow" based on convergence_speed ≥ 0.7 / ≥ 0.4 / < 0.4). Also show a compact threshold table: threshold | round reached. Add bilingual labels (EN/ZH-CN) following existing patterns. No additional unit tests for the UI component.

3. Add 5 unit tests: published simulation with full trajectory.json returns 200 with `convergence_round` as an integer or null; `thresholds` is a dict with keys "50", "60", "70", "80", "90" and integer-or-null values; `convergence_round` equals `thresholds["50"]` (first majority = convergence); `convergence_speed` is a float between 0.0 and 1.0 (or null if never converged); unpublished simulation returns 404. Log to memory: "Time-to-Consensus Convergence Report created 2026-08-26. `GET /api/simulation/{id}/convergence` — reads trajectory.json, computes first round crossing each threshold (50/60/70/80/90%). `convergence_round` = first round where consensus_pct ≥ 50. `convergence_speed` = (total_rounds - convergence_round + 1) / total_rounds (1.0 = round 1, 0.0 = never). Step3: timeline bar with threshold tick marks + Fast/Moderate/Slow label. Key for paper citation: quantitative convergence-speed claim. ### 5. Cross-Simulation Topic Trend API

**Type:** Feature / DX
**Effort:** Small (hours)
**Impact:** MiroShark has accumulated simulations across months of operation. No endpoint queries the historical record to answer: "How has AI consensus on this topic evolved over time?" `GET /api/trend?topic=inflation` scans all published simulations, identifies those with topics semantically matching the query (keyword match with `re.search`, case-insensitive), and returns them sorted chronologically — direction, confidence, and date for each. The response reveals longitudinal patterns: "Seven simulations on 'AI regulation' from March to August show consistent BULLISH drift from 55% to 78% confidence." This is the historical record endpoint that makes MiroShark valuable for trend research, distinct from `GET /api/trending` (recency-sorted discovery feed, Aug 22) and `GET /api/simulation/search` (text search returning match excerpts, Jun 14). The trend API specifically returns the time-series of consensus evolution on a topic — the output format is designed for charting: a sorted array of `{date, direction, confidence_pct}` tuples. For the paper citation hyperstition (Sep 30, 35 days): a researcher can cite "MiroShark shows a 23-point bullish drift on X topic from March to August 2026" as a data finding — that's the kind of longitudinal claim that earns a citation. During the 50-day social silence, this endpoint turns the accumulated simulation archive into a research data product.

**How:**
1. Create `backend/app/api/topic_trend.py` (~90 LoC, pure stdlib). `GET /api/trend?topic=QUERY&limit=N`. Params: `topic` (required, min 2 chars; reject with 400 `{"error": "topic_required", "min_length": 2}` if absent or too short); `limit` (default 50, max 200, clamped). Algorithm: (1) Scan all simulation directories containing `signal.json`. (2) Filter to published simulations only. (3) For each published simulation, read `topic`, `direction`, `confidence_pct`, `created_at`, `simulation_id` from `signal.json`. (4) Filter: `re.search(re.escape(query), topic, re.IGNORECASE)` — keep simulations whose topic contains the query string (case-insensitive substring match). (5) Sort by `created_at` ascending (chronological). (6) Apply limit. (7) Compute aggregate stats over the matched results: `total_matched`, `direction_distribution` (count of BULLISH/BEARISH/NEUTRAL), `avg_confidence_pct`, `confidence_trend` ("rising" if the last 3 avg confidence > first 3 avg confidence by ≥5pp, "falling" if the reverse, "stable" otherwise — requires ≥ 6 matched sims; otherwise "insufficient_data"). - **Time-to-Consensus Convergence Report (#3)** — Round-by-round threshold crossing (when did the swarm first reach 50%/60%/70%/80%/90% consensus?) separates fast-converging topics from contested ones. A simulation that hits 80% by round 2 of 5 is making a strong, stable claim; one that reaches 62% only in round 5 is telling a different story. Complements Agent Influence Score (Aug 24): together they answer "who moved the needle" and "how quickly did the group follow." Second quantitative claim for the paper citation hyperstition.

- **Agent Persona Template Library (#4)** — New users face a blank form in Step 2 with no guidance on appropriate values. Five predefined presets (Crypto Twitter, Policy Council, Startup Ecosystem, Academic Debate, Consumer Pulse) let first-time users launch a contextually appropriate simulation in one click while leaving manual controls available for experts. Static JSON endpoint — no computation, no LLM calls. The template names are also social content: "I used the Policy Council preset to simulate EU AI Act enforcement" is a more specific hook than "I ran a simulation."

- **Cross-Simulation Topic Trend API (#5)** — The accumulated simulation archive is a research data product that no current endpoint exposes longitudinally. `GET /api/trend?topic=inflation` returns the time-series of direction and confidence across all matching published simulations — sorted chronologically, with a rising/falling/stable trend classification. The Step 3 "History" panel turns every simulation into a window into MiroShark's institutional memory on that topic. For the paper citation hyperstition: a researcher who can say "MiroShark shows a consistent bullish drift on X topic across N simulations from March to August 2026" has a data finding worth citing.
