### 2. Simulation Round-by-Round Replay Stream

**Type:** Feature
**Effort:** Medium (1-2 days)
**Impact:** The tutorial hyperstition (Aug 15, **3 days**, 0/5) has a core problem: the best tutorial formats (YouTube screen-recording, Dev.to "watch it unfold" narrative) require a moving visual. A static share page is a screenshot — compelling, but not a story. A Replay Stream endpoint (`GET /api/simulation/{id}/replay`) streams the simulation round-by-round as Server-Sent Events at a configurable pace, letting a tutorial writer screen-record the belief drift chart animating in real time — 10 rounds playing out over 30–60 seconds — without running a new live simulation. This is specifically the missing ingredient for the YouTube tutorial format outlined in the Tutorial Seed Kit (off-limits): "run `miro simulate --watch` while recording" is off-limits, but replaying a pre-existing published simulation is fresh. The SSE stream also makes embedded widgets dynamic: instead of a static `<iframe>` snapshot, the embed can receive the SSE events and animate agent stances changing round-by-round, making every embedded simulation feel live. This is distinct from the Simulation Short URL Service (off-limits, Aug 8 — sharing), the CSV Export (off-limits, Aug 10 — data download), and the Per-Round Webhook Events (off-limits, Aug 4 — push to external webhook during a live run). This is pull-based replay of a completed simulation.

**How:**
1. Create `backend/app/api/replay.py` (~110 LoC, pure stdlib). `GET /api/simulation/{id}/replay?speed=1.0`. Publish-gated (unpublished simulations return 404). Query params: `speed` (float, default 1.0, clamped [0.25, 10.0]) controls seconds-per-round delay. Response: `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-cache`, `X-Accel-Buffering: no` (disables nginx buffering for SSE). **Stream logic** (~60 LoC): reads `trajectory.json`. Emits an initial `event: meta` with simulation metadata (topic, agent count, total rounds, direction, confidence) as JSON. Then, for each round `r` in order: sleep `(1.0 / speed)` seconds (using `time.sleep`), then emit `event: round` with JSON payload: `{round: r, agents: [{name, platform, stance, confidence_pct, post_text, stance_changed: bool}]}`. After all rounds: emit `event: complete` with `{direction, confidence_pct, simulation_id}` and close the connection. If `trajectory.json` is missing or malformed: emit `event: error` with `{"error": "Replay data unavailable"}` and close. Register at `GET /api/simulation/<id>/replay`. Add to `surfaces_catalog.py` (type: stream; surface number: next available).

2. Add a "Replay" button to the simulation share page (`Step3Simulation.vue` or share template): below the static belief drift chart, a `▶ Replay` button that opens an `EventSource` connection to `/api/simulation/{id}/replay?speed=2.0` (2× speed for share page — faster is more engaging), updates the chart data frame-by-frame as `round` events arrive, and shows the agent stance distribution changing in real time. Add a speed selector: 0.5× (slow, good for screen-recording narration), 1× (real time), 2× (default for share page), 5× (quick preview). Add a `tutorial-recording` mode via `?mode=tutorial`: sets speed to 0.5× and adds an on-screen "Recording" banner + round counter — gives tutorial creators a clean screen-recording context without needing to configure anything. Add the replay URL pattern (`/api/simulation/{id}/replay`) to the embed dialog with a code snippet showing how to consume SSE in JavaScript (`new EventSource(...)`). Update `docs/API.md` with the SSE event schema: `meta`, `round`, `complete`, and `error` event types, field definitions, and the `speed` parameter reference.

3. Add 5 unit tests (using Python's `unittest` and a mock SSE consumer): replay of a simulation with 5 rounds emits exactly 7 events (`meta` + 5 × `round` + `complete`), the `meta` event contains `total_rounds` and `direction` keys, each `round` event contains `round` and `agents` keys, `?speed=0.1` clamps to 0.25, unpublished simulation returns 404 (not SSE). Log to memory: "Replay stream created 2026-08-12 — SSE stream of completed simulation rounds. `GET /api/simulation/{id}/replay?speed=N`. Tutorial mode: `?mode=tutorial` (0.5× + recording banner). Enables screen-recording for video tutorials without re-running simulations. Distinct from Per-Round Webhook (push during live run) and CSV Export (file download)."

### 3. Per-Agent Timeline API

**Type:** Feature
**Effort:** Small (hours)
**Impact:** The most overlooked primitive in MiroShark's API surface: you can see what ALL agents believed at each round (trajectory.json), which agents flipped stances (stance_flips.json), who mentioned whom (mentions.json) — but there is no endpoint that tells the story of ONE agent from round 1 to round N. Tutorial writers who want a human-readable narrative need exactly this: "I followed Maria (environmental activist, 34, X platform) through 10 rounds of the EU climate mandate simulation. She started bullish at 72%, dropped to 41% after the carbon capture news at round 4, recovered to 68% by round 8, and ended bearish at 31% — a full reversal." This is the narrative hook that makes opinion simulation feel real rather than statistical. `GET /api/simulation/{id}/agents/{agent_name}/timeline` returns one agent's complete round-by-round journey: initial profile, each round's stance, confidence, post text (truncated to 200 chars for display), whether they were mentioned by other agents that round, and cumulative flip count. The endpoint re-uses data already computed by trajectory.json, mentions.json, and stance_flips.json — no new computation, just a new assembly pattern. This directly serves text-format tutorial writing (Dev.to, academic blog, LinkedIn) where following one character through a simulation is more compelling than reading aggregate statistics. Distinct from the Stance Flip Report (off-limits analog: aggregate top-5 flippers) — this is a single-agent full timeline.

**How:**
1. Create `backend/app/api/agent_timeline.py` (~120 LoC, pure stdlib). `GET /api/simulation/{id}/agents/{agent_name}/timeline`. Publish-gated. URL path param: `agent_name` (case-insensitive match against agent names in trajectory.json). On no match: 404 `{"error": "Agent not found", "simulation_id": id, "agent_name": agent_name}`. **Assembly logic** (~80 LoC): reads `trajectory.json` to get the full agent list and per-round data for `agent_name`. Reads `mentions.json` (if present) to get incoming `@agent_name` mentions per round. Reads `stance_flips.json` (if present) to get cumulative flip count by round. Assembles a response object: `{agent_name, platform, initial_stance, initial_confidence_pct, profile_summary (first 200 chars of agent description, if available), rounds: [{round_number, stance, confidence_pct, post_text (first 200 chars), mentioned_by: [agent_name_list], stance_changed: bool, cumulative_flips}], final_stance, final_confidence_pct, total_flips, total_mentions_received}`. If mentions.json or stance_flips.json is absent: populate `mentioned_by: []` and `cumulative_flips: 0` for all rounds (graceful degradation). `Cache-Control: public, max-age=1800`. Register at `GET /api/simulation/<id>/agents/<agent_name>/timeline`. Add to `surfaces_catalog.py` (type: analytics; surface number: next available).

2. Add a "Follow an Agent" panel to the share page (`Step3Simulation.vue`): a dropdown or search-as-you-type field listing all agent names. On selection, fetches `/api/simulation/{id}/agents/{name}/timeline` and renders a vertical timeline: agent profile chip (name, platform, stance dot), then one card per round (round number, stance color-coded, confidence %, 200-char post excerpt, flip indicator if `stance_changed: true`, mentioned-by count badge). Add an "Agent Story" export button below the timeline: generates a plain-text narrative block ("Round 1: Maria was bullish (72%). Round 4: After the carbon capture report, Maria shifted to bearish (41%) — a stance change...") that a tutorial writer can copy-paste directly into their article. This narrative export is the main tutorial-enablement mechanism. Add `agent_timeline()` to the frontend API helper module. Add `GET /api/simulation/{id}/agents/{name}/timeline` to the embed dialog with a note: "Follow one agent's journey for narrative content in tutorial articles."

3. Add 5 unit tests: valid agent name returns 200 with `rounds` array length matching trajectory.json round count, unknown agent name returns 404 with correct JSON schema, response contains `total_flips` and `total_mentions_received` keys, `mentioned_by` is always an array (even when mentions.json absent), `post_text` is truncated to ≤200 characters. Update `docs/API.md` with "Per-Agent Timeline" section: endpoint reference, URL encoding note for agent names with spaces (`encodeURIComponent(agentName)` in JS), the `profile_summary` field source (agent description), and the "Agent Story export" usage pattern for tutorial creation. Add a PR note: "Enables the 'follow one agent' narrative format — tutorial writers can get a copy-paste ready character arc from any published simulation."

### 4. Embed Light/Dark Theme Toggle

**Type:** DX improvement
**Effort:** Small (hours)
**Impact:** The tutorial hyperstition (Aug 15, **3 days**, 0/5) has a platform-fit problem that no prior idea addressed: every major long-form publishing platform — Substack, Medium, Ghost, Notion, WordPress.com, Hashnode, most personal Jekyll/Hugo blogs — uses a white or light-grey background. MiroShark's embed widget renders a dark-themed UI (`#0d0d0d` background). Embedding a dark-on-light page creates a jarring visual interruption that signals "foreign element" rather than "embedded content." Tutorial writers who notice this typically revert to screenshots, losing the interactive embed entirely. `?theme=light` on the embed URL (`/embed/{id}?theme=light`) renders white background, dark text, inverted chart colors, and adjusted badge palettes — making the embed feel native on any publishing platform. A third option, `?theme=auto`, respects the visitor's `prefers-color-scheme` media query (system dark mode = dark embed, system light mode = light embed) — the safest choice for tutorial writers who don't know their readers' settings. This change touches only the embed route's CSS layer; no backend data changes. The embed is already the primary "non-technical tutorial proof" artifact — making it work on any platform directly increases the number of platforms where a tutorial can include interactive content. This is distinct from the Social Preview Card SVG (off-limits, Aug 8 — static OG image), the Simulation Short URL (off-limits, Aug 8 — URL compression), and the Atom Feed (idea #5 below — discovery mechanism).

**How:**
1. In the embed route handler (`backend/app/api/embed.py` or the embed template path — locate via the `/embed/<id>` route): read the `theme` query param (`request.args.get('theme', 'dark')`). Valid values: `'dark'` (default), `'light'`, `'auto'`. Pass to the template context. In the embed template (locate `embed.html` or equivalent): add a `<style>` block at the top that injects theme CSS variables based on the `theme` value passed from the route. **Dark theme** (default, unchanged): `--bg: #0d0d0d; --text: #f9fafb; --surface: #111827; --border: #374151; --accent: #8B5CF6; --muted: #6B7280`. **Light theme**: `--bg: #ffffff; --text: #111827; --surface: #f9fafb; --border: #e5e7eb; --accent: #7c3aed; --muted: #6B7280`. **Auto theme**: inject both via CSS `@media (prefers-color-scheme: dark)` + `@media (prefers-color-scheme: light)` blocks; no server-side decision. Replace all hardcoded color values in the embed template's inline styles with `var(--bg)`, `var(--text)`, etc. Ensure chart library colors (if Chart.js or similar): pass the accent and muted colors to the chart config from the CSS variables. Invalid `theme` values default silently to `'dark'` (no 400 error — embed consumers shouldn't get broken pages from typos).

2. Update the embed dialog in `Step3Simulation.vue` (or wherever embed codes are generated): add a "Theme" toggle with three buttons (Dark / Light / Auto) that updates the embed `<iframe>` `src` URL in real time, showing a live preview of how the embed looks in each mode. The default shown in the dialog should be `?theme=auto` — it's the most universally safe. Add a tooltip next to the theme toggle: "Light mode fits Substack, Medium, and most blogs. Dark mode matches GitHub READMEs and Discord. Auto adapts to the reader's device." Update the embed URL displayed in the dialog to include `?theme=auto` by default. Add a copy-paste CSS snippet in the dialog ("If your platform strips query params from iframes, use this fallback CSS...") for platforms like Notion that may sanitize URLs. Update `docs/API.md` under the embed section: add a "Theme" subsection with the three valid values, their intended use cases, and a note about `auto` behavior on platforms that don't support `prefers-color-scheme`.

3. Add 3 unit tests: embed route with `?theme=light` returns HTML containing `--bg: #ffffff`, embed route with `?theme=dark` returns HTML containing `--bg: #0d0d0d`, embed route with `?theme=invalid` returns 200 (defaults to dark) rather than 400. Add a visual regression note in the PR: "Reviewers: test on a white-background page (GitHub Markdown preview in light mode, or a Substack draft post) to confirm the light embed looks native rather than styled." PR body should note: "Directly enables embedding on Substack, Medium, Ghost, Hashnode, and any light-background platform — the platforms most tutorial writers use for long-form content."

### 5. Simulation Atom Feed

**Type:** Feature / Integration
**Effort:** Small (hours)
**Impact:** MiroShark has no subscription mechanism. The 298 fork holders and 1,428 star-gazers can only discover new published simulations by visiting the site or following the (silent) Twitter account. An Atom feed (`GET /api/feed.xml`) of the 20 most recently published simulations creates a persistent, subscription-based discovery channel for ecosystem integrators, researchers, and community members. Any RSS reader (Feedly, Inoreader, NetNewsWire, self-hosted Miniflux, Newsboat for developers) becomes a real-time MiroShark output consumer. Each feed entry includes: simulation topic (as title), direction + confidence as subtitle, link to the share page, publication timestamp, and the summary text from `signal.json`. For ecosystem integrators (AntFleet, Capacitr, any monitoring tool): the feed is the standard protocol for polling new simulations without building a custom API integration. For community members: the subscription CTA ("subscribe to MiroShark simulations in your feed reader") converts passive star holders into regular consumers of MiroShark output — the kind of repeated exposure that eventually produces a tutorial writer. The feed is the missing outbound channel between the silent Twitter (36 days) and the API (requires developer effort to poll). This is distinct from the activity feed endpoint (which logs general platform events internally) and from the search endpoint (which lets users query by topic). This is a push/subscribe primitive. Pure stdlib: `xml.etree.ElementTree` for Atom, no dependencies.

**How:**
1. Create `backend/app/api/feed.py` (~90 LoC, pure stdlib). `GET /api/feed.xml`. No authentication — public simulations only. **Feed logic** (~60 LoC): scans the simulation storage directory for published simulations (those with `signal.json` present and `published: true`). For each: reads `simulation_id`, `topic`, `direction`, `confidence_pct`, `created_at`, `agent_count`, `round_count` from `signal.json`. Sorts by `created_at` descending. Takes the 20 most recent. Builds an Atom 1.0 feed using `xml.etree.ElementTree`: feed-level elements: `<title>MiroShark — Public Simulations</title>`, `<link rel="self" href="https://miroshark.xyz/api/feed.xml"/>`, `<link rel="alternate" href="https://miroshark.xyz"/>`, `<updated>{most_recent_created_at in ISO 8601}</updated>`, `<id>https://miroshark.xyz/api/feed.xml</id>`, `<generator>MiroShark</generator>`. Per-entry elements: `<id>https://miroshark.xyz/simulation/{id}/share</id>`, `<title>{topic} — {direction} ({confidence_pct}% confidence)</title>`, `<link href="https://miroshark.xyz/simulation/{id}/share"/>`, `<published>{created_at}</published>`, `<updated>{created_at}</updated>`, `<summary type="text">{agent_count} agents · {round_count} rounds · {direction} consensus at {confidence_pct}% confidence. Published {date}.</summary>`. Response: `Content-Type: application/atom+xml; charset=utf-8`, `Cache-Control: public, max-age=900` (15-minute cache — new simulations don't need immediate feed inclusion). Register at `GET /api/feed.xml`. Add to `surfaces_catalog.py` (type: discovery; surface number: next available).

2. Add a "Subscribe" link to the site: in the main navigation or the share page header, add an RSS/feed icon (`☁ Subscribe`) that links to `/api/feed.xml`. Add `<link rel="alternate" type="application/atom+xml" title="MiroShark Simulations" href="/api/feed.xml">` to the frontend `index.html` `<head>` — this causes browsers with feed reader extensions (and feed-reader apps on iOS/macOS) to auto-detect the feed. Add `feed.xml` to the documentation in `docs/API.md` under a "Feeds" section: Atom 1.0, 20 most recent published simulations, public/unauthenticated, 15-minute cache. Update `docs/ECOSYSTEM.md` with a "Integration Patterns" section: "Subscribe to MiroShark's Atom feed to receive new simulations in any feed reader: `https://miroshark.xyz/api/feed.xml`." This creates the canonical hook for ecosystem projects to advertise MiroShark integration ("powered by MiroShark's public simulation feed").

3. Add 5 unit tests: `GET /api/feed.xml` returns 200 with `Content-Type: application/atom+xml`, the response body is valid XML (parseable by `ET.fromstring()`), each entry element contains `<title>`, `<link>`, and `<id>` children, a simulation with `published: false` is excluded from the feed, the feed contains at most 20 entries regardless of how many published simulations exist. Log to memory: "Atom feed created 2026-08-12. `GET /api/feed.xml` — 20 most recent published simulations, Atom 1.0, public/unauthenticated, 15-min cache. Add subscribe CTA to navigation. Enables feed reader subscriptions and ecosystem integrator polling. Auto-detected by feed-reader browser extensions via `<link rel='alternate'>` in index.html."
