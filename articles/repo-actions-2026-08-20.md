### 2. Social Sharing Deep Links API

**Type:** Growth
**Effort:** Small (hours)
**Impact:** Every published MiroShark simulation has a result worth sharing: a direction (BULLISH/BEARISH/NEUTRAL), a confidence percentage, and a topic that someone cares about. The current Step3Simulation.vue share page has no "Share on X" or "Share on LinkedIn" button — users who want to share must manually copy the URL, open the platform, and write their own caption. Frictionless sharing is the fastest path to breaking a 44-day social silence without spending on advertising. `GET /api/simulation/{id}/share-links` returns pre-filled intent URLs: an X (Twitter) intent URL with the simulation result pre-composed as a tweet, and a LinkedIn share URL with title and summary prefilled. The X intent URL uses `x.com/intent/tweet?text=...` — no API key, no OAuth, works in any browser. On click, X opens with the tweet pre-written: "I simulated [topic] — the AI swarm says [DIRECTION] ([confidence_pct]% confidence). Under $1 and 10 minutes. Try it: miroshark.xyz/sim/[id] #MiroShark #SwarmIntelligence". LinkedIn uses `linkedin.com/shareArticle?mini=true&url=...&title=...&summary=...`. One endpoint, pure stdlib (`urllib.parse.quote`), ~50 LoC. The `Step3Simulation.vue` toolbar gains "Share on X" and "Share on LinkedIn" buttons — both open in a new tab with the result pre-composed. This is the viral loop primitive that's currently missing: users who care enough to run a simulation should be able to share it in one click, and every share carries the $1 / 10-min hook and a #MiroShark tag that feeds back into discovery.

**How:**
1. Create `backend/app/api/share_links.py` (~55 LoC, pure stdlib). `GET /api/simulation/{id}/share-links`. Publish-gated: reads `signal.json`, returns 404 `{"error": "simulation_not_found"}` if missing or unpublished. Extracts: `topic` (truncated to 80 chars for URL safety), `direction` (BULLISH/BEARISH/NEUTRAL), `confidence_pct`, `simulation_id`. Computes: **X intent URL** — base `https://x.com/intent/tweet`, text parameter: `I simulated "{topic}" — the AI swarm says {direction} ({confidence_pct:.0f}% confidence). Under $1, 10 minutes. See it: https://miroshark.xyz/sim/{simulation_id} #MiroShark #SwarmIntelligence` (total tweet character count: ~230 chars for a 50-char topic; keep under 280). Encode via `urllib.parse.quote(text, safe='')`. **LinkedIn share URL** — base `https://www.linkedin.com/shareArticle`, params: `mini=true`, `url=https://miroshark.xyz/sim/{simulation_id}`, `title={topic} — MiroShark Simulation`, `summary=Direction: {direction} · {confidence_pct:.0f}% confidence. Simulated by MiroShark swarm intelligence — $1 per simulation.`. Encode via `urllib.parse.urlencode`. Response: `{"simulation_id": id, "topic": topic, "direction": direction, "confidence_pct": confidence_pct, "links": {"twitter_intent": "https://x.com/intent/tweet?text=...", "linkedin": "https://www.linkedin.com/shareArticle?..."}}`. `Cache-Control: public, max-age=3600`. Register at `GET /api/simulation/{id}/share-links`. Add to `surfaces_catalog.py`. Update `docs/API.md` with the endpoint and an example response.

2. Add "Share on X" and "Share on LinkedIn" buttons to `Step3Simulation.vue` toolbar, adjacent to the existing `reproduce.json` / `signal.json` links. Each button: `window.open(shareLink, '_blank', 'noopener')`. Fetch share links once from `GET /api/simulation/{id}/share-links` when the share page loads — cache in component state. Button copy: "𝕏 Share result" and "in Share on LinkedIn". On mobile: a single "Share ↗" button that opens the platform share sheet (use the Web Share API: `navigator.share({title: topic, text: tweetText, url: shareUrl})` with fallback to the X intent URL on unsupported browsers). Also add the share links to the embed dialog's "Share" section alongside the existing `signal.json` and `reproduce.json` links.

### 3. Prometheus Metrics Endpoint

**Type:** Integration / DX
**Effort:** Small (hours)
**Impact:** MiroShark has no observability surface for self-hosters. Operators who run MiroShark behind Docker Compose or Kubernetes have no way to wire it into their existing Prometheus/Grafana stack — they must log into the host and manually inspect files to know how many simulations have run, how many are active, or how much LLM spend has accumulated. `GET /metrics` in standard Prometheus text format is the universal plug-in point for the entire Grafana ecosystem: any operator with Prometheus already running adds one scrape job (`- job_name: miroshark; static_configs: - targets: ['miroshark:5000']`) and immediately gets dashboards, alerts, and retention. Pure stdlib implementation — no `prometheus_client` package needed; Prometheus text format is a plain-text line format that Python can generate with string formatting. Exposes: `miroshark_simulations_total` (counter — total completed simulations), `miroshark_simulations_active` (gauge — simulations currently in progress), `miroshark_llm_tokens_total` (counter with `model` label — cumulative tokens consumed by model), `miroshark_simulation_cost_usd_total` (counter — cumulative LLM cost in USD), `miroshark_simulation_duration_seconds` (gauge — duration of the last completed simulation, useful for tracking model latency regressions). Data source: scan the simulations directory for `signal.json` files (completed), count directories without `signal.json` (in-progress), sum token counts from existing cost logs. Stateless read — no persistent metrics store needed; values derived at scrape time from existing simulation data.

**How:**
1. Create `backend/app/api/metrics.py` (~80 LoC, pure stdlib). `GET /metrics`. No authentication (Prometheus scrapers run unauthenticated by convention; if auth is needed, scraper credentials go in the Prometheus `basic_auth` config). Scans `{simulations_base_dir}/` to compute metrics: iterate all simulation directories. **`miroshark_simulations_total`**: count directories containing `signal.json`. **`miroshark_simulations_active`**: count directories without `signal.json` but with a lock file or creation timestamp < 30 min ago (heuristic for in-progress). **`miroshark_llm_tokens_total{model="..."}`**: sum `prompt_tokens` + `completion_tokens` from all cost log files (check what filename the backend uses for per-simulation cost tracking — likely `cost.json` or within `signal.json` itself; read one to confirm the schema). **`miroshark_simulation_cost_usd_total`**: sum `total_cost_usd` from all cost log files. **`miroshark_simulation_duration_seconds`**: read the `duration_seconds` field from the most recently completed `signal.json`. Format as Prometheus text exposition: `# HELP {metric} {description}\n# TYPE {metric} {counter|gauge}\n{metric}{labels} {value}\n`. Set `Content-Type: text/plain; version=0.0.4; charset=utf-8` (Prometheus scraper negotiates this MIME type). Cache: `Cache-Control: no-cache` (Prometheus expects fresh values on every scrape). Register at `GET /metrics`. Add to `surfaces_catalog.py`.

2. Add a `prometheus/` directory with a sample `docker-compose.monitoring.yml` (~25 lines): Prometheus container + Grafana container, Prometheus config file (`prometheus.yml`) pre-configured to scrape `miroshark:5000/metrics` every 15 seconds. Add a sample `grafana/provisioning/dashboards/miroshark.json` (~60 lines): a minimal Grafana dashboard JSON with 4 panels: total simulations (stat tile), active simulations (gauge), cumulative cost USD (stat tile), simulation duration seconds (time series). This gives self-hosters a working monitoring stack in one `docker compose up`. Update `docs/SELF-HOSTING.md` (or create it if absent) with a "Monitoring" section: "MiroShark exposes `/metrics` in Prometheus text format. See `prometheus/docker-compose.monitoring.yml` for a quickstart." Add to `README.md` pill buttons: "Metrics →" linking to `/metrics` (self-hosted) or the docs section.

3. Add 3 unit tests: `GET /metrics` returns 200 with `Content-Type` containing `text/plain`; response body contains `# TYPE miroshark_simulations_total counter`; `miroshark_simulations_total` value is a non-negative integer. Log to memory: "Prometheus Metrics Endpoint created 2026-08-20. `GET /metrics` — Prometheus text format, no auth. Metrics: miroshark_simulations_total (counter), miroshark_simulations_active (gauge), miroshark_llm_tokens_total{model} (counter), miroshark_simulation_cost_usd_total (counter), miroshark_simulation_duration_seconds (gauge). Scans simulation directories at scrape time — no persistent metrics store. `prometheus/docker-compose.monitoring.yml` + sample Grafana dashboard included."

### 4. Simulation Tagging API

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Researchers and operators who run batches of simulations have no way to organize them. A longitudinal study might involve 20 simulations on climate policy across six months; an operator might run weekly simulations on token sentiment; a product team might tag simulations by product launch phase. Without tags, finding related simulations requires remembering UUIDs or re-running searches. `POST /api/simulation/{id}/tags` writes a tag set to `{simulation_dir}/tags.json`. `GET /api/simulation/search?tag=X` filters the existing search index to return only tagged simulations. Builds on the search infrastructure that already exists (Simulation Full-Text Search, Jun 14) — tags are a structured filter that the search index can cheaply incorporate. Tags are also a foundation for future features: a "tag cloud" landing page, tag-based RSS feeds, tag-based operator dashboards. No new data model — just a lightweight `tags.json` file per simulation directory, the same pattern as `signal.json`, `webhook.json`, etc. Tag validation keeps the system clean: lowercase, alphanumeric plus hyphens, max 32 chars per tag, max 10 tags per simulation.

**How:**
1. Create `backend/app/api/tags.py` (~90 LoC, pure stdlib). Three endpoints: **`GET /api/simulation/{id}/tags`**: publish-gated. Reads `{simulation_dir}/tags.json` (returns `{"tags": []}` if file absent). Response: `{"simulation_id": id, "tags": ["tag1", "tag2"]}`. **`POST /api/simulation/{id}/tags`**: accepts JSON body `{"tags": ["tag1", "tag2"]}`. Validation: each tag must match `^[a-z0-9][a-z0-9\-]{0,31}$` (lowercase, alphanumeric + hyphens, starts with alphanumeric, max 32 chars); max 10 tags per simulation (merge with existing, deduplicate, reject if merged set exceeds 10 with a 400 error listing which tags were rejected). Merge semantics: add new tags to existing set (non-destructive — does not remove existing tags). Writes merged set back to `tags.json`. Returns `{"simulation_id": id, "tags": [...merged set...], "added": [...new tags...]}`. **`DELETE /api/simulation/{id}/tags/{tag}`**: removes one tag from `tags.json`. Returns 204 on success; 404 if tag not present. Register all three at their respective paths. Add to `surfaces_catalog.py`. Update `docs/API.md` with endpoint docs, validation rules, and a note on `GET /api/simulation/search?tag=X`.

2. Extend the existing search index (`search_service.py`) to support tag filtering. When rebuilding the search index, read `tags.json` for each simulation and include `tags: [...]` in the index entry. In the search handler: if `?tag=X` query param is present (can be combined with `?q=...`), filter the index to simulations whose `tags` array contains `X` (exact match, case-insensitive). Return the same `SearchResponse` format as the existing search endpoint. Add `?tag=` documentation to `docs/API.md` under "Search & Discovery." Add 3 unit tests for tag-filtered search: `GET /api/simulation/search?tag=election-2026` returns only simulations tagged `election-2026`; combining `?q=climate&tag=policy` returns simulations matching both; tag filter with no matches returns `{"results": [], "total": 0}`.

3. Add a tag input to the simulation share page (`Step3Simulation.vue`): below the simulation result card, a compact "Add tag" field (text input + submit button) for operators who want to label their own simulations. Submits to `POST /api/simulation/{id}/tags`. Displays existing tags as removable chips (clicking an `×` on a chip calls `DELETE /api/simulation/{id}/tags/{tag}`). Tags also appear on the embed dialog's "Metadata" section. Add 5 unit tests total: valid tag set writes correctly; invalid tag (uppercase, spaces, or > 32 chars) returns 400 with which tags failed; exceeding 10-tag limit returns 400; `DELETE` removes correct tag; `GET` returns empty array when `tags.json` absent. Log to memory: "Simulation Tagging API created 2026-08-20. `GET /api/simulation/{id}/tags`, `POST /api/simulation/{id}/tags` (merge semantics, max 10 tags, validation: ^[a-z0-9][a-z0-9-]{0,31}$), `DELETE /api/simulation/{id}/tags/{tag}`. Persists to {simulation_dir}/tags.json. Search extended: `GET /api/simulation/search?tag=X` and `?q=...&tag=X` combo. Step3 UI: tag input + chip display. Foundation for tag-cloud landing page and tag-based RSS."

### 5. Simulation Cost Receipt API

**Type:** Feature
**Effort:** Small (hours)
**Impact:** MiroShark's core value proposition is that a simulation costs under $1. But there is currently no way to verify this programmatically — no endpoint returns the itemized LLM cost of a completed simulation. Researchers who need to report API costs in papers (e.g., "each simulation consumed approximately N tokens at a cost of $X using model Y"), operators who want to audit LLM spend across their simulation history, and enterprise users evaluating total cost of ownership all need this data in a structured, machine-readable format. `GET /api/simulation/{id}/receipt.json` returns the full cost breakdown: model(s) used, prompt tokens, completion tokens, total tokens, per-model cost in USD, and total cost in USD. The data already exists — the backend logs token usage and cost during simulation execution; this endpoint exposes it as a structured artifact. Two additional endpoints complete the picture: `GET /api/usage/summary` returns aggregate spend across all simulations (total tokens, total cost, average cost per simulation, simulation count), and `GET /api/usage/by-model` returns per-model breakdown (useful for operators who have switched models and want to track cost migration). All endpoints are stateless reads of existing log files. This is also the foundation for a future operator budget cap feature (reject new simulations when monthly spend exceeds a configured limit).

**How:**
1. Create `backend/app/api/receipt.py` (~90 LoC, pure stdlib). Three endpoints: **`GET /api/simulation/{id}/receipt.json`**: publish-gated. Locates the simulation directory. Reads the simulation's cost log file — inspect the backend source to confirm its name and schema (likely `cost.json` within the simulation directory, or cost fields within `signal.json`; read one real simulation directory to confirm field names before implementing). Returns: `{"simulation_id": id, "topic": str, "created_at": ISO8601, "model": str (or list if multiple models used), "prompt_tokens": int, "completion_tokens": int, "total_tokens": int, "cost_usd_prompt": float, "cost_usd_completion": float, "cost_usd_total": float, "agents": int, "rounds": int, "platforms": [str], "cost_per_agent_usd": float (cost_usd_total / agents), "cost_per_round_usd": float (cost_usd_total / rounds)}`. If cost log data is unavailable (old simulation pre-dating cost tracking), return `{"simulation_id": id, "cost_usd_total": null, "note": "cost_data_unavailable: simulation predates cost tracking"}` — never return 500 for missing optional data. `Cache-Control: public, max-age=86400`. **`GET /api/usage/summary`**: no auth (operator-level endpoint; self-hosted deployments control their own network access). Scans all simulation directories, sums all available cost log data. Returns: `{"simulations_total": int, "simulations_with_cost_data": int, "total_tokens": int, "total_cost_usd": float, "avg_cost_usd_per_simulation": float, "min_cost_usd": float, "max_cost_usd": float, "computed_at": ISO8601}`. `Cache-Control: max-age=300` (5-min cache; scanning all simulations is expensive). **`GET /api/usage/by-model`**: returns per-model breakdown as an array: `[{"model": str, "simulation_count": int, "total_tokens": int, "total_cost_usd": float, "avg_cost_usd": float}]` sorted by `total_cost_usd desc`. Register all three at their paths. Add all to `surfaces_catalog.py`. Update `docs/API.md` with a "Cost & Usage" section.

2. Add a "Cost breakdown" accordion section to the simulation share page (`Step3Simulation.vue`): collapsed by default (to avoid price anxiety on the main result view), expandable on click. Shows: model name, prompt + completion tokens, total cost in USD formatted as "$0.XXXXXX" (6 decimal places to represent sub-cent costs correctly). Fetches from `GET /api/simulation/{id}/receipt.json`. If cost data is unavailable, shows "Cost data not available for this simulation." Also include cost in the embed dialog's metadata panel (alongside existing fields: simulation_id, agent_count, round_count). Update `docs/FEATURES.md`: add "Per-simulation cost receipts" to the feature list with a note that the $1/simulation figure is verifiable via API.

3. Add 5 unit tests: published simulation returns 200 with `cost_usd_total` as a float (or null for unavailable); `cost_per_agent_usd` equals `cost_usd_total / agents` within floating-point tolerance; unpublished simulation returns 404; `GET /api/usage/summary` returns `simulations_total >= 0` and `total_cost_usd >= 0.0`; `GET /api/usage/by-model` returns an array (possibly empty) where each entry has `model`, `simulation_count`, and `total_cost_usd`. Log to memory: "Simulation Cost Receipt API created 2026-08-20. `GET /api/simulation/{id}/receipt.json` — itemized cost: model, prompt_tokens, completion_tokens, total_tokens, cost_usd_prompt, cost_usd_completion, cost_usd_total, cost_per_agent_usd, cost_per_round_usd. `GET /api/usage/summary` — aggregate spend (total tokens, total cost, avg/min/max cost). `GET /api/usage/by-model` — per-model breakdown sorted by cost desc. Step3: collapsible cost accordion. Verifies $1/simulation claim programmatically. Foundation for operator budget cap feature."
