### 1. GitHub README SVG Badge

**Type:** Growth
**Effort:** Small (hours)
**Impact:** The embed widget (Nov 18) requires JavaScript, which GitHub's markdown renderer blocks entirely. Fork owners, researchers, and operators who want to surface a simulation result in a GitHub README, wiki, or Notion page have no current option — they can copy the URL, but that's just a link, not a visual signal. A `GET /badge/:sim_id.svg` endpoint serves a dynamically generated SVG badge (GitHub shields.io style): direction text (`BULLISH` / `BEARISH` / `NEUTRAL`), confidence percentage, and a direction-colored background (green/red/gray). The badge uses the same keyless `signal.json` lookup as existing public endpoints, cached with a 1-hour mtime gate so GitHub's CDN gets a fresh badge on each cache bust without hammering the API. `![MiroShark](https://miroshark.xyz/badge/SIM_ID.svg)` is a one-line drop-in. With 303 forks and zero external contributors, giving fork owners a visual artifact to put in their own READMEs creates a distribution channel from every active fork. Each badge is a backlink. The competitive gap: neither SimSwarm nor LeanSwarm has a badge endpoint — most simulation tools don't, because most don't have a stable public API for individual results.

**How:**
1. Create `backend/app/services/badge_service.py` (~80 LoC, pure stdlib). `generate_badge(sim_id: str) -> str`: load `storage/simulations/{id}/signal.json` (or return a "not available" badge if absent or unpublished). Extract `direction`, `confidence_pct`. Map direction to color: `BULLISH` → `#16a34a` (green), `BEARISH` → `#dc2626` (red), `NEUTRAL` → `#6b7280` (gray). Build SVG string via f-string: a 200×20 rectangle, left half dark (`#1f2937`, 80px wide) with text `MiroShark` in white 11px sans-serif, right half colored (120px) with text `{direction} {confidence_pct}%` in white 11px. Rounded corners (rx=3). For unpublished/missing: right half `#6b7280`, text `simulation not found`. Return raw SVG string. Cache path: `storage/simulations/{id}/badge.svg`, invalidated when `signal.json` mtime changes (compare mtime, regenerate if signal is newer). Add 4 unit tests: BULLISH → green background hex in SVG; BEARISH → red; NEUTRAL → gray; missing sim_id → "not found" text.
2. Add `GET /badge/:sim_id.svg` to `backend/app/api/badge.py`. Keyless (no auth required — badge must be embeddable from any context). `Content-Type: image/svg+xml`. `Cache-Control: max-age=3600, public`. `X-Content-Type-Options: nosniff`. Calls `generate_badge(sim_id)`, returns SVG response. Returns the "not available" badge (not 404) on missing sim — a 404 would render as a broken image in READMEs, while the gray fallback badge stays legible. Add to `surfaces_catalog.py` (type: `distribution`). Add to `docs/API.md` under "Sharing & Distribution" with a Markdown copy-paste snippet. Add 2 integration tests: endpoint returns `Content-Type: image/svg+xml`; `Cache-Control` header present.
3. Add a "Copy badge" button to the Step 3 share panel (alongside existing share buttons). Clicking copies the Markdown snippet `![MiroShark Simulation](https://miroshark.xyz/badge/{sim_id}.svg)` to clipboard with a "Copied!" toast. Show a live preview of the badge SVG below the button (rendered via `<img src="/badge/{sim_id}.svg">`). ### 2. Agent Stance Heatmap

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Every existing analytics endpoint summarizes agent behavior: final direction counts, top-N stance flippers, stability index across the final 5 rounds. None show the full evolution — which agents were bullish all along, which flipped mid-run, which oscillated before settling. The `trajectory.json` file already contains per-round `bullish_pct` per agent; a 2D matrix (agents × rounds) colored by bullishness is a natural read of that data. `GET /api/simulation/:id/heatmap` returns `{agents: [str], rounds: [int], values: [[float]]}` where `values[i][j]` is agent i's bullishness in round j (0–100 scale). The frontend renders this as an SVG heatmap grid in Step 3: each cell colored on a green (100) → gray (50) → red (0) scale. Researchers reading a simulation can immediately see "agents 1–40 were bullish from round 1; agents 60–80 flipped at round 12; agents 100–120 oscillated throughout." This is the missing temporal dimension. The Nov 16 Consensus Stability Index captured *aggregate* volatility; this captures *individual* volatility. Distinct from the Nov 6 "Agent Activity Heatmap" (which was about post/trade volume per agent, not stance values). SimSwarm does not publish individual per-agent trajectories in any visualization form — this is a differentiator.

**How:**
1. Create `backend/app/services/heatmap_service.py` (~120 LoC, pure stdlib). `build_heatmap(sim_id: str) -> dict`: load `trajectory.json` → extract per-round entries. Collect all unique agent IDs from entries (preserving insertion order as the agent-creation order). For each agent × round: look up `bullish_pct` in that round's agent list. If an agent didn't post in a round (possible for low-engagement agents): interpolate from the nearest prior round's value (forward-fill from last known; default 50 if no prior round). Build `agents: list[str]` (agent names, truncated to 20 chars), `rounds: list[int]` (sorted round numbers), `values: list[list[float]]` (len(agents) × len(rounds) matrix). If more than 100 agents: downsample to 100 by selecting every Nth agent uniformly (preserves first, last, and proportional distribution). If more than 48 rounds: retain every round. Write to `storage/simulations/{id}/heatmap.json` (immutable after completion, no mtime check needed). Return `{sim_id, agents, rounds, values, agent_count: int, round_count: int, downsampled: bool}`. Add 5 unit tests: 3-agent × 3-round case produces correct matrix values; forward-fill works when agent absent in a round; >100 agents triggers downsample (checks `downsampled: true`); agents list length equals `values` row count; rounds list length equals `values[0]` column count.
2. Add `GET /api/simulation/:id/heatmap` to `backend/app/api/heatmap.py`. Keyless for published sims. `Cache-Control: max-age=86400, public`. Response: heatmap JSON as above. If `trajectory.json` absent or sim not completed: `{available: false, reason: "trajectory_not_ready"}`. Add to `surfaces_catalog.py` (type: `analytics`). Add to `docs/API.md` under "Analytics" with a note: "Values are bullishness percentages (0–100). Forward-fill used for agents absent in a given round." Add 2 integration tests: endpoint returns `available: false` for an incomplete sim; `values` matrix is rectangular (all rows same length).
3. Add a "Heatmap" toggle button to the Step 3 analytics panel (alongside existing Stance Flips, Mentions, etc.). Clicking renders an SVG heatmap: agents on the Y-axis (sorted by most-bullish-overall first), rounds on the X-axis. Each cell colored via a 3-stop gradient: `bullish_pct > 60` → green (`#16a34a`), `40–60` → gray (`#6b7280`), `< 40` → red (`#dc2626`), with opacity scaled within each band (0.4–1.0) for granularity. Cell tooltips show `{agent_name}: {bullish_pct}% bullish, round {round}`. If `downsampled: true`, show a small notice: "Showing 100 of {agent_count} agents." Add a "Sort by: Most Bullish / Most Bearish / Most Volatile" toggle that re-sorts the Y-axis without a new API call. Add 2 frontend unit tests: heatmap grid renders with correct number of rows from `agents.length`; tooltip text matches cell's agent name and round.

### 3. Simulation Remix

**Type:** Feature
**Effort:** Small (hours)
**Impact:** A published simulation on a compelling topic is currently a dead end for every operator who isn't the original creator: they can read it, share it, but can't launch a variation without manually re-entering the same topic, agent count, rounds, and platforms from scratch. `POST /api/simulation/:id/remix` creates a new simulation pre-filled from the original's config, owned by the calling user, without duplicating the original. The response includes a pre-fill URL (`/new?from={original_id}`) that takes the operator directly to Step 1 with the topic pre-loaded and a Step 2 with the original's agent count, rounds, and platforms suggested as defaults (editable). The original simulation gets a `remix_count` counter incremented on each remix. `GET /api/simulation/:id/remixes` returns the list of public remixes (sim_id, operator, created_at) for the original. This creates a contribution loop from the gallery: an operator who runs a compelling BULLISH simulation gets organic engagement when others remix it; remix operators get a faster launch path; the original creator gets visibility. For the Nov 30 external PR hyperstition, a remix endpoint is the lowest-friction way for fork owners to contribute: clone the repo, add one endpoint, open a PR. That's a credible "good first issue" framing for the codebase.

**How:**
1. Create `backend/app/services/remix_service.py` (~100 LoC, pure stdlib). `create_remix(original_sim_id: str, operator_id: str) -> dict`: load `storage/simulations/{original_sim_id}/config.json`. Validate: `published: true`, `status: "completed"`. Build `remix_config`: copy `topic`, `agent_count`, `rounds_total`, `platforms` from original config. Add `source_remix_id: original_sim_id`, `operator_id: operator_id`. Generate a new `sim_id` (UUID4). Write `remix_config` to `storage/simulations/{new_sim_id}/config.json` with `status: "draft"` (not launched yet — remix pre-fills the UI, doesn't auto-launch). Increment `remix_count` on the original sim's `config.json` (create field if absent, default 0). Write a `storage/remixes/{original_sim_id}.json` append-log: `{remix_sim_id: new_sim_id, operator_id, created_at}`. Return `{remix_sim_id: new_sim_id, prefill_url: f"/new?from={original_sim_id}&draft={new_sim_id}", original_sim_id}`. `get_remixes(original_sim_id: str) -> list`: load `storage/remixes/{original_sim_id}.json`; for each entry filter to `published: true` by checking the remix's own `config.json`. Return up to 20 newest. Add 4 unit tests: remix on a non-published sim raises ValueError; `remix_count` incremented on original; returned `prefill_url` contains both IDs; `get_remixes` excludes non-published remix sims.
2. Add `POST /api/simulation/:id/remix` to `backend/app/api/remix.py`. Session-auth (must be logged in; can't remix your own sim). Request body: empty (all params from original). Rate-limit: 3 remixes per hour per operator (to prevent spam). Returns 201 with `{remix_sim_id, prefill_url, original_sim_id}`. Add `GET /api/simulation/:id/remixes` (keyless for published sims): returns `{remix_count: int, remixes: [{remix_sim_id, created_at}]}`. Add `remix_count` to the `Signal` OpenAPI schema and to the gallery card response. Add `source_remix_id` to `GET /api/simulation/:id` response. Add both routes to `surfaces_catalog.py` (type: `lifecycle`, `discovery`). Add to `docs/API.md` under "Simulation Lifecycle" with a "Remixing" subsection and note: "Remixing pre-fills the launch form — the remix is not launched automatically." Add 2 integration tests: POST returns 201 with `remix_sim_id`; GET returns `remix_count` matching number of published remixes.
3. Add a "Remix this scenario" button to Step 3 (visible to logged-in users who are NOT the sim's operator). Clicking calls `POST /api/simulation/:id/remix` and redirects to `/new?from={id}&draft={remix_id}` — Step 1 shows the topic pre-filled with an editable banner "Remixing: [original topic]", Step 2 shows the original's agent count and platforms as default values (all editable). Show a `{remix_count} remixes` counter below the topic on the Step 3 signal card, linking to a `/s/{id}/remixes` page that lists public remixes in a simple table. ### 5. Simulation Chain

**Type:** Feature
**Effort:** Medium (1-2 days)
**Impact:** Simulations are currently isolated: each run starts from a blank world-state, with no memory of prior runs on the same topic. For research use cases — "what happens to agent consensus when they're told the prior simulation said BULLISH?" — there's no mechanism to feed one simulation's output as the initial condition of the next. A simulation chain links two or more simulations in sequence: Sim B gets Sim A's signal injected as an opening director event ("Prior simulation of this topic returned BULLISH at 73% confidence across 100 agents over 48 rounds"). This creates a reflexivity-testing primitive: run Sim A clean, then chain Sim B to test whether knowledge of Sim A's result changes the consensus. The chain relationship is stored as `parent_sim_id` on the child simulation's config, and `GET /api/simulation/:id/chain` returns the full lineage tree. Chain depth is capped at 5 to prevent runaway recursion. Each node in the chain tree shows direction, confidence, and stability — the lineage becomes a data artifact itself. For the PolySwarm research community (arXiv 2604.03888), simulation chains are the missing primitive for multi-step scenario testing: "Phase 1: clean simulation. Phase 2: chain with Phase 1's result. Phase 3: chain with Phase 2's result + an exogenous shock." No existing open-source simulation tool implements this.

**How:**
1. Create `backend/app/services/chain_service.py` (~180 LoC, pure stdlib). `create_chain(parent_sim_id: str, operator_id: str, config_overrides: dict = None) -> dict`: load parent's `config.json` (validate: `published: true`, `status: "completed"`). Load parent's `signal.json` → extract `direction`, `confidence_pct`, `stability_label`, `agent_count`, `rounds_total`. Build chain director event string: `f"Prior simulation: {parent_direction} at {parent_confidence}% confidence across {parent_agent_count} agents over {parent_rounds} rounds (stability: {parent_stability_label})."`. Build child config: clone parent's `topic`, `agent_count`, `platforms`; set `parent_sim_id: parent_sim_id`; set `chain_depth: get_chain_depth(parent_sim_id) + 1`; inject the chain director event as `chain_context` field. Apply `config_overrides` (allow changing `agent_count`, `rounds_total`, `platforms` — not `topic`). Validate `chain_depth <= 5` (raise `ChainDepthError` otherwise). Generate new `sim_id`. Write to storage. `get_chain_depth(sim_id: str) -> int`: recursively follow `parent_sim_id` pointers in `config.json` files, counting depth (max 5 hops to avoid infinite loops on corrupt state). `get_chain_tree(root_sim_id: str) -> dict`: BFS from root_sim_id using `parent_sim_id` pointers, build `{sim_id, direction, confidence_pct, stability_label, created_at, children: []}` tree. Add 5 unit tests: `chain_depth > 5` raises `ChainDepthError`; chain director event string contains correct direction and confidence; `get_chain_depth` returns 0 for root sim; `get_chain_depth` returns 2 for grandchild sim; `get_chain_tree` BFS returns correct tree shape for a 3-node chain.
2. Add `POST /api/simulation/:id/chain` to `backend/app/api/chain.py`. Session-auth (must own the parent sim OR parent must be public). Request body: `{config_overrides?: {agent_count?: int, rounds_total?: int, platforms?: list}}`. Rate-limit: 10 chains per operator per 24h. Returns 201 with `{child_sim_id: str, chain_depth: int, chain_context_injected: str, launch_url: str}`. The child sim is created with `status: "draft"` — it pre-fills the launch form, it doesn't auto-launch. Add `GET /api/simulation/:id/chain` (keyless for published sims): returns `{root_sim_id: str, chain_depth: int, tree: {sim_id, direction, confidence_pct, stability_label, created_at, children: []}}`. Add `parent_sim_id`, `chain_depth` to the `Signal` OpenAPI schema. Add to `surfaces_catalog.py` (type: `lifecycle`, `analytics`). Add to `docs/API.md` under "Simulation Lifecycle" with a "Simulation Chains" subsection, a diagram (ASCII tree), and a note: "Chain depth is capped at 5. The child simulation is created as a draft — you review and launch it manually." Add 3 integration tests: POST returns 201 with `chain_context_injected` text; `chain_depth: 1` for immediate child; GET chain tree has correct number of nodes.
3. Add a "Chain this simulation" button to Step 3 (visible to operator; also visible to logged-in users when parent is public). Clicking opens a sidebar: "Start a chained simulation — the prior result will be injected as context." Shows the chain director event text (read-only preview), and optional overrides for agent count, rounds, and platforms. "Launch Chain" calls `POST /api/simulation/:id/chain`, then redirects to Step 2 with the child sim's config pre-filled. On Step 3 for a chained sim: show a "Chain context" banner above the signal card: "This simulation had access to: [parent direction] at [parent confidence]% from [parent topic]" with a "View parent →" link. Add a chain tree visualization on the Step 3 "Details" panel: each node is a small direction badge; arrows connect parent to child; the current sim is highlighted. Cap the displayed tree at 5 levels. Add 2 frontend unit tests: chain context banner renders when `parent_sim_id` is set; "Chain" button is hidden when `chain_depth >= 5`.
