### 1. Simulation Round Replay

**Type:** Feature
**Effort:** Small (hours)
**Impact:** `trajectory.json` is generated for every completed simulation and already powers the Per-Round Confidence Trajectory chart and Agent Stance Heatmap suggestions. It contains per-agent stance values, platform activity counts, and belief drift metrics for every round. The frontend, however, only surfaces the final state. There is no way to step through how consensus formed round by round — to see, for example, that the simulation started NEUTRAL at round 3, flipped BULLISH by round 8 when a platform event injected breaking news, then held BULLISH through round 48. A "Replay" mode in Step 3 adds a scrubber control (a range input from round 1 to N) that steps through the simulation's history. Each round tick updates: the direction badge (recalculated from that round's agent stances), the confidence dial (that round's aggregate confidence_pct), and the platform activity counts. The underlying `trajectory.json` is already loaded for the confidence trajectory chart — this reuses the same data fetch with zero new API surface. The only new backend surface is optional: a `GET /api/simulation/:id/trajectory/round/:n` convenience endpoint (returns a snapshot for a single round). The core feature can be implemented purely in the frontend by filtering the already-loaded trajectory data. For researchers publishing a simulation in an article or social post, being able to record and share a replay of the full consensus formation arc makes the result substantially more compelling than a single final badge. This is the temporal dimension already paid for, made visible.

**How:**
1. In `Step3Simulation.vue`, add a "Replay" toggle button to the analytics toolbar (alongside existing Stance Flips, Mentions, etc.). When activated: load the full `trajectory.json` via `GET /api/simulation/:id/confidence/trajectory` (already implemented). Parse rounds into a sorted array of snapshots, each with `{round: int, bullish_pct: float, bearish_pct: float, neutral_pct: float, confidence_pct: float, platform_counts: {twitter: int, reddit: int, polymarket: int}}`. Show a range scrubber (`<input type="range" min="1" max="N">`) labeled "Round N of M" with Previous/Next buttons and a Play/Pause button that auto-advances every 1.5 seconds. As the scrubber moves, reactively update the direction badge, confidence dial, and a "Platform Activity" mini-bar in the replay panel using the current round's snapshot values. Add a small "current round" label above the scrubber. Add a 2-round transition CSS animation on the direction badge when it changes value (scales up briefly, then settles). The direction at round N is derived from: `bullish_pct > bearish_pct + 10 → BULLISH; bearish_pct > bullish_pct + 10 → BEARISH; else NEUTRAL`. Add 2 frontend unit tests: scrubber at round 1 shows the first round's direction; Play advances the round counter automatically.
2. Add the optional `GET /api/simulation/:id/trajectory/round/:n` to `backend/app/api/trajectory.py` (create if absent, or add to `simulation.py`). Keyless for published sims. Loads `trajectory.json`, filters to entries where `round == n`, returns `{round: n, agent_snapshots: [{agent_id, bullish_pct, platform, action_type}], aggregate: {bullish_pct, bearish_pct, neutral_pct, confidence_pct}}`. Returns `{available: false}` if `trajectory.json` absent or round out of range. `Cache-Control: max-age=86400, public` (immutable after sim completes). Add to `surfaces_catalog.py` (type: `analytics`). Add to `docs/API.md` under "Analytics" with note: "Returns a single-round snapshot. Useful for step-through tools and round-level webhooks." Add 2 unit tests: returns 404-equivalent `{available: false}` for round 0; returns correct `aggregate.bullish_pct` matching the trajectory data for a known round.
3. Add a "Copy replay link" option to the Step 3 share panel. It generates a URL with a `?round=N` query param (e.g., `/s/SIM_ID?round=12`) that pre-opens the replay mode at a specific round. The page loads, reads `?round=N`, auto-opens the replay panel, and positions the scrubber at round N. This makes it shareable: "here's the exact moment the simulation flipped BULLISH" as a direct link. No new backend needed — purely a frontend URL read on mount. Add 1 frontend unit test: mounting `Step3Simulation.vue` with `?round=8` in the query sets the initial replay position to 8.

### 2. Open Graph Share Previews

**Type:** Growth
**Effort:** Small (hours)
**Impact:** Simulation permalinks (`/s/:id`) are bare HTML pages with no `<meta og:...>` tags. When pasted into Slack, Discord, Twitter, iMessage, or any modern messaging platform, they unfurl as plain URLs — no title, no description, no image. Every time an operator shares a simulation result — "here's the BULLISH consensus from 100 agents on this topic" — the link looks like noise instead of signal. Adding Open Graph metadata to simulation pages transforms every shared link into a mini-ad for the result. The tags needed: `og:title` (simulation topic), `og:description` (direction badge, confidence, agent count, round count — e.g., "BULLISH · 73% confident · 100 agents · 48 rounds"), `og:image` (a generated share card PNG or the site logo as fallback), `og:url` (canonical permalink), `twitter:card: summary_large_image`. On the backend, simulation permalinks are likely served via a template (`templates.py` exists in the API); the OG tags are injected server-side so crawlers see them without JavaScript. This is a 1-2 hour backend change with zero new data collection — `signal.json` already has everything needed for the description string. The viral multiplier: every shared simulation link now carries a visual preview. With the Dec 7 star hyperstition 11 stars short, every Slack link drop, Discord share, and Twitter post is a discovery event. OG tags make each one effective.

**How:**
1. Add `GET /api/simulation/:id/og-meta` to `backend/app/api/og.py` (or inline into `simulation.py`). Keyless for published sims. Load `signal.json` → extract `direction`, `confidence_pct`, `agent_count`, `rounds_total`, `topic`. Return `{title: str, description: str, image_url: str, canonical_url: str}`. Title: `"{topic} — MiroShark Simulation"` (truncated to 70 chars). Description: `"{DIRECTION} · {confidence_pct}% confident · {agent_count} agents · {rounds_total} rounds · miroshark.xyz"` (truncated to 160 chars). `image_url`: `/api/simulation/{id}/og.png` if the PNG endpoint exists (see step 2), else `https://miroshark.xyz/og-default.png`. `canonical_url`: `https://miroshark.xyz/s/{id}`. For non-published/incomplete sims: return neutral defaults (`title: "MiroShark — Simulate anything"`, `description: "Universal Swarm Intelligence Engine · $1 · 10 min · 100+ grounded agents"`). Add to `surfaces_catalog.py` (type: `meta`). Add 2 unit tests: published sim returns topic-based title; non-published sim returns neutral default title.
2. Add `GET /api/simulation/:id/og.png` to the same file. Pure-stdlib SVG-to-PNG approach is heavyweight (no Pillow in stdlib); instead, generate a minimal SVG and return `Content-Type: image/svg+xml` with `Content-Disposition: inline; filename="og.svg"` — most OG crawlers (Slack, Discord, iMessage) fetch and display SVGs correctly as preview images. Fallback: if `signal.json` absent or sim unpublished, return a generic MiroShark branding SVG (pre-built static file at `backend/static/og-default.svg`). Add 2 unit tests: published sim SVG contains the topic text; unpublished sim returns the default static SVG.
3. In the Vue SSR template (or in the FastAPI HTML response for `/s/:id`), inject OG meta tags server-side by calling `get_og_meta(sim_id)` before rendering the HTML response. Add to `<head>`: `<meta property="og:title" content="...">`, `<meta property="og:description" content="...">`, `<meta property="og:image" content="...">`, `<meta property="og:url" content="...">`, `<meta name="twitter:card" content="summary_large_image">`, `<meta name="twitter:title" content="...">`, `<meta name="twitter:description" content="...">`, `<meta name="twitter:image" content="...">`. ### 4. Confidence Distribution Histogram

**Type:** Feature
**Effort:** Small (hours)
**Impact:** The confidence dial shows `confidence_pct: 65%`. Two simulations can produce identical `confidence_pct` values with opposite internal dynamics: one where 95% of agents cluster between 60–70% bullish (strong, narrow consensus), and one where 40% of agents are >80% bullish and 30% are <20% bullish (a deeply divided agent population with a polarized split). The aggregate number is the same; the distributions are opposite; the conclusions are different. `GET /api/simulation/:id/confidence-distribution` loads the final-round per-agent `bullish_pct` values from `trajectory.json`, buckets them into 10 equal bands (0–10%, 10–20%, ..., 90–100%), and returns `{buckets: [{range: "60-70%", count: 42, pct: 42.0}], stats: {mean: float, median: float, std_dev: float, skew: "left" | "symmetric" | "right"}, shape: "unimodal" | "bimodal" | "flat", agent_count: int}`. The `shape` classification: "bimodal" if two non-adjacent buckets each hold >20% of agents with a valley (<10%) between them; "unimodal" if the top 3 adjacent buckets hold >60%; "flat" otherwise. The frontend adds a small histogram below the confidence dial in Step 3: 10 vertical bars, colored by range (green for 60–100%, gray for 40–60%, red for 0–40%), with the bar height proportional to the bucket count. A one-line annotation below the histogram: "Strong consensus (unimodal, σ=8.3)" or "Divided (bimodal: 42% bullish cluster, 31% bearish cluster)". This directly answers what experienced researchers want to know: is this 65% confident because everyone agrees a little, or because half the room disagrees strongly?

**How:**
1. Create `backend/app/services/distribution_service.py` (~110 LoC, pure stdlib). `build_confidence_distribution(sim_id: str) -> dict`: load `trajectory.json`. Find the max round number. Collect all agents' `bullish_pct` values from that final round. Create 10 buckets: `[0,10), [10,20), ..., [90,100]`. Count agents per bucket. Compute `mean = sum(values) / len(values)`, `median` (sorted midpoint), `std_dev = sqrt(sum((x - mean)^2 for x in values) / len(values))`. Classify `skew`: `mean - median > 5 → "left"`, `median - mean > 5 → "right"`, else `"symmetric"`. Classify `shape`: scan buckets for bimodal pattern (two peaks each >20% with a valley <10% between them); if top 3 adjacent buckets >60% of agents → "unimodal"; else "flat". Write cache to `storage/simulations/{id}/confidence_distribution.json` with mtime invalidation against `trajectory.json`. Return `{sim_id, agent_count, buckets: [{range_label: str, low: float, high: float, count: int, pct: float}], stats: {mean, median, std_dev, skew}, shape, generated_at}`. Add 5 unit tests: 10 agents all at 65% bullish → shape "unimodal"; 5 agents at 15% + 5 agents at 85% → shape "bimodal"; std_dev computed correctly for known values; skew "left" when mean < median - 5; bucket pct sums to ~100%.
2. Add `GET /api/simulation/:id/confidence-distribution` to `backend/app/api/distribution.py`. Keyless for published sims. `Cache-Control: max-age=86400, public` (immutable post-completion). Returns distribution JSON as above. If `trajectory.json` absent or sim not completed: `{available: false, reason: "trajectory_not_ready"}`. Add `OpenAPI ConfidenceDistributionResponse` schema: `buckets` array with `range_label`, `count`, `pct`; `stats` object; `shape` enum. Add to `surfaces_catalog.py` (type: `analytics`). Add to `docs/API.md` under "Analytics" with note: "Agent confidence values are from the final simulation round. `shape` is classified as unimodal, bimodal, or flat." Add 2 integration tests: endpoint returns `available: false` for an in-progress sim; `buckets` array length is exactly 10.
3. In `Step3Simulation.vue`, add a "Distribution" toggle below the confidence dial. When active: render a small histogram (10 bars, each ~20px wide, max height 80px, bar height proportional to `pct`). Color coding: bars for ranges 60–100% → green (`#16a34a`, opacity 0.7); 40–60% → gray (`#6b7280`, opacity 0.7); 0–40% → red (`#dc2626`, opacity 0.7). Tooltip on hover: `"{range_label}: {count} agents ({pct}%)"`. Below the histogram: a one-line annotation built from `shape` and `stats`: `"unimodal" + std_dev ≤ 10 → "Strong consensus (σ={std_dev}%)"`, `"bimodal" → "Divided (two clusters)"`, `"flat" → "Dispersed (σ={std_dev}%)"`. Add `shape` text as a small chip below the confidence dial when the Distribution panel is closed: "Unimodal" (blue), "Bimodal" (yellow), "Flat" (gray). Add 2 frontend unit tests: histogram renders with 10 bars; tooltip text matches `buckets[i].range_label` and `pct`.

### 5. Self-Hosted Setup Healthcheck

**Type:** DX improvement
**Effort:** Small (hours)
**Impact:** The Nov 21 Docker Hub publishing fix (`docker pull miroshark/miroshark`) means the barrier to self-hosting has dropped from "clone, build, configure" to "pull, configure, run." 303 forks exist. If even 5% attempt self-hosting, that's 15 operators debugging independently. The current diagnosis path is: check terminal logs, `docker logs`, read `INSTALL.md`, post a GitHub issue. There is no structured health endpoint that tells you exactly what's broken. `GET /api/health/full` returns a structured check for all required dependencies: LLM API (send a minimal test prompt), database (ping), storage (write + read a temp file), environment variables (check required vars are set without exposing their values). Each check returns `{name: str, status: "ok" | "warn" | "error", message: str, latency_ms: int}`. The frontend adds a "System Health" link in the account settings sidebar (for operators) that renders the health check as a checklist: green ✓ for ok, yellow ⚠ for warn, red ✗ for error, with an expansion panel per failed check showing the `message` and a "How to fix" hint from a static lookup table. For fork owners debugging a fresh deployment, this reduces mean-time-to-working from "ask a GitHub issue and wait" to "open `/health/full`, see which dependency is red, follow the hint." `status.py` likely already has a basic liveness ping — this is a full *readiness* check with actionable error messages.

**How:**
1. Create `backend/app/services/health_service.py` (~160 LoC, pure stdlib). `run_full_healthcheck() -> dict`: run each check as a function that returns `{name, status, message, latency_ms}`. (b) **database** — `graph_service.ping()` or equivalent; execute a no-op query (e.g., `MATCH (n) RETURN count(n) LIMIT 1` for Neo4j); status: `"ok"` on success, `"error"` with exception message on failure; latency_ms recorded. (c) **storage** — write `storage/.healthcheck-{uuid4()[:8]}` with content `"healthcheck"`, read it back, delete it; status: `"ok"` on round-trip success, `"error"` with errno on failure. (d) **llm** — send a minimal prompt ("Reply with the word OK.") to the configured LLM via the existing LLM client; status: `"ok"` if response received within 10s, `"warn"` if >5s, `"error"` on timeout or API error; latency_ms recorded; on `"warn"` or `"error"`, include a sanitized error message (strip API key patterns from stack trace using `re.sub`). (e) **version** — read `VERSION` file or git tag; status: always `"ok"`, message: version string. Aggregate: `overall_status = "ok"` if all ok/warn; `"error"` if any check is error. Return `{overall_status, checked_at: str, checks: [list of check results]}`. Add 4 unit tests: missing env var → environment check is "error"; storage failure → status "error"; all checks ok → overall_status "ok"; any check error → overall_status "error".

Run `run_full_healthcheck()` and return JSON. Add `GET /api/health` (unauthenticated, liveness-only) that returns `{status: "ok", version: str}` instantly without running active probes — keep this compatible with the existing `status.py` pattern. Add to `surfaces_catalog.py` (type: `ops`). Add to `docs/API.md` under "Operations" with a note: "Requires operator authentication. Runs active probes — may take up to 15 seconds. Do not use for liveness checks in Docker Compose or Kubernetes; use `GET /api/health` for that." Results render as a vertical checklist: each check is a row with an icon (✓/⚠/✗ colored green/yellow/red), the check `name` as a label, `latency_ms` as a right-aligned gray badge, and the `message` as a small monospace line below the label.
