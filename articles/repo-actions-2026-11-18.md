### 1. Scheduled Recurring Simulation

**Type:** Feature
**Effort:** Medium (1-2 days)
**Impact:** Operators monitoring ongoing topics — weekly crypto sentiment, daily election pulse, bi-weekly earnings reaction — relaunch the same simulation manually every time. A `recurrence` field in the simulation config (`{schedule: "weekly"|"daily"|"biweekly", day_of_week: int, hour_utc: int, enabled: bool}`) lets the system automatically relaunch with the same topic, agents, and platforms on the configured cadence. Each recurrence creates a new simulation with `parent_config_id` pointing to the original, allowing the gallery to group them as a time series. `GET /api/simulation/series/:config_id` returns all runs in chronological order with their signal direction, confidence, and stability — a lightweight longitudinal view: "BULLISH → NEUTRAL → BULLISH across 4 consecutive weekly runs." This is the missing piece for operators who care about *trajectory*, not just a single result. The PolySwarm paper (arXiv 2604.03888) explicitly notes that single-run evaluations miss directional drift over time — a recognized limitation in multi-agent forecasting research. No new data sources; purely a scheduler loop on existing launch infrastructure. The `batch_status.py` service already handles multi-simulation state, and the existing background task framework handles async launch.

**How:**
1. Create `backend/app/services/recurrence_service.py` (~200 LoC, pure stdlib). `RecurrenceConfig` dataclass: `{config_id: str, operator_id: str, topic: str, base_config: dict, schedule: Literal["daily","weekly","biweekly"], day_of_week: int | None, hour_utc: int, enabled: bool, created_at: str, last_run_at: str | None, next_run_at: str}`. `compute_next_run(config: RecurrenceConfig, from_dt: datetime) -> datetime`: for `daily` → next occurrence of `hour_utc`; for `weekly` → next `day_of_week` at `hour_utc`; for `biweekly` → next every-14-days occurrence. Write to `storage/recurrences/{config_id}.json`. `check_due(now: datetime) -> list[RecurrenceConfig]`: scan all `storage/recurrences/*.json`, load each, return configs where `enabled: true` and `next_run_at <= now.isoformat()`. `fire_recurrence(config: RecurrenceConfig) -> str`: clone `base_config`, set `source_recurrence_id = config.config_id`, launch via existing simulation launch path → returns new `sim_id`. Update `last_run_at`, compute and write `next_run_at`. Add a `GET /api/simulations/series/:config_id` endpoint: scan `storage/simulations/*/config.json` for `source_recurrence_id == config_id`, sort by `completed_at`, return `{config_id, runs: [{sim_id, completed_at, direction, confidence_pct, stability_label}]}`. Add 5 unit tests: `compute_next_run` returns correct next-daily datetime when `hour_utc=9`; weekly with `day_of_week=1` returns next Monday; biweekly returns exactly 14 days from last run; `check_due` returns only enabled configs past `next_run_at`; `fire_recurrence` updates `last_run_at` and sets `next_run_at` to future.
2. Add `POST /api/simulations/schedule` to `backend/app/api/recurrence.py`. Session-auth. Request body: `{topic: str, base_config: dict, schedule: str, day_of_week: int | null, hour_utc: int}`. Validates `hour_utc ∈ [0, 23]`, `day_of_week ∈ [0, 6]` when `schedule == "weekly"`. Creates `RecurrenceConfig`, writes to storage, computes `next_run_at`. Returns `{config_id, next_run_at, series_url: "/api/simulations/series/{config_id}"}`. Add `GET /api/simulations/schedule` (session-auth, lists operator's recurrences), `PATCH /api/simulations/schedule/:config_id` (toggle `enabled`, update `hour_utc`/`day_of_week`), `DELETE /api/simulations/schedule/:config_id` (disable and archive). Add a background task in the FastAPI app startup (`@app.on_event("startup")`) that runs `check_due` every 5 minutes in an `asyncio` background coroutine and fires due recurrences. Add all endpoints to `surfaces_catalog.py` (type: `lifecycle`). Add to `docs/API.md` under "Simulation Lifecycle" with a "Recurring Simulations" subsection and a time-series example. Add 3 integration tests: POST creates recurrence with correct `next_run_at`; PATCH toggle sets `enabled: false`; GET returns 0 items for operator with no schedules.
3. Add a "Schedule" toggle to Step 2 (below the launch button): "Repeat this simulation?" with a frequency selector (Daily / Weekly / Biweekly) and time picker. When toggled, the launch button becomes "Launch + Schedule" and shows "Next run: {next_run_at formatted}." After launch, the Step 3 page shows a "Part of a recurring series" header when `source_recurrence_id` is set, with a "View all {N} runs in this series" link that opens `GET /api/simulations/series/:config_id` as a timeline chart: each run plotted by date with `direction` color (green/red/gray) and `confidence_pct` as y-axis. Operators can disable the schedule from this timeline view without leaving Step 3. Add 2 frontend unit tests: Schedule toggle renders frequency selector when enabled; timeline chart renders with correct number of data points from series API response.

### 2. Simulation Health Score

**Type:** Feature
**Effort:** Small (hours)
**Impact:** A simulation run for 3 rounds with 10 agents on a single platform produces a signal — but that signal has very low validity. The same `direction: "BULLISH"` from 100 agents across 3 platforms over 48 rounds is a qualitatively different output. Currently these two results are displayed identically in the gallery. A `health_score` (0–100) built from four sub-dimensions makes quality legible at a glance: (1) **Coverage** — how many platforms were simulated (1 = 25pts, 2 = 50pts, 3 = 75pts, 4+ = 100pts, normalized to 25pt contribution); (2) **Depth** — `min(round_count / 24, 1.0) × 25pts` (24 rounds is the typical full run); (3) **Scale** — `min(agent_count / 50, 1.0) × 25pts` (50 agents is the standard pool); (4) **Richness** — 5pts each for: has director events, has controversy_score, has stability_index, has difficulty_score, has network graph (`world_graph.json` present). Max richness = 25pts. `health_label`: "High" (≥75), "Moderate" (40–74), "Low" (<40). Zero new data sources — all derived from existing `config.json` and presence/absence of service output files. Pure stdlib, computed once at sim completion and cached alongside `signal.json`. Researchers reading a simulation's results now have an immediate sense of whether the sample is worth citing.

**How:**
1. Create `backend/app/services/health_service.py` (~100 LoC, pure stdlib). `compute_health(sim_id: str) -> dict`: Load `config.json` → extract `{platforms: list, agents_count: int, rounds_total: int, director_events: list}`. Compute `coverage_pts = min(len(platforms), 4) / 4 * 25`. `depth_pts = min(rounds_total / 24, 1.0) * 25`. `scale_pts = min(agents_count / 50, 1.0) * 25`. `richness_pts = 0`; for each of `[signal.json (has controversy_score key), signal.json (has stability_index key), signal.json (has difficulty_score key), world_graph.json (file exists), director_events (non-empty)]`: +5 if present. `health_score = round(coverage_pts + depth_pts + scale_pts + richness_pts)`. `health_label`: ≥75 = "High", ≥40 = "Moderate", else "Low". Write to `storage/simulations/{id}/health.json`: `{sim_id, health_score: int, health_label: str, breakdown: {coverage_pts, depth_pts, scale_pts, richness_pts}, computed_at: str}`. Merge `health_score`, `health_label` into `signal.json`. Add 5 unit tests: 3-round / 10-agent / 1-platform / no enrichments → score < 40, label "Low"; 48-round / 100-agent / 3-platform / all enrichments → score = 100, label "High"; `breakdown` keys sum to `health_score`; sim with 50 agents = 25 scale_pts exactly; sim with 2 platforms = 12.5 coverage_pts.
2. Add `GET /api/simulation/:id/health` to `backend/app/api/health.py`. Keyless for published sims. `Cache-Control: max-age=86400, public`. Response: `{available: bool, health_score: int, health_label: str, breakdown: {coverage_pts: float, depth_pts: float, scale_pts: float, richness_pts: float}}`. Hook `compute_health(sim_id)` into the sim completion path alongside existing analytics computations. Add `health_score`, `health_label` to the `Signal` OpenAPI schema. Add to `surfaces_catalog.py` (type: `analytics`). Add to `docs/API.md` under "Analytics" with a note: "Health score measures simulation quality, not prediction accuracy." Add 2 integration tests: endpoint returns `health_score ∈ [0, 100]` for a completed published sim; `health_score` appears in `signal.json` after sim completes.
3. Add a health badge to the gallery card: a small colored pill (`health_label`, green/yellow/red) in the bottom-left of each card, alongside the existing confidence and direction badges. Add a `?min_health=75` gallery filter ("High quality only") — useful for researchers who want to filter out low-sample simulations. Add a health breakdown tooltip on hover: shows the four sub-dimension scores as a small bar chart. Add `health_score` to the article generator block: "Quality: {health_label} ({health_score}/100)" as a footnote on the signal card section. Add 2 frontend unit tests: gallery card renders health pill with correct color class for each label; `?min_health` query param filters the gallery results to `health_score >= value`.

### 3. JavaScript Embed Widget

**Type:** Integration
**Effort:** Small (hours)
**Impact:** MiroShark results exist at miroshark.xyz but can't be embedded inline in Substack posts, blog articles, research pages, or GitHub READMEs without a screenshot. A screenshot loses the data, the confidence number, the platform breakdown, and any interactivity. A lightweight JavaScript embed widget (`<script src="https://miroshark.xyz/embed.js">` + `<div data-miroshark-sim="SIM_ID">`) renders a live simulation result card inline — direction badge, confidence bar, platform list, topic title, and a "View full simulation" link. The widget is entirely read-side: it fetches the sim's `signal.json` from the existing public API and renders it in a shadow DOM (no style conflicts with the host page). Under 5KB minified. This addresses the distribution gap identified in every recent repo-actions round: reach doesn't grow if results only live on one domain. Every embedded simulation is a backlink. Every backlink is a referral. The oEmbed service handles link previews when URLs are pasted; the embed widget handles intentional inline embedding. These are complementary, not overlapping. Similar to how Polymarket embeds market odds into Substack — `polymarket.com/embed` is a recognized traffic driver for them.

**How:**
1. Create `frontend/src/embed/embed.js` (~150 LoC vanilla JS, no framework dependency). Runs as a standalone script tag. On `DOMContentLoaded`: find all `[data-miroshark-sim]` elements. For each: extract `SIM_ID = el.getAttribute("data-miroshark-sim")`. Fetch `https://miroshark.xyz/api/simulation/{SIM_ID}/signal.json` (keyless, public). On success: build a shadow root on the element, inject a minimal HTML card: topic title (truncated to 60 chars), direction badge (BULLISH/BEARISH/NEUTRAL with green/red/gray color), confidence bar (`confidence_pct` as a filled bar + percentage text), platform chips (`platforms` array), a subtle "MiroShark" watermark logo (SVG inline, 12px), and a "View full simulation →" link to the share URL. Card is 320px wide, auto-height, uses CSS variables for theming (overridable by host page via `--miroshark-bg`, `--miroshark-text`, `--miroshark-accent` custom props). On fetch error or 404: render a "Simulation not available" fallback card (no empty div). Build target: `frontend/public/embed.js` (minified, served as a static asset). `Cache-Control: max-age=86400, public` on the embed.js route. Add 3 unit tests (Vitest): card renders `direction` badge with correct text for each of BULLISH/BEARISH/NEUTRAL; card renders "Simulation not available" on HTTP 404; shadow DOM is attached (not global DOM pollution).
2. Add `GET /embed/:sim_id` to serve a full-page embed-compatible iframe version (for platforms like Substack that sandbox `<script>` tags). The iframe page is a minimal HTML shell (`<head>` with charset + viewport, `<body>` with the card HTML) generated server-side from `signal.json` — no Vue or Vite overhead, pure Jinja template. Add an `X-Frame-Options: ALLOWALL` header on this route (or `Content-Security-Policy: frame-ancestors *`) so it can be iframed from any origin. The embed.js widget auto-falls-back to `<iframe src="/embed/{SIM_ID}">` on CSP-blocked environments (detects via a try/catch around shadow DOM attachment). Update `GET /api/simulation/:id` to include `embed_url: "/embed/{sim_id}"` and `embed_script: '<div data-miroshark-sim="{sim_id}"></div><script src="https://miroshark.xyz/embed.js"><\/script>'` in the response. Add both to `surfaces_catalog.py` (type: `distribution`). Add to `docs/API.md` under "Sharing & Distribution" with a "Embed a simulation" section and a copy-pasteable snippet. Add 2 integration tests: `/embed/{sim_id}` returns 200 HTML with `direction` text; response includes `X-Frame-Options: ALLOWALL` header.
3. Add a "Copy embed code" button to the Step 3 share panel (alongside existing share buttons). Clicking copies the two-line snippet to clipboard and shows a "Copied!" toast. Show a live preview of the embed card below the button — the actual rendered widget using the same shadow DOM logic from `embed.js`, scoped to the preview container. Add a "Substack-compatible iframe" toggle that switches the snippet between the script-tag form and the iframe form. Add `embed_url` and `embed_script` to the OpenGraph and oEmbed metadata on the sim share page (so platforms that use oEmbed — Notion, Slack, Discord — will request the full card via oEmbed rather than the plain `<title>` preview). Add 2 frontend unit tests: "Copy embed code" button writes the two-line snippet to clipboard; Substack toggle switches snippet text to `<iframe>` form.

### 4. Automated Weekly Email Digest

**Type:** Integration
**Effort:** Small (hours)
**Impact:** Operators who run multiple simulations per week have no passive way to receive a summary of their own output. They must visit the gallery manually to see what completed. An automated weekly digest email (`GET /api/users/:id/simulations?week=last&format=digest`) covers all simulations completed in the prior 7 days: each in one row with direction badge, confidence, topic (truncated), and a "View" link. The email is sent every Monday at 09:00 UTC for each operator who has enabled digest mode. The existing `email_notify.py` service handles delivery — no new email infrastructure. This is distinct from the Nov 8 "Email Digest Export" (a manual single-simulation export to a list of recipients): this is a *subscription*, auto-triggered, covering the operator's own portfolio. Zero new data sources — the weekly digest is a filtered view of `signal.json` files the operator already owns. Operators subscribe via `PATCH /api/users/:id/settings` with `{email_digest: true, digest_day: "monday", digest_hour_utc: 9}`. The first send arrives the following Monday. No send if zero simulations completed in the prior 7 days. For operators building a research track record, a weekly digest is the minimum viable publication schedule.

**How:**
1. Create `backend/app/services/digest_service.py` (~160 LoC, pure stdlib). `DigestConfig` dataclass: `{operator_id: str, email: str, enabled: bool, digest_day: int, digest_hour_utc: int, last_sent_at: str | None, next_send_at: str}`. `compute_next_send(config: DigestConfig, from_dt: datetime) -> datetime`: same logic as `recurrence_service.compute_next_run` for weekly cadence. `build_digest(operator_id: str, since_dt: datetime) -> dict | None`: scan `storage/simulations/*/config.json` for `operator_id` match, `published: true`, `status: "completed"`, `completed_at >= since_dt.isoformat()`. Sort by `completed_at` descending. If count == 0: return `None` (no send). For each sim: load `signal.json` → extract `{sim_id, topic, direction, confidence_pct, controversy_score, health_label, share_url}`. Build `{operator_id, period_start: since_dt.isoformat(), period_end: datetime.utcnow().isoformat(), simulation_count: int, simulations: list[dict]}`. `send_digest(config: DigestConfig, digest: dict) -> bool`: use `email_notify.py`'s `send_email(to: str, subject: str, html_body: str)` function (or equivalent). Subject: `"MiroShark Weekly Digest — {simulation_count} simulations ({period_start_short}–{period_end_short})"`. HTML body: a minimal table (topic | direction badge | confidence | view link) generated via f-string with inline CSS. Returns True on success. Write `{digest_sent: true, sent_at: str, simulation_count: int}` to `storage/digests/{operator_id}/{send_date}.json`. Update `last_sent_at`, `next_send_at` in DigestConfig. Add 5 unit tests: `build_digest` returns None when no completed published sims in window; returns correct count when sims exist; `compute_next_send` returns next Monday at correct hour; `send_digest` returns False gracefully when `email_notify` raises; digest JSON written to storage on success.
2. Add `PATCH /api/users/:id/settings` digest fields to `backend/app/api/settings.py` (or create this endpoint if absent). Session-auth. Fields: `email_digest: bool`, `digest_day: int (0=Mon, 6=Sun)`, `digest_hour_utc: int`. Persist to `storage/users/{id}/settings.json`. Hook digest check into the same 5-minute background scheduler coroutine from the recurrence service (Step 1 of Idea #1 above): call `check_due_digests() -> list[DigestConfig]`, fire each. Add `GET /api/users/:id/settings` (session-auth): returns current settings including `digest_config`. Add a preview endpoint `GET /api/users/:id/digest/preview` (session-auth): returns `build_digest` output for the past 7 days without sending — lets operators preview what their next digest would contain. Add to `surfaces_catalog.py` (type: `distribution`). Add to `docs/API.md` under "Operators" with a "Weekly Digest" subsection. Add 2 integration tests: PATCH with `email_digest: true` writes `settings.json`; preview endpoint returns `simulation_count: 0` for operator with no published sims in past 7 days.
3. Add a "Weekly digest" toggle to the account settings page (or a new `/settings` page if absent). Toggle labeled "Email me a weekly summary of my simulations." Below: a day selector (Monday–Sunday) and a time selector (every hour UTC, default 09:00 UTC). A "Preview next digest" button fetches `/api/users/:id/digest/preview` and renders the digest table inline as a preview — with the same styling as the email HTML. When zero simulations in the preview window: show "No simulations in the past 7 days — your first digest will be sent when you have published simulations." Add 2 frontend unit tests: digest toggle writes `email_digest: true` via PATCH on change; preview table renders with correct row count from API response.

### 5. Trending Topics Feed

**Type:** Growth
**Effort:** Small (hours)
**Impact:** Every published simulation has a `topic` field. Currently there is no aggregation surface — a new visitor to miroshark.xyz has no way to see what other operators are simulating. The existing gallery shows an operator's own sims (or all public sims in bulk) but has no "what's hot" signal. `GET /api/trending` aggregates topic text from published simulations in the past 30 days, groups by keyword clusters, and returns a ranked list of trending topics: `{topic_cluster: str, representative_topic: str, simulation_count: int, avg_confidence_pct: float, modal_direction: str, last_simulated_at: str}`. Clustering uses a simple bag-of-words overlap (word-level Jaccard similarity ≥ 0.3 → same cluster), pure stdlib — no external NLP. Result cached at `storage/analytics/trending.json` with 1-hour mtime invalidation. The trending feed becomes the front page of miroshark.xyz for non-logged-in visitors: a live "here's what people are simulating" surface that creates social proof (1,500-star hyperstition needs organic discovery), reduces bounce rate, and surfaces viral topics before they go cold. For the academic community it's a lightweight pulse of what prediction-market-adjacent questions practitioners are studying. The PolySwarm paper (arXiv 2604.03888) notes that multi-agent systems on Polymarket focus almost exclusively on liquid markets — MiroShark's trending feed shows the full breadth of simulable topics that prediction markets haven't productized yet, a compelling research gap.

**How:**
1. Create `backend/app/services/trending_service.py` (~180 LoC, pure stdlib). `build_trending(since_days: int = 30, min_sims: int = 2) -> list[dict]`: scan `storage/simulations/*/config.json` for `published: true`, `status: "completed"`, `completed_at >= cutoff`. Collect `{sim_id, topic, direction, confidence_pct, completed_at}` per sim. Tokenize each topic: lowercase, split on `[^a-z0-9]`, remove stopwords (a fixed set of ~50 common English stopwords in the module). Build `{topic_tokens: set, ...}` per sim. Cluster: greedy union-find on Jaccard(topic_a_tokens, topic_b_tokens) ≥ 0.3. For each cluster: `simulation_count`, `modal_direction` (most frequent direction), `avg_confidence_pct` (mean), `last_simulated_at` (max completed_at), `representative_topic` (longest topic string in cluster — usually the most descriptive phrasing). Sort clusters by `simulation_count` descending, tie-break by `last_simulated_at` descending. Filter out clusters with `simulation_count < min_sims`. Return up to 20 clusters. Cache to `storage/analytics/trending.json` (1-hour mtime-based). Add 5 unit tests: two topics with Jaccard ≥ 0.3 merge into one cluster; two unrelated topics stay separate; cluster `modal_direction` is correct majority; `representative_topic` is the longest string in the cluster; empty input returns empty list.
2. Add `GET /api/trending` to `backend/app/api/trending.py`. Keyless. Query params: `?since_days=30` (default 30, clamp [7, 90]), `?limit=20` (default 20, clamp [5, 50]). `Cache-Control: max-age=3600, public`. Response: `{generated_at: str, since_days: int, cluster_count: int, clusters: [{topic_cluster: str, representative_topic: str, simulation_count: int, avg_confidence_pct: float, modal_direction: str, last_simulated_at: str}]}`. If fewer than `min_sims` clusters available: return `{available: false, reason: "insufficient_public_data"}` with HTTP 200 (not 404 — trending is always reachable). Add to `surfaces_catalog.py` (type: `discovery`). Add to `docs/API.md` under "Discovery" with a note: "Trending clusters update hourly. Topics appearing fewer than 2 times are excluded." Add 2 integration tests: endpoint returns `available: false` when fewer than 2 published sims exist in the window; `Cache-Control: max-age=3600` header present.
3. Add a "Trending" section to the homepage (or a `/trending` page at `/explore/trending`). Top-of-page layout: a 2-column grid of topic cluster cards. Each card: a large topic text, a direction badge pill (`modal_direction`), a confidence bar, a "simulated N times" counter, and a "Run this scenario →" button that pre-fills Step 1 with `representative_topic` as the topic input. Add a `?topic={representative_topic}` query param to Step 1 that pre-populates the topic field. Add a "Trending" link to the main nav (between "Explore" and "Docs"). Add the trending endpoint URL to `sitemap.py` as a static route (always indexed, not dynamic per-sim). Add 2 frontend unit tests: trending card renders "Run this scenario →" button that navigates to Step 1 with topic pre-filled; `/trending` page renders "No trending topics yet" empty state when API returns `available: false`.
