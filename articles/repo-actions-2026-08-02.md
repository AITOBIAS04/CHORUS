### 2. `miro doctor` CLI Health Command

**Type:** DX improvement
**Effort:** Small (hours)
**Impact:** Fork holders who cannot run MiroShark locally do not file issues — they quietly abandon. There are 298 forks and zero community PRs beyond the 5+ already counted; the activation gap between "forked" and "submitted a PR" is mostly a setup problem. A `miro doctor` command — modeled on `flutter doctor`, `brew doctor`, and `gh auth status` — runs a self-contained diagnostic pass and prints a clear report: green checkmarks for what's working, yellow warnings for degraded config, red errors for blocking issues. The output is also the canonical tutorial artifact: every developer-tool tutorial that targets beginners starts with "first check your setup" and the diagnostic output. A recording of `miro doctor` passing all checks is a 15-second shareable clip that demonstrates the tool is alive and working — exactly what the 26-day social silence needs. The Aug 15 tutorial deadline (0/5, 13 days) has a bottleneck on "getting started" content; `miro doctor` produces that content as a side effect of the command itself.

**How:**
1. In `cli/` (or wherever the CLI entry point lives), add a `doctor` subcommand. `miro doctor` (no args, no auth required). Checks run in sequence, each printing a status line: (1) **API reachability** — GET `/api/activity.json`; pass if HTTP 200, fail with URL if connection refused; (2) **Model availability** — GET `/api/models` or equivalent endpoint that lists available LLM providers; pass if at least one model is available, warn if expected models (Mercury 2, DeepSeek V4 Flash, Gemini 3 Flash) are absent; (3) **Backend version** — GET `/api/version` if it exists; print the version string; warn if unreachable; (4) **Python environment** — check `python --version` >= 3.9, warn if below; (5) **Node environment** — check `node --version` >= 18.0 for frontend dev; warn if absent or below (not a blocking error — API-only usage doesn't need Node); (6) **CLI version** — print the installed CLI version from `__version__`; (7) **WebSocket connectivity** — attempt a brief WebSocket handshake to `/ws` (if applicable); pass if handshake succeeds, warn if it fails (non-blocking); (8) **Recent simulation test** — GET `/api/simulation/search?q=test&limit=1`; pass if HTTP 200 (validates the search surface is live). Output format: aligned table with status emoji (✓ / ⚠ / ✗), check name, and detail string. Final summary line: "N checks passed, M warnings, P errors." Color output if `sys.stdout.isatty()`, plain text otherwise (pipeline-safe). Exit code: 0 if no errors, 1 if any error (warnings do not affect exit code — lets CI integrate with `miro doctor || exit 1`).
2. Add `--json` flag: `miro doctor --json` outputs a JSON object `{checks: [{name, status: "pass"|"warn"|"fail", detail}], passed, warned, failed, timestamp}`. This enables integration with monitoring tools (a GitHub Actions step can run `miro doctor --json | jq '.failed == 0'` to gate a deploy). Add `--fix` flag as a stub: prints "miro doctor --fix is not yet implemented — see docs/SETUP.md for manual remediation steps." The stub documents the future path without implementing it prematurely.
3. Add 5 unit tests (mock all network calls): all checks pass returns exit code 0, one failing check returns exit code 1, `--json` output is valid JSON with correct schema, color output is absent when stdout is not a TTY, `--fix` flag prints the stub message without raising. Update `docs/CLI.md` with the `doctor` subcommand reference, including example output for a clean install and a failed API connection. Add `miro doctor` as step 1 of the "Getting Started" section in `README.md` and `CONTRIBUTING.md`: "Before filing an issue, run `miro doctor` and include the output."

### 5. Simulation Comparison API

**Type:** Feature
**Effort:** Medium (1–2 days)
**Impact:** The academic citation hyperstition (Sep 1) requires MiroShark to be used as a research instrument. Researchers doing parameter sweeps — the methodological standard for computational social science — run the same topic under different conditions (agent count, platform composition, framing variants) and compare outcomes across conditions. Currently there is no way to do this comparison programmatically: each simulation result is a siloed JSON blob. A `GET /api/compare?a={id}&b={id}` endpoint that computes side-by-side comparison of any two published simulations — consensus alignment, confidence delta, round-by-round trajectory divergence, agent archetype overlap — converts MiroShark from "interesting toy" to "comparative research instrument." The comparison object is also the format that tutorial creators need for the "I ran the same topic twice with different parameters" demo posts that make for interesting Dev.to and Medium articles. Distinct from the Simulation Diff API (suggested Jul 22, which versioned the same simulation over time): this compares two independent simulations with potentially different topics, agents, and conditions. Implementation is ~180 LoC, pure stdlib, no new deps.

**How:**
1. Create `backend/app/api/compare.py` (~180 LoC, pure stdlib). `GET /api/compare?a={sim_id_a}&b={sim_id_b}`. Validation: both IDs must be non-empty strings; both simulations must exist and be published (return 404 if either is missing or unpublished, with message indicating which). Computation: load `signal.json` for both simulations. Build the comparison object: `{a: {id, topic, direction, confidence_pct, agents, rounds, platforms, cost_usd}, b: {id, topic, direction, confidence_pct, agents, rounds, platforms, cost_usd}, comparison: {consensus_aligned: bool (same direction), confidence_delta: float (b.confidence_pct - a.confidence_pct), direction_match: "same"|"opposite"|"neutral_vs_directional", topic_similarity: null (not computed — too expensive), agent_count_delta: int (b.agents - a.agents), round_count_delta: int, shared_platforms: [list], platforms_only_in_a: [list], platforms_only_in_b: [list], archetype_overlap: {shared: [list], only_in_a: [list], only_in_b: [list]} (if archetype data is available from trajectory.json; otherwise omit), trajectory_correlation: float (Pearson correlation of the per-round consensus_pct arrays across rounds shared by both — computed using only stdlib math; rounds only in one simulation are excluded from the correlation; null if either simulation has fewer than 2 rounds)}}`. `trajectory_correlation` tells researchers whether two simulations tracked the same opinion dynamics even if they started from different topics or agent configurations — a 0.9+ correlation on a replicated study is publishable evidence of reproducibility. Cache-Control: `public, max-age=300` (comparison results are deterministic given fixed simulation IDs). No auth required for public/published simulations. Register the route in the main app router. Add to `surfaces_catalog.py` (type: analytics; surface 42).
2. Add `GET /api/compare` to the OpenAPI spec: full request params schema, CompareResponse schema with all fields documented, example request/response using two real published simulation IDs (use the IDs from the existing test fixtures). Add `compare(sim_id_a, sim_id_b)` method to the Python SDK (`sdk/python/miroshark/client.py`, ~15 LoC): `MiroShark.compare(a: str, b: str) -> CompareResult`. `CompareResult` class with all comparison fields as properties; `CompareResult.to_dataframe()` returns a two-row pandas DataFrame (one row per simulation) suitable for display in Jupyter. Add `get_compare(aId: string, bId: string): Promise<CompareResult>` to the TypeScript SDK (`sdk/javascript/src/client.ts`). Add 8 unit tests: valid compare returns 200, missing simulation A returns 404 with message, missing simulation B returns 404 with message, unpublished simulation returns 404, `consensus_aligned` is true when both directions match, `confidence_delta` is correctly signed (b minus a), `trajectory_correlation` is null when fewer than 2 shared rounds, `shared_platforms` lists only platforms present in both.
3. Update `docs/API.md` with a "Simulation Comparison" section: endpoint reference, full JSON schema with field descriptions, curl example comparing two simulations, research use case note ("Use this to compare replications, parameter sweeps, or framing variants — the `trajectory_correlation` field measures opinion dynamics reproducibility"). Add a "Compare two simulations" step to the `quickstart.ipynb` Jupyter notebook in `sdk/python/notebooks/`: runs the same topic twice with different agent counts (e.g. 5 vs 15 agents), calls `.compare()`, displays the comparison in a two-row DataFrame and a side-by-side belief drift chart with matplotlib. The notebook cell output — two charts side by side, a table showing trajectory correlation 0.87 — is a publishable methodology figure.
