### 1. One-Click Dev Environment (Codespaces / Gitpod)

**Type:** DX improvement
**Effort:** Small (hours)
**Impact:** Docker Hub is now live. The self-hosting story improved in a week. The gap that remains is the contribution story: fork owners who want to send a PR still face a local setup sequence (Neo4j, OpenRouter key, Python 3.11+, Node 18+, uv, npm) that takes anywhere from 20 minutes to never. GitHub Codespaces eliminates that. A `.devcontainer/devcontainer.json` file tells GitHub to spin up a container with all dependencies pre-installed when a contributor clicks "Open in Codespaces" on any fork. Combined with a Gitpod `.gitpod.yml` for parity, this makes the entire dev environment a single click from the browser — no local install required. The leverage against the Nov 30 external PR deadline is direct: every fork owner who has the repo open in GitHub right now can open a Codespaces environment in two minutes and start editing. The only file needed is `.devcontainer/devcontainer.json`; the actual container build happens on GitHub's infrastructure. This costs zero infrastructure and zero backend work. It is a configuration change that reduces first-PR friction to its theoretical minimum.

**How:**
1. Create `.devcontainer/devcontainer.json` at the repo root. Base image: `mcr.microsoft.com/devcontainers/python:3.11` (official MS devcontainer image with Python 3.11). Set `"name": "MiroShark Dev"`. In `"features"`: add `ghcr.io/devcontainers/features/node:1` with `{"version": "18"}` for Node. In `"postCreateCommand"`: `"cd backend && pip install uv && uv sync && cd ../frontend && npm install"`. Set `"forwardPorts": [3000, 8000, 7474, 7687]` (frontend, backend, Neo4j HTTP, Neo4j Bolt). In `"portsAttributes"`: label port 3000 as `"MiroShark Frontend"`, 8000 as `"MiroShark API"`. Add `"customizations": {"vscode": {"extensions": ["ms-python.python", "Vue.volar", "dbaeumer.vscode-eslint"]}}`. Add a `"postStartCommand": "echo '⚡ MiroShark ready. Copy .env.example to .env and add your OPENROUTER_API_KEY.'"`. Add Neo4j as a devcontainer service in `docker-compose.devcontainer.yml` (a copy of the existing compose with only the neo4j service, so Codespaces starts it automatically via `"dockerComposeFile": ["docker-compose.devcontainer.yml", ".devcontainer/docker-compose.extend.yml"]`). Create `.devcontainer/docker-compose.extend.yml` to override the main compose service with `{"services": {"devcontainer": {"volumes": ["..:/workspace:cached"], "command": "sleep infinity"}}}`. Note: `.env` is git-ignored, so the postStartCommand message is the right handoff — contributors add their own key after the container starts.
2. Create `.gitpod.yml` at the repo root for Gitpod parity. Use `image: gitpod/workspace-python-3.11`. The `.gitpod.yml` install sequence mirrors `.devcontainer` so contributors on either platform get an identical experience.

### 2. Simulation CSV Export

**Type:** Feature
**Effort:** Small (hours)
**Impact:** `signal.json` captures the final aggregate result. `trajectory.json` captures per-round aggregate stance values. The raw per-agent action log — which platform each agent posted on, in which round, with what bullishness score, posting what action type — lives in `per-platform/actions.jsonl` files that surface through the Mentions and Stance Flips analytics but are never directly downloadable. For a researcher who wants to run MiroShark and then do their own analysis (regression, clustering, time-series correlation with real market data), there's currently no clean export path. A `GET /api/simulation/:id/export.csv` endpoint reads the per-agent action log, flattens it into a standard schema, and returns a downloadable CSV: one row per agent-round-platform event, with columns `sim_id, agent_id, agent_name, round, platform, action_type, bullish_pct, timestamp_utc`. This is distinct from the HuggingFace dataset auto-sync (Nov 14), which was about publishing a periodic batch to a dataset registry. This is a keyless single-simulation export endpoint — no registry, no batch job, no credentials. Pure stdlib CSV generation using Python's `csv` module. The use case: "I ran this simulation, here's the CSV, let me throw it into pandas." That's a one-day workflow that currently requires knowing about `actions.jsonl`, finding it in the storage path, and writing parsing code yourself.

**How:**
1. Create `backend/app/services/export_service.py` (~130 LoC, pure stdlib). `build_simulation_csv(sim_id: str) -> str | None`: validate sim is published and completed (check `signal.json` for `published: true`, `status: "completed"`). Load `storage/simulations/{sim_id}/signal.json` for the aggregate header row. Find per-platform action logs at `storage/simulations/{sim_id}/platforms/{platform}/actions.jsonl` for platforms in `["twitter", "reddit", "polymarket"]` (or equivalent paths — check `trajectory.json` for the actual platform keys). For each file: iterate lines, parse JSON per line. Each action entry contains at minimum: `agent_id`, `agent_name`, `round` (or `step`), `action_type`, `bullish_pct` (or the equivalent stance field). Build a unified row: `{sim_id, agent_id, agent_name, round, platform, action_type, bullish_pct}`. Collect all rows across all platforms, sort by `(round, platform, agent_id)`. Use `csv.writer` with `StringIO` to serialize. First row (before header): a comment line `# MiroShark simulation export — {sim_id} — topic: {topic} — direction: {direction} — confidence: {confidence_pct}% — exported: {utcnow}`. Header: `sim_id,agent_id,agent_name,round,platform,action_type,bullish_pct`. Cache to `storage/simulations/{sim_id}/export.csv` with mtime invalidation against the newest `actions.jsonl` file. Return raw CSV string. Add 4 unit tests: 2-agent × 2-round × 2-platform case produces correct row count (8 rows + header + comment); rows sorted by round then platform; unpublished sim returns None; CSV comment line contains `sim_id` and `direction`.
2. Add `GET /api/simulation/:id/export.csv` to `backend/app/api/export.py`. Keyless for published sims. `Content-Type: text/csv`. `Content-Disposition: attachment; filename="miroshark-{sim_id}-export.csv"`. `Cache-Control: max-age=86400, public` (immutable after sim completes). Calls `build_simulation_csv(sim_id)`. If sim not published or not completed: return `{error: "not_available", reason: "sim_not_published_or_incomplete"}` with 404 (not a CSV response in the error case — return JSON). If `actions.jsonl` files are absent (sim completed with no logged actions): return a CSV with only the header row and a comment explaining absence: `# No agent action log found for this simulation`. Add `OpenAPI ExportCSV` schema note in API docs: "Returns `text/csv`. First line is a comment. Header: `sim_id,agent_id,agent_name,round,platform,action_type,bullish_pct`." Add to `surfaces_catalog.py` (type: `export`). Add to `docs/API.md` under a new "Export" section with a `curl` example: `curl https://miroshark.xyz/api/simulation/SIM_ID/export.csv -o simulation.csv`. Add 2 integration tests: endpoint returns `Content-Type: text/csv` for published sim; 404 JSON response for non-published sim.
3. Add a "Download CSV" button to the Step 3 share panel (alongside existing share and embed buttons). Clicking triggers a direct download of `/api/simulation/:id/export.csv` via `window.open` or an `<a download>` link. Show a small tooltip on hover: "Download per-agent action log as CSV — compatible with Excel, pandas, and R." If the sim is in a non-completed state: render the button as disabled with tooltip "Available once simulation completes." Below the button, add a one-line info note: "Contains {agent_count × rounds_total} rows of agent-level data." Compute the estimate from `signal.json` values already loaded in Step 3 — no new API call. Add a matching download entry to `EmbedDialog.vue` (or equivalent) for operators who build integrations: a `curl` snippet pre-filled with the sim's ID. Add 2 frontend unit tests: "Download CSV" button renders only for completed published sims; disabled state renders correctly when sim is not completed.

### 3. Webhook Delivery Log

**Type:** DX improvement
**Effort:** Small (hours)
**Impact:** `docs/WEBHOOKS.md` describes a fully functional outbound webhook system: operators register endpoints, MiroShark fires POST requests on simulation lifecycle events (`completed`, `published`, `failed`). There is no delivery audit trail. If a webhook fires and the downstream server returns a 500, the operator has no way to know. If the endpoint is timing out, the only signal is that their downstream system isn't receiving data. The gap is a classic ops blind spot: a system that is designed to be invisible when it works provides no signal when it breaks. `GET /api/webhooks/:webhook_id/deliveries` returns the last 50 delivery attempts for a given webhook registration: `{delivery_id, event, status_code, latency_ms, timestamp_utc, success, truncated_request_body, truncated_response_body}`. Each delivery is logged asynchronously in the existing webhook dispatch path (write to `storage/webhooks/{webhook_id}/deliveries.jsonl` after each fire). The frontend adds a "Delivery History" panel in the webhook settings page: a table of recent deliveries with status code (green 2xx / red 5xx / yellow timeout), latency badge, event name, and a "Retry" button that re-fires the last failed delivery manually. This is distinct from "Webhook Event Testing Playground" (Nov 12), which was about sending test events to verify endpoint format. This is an audit trail for real production deliveries — the difference between a smoke-test button and an ops log.

**How:**
1. Add delivery logging to the existing webhook dispatch path. Find where webhooks are fired (likely `webhook_service.py` or similar). After each outbound POST: append a JSON line to `storage/webhooks/{webhook_id}/deliveries.jsonl` (create directory if absent). Line schema: `{delivery_id: str (uuid4[:8]), event: str, status_code: int | null, latency_ms: int, timestamp_utc: str (ISO 8601), success: bool, request_body_truncated: str (first 500 chars of JSON payload), response_body_truncated: str (first 200 chars of response text; empty string on timeout/network error), error: str | null (exception message on network failure, null on success)}`. For timeouts: `status_code: null`, `success: false`, `error: "timeout"`. For network errors (unreachable endpoint): `status_code: null`, `success: false`, `error: "connection_refused"` (or the sanitized exception type). Cap the deliveries file at 200 lines (prepend new, drop oldest beyond 200) using a simple in-memory rotation: load existing lines, prepend new line, truncate to 200, write back. Create `backend/app/services/delivery_log_service.py` (~80 LoC, pure stdlib) with two functions: `log_delivery(webhook_id, event, status_code, latency_ms, success, request_body, response_body, error)` (handles file I/O, truncation, rotation) and `get_deliveries(webhook_id, limit=50) -> list` (loads and parses `deliveries.jsonl`, returns newest `limit` entries). Add 4 unit tests: logging a successful delivery writes a line with `success: true`; request body truncated at 500 chars; file rotates at 200 lines (oldest dropped); `get_deliveries` returns newest entries first.
2. Add `GET /api/webhooks/:webhook_id/deliveries` to `backend/app/api/webhooks.py` (extend existing webhook routes). Auth-gated (must own the webhook registration). Query params: `?limit=50` (default 50, clamp [1, 200]). `Cache-Control: no-store` (audit log — always fresh). Response: `{webhook_id: str, endpoint_url: str (masked — show only domain + path, not query params), total_logged: int, deliveries: [{delivery_id, event, status_code, latency_ms, timestamp_utc, success, error}]}`. Omit `request_body_truncated` and `response_body_truncated` from the list endpoint (bandwidth); expose them only on `GET /api/webhooks/:webhook_id/deliveries/:delivery_id` for drill-down. Add both routes to `surfaces_catalog.py` (type: `ops`). Add to `docs/API.md` under a new "Webhooks — Delivery Log" subsection and to `docs/WEBHOOKS.md` under a "Monitoring deliveries" section. Add 2 integration tests: unauthenticated request returns 401; authenticated request returns `deliveries` array with correct `success` bool.
3. Add a "Delivery History" tab to the webhook settings UI (alongside the existing configuration panel). Layout: a header "Delivery History — last 50 events" with a "Refresh" button. Main content: a table with columns `When` (relative: "3 min ago"), `Event` (chip: `simulation.completed`, `simulation.published`), `Status` (HTTP status code badge — green `2xx`, yellow `3xx`, red `4xx`/`5xx`, gray `timeout`), `Latency` (ms, right-aligned), and an action column. Each row expands on click to show `request_body_truncated` and `response_body_truncated` in a monospace panel. Add a "Retry" button on each failed delivery (`success: false`): clicking calls `POST /api/webhooks/:webhook_id/deliveries/:delivery_id/retry` (a new endpoint that re-fires the original payload to the registered endpoint and appends a new delivery log entry). Show a summary bar at the top: "47 / 50 delivered successfully in the last 50 events." If `deliveries` is empty: show "No deliveries yet — webhook will fire when a simulation completes." Add 2 frontend unit tests: failed delivery row renders with red status badge; "Retry" button is hidden on successful deliveries.

### 4. Automated CHANGELOG.md Generator

**Type:** Content
**Effort:** Small (hours)
**Impact:** MiroShark has shipped 370+ commits and 90+ self-improving agent PRs with no machine-readable changelog. `CHANGELOG.md` doesn't exist in the repo. For fork owners evaluating whether to upgrade from their forked version, for operators running self-hosted instances deciding whether to pull the latest Docker image, and for new contributors trying to understand the project's velocity and history, the commit log is the only source of truth — and it's noisy (most recent commits are Dependabot bumps). An automated `CHANGELOG.md` generator reads GitHub releases and commit history, groups commits by type (using conventional commit prefixes: `feat:`, `fix:`, `ci:`, `chore:`, `test:`), and writes a human-readable `CHANGELOG.md` to the repo root. It runs as a GitHub Actions workflow step (or as a one-off skill invocation) triggered on each new release tag. For the Docker Hub story specifically: operators who `docker pull miroshark/miroshark` without reading the commit log now have one file to open to understand what changed in the last 30 days. For contributors looking for contribution area: "No CHANGELOG entry for the past 6 weeks on the API" is a gap they can fill. This is a low-infrastructure content win that makes the codebase's history legible with zero new API surfaces.

**How:**
1. Create `scripts/generate-changelog.sh` (pure bash, uses `gh api`). Steps: (a) fetch GitHub releases via `gh api repos/aaronjmars/MiroShark/releases --jq '[.[] | {tag_name, name, published_at, body}] | .[0:20]'` — these are the existing tagged releases; (b) fetch commits since the most recent release tag via `gh api repos/aaronjmars/MiroShark/commits -X GET --field since=RELEASE_DATE --jq '.[] | {sha: .sha[0:7], message: .commit.message | split("\n")[0], author: .author.login, date: .commit.author.date}'`; (c) classify each commit: `feat:` or `add(` → Features, `fix:` or `bug(` → Bug Fixes, `ci:` or `test:` or `chore:` → Maintenance, everything else → Other; (d) write `CHANGELOG.md` with sections: "## Unreleased" (commits since last release, omitting Dependabot/chore bumps unless there are no other commits), then one `## vX.Y.Z — YYYY-MM-DD` section per release (up to 10 releases), each with sub-sections Features/Bug Fixes/Maintenance listing the commit short-SHA (linked to `github.com/aaronjmars/MiroShark/commit/SHA`), message, and author. Skip Dependabot commits in Features and Bug Fixes sections (they appear only in Maintenance if the section is non-empty). Add a header: `# Changelog\n\n> Auto-generated. Last updated: {today}.\n\nAll notable changes to MiroShark are documented here.\n`. Add a footer: `---\n*Auto-generated from GitHub commit history. Run \`scripts/generate-changelog.sh\` to refresh.*`. If no releases exist: treat the full commit history as "Unreleased" and group by month instead of release tag.
2. Create `.github/workflows/changelog.yml`. Trigger: `on: release: types: [published]` (fires when a new GitHub release is published) and `on: workflow_dispatch` (manual trigger). Steps: `actions/checkout` with `token: ${{ secrets.GITHUB_TOKEN }}`; run `scripts/generate-changelog.sh > CHANGELOG.md`; stage and commit with `git add CHANGELOG.md && git commit -m "docs: regenerate CHANGELOG.md for ${{ github.ref_name }}" && git push origin main` (use `git config user.name "github-actions[bot]"` and `user.email "github-actions[bot]@users.noreply.github.com"` before committing). Add a step dependency: only commit if `CHANGELOG.md` changed (`git diff --quiet CHANGELOG.md || git add ...`). Note: this workflow commits directly to main for the changelog file only, which is an exception to the usual "PR-only" rule; acceptable because CHANGELOG.md is a generated artifact, not code. Add `permissions: contents: write` to the job. The `workflow_dispatch` trigger also allows the agent to run this skill manually via `gh workflow run changelog.yml` to generate an initial changelog.
3. Add a `CHANGELOG.md` link to the README (after the Docs badge row): `<a href="CHANGELOG.md"><img src="docs/images/doc-changelog.svg" alt="Changelog" height="30" align="absmiddle"></a>` — or, if SVG badge images are too heavyweight to add, a plain Markdown link: `[📋 Changelog](CHANGELOG.md)`. Add a brief entry in `docs/INSTALL.md` under "Keeping up to date": "See [CHANGELOG.md](../CHANGELOG.md) for a summary of changes in each version. The changelog is regenerated automatically on each new release." As a first run: execute `scripts/generate-changelog.sh` locally to populate `CHANGELOG.md` with the full history up to today, then include it in the same PR as the script and workflow. This ensures the file exists from day one rather than waiting for the next release.

### 5. "Similar Simulations" Discovery

**Type:** Feature
**Effort:** Small (hours)
**Impact:** The gallery search endpoint (`GET /api/simulation/search?q=…`, Nov 14) allows operators to search by keyword. What it doesn't do is surface related simulations automatically after a run completes. When an operator finishes a simulation on "Federal Reserve rate cuts Q1 2027," they're in a research mindset — the most natural next action is "what have others run on adjacent topics?" — but the UI offers them nothing except the gallery home page. `GET /api/simulation/:id/similar` returns up to 5 published simulations with high topic overlap to the given simulation, ranked by similarity score. Similarity is computed with a lightweight TF-IDF word overlap in pure Python stdlib: build an inverted index of topic terms across all published simulations (mtime-cached to `storage/analytics/topics_index.json`), compute cosine-ish overlap scores, return top 5 excluding the query sim and any sims with the same operator. This is distinct from search (Nov 14), which is input-driven discovery. This is output-driven discovery: you've already run your simulation, here are five more you might find relevant. The analogy is "you might also like" after a purchase — it converts the signal card endpoint from a terminal view into a discovery loop. For the star hyperstition, every session that extends from one simulation to two to five is an operator who stays engaged longer, more likely to share, more likely to star.

**How:**
1. Create `backend/app/services/similarity_service.py` (~150 LoC, pure stdlib). `build_topics_index() -> dict`: scan `storage/simulations/*/signal.json` files. For each `published: true`, `status: "completed"` sim: load `{sim_id, topic, operator_id, direction, confidence_pct, created_at}`. Tokenize `topic`: lowercase, split on whitespace and punctuation (`re.split(r'[\s\W]+', topic.lower())`), remove stopwords (hardcode a 50-word English stoplist: "the", "a", "an", "and", "or", "in", "on", "at", "for", "of", "to", "is", "are", "was", "were", "with", "about", "how", "what", "will", "can", "this", "that", "from", "by", "as", "be", "has", "have", "had", "it", "do", "does", "not", "if", "but", "so", "up", "out", "also", "than", "then", "they", "them", "their", "into", "over", "after", "before", "when", "where"). Build term-frequency dict per sim. Build inverted index: `{term: [sim_id, ...]}`. Cache full index (sims list + inverted index) to `storage/analytics/topics_index.json` with 1-hour mtime invalidation (compare `topics_index.json` mtime against newest `signal.json` mtime in storage). `find_similar(sim_id: str, top_n: int = 5, exclude_operator_id: str = None) -> list`: load index. Get query sim's terms. For each candidate sim: score = `len(intersection(query_terms, candidate_terms)) / len(union(query_terms, candidate_terms))` (Jaccard similarity). Filter out query sim itself, optionally filter by `exclude_operator_id`. Sort by score descending, return top `top_n` entries with `{sim_id, topic, direction, confidence_pct, similarity_score, created_at}`. Return empty list if score < 0.1 for all candidates (no meaningful overlap). Add 5 unit tests: identical topic returns score 1.0; zero overlap returns empty list (filtered by 0.1 threshold); stopwords excluded from scoring; `sim_id` excluded from its own results; `exclude_operator_id` removes that operator's sims.
2. Add `GET /api/simulation/:id/similar` to `backend/app/api/similar.py`. Keyless for published sims. Query params: `?limit=5` (default 5, clamp [1, 10]). `Cache-Control: max-age=3600, public`. Response: `{sim_id: str, topic: str, similar: [{sim_id, topic, direction, confidence_pct, similarity_score, created_at}], count: int}`. If the query sim is not published: `{available: false, reason: "sim_not_published"}` with 404. If index has fewer than 10 published sims total: `{available: false, reason: "insufficient_sims_to_compare"}` with 200. The `similarity_score` field is included in the response (0.0–1.0, two decimal places) so frontend can optionally display it. Add `OpenAPI SimilarSimulationsResponse` schema. Add to `surfaces_catalog.py` (type: `discovery`). Add to `docs/API.md` under "Discovery" with a note: "Uses Jaccard similarity on topic terms. Results exclude the query simulation and sims with fewer than 10% term overlap." Add 2 integration tests: endpoint returns `available: false` when fewer than 10 sims in index; returned `similar` entries all have `similarity_score > 0`.
3. Add a "Related simulations" section to the Step 3 signal card. After the main direction/confidence block: render up to 3 similar simulation cards (compact layout: topic truncated to 60 chars, direction badge small, confidence percentage, "View →" link). Fetch from `/api/simulation/:id/similar?limit=3` on mount (non-blocking — if the request fails or returns `available: false`, the section is simply absent). Header: "Similar simulations" with a gray "based on topic overlap" subtext. Each card is a `<RouterLink>` to `/s/{sim_id}`. If `similar.length === 0` (no matches above threshold): section is not rendered at all — no "No similar simulations found" empty state. On the gallery page, add a `similar_count` field to each gallery card's metadata (precomputed from the similarity index) — show a small "🔁 N related" chip below the topic text for sims with `similar_count > 0`. Add 2 frontend unit tests: section renders with 3 cards when `similar` has 3 entries; section is absent when API returns `available: false`.
