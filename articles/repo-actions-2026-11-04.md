### 1. Simulation Tags & Collections

**Type:** Feature / Community
**Effort:** Small (hours)
**Impact:** Right now every simulation sits in a flat gallery — no way to group "all my crypto Q4 runs" or "scenarios I want to revisit." A tagging system + curated collections turns the gallery from a pile into an organized research workspace. `PUT /api/simulation/:id/tags` accepts an array of lowercase slug tags (max 10 per sim, max 30 chars each). `GET /api/simulations?tags=crypto,2026` returns a filtered list. `POST /api/collections` creates a named collection (`slug`, `title`, `description`, `simulation_ids[]`) with a shareable public URL at `/c/:slug` — a mini portfolio page ("All my Bitcoin price calls from Q4 2026"). Collections are session-owned; the public URL is only resolvable if the collection is set public. Researchers bookmarking scenario batches, newsletter operators grouping their weekly calls, and community members curating "best of" lists all benefit immediately.

**How:**
1. Add `tags` field to the simulation storage schema: `storage/simulations/{id}/config.json` gets a new `"tags": []` array (default empty). Create `backend/app/services/tag_service.py` (~120 LoC, pure stdlib). `update_tags(session_token, sim_id, tags)`: validate ownership; validate each tag matches `^[a-z0-9-]{1,30}$`; cap at 10; write back to `config.json`. `list_by_tags(session_token, tags)`: scan all session-owned sims, return those whose tag array intersects the query set. `GET /api/simulations?tags=` added to the simulations list endpoint (AND logic for multiple tags). Create `backend/app/services/collection_service.py` (~140 LoC). `create_collection(session_token, slug, title, description, sim_ids, public)`: validate slug `^[a-z0-9-]{3,50}$`; check uniqueness in `storage/collections.json` registry (handle → session_token map, same pattern as operator profile); store collection to `storage/collections/{slug}.json`. `get_collection(slug)`: load from disk; if `public=false` and caller isn't owner, return None (renders 404). Add 5 unit tests: invalid tag character returns 400; more than 10 tags returns 400; `list_by_tags` returns only sims with all specified tags; collection slug uniqueness enforced across sessions; `public=false` collection returns None for non-owner lookup.
2. Add `PUT /api/simulation/:id/tags` (session-auth, body `{tags: list[str]}`), `GET /api/collections` (session-auth, lists own collections), `POST /api/collections` (session-auth), `GET /api/collections/:slug` (keyless if public, session-auth if private), `DELETE /api/collections/:slug` (session-auth). Add to `surfaces_catalog.py` (type: `organization` × 5 routes). Add to `docs/API.md` under a new "Organization" section. OpenAPI schemas: `TagsUpdateRequest`, `CollectionCreateRequest`, `CollectionResponse`. Add 2 integration tests: `PUT /api/simulation/:id/tags` persists tags to `config.json`; `GET /api/collections/:slug` returns 404 for private collection from unauthenticated request.
3. Add tag chip UI to each gallery card: a row of small colored `#tag` chips under the simulation title. Clicking a chip filters the gallery to that tag. Add a tag editor on the simulation detail page: a text input with auto-complete from the session's existing tags (deduplicated list from `GET /api/simulations?tags=`). ### 2. Agent Demographic Diversity Score

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Every simulation builds a roster of 100+ grounded agents with demographic attributes (age, profession, risk tolerance, platform affiliation). The existing analytics surfaces measure *what* agents concluded (stances, confidence, mentions). None of them measure *who* those agents were — whether the roster was a monoculture or genuinely diverse. A `diversity_score` (0–100, where 100 = perfectly uniform distribution across all measured dimensions) in `signal.json` gives operators a single number: "this simulation had 87/100 demographic diversity." A `GET /api/simulation/:id/diversity` endpoint returns the full breakdown: age quartile distribution, top-5 professions by count, risk tolerance distribution (conservative/moderate/aggressive), and cross-platform coverage (% agents on each platform). Operators who care about "are my simulation results biased by a homogeneous agent pool?" now have a data point. High-diversity simulations that reach strong consensus are more convincing signals than low-diversity ones.

**How:**
1. Create `backend/app/services/diversity_service.py` (~180 LoC, pure stdlib). Input: the agent list from the simulation's `agents.json` (or equivalent agent roster file — wherever agent demographic attributes are stored after graph building). Compute for each dimension: age → bucket into quartiles (Q1: <30, Q2: 30–44, Q3: 45–59, Q4: 60+), extract counts, compute normalized entropy (Shannon entropy / log(N_buckets)); profession → extract unique profession strings, compute normalized entropy; risk_tolerance → three buckets (conservative/moderate/aggressive), compute normalized entropy; platform → three buckets (X, Reddit, Markets), compute normalized entropy. `diversity_score = round(mean([age_entropy, profession_entropy, risk_entropy, platform_entropy]) * 100)`. Build the response object: `{diversity_score: int, age_distribution: {q1: int, q2: int, q3: int, q4: int}, profession_distribution: [{profession: str, count: int}] (top-10 by count), risk_distribution: {conservative: int, moderate: int, aggressive: int}, platform_distribution: {x: int, reddit: int, markets: int}, agent_count: int}`. Cache result to `storage/simulations/{id}/diversity.json` (computed once per simulation — no TTL needed; roster is immutable after the sim completes). Write `diversity_score` to the simulation's `signal.json` during the signal-writing step. Add 5 unit tests: all agents same age bucket → `age_entropy = 0.0`; perfectly even age distribution → `age_entropy = 1.0`; `diversity_score` is in range [0, 100]; cached result returned on second call without re-computing; missing `agents.json` returns a graceful `null` diversity rather than a 500.
2. Add `GET /api/simulation/:id/diversity` to a new `backend/app/api/diversity.py`. Publish-gated (same as other analytics endpoints — only accessible for published simulations). Session-auth. Response: `Content-Type: application/json`, `Cache-Control: max-age=3600, private` (immutable data, long cache). Return the full `DiversityResponse` object. During simulation completion (wherever `signal.json` is written), call `diversity_service.compute(sim_id)` and merge `diversity_score` into the signal payload. Add `diversity_score` to the OpenAPI `Signal` schema. Add to `surfaces_catalog.py` (type: `analytics`). Add to `docs/API.md` under "Analytics". Add 2 integration tests: endpoint returns 200 with `diversity_score` for a completed published sim; `diversity_score` is present in `signal.json` after sim completion.
3. Add a "Diversity" tab to the Step 3 analytics panel (alongside Stance Flips, Mentions, etc.). Show: a large `diversity_score` badge (green ≥80, yellow 50–79, red <50) with a label ("Highly diverse / Balanced / Homogeneous"); four horizontal bar charts (age quartile, risk tolerance, platform, top-10 professions). Include a one-line tooltip: "Diversity score measures how balanced the agent pool was across age, profession, risk tolerance, and platform." Add `diversity_score` as a sortable column in the gallery (ascending = "most homogeneous first" for filtering bias-sensitive sims). Add 2 frontend unit tests: diversity panel renders with score badge when `diversity_score >= 0`; gallery sort by `diversity_score` changes the sort URL param.

### 5. Webhook Retry & Redelivery Endpoint

**Type:** Feature / Performance
**Effort:** Small (hours)
**Impact:** When an operator's webhook endpoint is temporarily down (deploy in progress, server restart, transient 5xx), MiroShark fires the webhook, gets a failure response, and the event is lost forever. There is no retry, no queue, no redelivery. For operators who pipe simulation completions into Slack, Zapier, or a custom backend, this means missed notifications with no recovery path. `POST /api/admin/webhooks/redeliver` processes queued failed deliveries with exponential backoff: attempts 1-3 at 0s, 30s, 300s delay respectively. Failed attempts are appended to `storage/webhook_retry.jsonl` during the original webhook call (whenever a non-2xx response or timeout is received). The redelivery endpoint reads this log, groups by simulation ID, and retries the most recent attempt for each. Each entry tracks `{simulation_id, payload, attempt_count, last_attempted_at, status}`. Operators who maintain high-reliability downstream pipelines (Zapier automation, custom dashboards) get a "retry failed deliveries" button in the admin panel.

**How:**
1. Modify the existing webhook dispatch code (wherever `POST` to the webhook URL is performed): on any non-2xx HTTP response or `requests.exceptions.Timeout`, append a retry record to `storage/webhook_retry.jsonl` using `json.dumps({...}) + "\n"` (atomic line append). Record format: `{simulation_id: str, payload: dict, webhook_url: str, attempt_count: int, last_attempted_at: ISO8601, status: "queued" | "delivered" | "exhausted"}`. Initial append sets `attempt_count=1`, `status="queued"`. Create `backend/app/services/webhook_retry_service.py` (~150 LoC, pure stdlib). `get_queued()`: read `storage/webhook_retry.jsonl`, parse lines, return only records with `status="queued"` and `attempt_count < 3` (exhausted after 3 attempts). `redeliver_all()`: for each queued record, check exponential backoff constraint: `last_attempted_at + (30s * 2^(attempt_count-1)) <= now` — skip if still in backoff window. Attempt delivery using `urllib.request.urlopen` with 10s timeout. On success: update record `status="delivered"`. On failure: increment `attempt_count`; if `attempt_count >= 3`, set `status="exhausted"`. Rewrite the file with updated records. Return `{attempted: int, delivered: int, exhausted: int, still_queued: int}`. Add 5 unit tests: backoff constraint: attempt 2 within 30s of attempt 1 is skipped; `attempt_count >= 3` sets `status="exhausted"`; successful redelivery updates `status="delivered"`; `get_queued` excludes `status="delivered"` and `status="exhausted"` records; empty `webhook_retry.jsonl` returns `{attempted:0, delivered:0, exhausted:0, still_queued:0}`.
2. Add `POST /api/admin/webhooks/redeliver` to `backend/app/api/admin.py`. Requires `ADMIN_TOKEN` auth. No request body. Calls `webhook_retry_service.redeliver_all()`. Response: `{attempted: int, delivered: int, exhausted: int, still_queued: int, timestamp: ISO8601}`. Add `GET /api/admin/webhooks/retry-queue` (ADMIN_TOKEN auth) returning the current queue: `{total: int, queued: int, exhausted: int, records: [{simulation_id, attempt_count, last_attempted_at, status}]}` — without exposing the raw payload (security: webhook URLs and payloads may contain tokens). Add to `surfaces_catalog.py` (type: `admin` × 2 routes). Add to `docs/API.md` under "Admin" alongside the usage stats endpoint. OpenAPI schemas: `RedeliveryResponse`, `RetryQueueResponse`. Add 2 integration tests: `POST /redeliver` returns 200 JSON with the four integer fields; `GET /retry-queue` returns 200 JSON with a `records` array.
3. Add a "Webhook Retry Queue" card to the admin Settings panel (alongside the Usage card from the usage stats idea). The card shows: total queued count, total exhausted count, and a "Redeliver Now" button. After clicking, show inline feedback: "Attempted N deliveries — X succeeded, Y exhausted." Add a small collapsible "Queue Details" section listing recent exhausted records with simulation IDs and attempt counts (without exposing URLs or payloads). Auto-refresh the queue count every 60s via polling. Add 2 frontend unit tests: "Redeliver Now" button calls `POST /api/admin/webhooks/redeliver`; exhausted count is displayed in red when > 0.
