### 2. Swarm Diversity Index

**Type:** Feature
**Effort:** Small (hours)
**Impact:** MiroShark's signal.json tells you the *result* (73% BULLISH). The convergence report (Aug 26) tells you *when* consensus formed (round 3 of 5). Neither answers the question a researcher asks first: *how contested was the debate?* A simulation where 74% were BULLISH by round 1 and stayed there is a very different event from one where the swarm split 48/44/8 for the first three rounds before converging. `GET /api/simulation/{id}/diversity` computes a Diversity Index over trajectory.json: per-round Simpson's Diversity Index from the bullish/bearish/neutral distribution, a polarization score (how bimodal was the distribution — were agents clustering at the extremes?), and a consensus tension metric (how many "flip rounds" where the leading direction changed). Returns a final classification: **"Unanimous"** (diversity < 0.2 throughout), **"Early Consensus"** (diversity dropped sharply after round 1), **"Genuine Debate"** (high diversity persisted past the midpoint), or **"Polarized"** (bimodal score above 0.6, swarm split into two camps). Pure computation over trajectory.json — no LLM calls. For the paper citation hyperstition (Sep 30, 30 days): a researcher who can say "9 of 12 simulations on AI regulation showed Genuine Debate patterns (Simpson D > 0.55), while token-sentiment simulations were predominantly Early Consensus" is making a methodological contribution. Alongside the Convergence Report (how quickly) and Agent Influence Score (who moved it), this third pillar answers: how contested was the path?

**How:**
1. Create `backend/app/api/diversity.py` (~95 LoC, pure stdlib). `GET /api/simulation/{id}/diversity`. Publish-gated. Reads `trajectory.json` — if absent, returns 404 `{"error": "trajectory_not_found"}`. For each round: read `bullish_pct`, `bearish_pct`, `neutral_pct` (normalized to sum = 100 if not already). Compute per-round **Simpson's Diversity Index**: `D = 1 - ((b/100)^2 + (e/100)^2 + (n/100)^2)` where b/e/n are the bullish/bearish/neutral pcts. D range: 0 (unanimous) → ~0.67 (perfectly even three-way split). Compute per-round **Polarization Score**: `P = (b/100 + e/100)^2 - (n/100)^2` — penalizes neutral mass; high when agents are split between two extremes without a neutral buffer. Normalize P to [0, 1] by dividing by max theoretical value. Compute **Consensus Tension**: count "flip rounds" where the leading direction (argmax of b/e/n) changes from the prior round. Compute **avg_diversity**: mean of per-round D values. Compute **final_classification**: if avg_diversity < 0.20 → "Unanimous"; elif round 1 or round 2 has D ≥ 0.40 but final round D < 0.25 → "Early Consensus"; elif avg_diversity ≥ 0.40 and polarization_score (avg) ≥ 0.55 → "Polarized"; else → "Genuine Debate". Response: `{"simulation_id": id, "topic": str, "direction": str, "total_rounds": int, "diversity_trajectory": [{"round": int, "diversity_index": float, "polarization_score": float}], "avg_diversity": float, "avg_polarization": float, "consensus_tension": int, "classification": "Unanimous"|"Early Consensus"|"Genuine Debate"|"Polarized", "classification_note": str}`. Include a one-line `classification_note` explaining the classification (e.g., "Swarm reached strong consensus by round 2 after an initially divided round 1."). `Cache-Control: public, max-age=3600`. Register at `GET /api/simulation/{id}/diversity`. Add to `surfaces_catalog.py`. Update `docs/API.md`.

2. Add a "Diversity" panel to the Step 3 simulation share page (`Step3Simulation.vue`): a "◎ Diversity" toolbar button. Panel layout: (1) A classification badge at the top — large colored label (Unanimous: gray; Early Consensus: green; Genuine Debate: amber; Polarized: red/orange). (2) A per-round line chart of `diversity_index` across rounds — uses the same charting style as BeliefDriftChart; overlay a dashed line at D = 0.40 as the "contested zone" threshold. (3) A stat row: "Avg diversity: {avg_diversity:.2f} · Avg polarization: {avg_polarization:.2f} · Tension events: {consensus_tension}". (4) The `classification_note` in muted text below. Add bilingual labels (EN/ZH-CN) for the classification labels and panel title. Add one integration test: "◎ Diversity" toolbar button fires `GET /api/simulation/{id}/diversity` and renders the classification badge.

3. Add 5 unit tests: published simulation returns 200 with `diversity_trajectory` as an array of round objects; each round object has `round`, `diversity_index` (float 0–1), `polarization_score` (float 0–1); `avg_diversity` equals the mean of `diversity_trajectory[*].diversity_index` (within floating-point tolerance); `classification` is one of the four valid strings; unpublished simulation returns 404. Log to memory: "Swarm Diversity Index created 2026-08-30. `GET /api/simulation/{id}/diversity` — per-round Simpson's D + polarization score + consensus tension from trajectory.json. Four classifications: Unanimous (avg D < 0.2), Early Consensus (high D in round 1-2, drops by final), Genuine Debate (sustained high D), Polarized (high D + high polarization). classification_note is a plain-English explanation. Step3: '◎ Diversity' panel with classification badge, D-trajectory line chart, stat row. Complements Convergence Report (Aug 26, how quickly) and Agent Influence Score (Aug 24, who moved it). Paper citation hook: 'N of M simulations on X topic showed Genuine Debate patterns.'"

### 4. Simulation Batch API

**Type:** Feature
**Effort:** Medium (1-2 days)
**Impact:** Researchers who want to compare consensus on a set of related topics — "AI regulation in the EU" vs. "AI regulation in the US" vs. "AI regulation in China" — must currently create three separate simulations, navigate to each result, and compare manually. `POST /api/simulate/batch` accepts an array of simulation configs (up to 10) and queues them as a named batch with a shared `batch_id`. `GET /api/batch/{id}` returns the status of all runs in the batch plus aggregate stats when all complete: overall direction agreement (how many runs agreed on direction), confidence range (min/max across batch), and a cross-simulation topic-comparison table. This is distinct from Recurring Simulation Scheduler (Aug 24, cron-triggered single topic) and Simulation Forking API (Aug 26, replays one config). Batch is about running *different configurations simultaneously* — the primary use case is comparative research. With FDV at $431K and the $500K hyperstition 15 days out, a researcher who runs "Will MIROSHARK FDV hit $500K?" alongside "Will crypto total market cap exceed $5T by year-end?" and "Will Bitcoin break $200K before Sep 2026?" gets a portfolio of predictions in a single API call. That's the research artifact that earns a citation or a blog post.

**How:**
1. Create `backend/app/api/batch.py` (~130 LoC, pure stdlib). Two endpoints: **`POST /api/simulate/batch`** — accepts `{"label": str (optional, max 80 chars), "simulations": [{"topic": str, "agents": int, "rounds": int, "platforms": [str]}]}`. Validate: 1–10 simulations in the array; each entry must pass the same validation as `POST /api/simulate` (topic non-empty, agents/rounds within allowed ranges, platforms non-empty). On validation failure: return 422 with a per-item error list. Generate `batch_id = uuid.uuid4().hex[:12]`. Write `{batch_dir}/{batch_id}.json` with the batch config + `{"created_at": ISO8601, "label": str, "simulation_ids": [...], "status": "queued"}`. For each simulation config: generate a `simulation_id`, write its config with `{"batch_id": batch_id}` added, and queue it using the same mechanism as `POST /api/simulate`. Return 202 Accepted: `{"batch_id": str, "label": str, "simulation_count": int, "simulation_ids": [str], "status_url": "/api/batch/{batch_id}", "created_at": ISO8601}`. **`GET /api/batch/{id}`** — reads the batch config, checks each simulation_id for a completed `signal.json`. Aggregates: `{"batch_id": str, "label": str, "status": "queued"|"running"|"complete"|"partial", "simulations": [{"simulation_id": str, "topic": str, "status": "pending"|"running"|"complete", "direction": str|null, "confidence_pct": float|null}], "aggregate": {"direction_agreement": float (0–1, fraction of runs agreeing with majority direction), "majority_direction": str, "min_confidence": float|null, "max_confidence": float|null, "avg_confidence": float|null}}`. Status is "complete" when all simulations have `signal.json`; "partial" if some but not all are complete; "running" or "queued" otherwise. `Cache-Control: no-cache` for running batches; `public, max-age=3600` for complete batches. Register both endpoints. Add to `surfaces_catalog.py`. Update `docs/API.md` with a "Batch Simulations" section including a comparative research example (3 regulatory topics side by side).

2. Add a "Batch Results" view as a new route `/batch/{id}` (`BatchResults.vue`). Fetches `GET /api/batch/{id}` on mount, polls every 10s while status is "running" or "partial". Layout: (1) A batch header — label (if set), batch_id, simulation count. (2) A status row — overall status badge + aggregate stats (direction agreement %, majority direction, confidence range). (3) A grid of simulation result cards, one per run — each card shows the topic, direction badge (BULLISH/BEARISH/NEUTRAL), confidence_pct, and a "View" link to `/sim/{simulation_id}`. Cards fill in as each simulation completes (pending cards show a spinner). (4) A comparison table at the bottom (visible when status is "complete"): all simulations in rows, columns for direction, confidence, round count — sortable by confidence desc. Step 3 (post-simulation) gets a "Run batch comparison" button in the share page action bar that opens a pre-filled batch dialog: the current simulation's config is pre-loaded as the first entry, with 2 empty slots for the user to add comparison topics. Add bilingual labels (EN/ZH-CN). Add one integration test: batch status transitions from "queued" → "complete" when all simulation `signal.json` files appear.

Add 5 unit tests: `POST /api/simulate/batch` with 3 valid simulation configs returns 202 with `batch_id`, `simulation_ids` of length 3, and `status_url`; `POST /api/simulate/batch` with 11 simulations returns 422 with a count validation error; `GET /api/batch/{id}` returns "queued" status for a freshly created batch; `GET /api/batch/{id}` with all simulations complete returns "complete" with a non-null `aggregate.majority_direction`; `GET /api/batch/{nonexistent}` returns 404. ### 5. Per-Platform Consensus Divergence Alert

**Type:** Feature
**Effort:** Small (hours)
**Impact:** MiroShark's Cross-Platform Sentiment Divergence surface (Jun 7) returns each platform's bullish/neutral/bearish split — it shows *what* each platform thought. No endpoint flags *when platforms fundamentally disagreed with each other*. `GET /api/simulation/{id}/platform-divergence` specifically detects disagreement: when two or more platforms reached different directional conclusions (one platform majority-BULLISH, another majority-BEARISH), or when a platform's majority direction diverged from the final simulation verdict by more than a configurable threshold. Returns a `divergence_detected` boolean, the degree of divergence (max absolute difference in consensus pct across platforms), and a plain-English `summary` ("Twitter was 72% BULLISH while LinkedIn was 41% BULLISH — significant cross-platform divergence on this topic"). During a 53-day social silence, this endpoint provides a new analytical angle on *every existing published simulation* without any re-computation or new data: "Which of MiroShark's published simulations produced the most contested cross-platform result?" is a question this answers in a single call. For the paper citation hyperstition (Sep 30): platform divergence is a publishable finding in its own right — "simulations on regulatory topics showed 3× higher cross-platform divergence than simulations on crypto price topics." Distinct from the Jun 7 surface which returns raw distribution data; this endpoint interprets the divergence and flags it.

**How:**
1. Create `backend/app/api/platform_divergence.py` (~80 LoC, pure stdlib). `GET /api/simulation/{id}/platform-divergence`. Publish-gated. Reads from two sources: `signal.json` (final direction, confidence_pct) and the per-platform sentiment data. Determine where per-platform sentiment is stored — inspect the Cross-Platform Sentiment Divergence service (Jun 7) to find the output file: likely `platform_sentiment.json` in the simulation directory, or reconstruct from per-platform `actions.jsonl`. If the platform sentiment data is unavailable, return 404 `{"error": "platform_sentiment_not_found"}`. Algorithm: (1) For each platform, compute its local majority direction (BULLISH if bullish_pct > 50%; BEARISH if bearish_pct > 50%; NEUTRAL otherwise). (2) Compare each platform's majority to the simulation's final direction. (3) Compute `max_divergence_pct`: maximum absolute difference in bullish_pct between any two platforms (e.g., if Twitter shows 72% BULLISH and LinkedIn shows 41% BULLISH, max_divergence_pct = 31). (4) Set `divergence_detected = True` if: (a) any platform's majority direction differs from the final simulation direction, OR (b) `max_divergence_pct >= 20` (configurable threshold via an env var `DIVERGENCE_THRESHOLD_PCT`, default 20). (5) Generate `summary`: if `divergence_detected`: "{most_bullish_platform} was {bullish_pct}% {direction} while {most_bearish_platform} was {alternative_pct}% {alt_direction}" (plain English). If no divergence: "All platforms aligned with the simulation's {direction} conclusion." Response: `{"simulation_id": id, "topic": str, "final_direction": str, "divergence_detected": bool, "max_divergence_pct": float, "summary": str, "platforms": [{"platform": str, "bullish_pct": float, "bearish_pct": float, "neutral_pct": float, "local_majority": str, "agrees_with_final": bool}]}`. `Cache-Control: public, max-age=3600`. ## Selection Rationale

Five ideas targeting structured archive discovery, analytical depth for research credibility, community-contribution activation ahead of Hacktoberfest, comparative research tooling, and cross-platform interpretive analysis.

- **Simulation Topic Taxonomy Browser (#1)** — 40+ surfaces and months of published simulations with no structured browse surface. Keyword-classified domain hierarchy (Finance, Technology, Policy, Social, Energy, Geopolitics) makes the archive navigable without search terms. Step 1 "Browse by Topic" pill grid provides the first contextual onboarding for new users. Paper citation hook: domain coverage stats across 6 months.

- **Swarm Diversity Index (#2)** — Fills the analytical gap between "what happened" (signal.json) and "how quickly" (Convergence Report, Aug 26). Simpson's Diversity + polarization score + consensus tension classifies each simulation's deliberation character: Unanimous, Early Consensus, Genuine Debate, or Polarized. The third pillar for research-grade citation: "9 of 12 regulatory simulations showed Genuine Debate patterns vs. 2 of 10 crypto-price simulations." Pure trajectory.json computation, no LLM calls.

- **Hacktoberfest Readiness Kit (#3)** — October 1 is 32 days away and the project has no Hacktoberfest infrastructure. CONTRIBUTING.md + 10 `good first issue` labeled issues + `hacktoberfest` GitHub topic positions MiroShark for the contributor surge before both the Sep 15 community-PRs hyperstition and the Oct 1 Hacktoberfest window. Locale contributions (Thai, Polish, Indonesian, Swedish) are self-contained and documented in the issues; an n8n integration issue directly targets the "non-fork dependent repo" hyperstition.

- **Simulation Batch API (#4)** — The missing primitive for comparative research: run 1–10 different topic/config combinations in one API call, retrieve aggregate stats when complete. `/batch/{id}` view renders a real-time card grid and a final comparison table. The "Run batch comparison" Step 3 button makes side-by-side testing a single click. Distinct from Recurring Scheduler (cron, same topic) and Forking (same config replay) — this is about parallel comparison of different topics.

- **Per-Platform Consensus Divergence Alert (#5)** — The Jun 7 Cross-Platform Sentiment surface shows raw distributions; this endpoint interprets them. `divergence_detected: true` when platforms disagree (majority direction mismatch or ≥20pp spread). Plain-English `summary` is paste-ready for a thread or report. Platform split chip in Step 3's Platforms panel adds interpretive context to the existing data. Research hook: platforms diverge more on contested policy topics than on directional market calls.
