### 1. GraphML/GEXF Export for Agent Mention Network

**Type:** Feature
**Effort:** Small (hours)
**Impact:** The Agent Mention Network (`GET /api/simulation/<id>/mentions`) exists and returns JSON. Social network analysis researchers — the exact audience for the academic citation hyperstition — don't use JSON for graph analysis; they use Gephi (GraphML) or NetworkX/igraph (GEXF/GraphML). AntFleet's `bench-miroshark` repo is explicitly benchmarking MiroShark's simulation quality; the mention network topology is a primary benchmark signal. Without a standard graph format, they have to hand-convert the JSON. Two new endpoints — `GET /api/simulation/<id>/mentions.graphml` and `.gexf` — expose the same data in the two most common social network analysis interchange formats, zero new backend logic required (pure format transformation of the existing JSON). This is one of the structural features papers in the "social network analysis of LLM simulations" genre specifically call out as required for reproducibility.

**How:**
1. Create `backend/app/api/mentions_export.py` (~90 LoC, pure stdlib). `GET /api/simulation/<id>/mentions.graphml`: read `mentions.json` from the simulation directory (already generated by the mentions service). Build a GraphML XML document using `xml.etree.ElementTree` (stdlib): `<graphml>` root with `<graph id="G" edgedefault="directed">`. One `<node id="{agent_name}">` element per agent in the roster. One `<edge source="{mentioner}" target="{mentioned}">` per mention entry with `<data key="weight">{count}</data>` and `<data key="platform">{platform}</data>`. Add `<key>` declarations for weight (int) and platform (string) at the graph level. `Content-Type: application/xml; charset=utf-8`, `Content-Disposition: attachment; filename="mentions-{sim_id}.graphml"`. `GET /api/simulation/<id>/mentions.gexf`: same data, GEXF 1.2 format (`<gexf xmlns="http://gexf.net/1.2">`). GEXF's `<attributes>` block declares weight and platform; `<nodes>` and `<edges>` sections follow standard GEXF structure. Both routes are publish-gated (same as the JSON endpoint): unpublished simulations return 404. Cache-Control: `public, max-age=3600` (graph structure is immutable for a finished simulation). Register both routes in the app router. Add both to `surfaces_catalog.py` (type: export; surfaces 42 and 43).

2. Add `<link rel="alternate" type="application/xml" title="Agent Mention Network (GraphML)" href="/api/simulation/{id}/mentions.graphml">` to the share page `<head>` (analogous to the existing RSS link tags). Add a "Download Graph" section to `EmbedDialog.vue` alongside the existing download options: two buttons — "GraphML (Gephi)" and "GEXF (NetworkX)" — each opening the respective endpoint URL. Add a `download_mentions_graph(sim_id, format='graphml')` method to the Python SDK (`sdk/python/miroshark/client.py`, ~10 LoC): fetches the endpoint and writes to `{sim_id}.{format}`. Add `downloadMentionsGraph(simId: string, format: 'graphml' | 'gexf'): Promise<Blob>` to the TypeScript SDK.

3. Add 5 unit tests: `.graphml` endpoint returns 200 with `Content-Type: application/xml` for a published sim, `.gexf` returns 200 with GEXF namespace for a published sim, both return 404 for unpublished, GraphML output is valid XML (parse with `ElementTree.fromstring`), node count in GraphML matches the agent roster count. Update `docs/API.md` with a "Graph Exports" section: endpoint reference, format specs with download examples, a code snippet for loading the GraphML directly into NetworkX (`nx.read_graphml('mentions-{id}.graphml')`) and Gephi (file → open). Add to `README.it.md` the Italian citation note when it ships: `formato GraphML e GEXF per analisi delle reti sociali`.

### 2. CITATION.cff + `docs/CITING.md`

**Type:** Community
**Effort:** Small (hours)
**Impact:** The "Will a MiroShark simulation be cited in a peer-reviewed or pre-print paper by September 1?" hyperstition has 28 days. CITATION.cff at the repo root is a YAML metadata file (GitHub Citation File Format spec) that causes GitHub to render a green "Cite this repository" button on the repo landing page — the exact button academic users look for before including a tool in a methods section. Without CITATION.cff, citing MiroShark requires hand-crafting a BibTeX entry from the README, which researchers skip in favor of tools that have it ready. Zenodo auto-imports repos that use CITATION.cff and mints a free DOI — a persistent identifier that survives GitHub URL changes and is required by many conference and journal submission systems. This is a zero-LoC change (pure config + docs) that activates the academic discovery pipeline: Google Scholar, Semantic Scholar, OpenAlex, and Zenodo all index repos with CITATION.cff. It's also the missing piece of the provenance story: the reproduce.json gives simulation-level provenance; CITATION.cff gives tool-level provenance.

**How:**
1. Create `CITATION.cff` at the repo root (standard YAML, no special tooling needed). Fields: `cff-version: "1.2.0"`, `message: "If you use MiroShark in your research, please cite it as below."`, `type: software`, `title: "MiroShark — Universal Swarm Intelligence Engine"`, `abstract: "Open-source multi-agent simulation engine for opinion dynamics, crisis testing, and market reaction modeling. Spawns hundreds of grounded agents across Twitter, Reddit, and prediction market environments for a given scenario, under $1 per run."`, `authors: [{family-names: Mars, given-names: Aaron, alias: aaronjmars}]`, `repository-code: "https://github.com/aaronjmars/MiroShark"`, `url: "https://www.miroshark.xyz"`, `license: MIT`, `version: "1.0.0"` (or the actual current version from package.json), `date-released: "2026-01-01"` (use the repo creation date), `keywords: [swarm-intelligence, opinion-simulation, multi-agent-systems, AI-simulation, computational-social-science, prediction-markets]`. GitHub reads this file and displays a "Cite this repository" dropdown on the repo's main page with APA, BibTeX, and CFF formats pre-generated. Run `cfflint CITATION.cff` (available via pip) in CI to validate on each push.

2. Create `docs/CITING.md` (~80 lines). Sections: **Citing MiroShark the tool** (BibTeX block using CITATION.cff fields, APA format, note about Zenodo DOI once registered); **Citing a specific simulation result** (BibTeX block template using the simulation's `reproduce.json` fields: `title` = scenario text, `year` = simulation year from `reproduce.json`, `note` = "Simulation ID: {id}. Reproduce: {reproduce_url}. IPFS CID: {cid} (if WaybackClaw submitted). DKG Knowledge Asset: {dkg_id} (if OriginTrail anchored)."); **Zenodo DOI registration** (step-by-step: log into zenodo.org, authorize GitHub, flip the MiroShark repo toggle — Zenodo mints a DOI on the next GitHub release); **How to check a simulation is citation-ready** (checklist: simulation is published, reproduce.json present, WaybackClaw submitted, quality_health ≥ good, at least 5 rounds completed); **BibTeX for the reproduce.json endpoint** (curl example showing how to fetch `GET /api/simulation/{id}/reproduce.json` and which fields map to BibTeX keys). Add `docs/CITING.md` to the documentation table in `README.md` and to the localized README variants. Add a `## Citation` section to the main `README.md` showing the one-liner BibTeX and linking to `docs/CITING.md`.

3. Add `CITATION.cff` validation to the CI workflow (`.github/workflows/ci.yml` or equivalent): add a step `pip install cffconvert && cffconvert validate` that runs on pull_request and push to main. This prevents malformed CITATION.cff from breaking GitHub's cite-button rendering. Add a "citation-ready" checklist badge generator stub to `surfaces_catalog.py` (type: meta; surface 44): `GET /api/simulation/<id>/citation-readiness` — returns `{published: bool, reproduce_json: bool, waybackclaw_submitted: bool, quality_health: str, rounds_completed: int, citation_ready: bool}` where `citation_ready` is true when all checklist conditions pass. ~30 LoC; enables the `/verified` page to add a "⭐ Citation Ready" badge to qualifying simulations.

### 3. Per-Round Webhook Events

**Type:** Integration
**Effort:** Small (hours)
**Impact:** Completion webhooks fire once on simulation end. Real-time integration pipelines — Zapier, n8n, Make, custom Python scripts — need mid-run signals to monitor belief drift as it happens. The paper "Hidden Anchors in Multi-Agent LLM Deliberation" (arXiv 2606.19494) specifically studies how consensus forms in early rounds vs late rounds; detecting this in production requires a per-round callback. Enterprise operators running crisis-response simulations want a Slack message the moment the simulation shows a strong consensus forming, not 45 minutes later at completion. Adding a `simulation.round_complete` webhook event type — fired after each round with the round's belief snapshot — enables streaming integration without polling. The 11 ecosystem projects (AntFleet's bench, Capacitr's integration spec, Signa's skills) all need this to build real-time dashboards without the 15-second polling lag from `/watch/{id}`.

**How:**
1. In the simulation loop (wherever round completion is recorded — likely `backend/app/core/simulation_engine.py` or similar), add a call to the webhook dispatch function after each round's `trajectory.json` is updated. The `simulation.round_complete` payload (JSON): `{event: "simulation.round_complete", simulation_id: str, round: int, total_rounds: int, consensus_pct: float, direction: "bullish"|"neutral"|"bearish", delta_from_prior: float, agents_active: int, timestamp: str (ISO 8601)}`. The `delta_from_prior` field (current `consensus_pct` minus prior round's `consensus_pct`) is the divergence signal that the anchor-detection research requires. Dispatch uses the same HMAC signing mechanism as completion webhooks (`X-MiroShark-Signature` header if `WEBHOOK_SECRET` is set). Delivery is fire-and-forget (same as completion webhook) — network errors are logged to `webhook-log.jsonl` but do not block the simulation. Gate per-round webhooks behind a new env var `WEBHOOK_ROUND_EVENTS=true` (defaults to `false` — opt-in to avoid spamming existing webhook receivers with 30+ events per simulation).

2. Add `WEBHOOK_ROUND_EVENTS` to `.env.example` and `docs/CONFIGURATION.md` (new row in the Webhooks section). Add `simulation.round_complete` to `docs/WEBHOOKS.md`: full payload schema, example JSON, curl simulation example, use-case note ("Use this to build real-time consensus monitors, stop-loss triggers, or streaming dashboards — the `delta_from_prior` field signals inflection points before completion"). Add `WEBHOOK_DIVERGENCE_THRESHOLD` optional env var: when set (e.g. `0.15` = 15% round-over-round shift), also fires a `simulation.divergence_alert` event only on rounds where `abs(delta_from_prior) >= threshold`. This allows operators to receive selective alerts on dramatic belief shifts without processing every round. Document both events in `docs/WEBHOOKS.md`.

3. Add 5 unit tests: `simulation.round_complete` fires on each round with correct payload schema, `WEBHOOK_ROUND_EVENTS=false` (default) produces zero per-round calls, HMAC signature is correct on per-round event, `delta_from_prior` is correctly computed as current minus prior consensus_pct, `simulation.divergence_alert` fires only when `abs(delta_from_prior) >= threshold`. Update the EmbedDialog's webhook configuration section to include a "Per-round events" toggle (checkbox, disabled by default) that sets `WEBHOOK_ROUND_EVENTS=true` in the operator's `.env`. Add a "real-time streaming" example to `docs/WEBHOOKS.md`: a 20-line Python script using `http.server.BaseHTTPRequestHandler` that receives per-round events and prints a live belief bar to the terminal — a self-contained demo that tutorial creators can run without any dependencies.

### 4. Ecosystem Project Health API

**Type:** Integration
**Effort:** Small (hours)
**Impact:** `GET /api/ecosystem.json` returns the 11 ecosystem projects as a static registry. There's no liveness data — no way to tell if AntFleet's bench-miroshark repo is active (last commit last week? last year?), or if Blue Agent is still maintained, or if Crucible Sim is a student project that stopped after one commit. New operators choosing which ecosystem tools to integrate with have no signal beyond the ECOSYSTEM.md list. Adding a `GET /api/ecosystem/health` endpoint that returns the registry augmented with last-commit-date, open-issue-count, and star-count for each project creates a living health snapshot. This also creates social accountability for ecosystem members: a visible "last active" date next to each project incentivizes maintenance. The Noelclaw removal (PRs #266/#267, this week) shows the ecosystem is already being curated manually — this API makes the curation data available programmatically to downstream tools.

**How:**
1. Create `backend/app/api/ecosystem_health.py` (~110 LoC, pure stdlib). `GET /api/ecosystem/health`: read the ecosystem registry from `backend/app/data/ecosystem.json` (or wherever the Ecosystem JSON Registry service stores its data). For each project with a `github_url` field, extract the `owner/repo` slug and call `gh api repos/{owner}/{repo} --jq '{pushed_at, open_issues_count, stargazers_count, archived, disabled}'` (using subprocess with the `gh` CLI — GitHub auth is handled internally by `gh`). Aggregate results into an `EcosystemHealthEntry` dict: `{name, github_url, last_commit_at: str|null, open_issues: int|null, stars: int|null, archived: bool|null, status: "active"|"stale"|"archived"|"unknown"}`. Status logic: `active` if `last_commit_at` is within 90 days, `stale` if 90–365 days, `archived` if GitHub marks it archived, `unknown` if no GitHub URL or API call fails. Mtime-cache the entire response to `ecosystem_health.json` for 4 hours (these stats don't need real-time precision). `Cache-Control: public, max-age=14400`. Register route in the main app router. Add to `surfaces_catalog.py` (type: meta; surface 44 or 45 depending on citation-readiness above).

2. Update the `GET /api/ecosystem.json` response to include a `health_snapshot_url: "/api/ecosystem/health"` field and a `health_last_updated` timestamp (when ecosystem_health.json was last written). This links the static registry to the live health data without changing existing consumers. Add an ecosystem health section to `ECOSYSTEM.md`: above the project table, add a "Status key" legend (🟢 Active, 🟡 Stale, 🔴 Archived, ⚪ Unknown) and a note that the live status is available via `GET /api/ecosystem/health`. Update the frontend `/ecosystem` page (if it exists) or the ECOSYSTEM.md rendered view: add a status badge next to each project row using the health endpoint data.

3. Add 4 unit tests: endpoint returns 200 with a list of entries matching the registry count, `status` field is one of the four valid values, mtime cache is used on repeat calls within 4h (verify filesystem cache file is read on second call), an entry with no GitHub URL has `status: "unknown"`. Add a cron job annotation in `aeon.yml` (or wherever the health monitor cron lives) to refresh `ecosystem_health.json` daily: `gh api repos/{owner}/{repo}` for each of the 11 ecosystem projects, writing the cached JSON. This ensures the data is fresh even if the API endpoint isn't hit daily. Document `GET /api/ecosystem/health` in `docs/API.md` under a new "Ecosystem" section alongside the existing `GET /api/ecosystem.json` entry.
