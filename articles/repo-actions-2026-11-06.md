### 1. Simulation Comparison View

**Type:** Feature
**Effort:** Small (hours)
**Impact:** An operator who runs "Will the Fed cut rates in December?" three times with different agent counts or scenario framings has no way to place those results side-by-side. They have to open three tabs and cross-reference manually. `GET /api/compare?ids=id1,id2` returns a structured comparison object: each simulation's direction, confidence, stance distribution (bullish/neutral/bearish pct), quality health score, round count, agent count, and the top 3 differentiating arguments (agent posts that appear in one sim but not the other, filtered by influence quartile). The endpoint also computes a `consensus_delta` field: the signed distance between the two simulations' `confidence_pct` values (positive = id1 is more bullish, negative = id1 is more bearish). Researchers A/B testing "Fed cut" vs "Fed hold" scenarios, operators iterating on the same topic, and community members comparing their runs to a baseline all get immediate value. Zero new data sources — pure cross-reference of existing `signal.json`, `trajectory.json`, and `actions.jsonl` files.

**How:**
1. Create `backend/app/services/compare_service.py` (~160 LoC, pure stdlib). Accept `sim_ids: list[str]` (exactly 2 for now; validate length with 400 if `len != 2`; session-auth requires both sims owned by or published by the requesting session). For each sim, load: `signal.json` → `{direction, confidence_pct, bullish_pct, neutral_pct, bearish_pct, quality_health, total_rounds, agent_count, topic}`. From `actions.jsonl` for each sim, build a set of unique (agent_name, post_text_normalized) pairs where normalized = lowercased + whitespace-stripped. The "differentiating arguments" for sim A vs sim B: take the top-20 posts by agent influence (read from `stance_flips.json` if present, otherwise use post_count as a proxy); filter to posts with no normalized-text match in sim B within a 0.6 Jaccard similarity threshold (use stdlib `difflib.SequenceMatcher` on trigrams — no ML dependency). Return top-3 from each side. Build the response: `{sim_a: {...signal fields, top_arguments: [{agent, post, round}]}, sim_b: {...}, consensus_delta: float, direction_match: bool, confidence_gap: float, topic_similarity: float (SequenceMatcher on topics)}`. Cache to `storage/compare_cache_{id1}_{id2}.json` with a 30-min mtime TTL (immutable data, cheap to recompute). Add 5 unit tests: `len(ids) != 2` returns 400; `direction_match=True` when both are BULLISH; `consensus_delta` is signed correctly (positive when sim_a confidence > sim_b); differentiating arguments list is capped at 3; cache file is written and re-read on second call without re-computing.
2. Add `GET /api/compare` to `backend/app/api/compare.py`. Query params: `ids` (comma-separated, exactly 2). Auth: session-auth OR both sims published (same visibility logic as `/api/simulation/:id` detail). Response: `Content-Type: application/json`, `Cache-Control: max-age=1800, private`. Return full `ComparisonResponse` object. Add to `surfaces_catalog.py` (type: `analytics`). OpenAPI schema: `ComparisonResponse`, `SimulationSummary`, `DifferentiatingArgument`. Add to `docs/API.md` under "Analytics" with a callout: "Pass exactly two simulation IDs. Both must be owned by the requesting session or published." Add 2 integration tests: compare two completed published sims returns 200 with `consensus_delta`; comparing an unpublished sim from another session returns 403.
3. Add a "Compare" button to the gallery page: when two gallery cards are checked, a floating bottom bar appears with a "Compare these two →" button. Clicking navigates to `/compare?ids=id1,id2`. The `/compare` frontend route renders a two-column split view: left column shows sim A's signal fields, right column shows sim B's. A center column shows the delta metrics: a `consensus_delta` gauge (arrow pointing left/right with magnitude), `direction_match` badge (green "Agree" or red "Disagree"), and the differentiating argument pairs side-by-side. Add 2 frontend unit tests: "Compare these two" button appears only when exactly 2 sims are checked; `/compare` route renders both simulation summaries without error.

### 2. Agent Activity Heatmap

**Type:** Feature
**Effort:** Small (hours)
**Impact:** A completed simulation has no visualization of *when* agents were active across rounds and platforms. The existing analytics surfaces measure *what* happened (stances, confidence, mentions) but not *when the action peaked*. `GET /api/simulation/:id/activity-heatmap` returns a `round × platform` matrix: for each (round, platform) cell, the post count. A 24-round × 3-platform simulation produces a 72-cell matrix. Frontend renders it as a colored heatmap grid: brighter cells = more posts. Operators can immediately see that round 7 on X was the hottest debate moment, while Reddit stayed quiet until round 14. This is the missing temporal + spatial view of agent activity — complementary to the Interaction Network (which is spatial only, with no time axis). Zero new data sources — pure aggregation over `actions.jsonl`.

**How:**
1. Create `backend/app/services/activity_heatmap_service.py` (~100 LoC, pure stdlib). Input: `actions.jsonl` for the simulation. Parse each line: extract `{round: int, platform: str}`. Aggregate into a dict `{(round, platform): count}`. Normalize to `{round: int, platform: str, post_count: int, intensity: float}` where `intensity = post_count / max_post_count` (0.0–1.0, for frontend color mapping). Build the response: `{matrix: [{round, platform, post_count, intensity}], rounds: int (total), platforms: [str] (unique platforms observed), peak_cell: {round, platform, post_count} (the max cell), total_posts: int}`. Cache to `storage/simulations/{id}/activity_heatmap.json` (immutable after sim completes — no TTL). Add 5 unit tests: empty `actions.jsonl` returns `matrix=[]`; `intensity` of the max-count cell is `1.0`; `intensity` of a zero-count cell is `0.0`; `peak_cell` matches the highest-count cell; response includes all unique platforms observed in the data.
2. Add `GET /api/simulation/:id/activity-heatmap` to `backend/app/api/activity_heatmap.py`. Publish-gated (same as other analytics endpoints). Session-auth. Response: `Content-Type: application/json`, `Cache-Control: max-age=3600, private`. Return the full `ActivityHeatmapResponse` object. Add to `surfaces_catalog.py` (type: `analytics`). OpenAPI schema: `ActivityHeatmapResponse`, `HeatmapCell`. Add to `docs/API.md` under "Analytics". Add 2 integration tests: returns 200 with non-empty `matrix` for a completed published sim with actions; `peak_cell.post_count` equals the maximum value in the matrix.
3. Add an "Activity" tab to the Step 3 analytics panel (alongside Stance Flips, Mentions, etc.). The tab renders the heatmap as a CSS grid: rows = rounds (Y axis), columns = platforms (X axis), cells colored from light gray (0 posts) to deep purple (peak posts) using an inline CSS `background-color: rgba(139, 92, 246, {intensity})` formula. Hovering a cell shows a tooltip: "Round {N} · {Platform} · {post_count} posts". A legend bar at the bottom shows the color scale (0 → peak). Add `peak_cell` summary at the top: "Most active: Round {N} on {Platform} ({post_count} posts)." Add 2 frontend unit tests: heatmap grid renders with the correct number of cells (`rounds × platforms`); hovering a cell displays a tooltip with post count.

### 3. Per-Agent Journey Replay

**Type:** Feature
**Effort:** Small (hours)
**Impact:** The existing "Trace Interview" shows the reasoning chain behind a single agent reply in one round. The Interaction Network shows aggregate agent-to-agent mention patterns. Neither surface lets an operator follow one agent's complete arc across the entire simulation: when they posted, how their stance evolved, which rounds they were mentioned by others, and what their final position was. `GET /api/simulation/:id/agent/:agent_name/journey` returns a time-ordered list of all posts from that agent across every round, with their stance label per round, mentions received per round, and the moments their stance changed. This is the longitudinal view of a single simulated persona — useful for understanding *who* drove the narrative and *how* a contrarian evolved into a consensus-driver (or didn't). Zero new data sources — pure extraction from `actions.jsonl`, `trajectory.json`, and `mentions.json` (if present).

**How:**
1. Create `backend/app/services/agent_journey_service.py` (~140 LoC, pure stdlib). Accept `sim_id: str`, `agent_name: str`. Load `actions.jsonl` — filter to lines where `agent_name` matches (case-insensitive). For each matching post, extract `{round, platform, post_text, stance}`. Load `trajectory.json` — extract stance-per-round for this agent (if the trajectory schema tracks individual agent stances; if it only tracks aggregate, skip per-round stance and use post-level stance label from actions). Load `mentions.json` (if exists via mentions_service) — extract rounds and agents who mentioned this agent. Build the response: `{agent_name: str, total_posts: int, rounds_active: [int], posts: [{round, platform, post_text, stance, mentions_received: [str]}], stance_history: [{round, stance}], flip_rounds: [int] (rounds where stance changed from prior round), final_stance: str}`. Sort everything by round ascending. Cache to `storage/simulations/{id}/agent_journey_{agent_name_slug}.json` with mtime TTL matching the sim's immutable status. Add 5 unit tests: unknown `agent_name` returns empty posts array (not 404); `flip_rounds` correctly identifies round where stance changed; `mentions_received` is empty list when `mentions.json` absent; `rounds_active` contains only rounds with at least one post; response is sorted by round ascending.
2. Add `GET /api/simulation/:id/agent/:agent_name/journey` to `backend/app/api/agent_journey.py`. Publish-gated. Session-auth. `agent_name` is URL-decoded (handle spaces and special characters). Response: `Content-Type: application/json`, `Cache-Control: max-age=3600, private`. Return the full `AgentJourneyResponse` object. Add to `surfaces_catalog.py` (type: `analytics`). OpenAPI schema: `AgentJourneyResponse`, `AgentPost`, `StanceHistoryEntry`. Add to `docs/API.md` under "Analytics" with a note: "agent_name must match exactly as it appears in the simulation roster (case-insensitive, URL-encoded if spaces)." Add 2 integration tests: returns 200 with non-empty posts for a valid agent in a completed published sim; `final_stance` matches the agent's stance in the last round they posted.
3. Add a clickable agent name throughout the Step 3 UI: anywhere an agent name appears (Stance Flips panel, Mentions panel, Interaction Network tooltip), clicking it opens a "Journey" drawer. The drawer is a vertical timeline: each entry shows round number, platform badge, post text (truncated to 160 chars with expand), and a stance chip (BULLISH/BEARISH/NEUTRAL in the existing chip colors). Stance flip moments are highlighted with a colored divider ("Stance changed: BEARISH → BULLISH"). A summary header shows: "Agent: {name} · {total_posts} posts across {rounds_active.length} rounds · Final stance: {final_stance}." Add 2 frontend unit tests: clicking an agent name in the Mentions panel opens the Journey drawer; stance flip dividers render only on rounds in `flip_rounds`.

### 4. Topic Consensus Trend

**Type:** Feature
**Effort:** Small (hours)
**Impact:** An operator who runs "Will Bitcoin break $100K before year-end?" every two weeks across November has four data points — four `signal.json` files each with a direction and confidence. There is no view that aggregates those into a trend line: "confidence was 61% on Oct 15, dropped to 54% on Oct 29, recovered to 68% on Nov 5." `GET /api/topic-trend?q=Bitcoin&days=90` scans all published simulations whose topic matches the query string (case-insensitive substring, min 3 chars) within the specified window, extracts `{created_at, direction, confidence_pct}` from each, and returns them sorted by date. The endpoint also computes a `momentum` field: the signed difference between the first and last confidence values in the window (positive = confidence rising). This is a pure data-mining endpoint — no new storage, no new schemas — built entirely from existing `signal.json` files. Operators building tracking dashboards, newsletter writers covering evolving sentiment, and community members debating "what does the swarm think now vs. 3 weeks ago" all benefit without changing any simulation behavior.

**How:**
1. Create `backend/app/services/topic_trend_service.py` (~110 LoC, pure stdlib). Accept `q: str` (min 3 chars; validate with 400 if shorter), `days: int` (default 90, clamp 7–365), `session_token: str`. Scan `storage/simulations/*/signal.json` for the requesting session's published sims created within the window. Filter: `topic.lower().find(q.lower()) != -1`. Extract from each match: `{simulation_id, topic, created_at, direction, confidence_pct}`. Sort by `created_at` ascending. Compute `momentum = last_confidence_pct - first_confidence_pct` (or `None` if fewer than 2 results). Build the response: `{query: str, days: int, result_count: int, momentum: float | None, direction_mode: str (most common direction string, or "MIXED" if no majority), data_points: [{simulation_id, topic, created_at, direction, confidence_pct}]}`. Cache to `storage/topic_trend_cache_{session_hash}_{q_slug}_{days}.json` with a 15-min mtime TTL. Add 5 unit tests: `q` under 3 chars returns 400; sims outside the time window are excluded; `momentum` is `None` when only 1 result; `direction_mode` is "MIXED" when results are split evenly; results are sorted by `created_at` ascending.
2. Add `GET /api/topic-trend` to `backend/app/api/topic_trend.py`. Session-auth (session-scoped — returns only the operator's own published sims). Query params: `q` (required, min 3 chars), `days` (optional int, default 90). Response: `Content-Type: application/json`, `Cache-Control: max-age=900, private`. Return the full `TopicTrendResponse` object. Add to `surfaces_catalog.py` (type: `analytics`). OpenAPI schema: `TopicTrendResponse`, `TrendDataPoint`. Add to `docs/API.md` under "Analytics" with a callout: "Returns all published simulations matching the topic query string within the requested window. Use `days=365` for a full-year view." Add 2 integration tests: returns 200 with `data_points` for a session with ≥2 published sims matching the query; `momentum` is positive when second sim has higher confidence than first.
3. Add a "Topic Trend" entry to the gallery header toolbar (alongside the "Bulk export" and "Collections" controls in future UI state). Clicking opens a search bar: type a topic fragment, select a time window (30 / 60 / 90 days), and click "Show trend." The view renders a sparkline chart: X axis = date, Y axis = `confidence_pct`, colored by direction (green dot = BULLISH, red = BEARISH, gray = NEUTRAL). A summary line above the chart: "9 simulations matching 'Bitcoin' · confidence trending +7% over 90 days." Each dot is clickable, opening the simulation detail for that run. Add 2 frontend unit tests: sparkline renders with one dot per `data_point`; clicking a dot navigates to the correct simulation detail URL.

### 5. Dynamic Consensus Badge

**Type:** Integration / Growth
**Effort:** Small (hours)
**Impact:** GitHub repos, Notion pages, Substack posts, and Ghost blogs all support inline SVG images. MiroShark already generates a 1200×630 share card PNG and a belief trajectory chart SVG, but neither is designed to sit inline in a README alongside `stars | forks | license` badges. `GET /api/simulation/:id/consensus-badge.svg` returns a Shields.io-style flat SVG: a left label block ("MiroShark") in dark gray and a right value block ("BULLISH · 78%") colored by direction (green for BULLISH, red for BEARISH, gray for NEUTRAL). The SVG is under 1KB, renders crisply at any size, and updates dynamically — if the simulation is re-analyzed or re-published with updated data, the badge reflects the current `signal.json` without the user changing the embed URL. Operators who publish MiroShark analyses on their GitHub profiles, in strategy repos, or in newsletters can drop one line and get a living consensus indicator. This is distinct from the share card (too large for inline), the trajectory chart (shows the full belief arc), and the archive badge (shows quality score). It is the lightest possible signal surface — one number, one color, one embed.

**How:**
1. Create `backend/app/services/badge_service.py` (~80 LoC, pure stdlib). Accept `sim_id: str`. Load `signal.json` for the simulation. Extract `{direction, confidence_pct, quality_health}`. Direction-to-color map: `{"BULLISH": "#22c55e", "BEARISH": "#ef4444", "NEUTRAL": "#6b7280"}`. Build the SVG string using an f-string template (no external dependencies): a standard Shields.io "flat" layout — `<svg>` with two `<rect>` blocks (left dark gray `#555`, right direction color), two `<text>` blocks (left "MiroShark" in white, right "{direction} · {confidence_pct}%" in white), and a `<title>` for accessibility ("MiroShark simulation: {direction}, {confidence_pct}% confidence"). Total SVG width: left block 90px + right block dynamic (10px per char + 20px padding). Font: `DejaVu Sans,Verdana,Geneva,sans-serif` at 11px — the standard Shields.io font stack. Encode special chars (`<`, `>`, `&`) in the topic field if included in a future title variant. Add a `Cache-Control: max-age=300` header (5-min browser cache — fresh enough for live embedding, light enough to avoid hammering disk on shared gallery pages). Add 5 unit tests: BULLISH direction produces the green `#22c55e` fill; BEARISH produces `#ef4444`; badge SVG starts with `<svg` and ends with `</svg>`; confidence_pct appears in the value block text; `<title>` tag is present for accessibility.
2. Add `GET /api/simulation/:id/consensus-badge.svg` to `backend/app/api/badge.py` (or extend the existing share surface module). Keyless (public) if the simulation is published; return 404 for unpublished sims (do not return a placeholder "not found" badge — 404 is the correct behavior so private analyses don't surface as blank badges). Response: `Content-Type: image/svg+xml`, `Cache-Control: max-age=300, public`, `ETag` derived from `signal.json` mtime (enables conditional GET). No session auth required for published sims. Add to `surfaces_catalog.py` (type: `share`). Add to `docs/API.md` under "Sharing" alongside the share card and trajectory chart: "Embed a live consensus badge in any Markdown or HTML with `![consensus](https://your-instance/api/simulation/{id}/consensus-badge.svg)`." Add 2 integration tests: returns `Content-Type: image/svg+xml` for a published sim; returns 404 for an unpublished sim.
3. Add "Consensus Badge" to the Step 3 EmbedDialog share panel (alongside share card, GIF, badge, QR code). The panel shows: a live preview of the SVG badge at 1× and 2× scale; a copy-ready Markdown snippet (`![MiroShark consensus](...)`) and an HTML `<img>` snippet; and a brief note: "Embed this badge in a GitHub README, Notion page, or Substack post. It updates automatically when this simulation's data changes." Auto-select the full Markdown snippet on click. Add a `?style=flat-square` variant in a future iteration (noted in a code comment, not implemented). Add 2 frontend unit tests: badge preview renders without error for a completed published simulation; "Copy Markdown" button copies the correct `![](...)` snippet to clipboard.
