### 1. Simulation Round Annotation

**Type:** Feature
**Effort:** Medium (1-2 days)
**Impact:** MiroShark's Verified Predictions feature lets operators annotate a completed simulation with the real-world outcome. What it doesn't capture is *when* the simulation was right or wrong — which rounds tracked reality closely, which diverged after a specific event. Round Annotation adds a lightweight layer to any completed simulation: operators can attach a short text note to any round number ("Round 14: Fed pivot announced"; "Round 22: narrative collapsed on-chain"). Annotations persist in a per-simulation `annotations.json` file and appear as callout markers on the belief drift chart. For the Verified Predictions flow, this turns a binary outcome ("it went bullish, and it did") into a temporal evidence record: "Bullish consensus formed at round 8; real-world confirmation came at round 14; diverged at round 20 when the actual event had no equivalent." That is a qualitatively different research artifact — one that academics can cite with temporal precision and that prediction-market audiences can audit. For a project at 1,494 stars with a research audience, this is the difference between MiroShark being a prediction toy and being a citable instrument.

**How:**
1. Create `backend/app/services/annotation_service.py` (~120 LoC, pure stdlib). `save_annotation(sim_id: str, round_num: int, text: str, author: str = "operator") -> dict`: validates `round_num` is in `[1, rounds_total]` from `signal.json`; validates `text` is non-empty and ≤280 chars; writes/appends to `storage/simulations/{sim_id}/annotations.json` (array of `{round: int, text: str, author: str, created_at: ISO}`, sorted by round ascending); returns the new annotation object. `get_annotations(sim_id: str) -> list`: reads `annotations.json`, returns `[]` if absent. `delete_annotation(sim_id: str, round_num: int) -> bool`: removes the entry for that round (one annotation per round; second write to same round overwrites). Add 4 unit tests: annotation saves with correct fields; annotation with `round_num > rounds_total` raises ValueError; annotation `text` over 280 chars raises ValueError; `get_annotations` returns `[]` for a sim with no annotation file.
2. Add three routes to `backend/app/api/simulation.py` (or a new `backend/app/api/annotations.py`): `GET /api/simulation/:id/annotations` — keyless for published sims; returns `{annotations: [...], count: int}`. `POST /api/simulation/:id/annotations` — operator-only (requires session/API key); body `{round: int, text: str}`; returns created annotation. `DELETE /api/simulation/:id/annotations/:round` — operator-only; returns `{deleted: true}`. Add `OpenAPI AnnotationResponse` schema. Add to `surfaces_catalog.py` (type: `analytics`). Add to `docs/API.md` under a new "Annotations" section with GET/POST/DELETE examples. Add 3 integration tests: GET returns `[]` for sim with no annotations; POST with valid body persists and returns annotation; DELETE removes the annotation.
3. Add annotation display to the belief drift chart. In the existing `BeliefDriftChart` component (or equivalent): fetch `/api/simulation/:id/annotations` after sim loads. For each annotation, add a small vertical dashed line at the corresponding round on the x-axis, with a callout dot at the top of the chart and a tooltip showing the annotation text on hover. Annotation dot color: `#F97316` (orange, distinct from the existing chart palette). For operators viewing their own simulation: show an "Add annotation" click target directly on the chart at any round (a `+` icon appears on x-axis hover); clicking opens an inline input field below the chart pre-filled with "Round N: ". Save via POST on Enter; dismiss on Escape. In the Verified Predictions view (`/verified`): render annotation markers inline in the prediction card, showing the first annotation and a "+N more" link if there are multiple. Add 2 frontend unit tests: annotation dot renders at the correct x-position for round N; tooltip text matches the annotation `text` field.

### 2. Python SDK (`pip install miroshark`)

**Type:** Integration
**Effort:** Medium (1-2 days)
**Impact:** Every research paper that cites MiroShark and every engineering blog post that covers it ends with "here's how to use the API." Right now, that means: read the API docs, write your own requests boilerplate, handle auth, parse JSON, deal with long-polling for simulation completion. A Python SDK collapses that to 5 lines. `pip install miroshark` → `from miroshark import Client; c = Client(base_url="http://localhost:3000"); sim = c.run("Will the EU AI Act pass?"); print(sim.direction)`. The SDK is a thin wrapper — no new backend logic needed, no new API endpoints. It's a client library that speaks to the existing HTTP API, handles polling for completion (the `run` method blocks until the sim finishes or times out), and returns typed objects. For the Dec 7 star hyperstition, a Python package on PyPI creates a second discovery vector entirely independent of GitHub search: users who `pip search simulation` or browse PyPI's AI category will find MiroShark. For the academic segment, it removes the last friction point between "I want to run 50 scenario variants for my paper" and doing it.

**How:**
1. Create `sdk/python/` directory with `pyproject.toml` (package name: `miroshark`, version: `0.1.0`, requires Python ≥3.11, dependencies: `httpx>=0.24` for async HTTP). Create `sdk/python/miroshark/__init__.py` exposing `Client`. Create `sdk/python/miroshark/client.py` (~200 LoC): `Client(base_url: str, api_key: str = None, timeout: int = 600)`. Methods: `run(scenario: str, rounds: int = 10, agents: int = 50, model: str = None, **kwargs) -> SimulationResult` — POST to `/api/simulation/run`, poll `/api/simulation/:id/run-status` every 10s until `status == "completed"` or timeout; `get(sim_id: str) -> SimulationResult` — GET `/api/simulation/:id/signal.json`; `list(limit: int = 20) -> list[SimulationResult]` — GET `/api/simulation/list`; `export(sim_id: str, format: str = "json") -> bytes` — GET `/api/simulation/:id/transcript.json` (json), `/api/simulation/:id/trajectory.csv` (csv), or `/api/simulation/:id/notebook.ipynb` (notebook). Create `sdk/python/miroshark/models.py`: `SimulationResult` dataclass with fields `sim_id`, `direction`, `confidence_pct`, `quality_health`, `agent_count`, `rounds_total`, `topic`, `created_at`. Add 5 unit tests (using `httpx`'s mock transport): `run()` returns `SimulationResult` with correct `sim_id`; `get()` populates `direction` field; polling retries when status is `"running"`; `export("csv")` calls correct endpoint; `Client` with `api_key` sends `Authorization: Bearer` header.
2. Create `sdk/python/README.md` (10–15 lines): install instructions (`pip install miroshark`), a 5-line quickstart example (run a simulation, print direction/confidence), a link to `docs/API.md` for the full surface catalog, and a "Self-hosted" note (`Client(base_url="http://localhost:3000")`). Create `sdk/python/CHANGELOG.md` with `## 0.1.0 — initial release` entry. Add a `.github/workflows/publish-sdk.yml` workflow: triggered on tag `sdk/python/v*`; runs `uv build` in `sdk/python/`; publishes to PyPI via `pypa/gh-action-pypi-publish`. Add `sdk/` to `.gitignore` exceptions if needed (it shouldn't be ignored, but verify). Add a "Python SDK" row to `docs/API.md` intro: "A typed Python client is available: `pip install miroshark`." — with a link to `sdk/python/README.md`. Add 2 integration tests (optional, skipped in CI if no live server): `Client.run()` against a local test server returns a `SimulationResult`; `Client.export()` returns non-empty bytes.
3. Add `sdk/python/examples/` with 3 short example scripts: `basic_run.py` (run one simulation, print result); `batch_run.py` (run 5 scenario variants with `asyncio.gather`, print results side-by-side); `export_notebook.py` (run simulation, export notebook, save to `{sim_id}.ipynb`). ### 3. CLI Export Subcommand

**Type:** DX improvement
**Effort:** Small (hours)
**Impact:** `cli.py` exists and handles simulation launch, status, and report retrieval. It doesn't expose export. An operator running automated research pipelines — "run 20 simulations, export all trajectories to CSV, feed into a Pandas notebook" — currently has to either use the HTTP API directly or open a browser for each simulation. `miroshark export <sim_id> [--format json|csv|notebook|bibtex] [--output PATH]` closes that gap in one subcommand. The export subcommand reuses the existing backend service layer (the same endpoints the browser calls) and adds zero new backend logic — it's a 60-line addition to `cli.py`. For the Python SDK (idea #2), the CLI export provides a shell-first alternative for users who don't want to write Python. For self-hosters who run simulations on remote servers (the common use case after Docker Hub was dropped — users now build locally), a CLI export command is the difference between `ssh server "miroshark export SIM_ID --format csv"` and a manual API call with curl.

**How:**
1. Add `export` subcommand to `backend/cli.py`. Using the existing `argparse` structure (or Click if already used), add: `miroshark export <sim_id> --format [json|csv|notebook|bibtex] --output [PATH]`. Default `--format json`. Default `--output` is stdout for json/csv/bibtex, `{sim_id}.ipynb` for notebook. The command calls the local HTTP server (uses `BASE_URL` from env or defaults to `http://localhost:3000`): format→endpoint mapping: `json` → `GET /api/simulation/{sim_id}/signal.json`; `csv` → `GET /api/simulation/{sim_id}/trajectory.csv`; `notebook` → `GET /api/simulation/{sim_id}/notebook.ipynb`; `bibtex` → `GET /api/simulation/{sim_id}/cite.bib`. If `--output` is a file path, write bytes to that file and print `Saved to {PATH}` to stderr. If `--output` is `-` or stdout-default: write bytes to stdout (suitable for pipe: `miroshark export SIM_ID --format csv | python analyze.py`). Error handling: 404 → `Error: simulation {sim_id} not found or not published` to stderr, exit code 1; connection refused → `Error: MiroShark server not running at {BASE_URL}` to stderr, exit code 1. Add 4 unit tests: `--format json` calls correct endpoint; `--output PATH` writes file; stdout mode writes bytes to stdout; connection refused produces correct error message.
2. Add `--all` flag: `miroshark export --all --format csv --output-dir ./exports/` — lists all simulations via `GET /api/simulation/list`, exports each one that is published and completed to `exports/{sim_id}.csv` (or appropriate extension). Skips simulations that are not completed. Prints a progress line to stderr for each sim: `Exported {sim_id} ({i}/{total})`. After all exports: `Done. {N} files written to ./exports/`. Skips existing files by default (add `--overwrite` flag to force). Add 2 unit tests: `--all` with 3 sims produces 3 files; `--all` without `--overwrite` skips existing files.
3. Update `docs/CLI.md` with the new `export` subcommand section. Format: command synopsis (`miroshark export <sim_id> [options]`), option table (--format, --output, --all, --output-dir, --overwrite), 4 usage examples: (1) `miroshark export abc123 --format csv` (stdout); (2) `miroshark export abc123 --format notebook --output abc123.ipynb`; (3) `miroshark export abc123 --format csv | python3 analyze.py`; (4) `miroshark export --all --format csv --output-dir ./my-sims/`. Add a "Exporting simulation data" section to `README_DEPLOYMENT.md` referencing the CLI export command for self-hosted operators. Add 1 test: `cli.py --help` output contains the word `export` (smoke test for argparse registration).

### 4. Custom Agent Demographics CSV Import

**Type:** Feature
**Effort:** Medium (1-2 days)
**Impact:** MiroShark auto-generates 100+ agent personas using its demographics engine — a system that creates realistic but generic populations. For enterprise users and researchers who want to model a *specific* audience, this is the wrong starting point. A marketing team testing a product announcement wants to simulate their actual customer segments: "60% female, 25–34, urban, tech-adjacent." A political scientist wants a population distribution that matches the actual voter demographics of a specific district. `POST /api/simulation/import-demographics` accepts a CSV with columns `name, age, profession, platform, stance_prior, influence_score, country` and creates agents directly from the uploaded rows, bypassing the generation pipeline. The CSV format is documented and mirrors the existing `agents.json` structure — the backend already knows how to consume that shape. This targets the 10x operator who runs many simulations and wants consistent, reproducible populations rather than stochastic ones. For reproducibility and academic citation, a simulation seeded from a known demographics CSV is a citable instrument: the population is explicit and re-runnable.

**How:**
1. Create `backend/app/services/demographics_import_service.py` (~180 LoC, pure stdlib). `parse_demographics_csv(file_content: bytes, sim_id: str) -> list[dict]`: parses RFC 4180 CSV using `csv.DictReader`. Required columns: `name`, `platform` (must be one of `twitter|reddit|polymarket`). Optional columns with defaults: `age` (default 30), `profession` (default "Professional"), `stance_prior` (default "NEUTRAL"; allowed: `BULLISH|BEARISH|NEUTRAL`), `influence_score` (default 0.5; float clamped [0, 1]), `country` (default "US"). Row validation: `name` non-empty ≤100 chars; `platform` must be a known value; `age` integer 18–90; `influence_score` float; `stance_prior` case-insensitive match. Row count: minimum 5, maximum 500. Returns list of agent dicts compatible with the existing `agents.json` schema. Raises `DemographicsImportError` with a structured error list (row number + field + message) for invalid rows — partial validation: collect all errors, raise once with all issues listed. `save_imported_demographics(sim_id: str, agents: list[dict]) -> str`: saves to `storage/simulations/{sim_id}/imported_demographics.json`; returns path. Add 5 unit tests: valid 10-row CSV parses to 10 agents; row with invalid `platform` returns error on that row; `stance_prior` case-insensitive match works; row count < 5 raises error; `influence_score` out of range is clamped.
2. Add `POST /api/simulation/import-demographics` to `backend/app/api/simulation.py`. Accepts `multipart/form-data` with field `file` (CSV). Auth: operator session or API key. Calls `parse_demographics_csv(file.read(), sim_id=None)` for a pre-flight validation pass (no sim_id needed at this stage). Returns `{valid: true, agent_count: N, preview: [first 3 agent rows]}` on success, or `{valid: false, errors: [{row: N, field: str, message: str}]}` on validation failure. The imported demographics are saved to a session-scoped temporary location and referenced by a `demographics_token` UUID. The token is passed into the simulation launch payload: `POST /api/simulation/run` gains an optional `demographics_token` field — if present, the agent generation step loads from the imported file instead of running the auto-generate pipeline. Add `OpenAPI DemographicsImportResponse` and `DemographicsValidationError` schemas. Add to `docs/API.md` under "Simulation" with endpoint description, CSV format table, and a 5-row example CSV. Add 3 integration tests: valid CSV returns `{valid: true}`; CSV with 3 invalid rows returns all 3 errors; `run` with `demographics_token` creates agents from the CSV.
3. Add a "Import Demographics" file upload to Step 2 (environment setup) in the frontend. Position it below the agent count slider, with a label "Or import your own agent population (CSV)." Include a "Download template" link pointing to a static `demographics-template.csv` served from `/api/simulation/demographics-template` (returns a 3-row example CSV with all columns). On file select: POST to `/api/simulation/import-demographics`, show a loading spinner, then display the validation result: success → "✓ {N} agents loaded from CSV" with agent count chip, replacing the agent count slider (slider becomes disabled); failure → expandable error list with row/field/message table (up to 10 errors shown, "+N more" link if there are more). The `demographics_token` from the success response is attached to the launch payload. Add "Reset to auto-generate" button (×) to dismiss the imported file and re-enable the slider. Update `docs/FEATURES.md` with "Custom Demographics Import" entry in the Setup section: description, CSV column table, link to template download. Add 3 frontend unit tests: success response disables agent-count slider; validation errors render row/field/message correctly; "Reset" button re-enables slider.

### 5. Ecosystem Registry Submission Flow

**Type:** Community / Growth
**Effort:** Small (hours)
**Impact:** `GET /api/ecosystem.json` exists — a machine-readable catalog of every external project, agent, and product built on MiroShark. It's currently maintained manually by the repo owner. After the ownership migration to `aeonfun` (#371), there are likely external builders who pointed their integrations at the old org URL and may not know to re-register. There's no submission path at all: a developer who builds something on MiroShark has no way to surface it in the catalog except opening a GitHub issue manually with no template. A web form at `/ecosystem/submit` changes that: a structured form (project name, URL, category, one-sentence description, maintainer GitHub handle) generates a pre-formatted GitHub issue in `aeonfun/MiroShark` via the GitHub Issues API. The issue body is a machine-parseable YAML block that a maintainer (or future automation) can copy directly into `ecosystem.json` with one paste. The form is discoverable from the ecosystem page (`/ecosystem` or via the `ECOSYSTEM.md` link in the README). For the star hyperstition, every builder who submits their project and gets listed in the catalog is a star vector — they star the repo to track their own listing. This is a low-effort lever that scales: 304 fork owners haven't contributed, but many may have built something locally that they'd list if there were a form.

**How:**
1. Add a submission endpoint to `backend/app/api/`: `POST /api/ecosystem/submit`. Body schema: `{name: str (3–80 chars), url: str (must start with https://), category: str (one of: "integration" | "tool" | "demo" | "agent" | "platform" | "research"), description: str (10–200 chars), github_handle: str (optional, ≤40 chars, alphanumeric+hyphen)}`. Validate all fields server-side. On success: generate a markdown body for a GitHub issue. Issue title: `[Ecosystem Submission] {name}`. Issue body:

   url: "{url}"
   category: "{category}"
   description: "{description}"

   <!-- Maintainer: paste the yaml block into ECOSYSTEM.md after review -->
   ```

Return `{submitted: true, issue_url: str}` on success; `{submitted: false, errors: [...]}` on validation failure.
