### 1. Simulation Round Replay Scrubber

**Type:** Feature
**Effort:** Medium (1–2 days)
**Impact:** Every completed simulation stores per-round belief progression in `trajectory.json`, but the only way to experience that progression today is to read raw JSON or look at static charts. A round-by-round replay control — Play, Pause, Step Forward, Step Back — turns every finished simulation into a watchable story. Researchers can pinpoint the exact round where sentiment shifted; journalists get a "frame-by-frame" narrative; casual users experience the simulation as something more like a film than a spreadsheet. No new backend data is needed; the trajectory data is already fetched. This is the highest-leverage UX improvement available without any new API surface.

**How:**
1. Add a `ReplayController.vue` component to `frontend/src/components/`. It exposes four actions: play (auto-advances rounds every 1.5s using `setInterval`), pause, step-forward, step-back. Current round stored as a `ref<number>` initialized to the last round. A progress bar (thin violet line, same palette as existing UI) shows position `currentRound / totalRounds`. On every round change, emit a `roundChanged(n)` event. Add 3 unit tests: play starts interval; pause clears interval; step-back clamps at round 1 (no underflow).
2. Wire `ReplayController.vue` into `Step3Simulation.vue`. On `roundChanged(n)`, filter the displayed agent roster and stance distribution bars to show only data up to round `n` (use the round-indexed trajectory data already in the store). The belief percentage shown per agent becomes their belief at round `n`, not the final value. Add a small "Round N of M" counter above the agent roster. For incomplete/running simulations, hide the replay controller entirely (the live view already shows real-time progress). Add 2 unit tests: `roundChanged(1)` shows initial beliefs; `roundChanged(last)` shows final beliefs.
3. Add a `BeliefDriftChart` playhead marker: a vertical dashed line on the `BeliefDriftChart` (the belief-over-time chart already in the UI) that moves to the current replay round when the scrubber advances. This gives a dual-axis view — the chart shows the full trajectory, the playhead shows "where you are." Implement by passing `currentRound` as a prop to `BeliefDriftChart.vue` and rendering the line via an SVG `<line>` element at the proportional x position. Add 1 unit test: playhead x-position is `(currentRound / totalRounds) * chartWidth` (±1px tolerance).

### 2. REST API Rate Limit Headers

**Type:** DX
**Effort:** Small (hours)
**Impact:** Self-hosted MiroShark deployments have no rate-limit signaling today — ecosystem builders who poll `/api/activity.json` or call `/api/simulation/search` at high frequency get no feedback until they start seeing 5xx errors from an overloaded instance. Adding standard `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` headers (per the de facto IETF draft standard) to every API response gives API consumers the information they need to self-throttle, makes the platform safer for high-volume use cases (batch scanning, webhook integrations, academic scrapers), and signals production maturity to anyone evaluating MiroShark as infrastructure. The implementation is a single FastAPI middleware; no new storage layer is needed (in-memory token bucket per IP is sufficient for single-process deployments, acceptable because restarts reset the counter and that's fine for rate signaling).

**How:**
1. Create `backend/app/middleware/rate_limit.py` (~80 LoC). Implement a simple token-bucket rate limiter: a `dict[str, tuple[int, float]]` mapping client IP to `(tokens_remaining, last_refill_ts)`. On each request, compute tokens consumed since last refill (`elapsed * rate`), clamp to `max_tokens`, decrement by 1. Default: `max_tokens=200`, `rate=200/3600` (200 req/hr). Skip rate limiting for health check endpoints. If tokens drop below 0, return `429 Too Many Requests` with `Retry-After` header. Always attach `X-RateLimit-Limit: 200`, `X-RateLimit-Remaining: N`, `X-RateLimit-Reset: {unix_ts_of_next_full_refill}` to every response (even non-limited ones). Add 5 unit tests: header present on 200 response; `X-RateLimit-Remaining` decrements on each call; `429` returned when bucket exhausted; `Retry-After` header present on `429`; `/api/health` exempt from limiting.
2. Register the middleware in `backend/app/main.py` via `app.add_middleware(RateLimitMiddleware)`. Read `RATE_LIMIT_MAX` and `RATE_LIMIT_PER_HOUR` from environment (with the defaults above) so self-hosters can tune without code changes. Document in `.env.example` alongside the existing env vars with a brief comment. Add 1 integration test: 201 requests in a row from the same IP returns the 201st as `429`.
3. Add a "Rate limits" section to `docs/API.md` (3–5 sentences): what the headers mean, the default limits, how to configure, and the recommendation for polling consumers to check `X-RateLimit-Remaining > 10` before issuing the next request. Add a code snippet showing a Python `requests` wrapper that reads these headers and sleeps until `X-RateLimit-Reset` when remaining drops below 5.

### 3. Agent Influence Force-Directed Network Graph

**Type:** Feature
**Effort:** Medium (1–2 days)
**Impact:** `mentions_service.py` already extracts a directed @-mention graph from every simulation's `actions.jsonl` — who cited whom, how many times. The existing `MentionsPanel.vue` renders this as a ranked list and a table matrix, which is accurate but doesn't reveal the *structure* of information flow: hubs, clusters, isolated agents, bidirectional relationships. A force-directed network graph (SVG, no external library — D3's force simulation is already a transitive dependency via the charting stack) shows this structure at a glance. A researcher can immediately see whether the simulation converged through one influential hub or through distributed peer-to-peer consensus. The graph is the most shareable visualization the platform has produced — a single screenshot captures the whole simulation's social dynamics.

**How:**
1. Add a `MentionNetworkGraph.vue` component (~200 LoC, no new npm deps). Accept `mentions` prop (the `GET /api/simulation/:id/mentions` response object). Extract `nodes` (unique agents, radius proportional to `influence_score` clamped to [6, 20]px, color-coded by final stance: violet=BULLISH, gray=NEUTRAL, red=BEARISH) and `edges` (mention pairs, stroke-width proportional to mention count, directed arrow using SVG `<marker>`). Use a simple spring-force layout: for each tick, apply attractive force along edges and repulsive force between all node pairs (Coulomb's law, constant `k=50`). Run 200 ticks on mount, then stop (no continuous animation). SVG viewBox adapts to container width. Clicking a node highlights its edges in bright violet and dims all others; clicking background resets. Add 3 unit tests: node count equals unique agent count; edge count equals non-zero mention pairs; click highlight adds `active` CSS class to node's edges.
2. Add a "Network" toolbar button to `Step3Simulation.vue` (sibling to "@ Mentions" and "↻ Stance Shifts"). Clicking it opens the `MentionNetworkGraph.vue` overlay (same modal container as other overlays). Lazy-load mentions data: if the mentions API was already fetched (by "@ Mentions" panel), use the cached result; otherwise fetch on open. Add a "Download SVG" button to the overlay header — triggers `URL.createObjectURL(new Blob([svgEl.outerHTML], {type: 'image/svg+xml'}))` and an anchor click. Add 2 unit tests: "Network" button only renders when simulation is complete; "Download SVG" triggers a Blob download (mock `URL.createObjectURL`).
3. Update `GET /api/simulation/:id/mentions` to include a `graph` key in the response alongside the existing `ranked_agents` and `mention_matrix` keys: `{"graph": {"nodes": [{name, influence_score, final_stance}], "edges": [{source, target, count}]}}`. This avoids a second API call from the frontend. Backfill via `mentions_service.py` (add `_build_graph(agents, mention_matrix)` helper). Add to OpenAPI with `MentionGraphNode` and `MentionGraphEdge` schemas. Add 2 unit tests: `graph.nodes` length matches `ranked_agents` length; `graph.edges` are sorted by count descending.

### 4. Simulation Fork / Clone Endpoint

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Running a simulation twice with the same parameters — to test whether results are stable, or to try a small variation — currently requires remembering (or copying out) every setup option and re-entering them from scratch. `POST /api/simulation/:id/fork` creates a new simulation record with all parameters copied from the source: topic, agent count, platform list, injected events, round count, direction hint. The fork is returned as a new `simulation_id` in the `pending` state, ready to run with `POST /api/simulation/:id/run`. No new execution is triggered automatically. This single endpoint makes the A/B Compare workflow (suggested Oct 20) actually ergonomic — fork, tweak one parameter, run, compare — and turns MiroShark into a proper experiment platform rather than a one-shot oracle. Researchers running multiple trials can script it with the existing REST API.

**How:**
1. Create `backend/app/services/fork_service.py` (~60 LoC, pure stdlib). Load the source simulation's config from its directory (read `agents.json`, `config.json`, or whatever parameter store the simulation uses — check `backend/app/services/` for the canonical config read pattern). Generate a new `simulation_id` (same UUID4 pattern as new simulations). Write the forked config to a new simulation directory. Set `status: "pending"`, `forked_from: source_id`, `created_at: now()` in the new sim's metadata. Do NOT copy result files (`trajectory.json`, `signal.json`, `actions.jsonl`) — only config. Add 4 unit tests: fork of a completed sim creates a new pending sim; `forked_from` field set correctly; result files not copied; fork of a non-existent sim returns `None` (caller raises 404).
2. Add `POST /api/simulation/:id/fork` to `backend/app/api/simulation.py`. Publish-gate: only the session that ran the source sim (or if the source is public) can fork it — use the same ownership check as `GET /api/simulation/:id`. Request body: optional `{"overrides": {"topic": str, "agent_count": int}}` to modify specific parameters in the fork (validate against the same schema as new sim creation; reject unknown keys with 400). Response: `{"forked_simulation_id": str, "source_simulation_id": str, "status": "pending", "created_at": ISO8601}`. Add to `surfaces_catalog.py` (type: `simulation`) and OpenAPI with `ForkResponse` schema. Add to `docs/API.md` under "Simulation Lifecycle." Add 3 integration tests: valid fork returns 200 with `forked_simulation_id`; source not found returns 404; unowned private source returns 403.
3. Add a "Fork & Rerun" button to `Step3Simulation.vue`'s result header (appears only on completed simulations, next to the "Share" button). Clicking it calls `POST /api/simulation/:id/fork`, then immediately calls `POST /api/simulation/{forked_id}/run`, and opens the new simulation's Step 3 view. Show a brief "Forking…" loading state on the button. Add 1 frontend unit test: button calls fork endpoint and navigates to new simulation on success.

### 5. Hugging Face Dataset Auto-Sync

**Type:** Integration
**Effort:** Small (hours)
**Impact:** The `MiroShark/social-prediction-market-sim` Hugging Face dataset is linked from the README badge but has not been described as growing automatically — it appears to be a static snapshot. Every public simulation MiroShark runs is a potential data point: topic, direction, confidence, cost, agent count, platform mix, created_at. Continuously appending these rows to the HF dataset via a daily GitHub Actions job transforms the README badge from a static credential into a live counter. HF datasets surface in academic paper searches, HF's trending datasets list, and LLM training data sourcing pipelines — a continuously growing dataset is indexed more aggressively and cited more readily than a frozen one. The dataset becomes a distribution surface that works 24/7 with no operator effort.

**How:**
1. Create `scripts/sync-hf-dataset.sh` (~60 lines). Uses `huggingface_hub` Python CLI (`huggingface-cli`) — install via `pip install huggingface_hub` at job start. Queries `GET /api/simulation/search?q=&limit=50&sort=created_at` (or reads local simulation directories) to collect public completed simulations not yet synced. For each, emits a JSON row: `{simulation_id, topic, direction, confidence_pct, bullish_pct, bearish_pct, neutral_pct, cost_usd, agent_count, round_count, platforms: [str], peak_round, created_at}`. Appends rows to a local `hf_sync_buffer.jsonl`, then calls `huggingface-cli upload MiroShark/social-prediction-market-sim hf_sync_buffer.jsonl data/$(date +%Y-%m-%d).jsonl --repo-type dataset`. Uses `.hf_sync_cursor` (stores last-synced `created_at` ISO timestamp) to avoid re-uploading. Requires `HF_TOKEN` env var (write-access token for the dataset repo). Exits cleanly with a summary log line if no new sims since last sync. Add a sandbox note: if `huggingface-cli` upload fails (network block), write rows to `.pending-hf/` for postprocessing.
2. Add a new GitHub Actions workflow `.github/workflows/hf-sync.yml` (or add a `hf-sync` step to the existing cron workflow). Schedule: daily at 06:00 UTC (before aeon's morning skills run). Steps: checkout, install `huggingface_hub`, run `scripts/sync-hf-dataset.sh`. Set `HF_TOKEN` from repo secrets. On failure: continue (don't fail the workflow — dataset sync is best-effort). Log `[hf-sync] Synced N rows, cursor: TIMESTAMP` to workflow output. Keep the job under 2 minutes for normal operation.
3. Add `HF_TOKEN` to `.env.example` (with a comment: "Hugging Face write token for dataset sync — get at huggingface.co/settings/tokens") and to `docs/INSTALL.md` optional secrets section (after the existing `OPENROUTER_API_KEY` instructions). Add a `make hf-sync` target to the Makefile (if one exists) or document as `./scripts/sync-hf-dataset.sh` in `docs/API.md` under a new "Dataset" section. No unit tests needed (it's a shell script with no business logic); add 1 smoke test: dry-run mode (`HF_DRY_RUN=1`) prints rows to stdout without uploading.
