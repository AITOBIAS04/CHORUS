### 1. Observability Live Trace Panel in Simulation UI

**Type:** Feature
**Effort:** Medium (1–2 days)
**Impact:** The `/api/observability/events/stream` SSE endpoint is live and emits typed events (agent posts, LLM calls, round transitions, cost increments) during simulation runs. But Step3Simulation.vue has no UI for it — users who want to understand *why* a simulation reached a particular outcome must parse raw JSON from the API. A collapsible "Trace" panel that subscribes to the SSE stream and renders a running timeline (event type + agent name + round + token cost + latency) transforms debugging from a post-hoc log read into a real-time experience. Researchers can watch the swarm deliberate. Power users can catch cost spikes before they complete. The observability infrastructure is already built and proven — this is the UI cap on a complete stack.

**How:**
1. Add a `TracePanel.vue` component that opens an `EventSource` to `/api/observability/events/stream?simulation_id={id}` when mounted. Render each incoming event as a row: colored pill for event type (AGENT_POST, LLM_CALL, ROUND_END, COST_UPDATE), agent name (truncated to 20 chars), round number, and cost delta in micro-USD. Cap the rendered list at 200 rows (ring buffer) to prevent DOM growth. Auto-scroll to the latest event.
2. Add a "Trace" toolbar button to Step3Simulation.vue (sibling to "@ Mentions", "↻ Stance Shifts") that toggles the `TracePanel.vue` overlay. Only enable the button during an active simulation run (check existing `simulation.status` from the store); show it as disabled (grayed, tooltip "available during active runs") when the simulation is complete — the post-run LLM call history is still browsable via `GET /api/observability/llm-calls?simulation_id={id}`.
3. Add `GET /api/observability/llm-calls?simulation_id={id}` display to a "Past calls" tab inside the TracePanel for completed simulations — reads from the existing endpoint, renders a sortable table (model, prompt tokens, completion tokens, latency ms, cost USD). Add 2 frontend unit tests: EventSource connection opens on mount; ring buffer caps at 200 rows and drops oldest on overflow.

### 2. Simulation A/B Compare Endpoint

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Researchers and product teams who run the same topic twice — to test different agent counts, platform mixes, or injected events — have no structured way to compare outcomes. They must open two browser tabs and compare by eye. A `GET /api/simulation/compare?a={id1}&b={id2}` endpoint returns a structured diff: final stance delta (bullish_pct A vs B), confidence delta, rounds-to-consensus delta, cost delta, and top-3 agents with the largest belief divergence between the two runs. No new storage — pure computation over the two simulations' existing `signal.json` and `trajectory.json` files. The compare endpoint becomes the foundation for the batch runner's summary output and the research citation format ("simulation A showed 68% bullish vs simulation B's 42% — same topic, Bull vs Bear seed").

**How:**
1. Create `backend/app/services/compare_service.py` (~120 LoC, pure stdlib). Load `signal.json` for both `a` and `b` (publish-gated: both must be published or owned by the requesting session). Compute: `stance_delta = {bullish_delta, bearish_delta, neutral_delta}` (B minus A), `confidence_delta`, `rounds_to_consensus_delta` (using `peak_round.py`'s logic), `cost_delta_usd`. For agent divergence: intersect agent rosters by name, compute per-agent `|final_belief_pct_A - final_belief_pct_B|`, return top-3 sorted descending with both values. Handle non-overlapping rosters gracefully (skip agents absent from one sim). Add 5 unit tests: identical sims produce all-zero deltas; agent missing from one sim is excluded; non-published sim returns 404; cost delta handles null cost fields; top-3 agents sorted by absolute divergence.
2. Add `GET /api/simulation/compare` to `backend/app/api/simulation.py`. Query params: `a` (sim ID), `b` (sim ID). Validate both IDs present; return 400 if missing, 404 if either sim not found/accessible. Response shape: `{"simulation_a": {id, topic, direction, confidence_pct}, "simulation_b": {id, topic, direction, confidence_pct}, "deltas": {stance_delta, confidence_delta, rounds_to_consensus_delta, cost_delta_usd}, "top_divergent_agents": [{name, belief_a, belief_b, delta}×3], "generated_at": ISO8601}`. Cache-Control: `max-age=300`. Add to surfaces_catalog.py (type: `analytics`) and OpenAPI with `CompareResponse` schema. Document in `docs/API.md` under "Comparison." Add 2 integration tests: valid pair returns 200; mismatched IDs return 404.
3. Add a "Compare" button to the public gallery card (appears only when exactly one other simulation is already "pinned for compare" — click first card to pin, click second to open compare modal). In the compare modal, render the two simulation headers side-by-side with a delta column for each metric. Color-code deltas: green for higher confidence or faster consensus, red for lower. Add 1 frontend unit test: delta column renders "+12.4pp" with green class when `confidence_delta > 0`.

### 3. Polymarket Context Lookup

**Type:** Integration
**Effort:** Small (hours)
**Impact:** `polymarket_service.py` exists in the services directory but has no public API route. The service likely queries Polymarket (the largest on-chain prediction market) for markets related to a simulation's topic. Surfacing it as `GET /api/simulation/:id/polymarket` — returning the top 3 matching Polymarket markets (question text, current YES price, liquidity in USD, close date) — positions MiroShark as a calibration tool alongside real-money prediction markets, not a replacement. A user who runs a "Will the Fed cut rates?" simulation sees 72% BULLISH from the swarm and immediately sees Polymarket pricing YES at 68% — validating or challenging the result. This is a differentiation story, a discovery hook, and a distribution lever (Polymarket users cross-posting).

**How:**
1. Extend `polymarket_service.py` to add a `find_related_markets(topic: str, limit: int = 3) -> list[dict]` function. Use the Polymarket public API (`/api/markets?search={keywords}` or the CLOB endpoint — no auth required for read access). Extract 3–5 keywords from the topic string using the same stopword filter already in `topic_trends_service.py` (or a shared utility). Return for each matching market: `{"question": str, "yes_price": float (0–1), "liquidity_usd": float, "close_date": ISO8601|null, "market_url": str}`. If the Polymarket API is unreachable (sandbox network block), write the request to `.pending-polymarket/{sim_id}.json` and return `{"status": "pending"}` — the same prefetch/postprocess pattern used for other auth-required APIs. Add 4 unit tests: keyword extraction excludes stopwords; returns at most `limit` markets; `yes_price` is clamped to [0, 1]; returns empty list (not error) when no markets found.
2. Add `GET /api/simulation/:id/polymarket` to `backend/app/api/simulation.py`. Publish-gated. Cache-Control: `max-age=300` (Polymarket prices update in real time; 5-min staleness is acceptable for an informational sidebar). Response: `{"simulation_id": str, "topic": str, "markets": [...], "fetched_at": ISO8601}`. Return 200 with empty `markets: []` when no matches found (not 404 — absence of matching markets is a valid result). Add to `surfaces_catalog.py` (type: `integrations`) and OpenAPI with `PolymarketContextResponse` schema. Document in `docs/API.md` under "Integrations" with a note on the 5-min cache and the `pending` status shape. Add 2 integration tests: published sim returns 200; response always includes `fetched_at`.
3. Add a "Prediction Markets" section to Step3Simulation.vue's result sidebar (below the confidence badge, above the share link). Show up to 3 market cards: question truncated to 60 chars, a YES price bar (green fill proportional to `yes_price`, label "YES 68%"), and a "View on Polymarket ↗" link. Load lazily on component mount (non-blocking). If `markets` is empty, render nothing. If status is "pending", show a muted "Polymarket data loading…" placeholder. Add 1 frontend unit test: `yes_price=0.68` renders bar at 68% width with label "YES 68%".

### 4. Agent Bio Card API

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Every simulation produces rich per-agent data across `trajectory.json` (belief progression, round-by-round stance) and `actions.jsonl` (post text, mentions, platform). But the only agent-level endpoint is the aggregate export. There is no structured character sheet for a single agent. `GET /api/simulation/:id/agents/:agent_name/bio` returns a bio card: demographic, occupation, initial belief, final belief, total posts, influence score, top-3 mentions (agents they cited most), and a "signature phrase" (most distinctive 5-gram from their posts, computed via simple term frequency against the simulation's full post corpus). Agent bio cards make simulations feel like stories rather than statistics, support the persona/diversity use cases researchers cite in forks, and give journalists and content creators a quotable unit — "Agent 'Maya Chen, ESG analyst' began BULLISH at 74% and ended BEARISH at 31% after citing @TradingDesk_Alex 4 times."

**How:**
1. Create `backend/app/services/agent_bio_service.py` (~180 LoC, pure stdlib). Load `trajectory.json` for the agent's per-round belief series. Load `actions.jsonl` filtering by `agent_name` (case-insensitive). Compute: `initial_belief_pct` (round 1 value), `final_belief_pct` (last round), `stance_arc` (list of stances across rounds — e.g. `["BULLISH", "BULLISH", "NEUTRAL", "BEARISH"]`), `total_posts` (count of actions), `influence_score` (read from trajectory's final round or compute as mentions received / total agents), `top_mentions` (top 3 `@agent_name` patterns from post text, using same extraction logic as `mentions_service.py`), `signature_phrase` (5-gram with highest TF relative to whole-simulation corpus, computed by scanning all `actions.jsonl` files for other agents, excluding stopwords, picking the 5-gram that appears ≥2× in this agent's posts but <10% of total posts across all agents). Demographic fields (`occupation`, `age`, `location`, etc.) read from `agents.json`. Cache to `agent_bios/{agent_name_slug}.json` alongside the simulation data with 1-hour mtime invalidation. Add 5 unit tests: agent not in sim returns empty result; `stance_arc` has one entry per round; stopword-filtered corpus correctly identifies signature phrase; influence_score is non-negative float; top_mentions is at most 3 entries.
2. Add `GET /api/simulation/:id/agents/:agent_name/bio` to `backend/app/api/simulation.py`. Publish-gated. URL-decode `agent_name` (handles spaces in names). Return 404 if agent not in sim. Response: `{"simulation_id": str, "agent_name": str, "demographic": {occupation, age, location, ...}, "initial_belief_pct": float, "final_belief_pct": float, "stance_arc": [str], "total_posts": int, "influence_score": float, "top_mentions": [str], "signature_phrase": str|null, "generated_at": ISO8601}`. Cache-Control: `max-age=3600`. Add to `surfaces_catalog.py` (type: `analytics`) and OpenAPI with `AgentBioResponse` schema. Add to `docs/API.md` under "Agent Analytics." Add 2 integration tests: valid agent returns 200 with all required fields; unknown agent returns 404.
3. Add an agent bio tooltip/popover to Step3Simulation.vue. When a user hovers or taps any agent name (in the agent roster panel, in the mention matrix, or in the stance shifts table), fetch `/api/simulation/:id/agents/:agent_name/bio` and show a small popover: name + occupation as headline, stance arc as colored dot sequence (green=BULLISH, red=BEARISH, gray=NEUTRAL), `initial → final` belief as "74% → 31%", top-3 mentions as `@name` chips. Cache fetched bios in a component-level Map to avoid refetching on hover. Add 1 frontend unit test: hovering agent name triggers fetch and renders popover with `stance_arc` dots.

### 5. Ecosystem Embed Widget

**Type:** Growth
**Effort:** Small (hours)
**Impact:** `ECOSYSTEM.md` lists active ecosystem partners (Sparkleware, Wonderwall, x402, Waybackclaw, DKG, etc.) who build on or integrate MiroShark. But the ecosystem relationship is currently one-directional — partners link to MiroShark; MiroShark doesn't flow live content back. A `GET /api/ecosystem/embed.js` endpoint that returns a self-contained (<2KB) JavaScript snippet lets any ecosystem partner add a live "Latest MiroShark Simulation" card to their site with a single `<script>` tag. The widget reads from the existing activity feed (no new backend state), renders a 280×120px card showing the most recent public simulation (topic truncated to 50 chars, stance split bar, confidence percentage, "Run your own →" link), and auto-refreshes every 5 minutes. Free distribution through every ecosystem integration, every time an ecosystem partner site renders the widget.

**How:**
1. Create `backend/app/api/embed.py` (60 LoC). `GET /api/ecosystem/embed.js`: reads the top entry from `GET /api/activity.json` (already implemented), injects the topic, direction, confidence_pct, and share URL into a minimal self-contained JavaScript string (no external dependencies, no `eval`, no `innerHTML` — builds DOM elements via `document.createElement`). The widget targets a `<div id="miroshark-widget">` (or auto-inserts one if absent). Cache-Control: `max-age=300` (5 min). Set `Content-Type: application/javascript`. The JS itself fetches fresh data from `/api/activity.json?limit=1` on each render cycle (respecting the same 5-min cache on the client via `localStorage` with a `miroshark_widget_cache_ts` key). Add `Access-Control-Allow-Origin: *` header so cross-origin partner sites can load it. Add 3 unit tests: response Content-Type is `application/javascript`; response body contains `document.createElement`; no inline `eval` or `innerHTML` usage (security check by string scan).
2. Add a `GET /api/ecosystem/embed-preview` HTML endpoint (10 LoC) that renders a minimal HTML page loading the `embed.js` snippet — for partners to preview the widget before integrating. This endpoint is for the docs only, not indexed. Cache-Control: `no-cache`. Add this and `embed.js` to `surfaces_catalog.py` (type: `integrations`) and to `docs/API.md` under "Ecosystem Embed" with a 3-line integration guide: "Paste `<script src='https://miroshark.xyz/api/ecosystem/embed.js'></script>` and `<div id='miroshark-widget'></div>` into any page."
3. Send a PR to each of the 3 most active ecosystem repos listed in `ECOSYSTEM.md` adding the widget snippet to their README (one-line `<script>` tag, one-line `<div>` tag, with a screenshot of the rendered card). This distributes the widget immediately at launch without waiting for organic adoption. Add a "Powered by MiroShark" note in 8px text below the widget card (rendered by the JS, not removable — attribution in exchange for the free widget). Add 1 frontend unit test: widget renders in a container with no pre-existing `<div id="miroshark-widget">` by auto-inserting the target element.
