### 1. Simulation Replay Visualizer

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Every MiroShark simulation's per-round belief drift data sits in `trajectory.json` but is currently rendered only as a static chart. A "▶ Replay" button on the Step 3 share page animates the belief evolution round-by-round at a configurable speed (0.5×, 1×, 2×) with a progress scrubber and pause/resume controls. Watching a consensus form in real time — seeing 200 agents shift from 60/40 to 90/10 over 8 rounds — is a qualitatively different experience than reading a static line chart. It makes simulations shareable as screen recordings and dramatically raises the "watchable" factor for non-technical audiences. Distinct from BeliefDriftChart (static chart) and Per-Round Confidence Trajectory (adds confidence line to existing chart) — this is a time-machine player, not a chart overlay.

**How:**
1. Create `frontend/src/components/SimulationReplayPlayer.vue` (~130 LoC). Props: `trajectoryData` (array of per-round objects from `trajectory.json`). Internal state: `currentRound` (0-indexed), `isPlaying` (bool), `speedMultiplier` (0.5 / 1 / 2). Displays: (1) A belief bar at the current round — horizontal stacked bar (violet = bullish, gray = neutral, red = bearish) showing percentages for just that round, updating as the player advances. (2) A progress scrubber (`<input type="range">`) showing current round out of total. (3) Play/Pause button (`▶`/`⏸`), speed selector (`0.5× 1× 2×`), and a round counter ("Round 3 / 8"). Interval logic: `setInterval(() => currentRound++; if (currentRound >= totalRounds) clearInterval(), 1000 / speedMultiplier)`. Uses `onUnmounted` hook to clear the interval. No new backend endpoint needed — the player consumes `trajectory.json` data already fetched in Step 3. Add to `Step3Simulation.vue` as a `⏵ Replay` toolbar button that opens the player in a modal/overlay. Bilingual labels (EN/ZH-CN).

2. Add a `captureReplay()` method that uses the Canvas API to snapshot each round's bar as a frame, then assembles them into a downloadable GIF via a pure-JS GIF encoder (e.g., `gif.js` — add as a frontend dev dependency, ~20KB gzipped). The "⬇ Download GIF" button renders the entire replay to a 400×120px animated GIF the user can post to Discord, Telegram, or Twitter. If gif.js import fails (tree-shaking issue), fall back to a "Download Frames as ZIP" option that exports each round's bar as a PNG. Add the `gif.js` package to `frontend/package.json`. This is the viral surface: a GIF of a MiroShark simulation completing is the cleanest possible social post about the project.

3. Add a `?replay=1` query param to the simulation URL (`/simulation/{id}?replay=1`). When present, auto-open the replay player modal on page load. The "Copy Replay Link" button appends `?replay=1` to the current URL and copies it to clipboard. This creates a shareable URL that immediately begins playback when opened — the strongest possible social hook for a deep-linked simulation share.

### 2. Air-Gap Bundle Generator

**Type:** DX / Community
**Effort:** Medium (1-2 days)
**Impact:** Issue #240 (offline HuggingFace models for air-gapped environments) has been open 84 days with 4 comments — making it MiroShark's most-engaged open issue. Enterprise users (financial institutions, government labs, regulated industries) cannot run MiroShark in environments with outbound internet access because the simulation engine fetches model weights from HuggingFace at runtime. A `make air-gap-bundle` target that pre-downloads all required model artifacts into a portable `data/models/` directory, generates an offline config patch, and packages everything into a single tarball solves this class of deployment entirely. Closes issue #240. Shows responsiveness to community feedback 84 days late — but shipping is always better than not shipping. Distinct from the HuggingFace Live Dataset Sync (Sep 26 — pushes simulation results *to* HuggingFace) — this pulls model weights *from* HuggingFace into a local bundle.

**How:**
1. Create `scripts/build-air-gap-bundle.sh` (~100 LoC). Requires: `HF_TOKEN` (optional; needed only for gated models), `python3`, `pip`. Steps: (1) Parse `backend/app/config.py` (or equivalent) for all model identifiers (search for any `hf_hub_download()`, `from_pretrained()`, or `snapshot_download()` calls using `grep -r "snapshot_download\|hf_hub_download\|from_pretrained" backend/`). (2) For each model ID found, call `python3 -c "from huggingface_hub import snapshot_download; snapshot_download(repo_id='${MODEL_ID}', local_dir='data/models/${MODEL_SLUG}')"`. (3) Generate `data/models/offline_config.json`: maps each original model ID to its local path. (4) Write `scripts/apply-air-gap-config.sh` that patches `backend/app/config.py` (or the equivalent config file) to use `local_dir` paths instead of remote downloads. (5) Package `data/models/` into `air-gap-bundle-$(date +%Y%m%d).tar.gz`. Prints the bundle size and sha256 checksum. Add a `--dry-run` flag that lists models to be downloaded without fetching them.

2. Update `backend/app/` to support an `OFFLINE_MODELS_DIR` environment variable. When set, all model loading code checks `${OFFLINE_MODELS_DIR}/{model_slug}/` before attempting any HuggingFace network call. If the directory exists and is non-empty, use it directly (load from local path). If not set or directory is empty, fall back to normal HuggingFace download. This is a one-line change per model load site: wrap each download call with `if os.environ.get("OFFLINE_MODELS_DIR") and os.path.exists(local_path): return load_from_local(local_path)`. Add `OFFLINE_MODELS_DIR` to `docs/INSTALL.md` as an "Air-Gap Deployment" section with a 3-step guide: (1) On an internet-connected machine: `make air-gap-bundle`; (2) Transfer the tarball to the air-gapped machine; (3) Extract to `data/models/` and set `OFFLINE_MODELS_DIR=./data/models` in `.env`. Add 2 unit tests: when `OFFLINE_MODELS_DIR` is set and local path exists, the model loader returns the local path without a network call; when `OFFLINE_MODELS_DIR` is unset, normal flow proceeds unchanged.

3. Post a comment on issue #240 (via `gh issue comment 240 -R aaronjmars/MiroShark --body "..."`) acknowledging the request and describing the solution: `OFFLINE_MODELS_DIR` env var + `make air-gap-bundle` script + `scripts/apply-air-gap-config.sh`. Attach a minimal usage example. Close the issue with `gh issue close 240 -R aaronjmars/MiroShark --comment "Resolved in PR #..."` after the PR merges. ### 3. JSON-LD Structured Data for Simulations

**Type:** Growth / DX
**Effort:** Small (hours)
**Impact:** Every published simulation result page at `/simulation/{id}` is currently a Vue SPA with no structured metadata. Search engines index the page as opaque JavaScript. Adding `<script type="application/ld+json">` blocks with `schema.org/Dataset` and `schema.org/ClaimReview` markup turns each simulation result into a structured data record that Google, Bing, and AI search engines (Perplexity, You.com, ChatGPT Search) can parse and surface in rich answer boxes. A researcher who searches "crypto AI prediction Sep 2026" or "BTC social simulation result" could see a MiroShark result card directly in the SERP — with topic, direction, confidence, and a link to the full page. After 83 days of social silence with no paid promotion and no organic discovery, this is the highest-leverage zero-effort distribution surface available: every simulation published from this point forward is indexed as structured data. No new backend required — the JSON-LD is injected into the existing Vue SSR/meta tags.

**How:**
1. Create `frontend/src/composables/useSimulationJsonLd.js` (~60 LoC). Accepts a simulation object (from `signal.json`). Returns a JSON-LD object conforming to `schema.org/Dataset` with these fields: `@context: "https://schema.org"`, `@type: "Dataset"`, `name: "${topic} — MiroShark Simulation"`, `description: "Swarm intelligence simulation on '${topic}'. ${agent_count} agents, ${total_rounds} rounds. Result: ${direction} (${confidence_pct}% confidence)."`, `creator: {"@type": "SoftwareApplication", "name": "MiroShark", "url": "https://github.com/aaronjmars/MiroShark"}`, `datePublished: "${published_at}"`, `variableMeasured: [{"@type": "PropertyValue", "name": "direction", "value": "${direction}"}, {"@type": "PropertyValue", "name": "confidence_pct", "value": ${confidence_pct}}, {"@type": "PropertyValue", "name": "agent_count", "value": ${agent_count}}]`, `url: "${current_page_url}"`, `keywords: ["swarm intelligence", "AI simulation", "social prediction", "${topic}"]`. Also emit a secondary `ClaimReview` block for the simulation's directional signal: `@type: "ClaimReview"`, `claimReviewed: "${topic}"`, `reviewRating: {"@type": "Rating", "ratingValue": "${direction}", "bestRating": "BULLISH", "worstRating": "BEARISH"}`, `author: {"@type": "SoftwareApplication", "name": "MiroShark"}`. Inject into `<head>` via `useHead()` (Vueuse) or Vue Router's `meta` hooks in `Step3Simulation.vue`.

2. Add the same JSON-LD to the static embed page (`GET /api/simulation/{id}/embed` if it exists, otherwise add a `GET /api/simulation/{id}/meta.json` endpoint returning just the SEO-relevant fields). Also add standard `<meta>` tags in the Step 3 page: `og:title`, `og:description`, `og:type: "article"`, `twitter:card: "summary"`, `twitter:title`, `twitter:description`. These aren't JSON-LD but complete the discoverability picture. The `og:description` format: `"${total_agents} AI agents simulated '${topic}' over ${rounds} rounds. Consensus: ${direction} (${confidence}% confidence). Powered by MiroShark."`. No unit tests needed — JSON-LD is declarative markup. Add a documentation note in `docs/FEATURES.md` under a new "SEO / Structured Data" section.

3. Submit the MiroShark simulation index page to Google Search Console as a sitemap source. Create `backend/app/api/sitemap.py` (~50 LoC): `GET /sitemap.xml` returns an XML sitemap of all published simulation URLs (`/simulation/{id}`) sorted by `published_at` descending, `<lastmod>` set to `published_at`, `<changefreq>weekly`, `<priority>0.8`. Limit to 5,000 most recent (XML sitemap spec cap is 50,000 but 5,000 is sufficient to start). Add to `surfaces_catalog.py`. Add `<loc>{base_url}/sitemap.xml</loc>` to `robots.txt` (create if absent). Register at `GET /sitemap.xml`. Add 2 unit tests: endpoint returns valid XML with `<?xml version="1.0"...>` header; each URL in the sitemap passes a basic URL validation.

### 5. Simulation Difficulty Score

**Type:** Feature / Research
**Effort:** Small (hours)
**Impact:** MiroShark's `signal.json` currently answers "what did the swarm conclude?" but not "how hard was it to conclude?" A `difficulty_score` (0.0–1.0) added to `signal.json` and `GET /api/simulation/{id}/signal` captures how contested a simulation was: 0.0 = immediate runaway consensus (90%+ in round 1), 1.0 = tight deadlock with many stance flips that barely resolved by the final round. Computed from three normalized sub-scores: (1) rounds taken as a fraction of max rounds; (2) max per-round divergence (the spread between bullish and bearish at the most contested moment); (3) stance flip count as a fraction of agent_count. Researchers use it to filter for "interesting" simulations — a difficulty of 0.85 means the swarm was genuinely split and the consensus emerged under pressure. Complements the Simulation Comparison API (Sep 26 — `trajectory_overlap`) by providing a single-number quality signal per simulation without needing a second simulation to compare against. For the paper citation hyperstition (Sep 30, 2 days): "simulation difficulty score of 0.72" is the kind of quantitative methodological finding that appears in methodology sections.

**How:**
1. Create `backend/app/services/difficulty_service.py` (~80 LoC, pure stdlib). Function `compute_difficulty(signal_data: dict, trajectory_data: list) -> float`. Algorithm: (1) **Round fraction** (`r_frac`): `total_rounds / max_rounds` where `max_rounds` is read from config (default 10). Clamp to [0, 1]. Higher rounds = harder deliberation. (2) **Consensus tightness** (`c_tight`): take the final-round belief split from `trajectory_data[-1]`; `c_tight = 1.0 - abs(bullish_pct - bearish_pct) / 100.0`. Clamp to [0, 1]. A 90/10 split gives 0.2 (easy); a 52/48 split gives 0.96 (hard). (3) **Stance volatility** (`s_vol`): `stance_flip_count / agent_count` where `stance_flip_count` is the total number of per-agent direction changes across all rounds (scan `trajectory_data` per-agent series; if not available, set `s_vol = 0.0`). Clamp to [0, 1]. (4) Final score: `difficulty = round(0.35 * r_frac + 0.45 * c_tight + 0.20 * s_vol, 3)`. Weights: tightness is the dominant signal (0.45) because a runaway consensus is unambiguously "easy" regardless of round count. Add 5 unit tests: immediate consensus (all bullish round 1) → score < 0.2; near-deadlock final round (52/48) → score > 0.8; full round count with neutral agents → score in [0.3, 0.7]; score is always in [0, 1]; tie score computation via known input.

2. Inject `difficulty_score` into `signal.json` at simulation completion time. Edit the simulation completion handler: after writing `signal.json`, re-read it, call `compute_difficulty(signal_data, trajectory_data)`, and append `"difficulty_score": result` to the JSON. For existing completed simulations (backfill): add a `scripts/backfill-difficulty.py` (~40 LoC) that scans all simulation directories with a `signal.json` + `trajectory.json`, computes difficulty for each, and writes it back. Idempotent: skips simulations that already have `difficulty_score`. Add `difficulty_score` to the `GET /api/simulation/{id}/signal` OpenAPI response schema and `docs/API.md`. Add `difficulty_score` to `surfaces_catalog.py` as a new field (not a new endpoint — it augments existing surfaces).

3. Surface `difficulty_score` in the Step 3 UI. Add a small `difficulty chip` next to the existing direction badge: a horizontal pill labeled `Difficulty: {0.00–1.00}` with a color gradient (green at 0.0 → yellow at 0.5 → red at 1.0, using the same violet/gray/red palette mapped to a green→yellow→red scale for this specific metric). Tooltip on hover: "How contested this simulation was. 0.0 = immediate consensus. 1.0 = near-deadlock." Add `difficulty_score` to the EmbedDialog metadata row. Add difficulty data to the Simulation Comparison API response (Sep 26 — `GET /api/compare`) by including `difficulty_score` per simulation in the `simulations` array; the comparison then shows at a glance whether two simulations had similar or very different difficulty profiles. No new unit tests needed for the UI change — chip is purely presentational. Log to memory: "Simulation Difficulty Score created 2026-09-28. difficulty_score (0.0–1.0) appended to signal.json at completion: 0.35*round_fraction + 0.45*consensus_tightness + 0.20*stance_volatility. backfill-difficulty.py for existing sims. UI: difficulty chip (green→yellow→red). Comparison API: includes difficulty_score per sim. Paper hook: quantitative difficulty metric for methodology sections."
