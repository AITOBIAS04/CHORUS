### 1. Simulation ZIP Export

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Researchers using MiroShark for longitudinal analysis — confirmed by the Towards AI coverage, the Crucible Sim academic fork (wshuyi), and the OrcaRouter integration pattern — currently download simulation artifacts one file at a time: `signal.json`, `trajectory.json`, `reproduce.json`, `signed-result.json`, and per-platform `actions.jsonl` files. `GET /api/simulation/{id}/export.zip` returns all of them in a single archive. This is the standard "take my work with me" primitive for any data-producing tool. One endpoint, pure stdlib (`zipfile`, no external dependencies), ~60 LoC. Makes MiroShark archivable, citable, and shareable in a single action. The ZIP serves as the natural attachment format for research: a researcher can attach `miroshark-sim-12345.zip` to a paper submission, a Slack message, or a GitHub issue comment and the recipient gets the full reproducible record. Downstream: the ZIP is also the natural input format for a future batch-analysis tool and for the "export → re-import → continue simulation" feature arc.

**How:**
1. Create `backend/app/api/export.py` (~60 LoC, pure stdlib). `GET /api/simulation/{id}/export.zip`. Publish-gated: check `signal.json` exists and simulation is published; return 404 `{"error": "simulation_not_found"}` if not. Build the archive using `zipfile.ZipFile` in memory (no temp file on disk): add `signal.json`, `trajectory.json`, `reproduce.json`, `signed-result.json` from the simulation directory if each exists. Scan `{simulation_dir}/platforms/` (or wherever per-platform `actions.jsonl` files live) and add each to `platforms/{platform_name}/actions.jsonl` within the ZIP. Add a top-level `README.md` inside the ZIP (~10 lines): simulation ID, topic (from signal.json), created_at, export timestamp, file manifest. Set `Content-Type: application/zip` and `Content-Disposition: attachment; filename="miroshark-{id}.zip"`. Set `Cache-Control: public, max-age=3600` (result is immutable for published sims). Register at `GET /api/simulation/{id}/export.zip`. Add to `surfaces_catalog.py`. Update `docs/API.md` with the endpoint reference and list of included files.

2. Add a "Download all" button to the simulation share page (`Step3Simulation.vue`): a single `⬇ Download ZIP` button in the toolbar next to the existing `signal.json` / `reproduce.json` links. On click: `window.location = /api/simulation/${id}/export.zip`. Also expose the download URL in the embed dialog's "Export" section alongside the individual file links. Update `docs/FEATURES.md` to note the bulk export capability.

3. Add 5 unit tests: published simulation returns 200 with `Content-Type: application/zip`; unpublished or missing simulation returns 404; the returned ZIP contains at minimum `signal.json` and a `README.md`; `Content-Disposition` header contains `miroshark-{id}.zip`; response is a valid ZIP (readable by `zipfile.ZipFile(io.BytesIO(response.data))`).

### 2. Open Graph Simulation Share Cards

**Type:** Growth / DX
**Effort:** Small (hours)
**Impact:** Every MiroShark simulation has a public share URL (`/sim/{id}`). When that URL is pasted on X (Twitter), Discord, LinkedIn, or any OG-aware platform, the link preview currently shows generic MiroShark branding — the same title, description, and image regardless of topic. Per-simulation Open Graph metadata — `og:title` = the simulation topic, `og:description` = direction + confidence_pct + verdict, `og:image` = a generated SVG result card — transforms every shared link into a self-contained advertisement. The link preview becomes the headline: "US Tech Layoffs Q3 2026 → Bearish (87% confidence)." This is the primary viral amplification mechanism for any web product: content sharing drives discovery. In a 42-day social silence period where zero organic mentions are landing, every existing simulation share link is a missed impression. With OG cards live, each of the project's active simulation users automatically carries MiroShark branding every time they share a result. The SVG result card can be generated pure-server-side (Python `xml.etree.ElementTree` or string template, no image library required). No external CDN or image service needed.

**How:**
1. Create `backend/app/api/og_card.py` (~80 LoC, pure stdlib). `GET /api/simulation/{id}/og-card.svg` — generates and returns a simulation result card as an SVG. Publish-gated: reads `signal.json`, returns 404 if not found. Card layout (600×315px, standard OG image dimensions): dark background (`#0d0d0d`), MiroShark logotype in top-left (text, no image dependency), simulation topic in large bold white text (truncated to 60 chars with ellipsis), direction badge (BULLISH/NEUTRAL/BEARISH) with color coding (green/#22c55e, gray/#6b7280, red/#ef4444) and confidence_pct, a dividing line, three stance percentage bars (bullish/neutral/bearish) proportionally sized, and a bottom footer: `miroshark.xyz · $1 per simulation`. Generate as a string-templated SVG. `Content-Type: image/svg+xml`. `Cache-Control: public, max-age=86400`. Register at `GET /api/simulation/{id}/og-card.svg`. Add to `surfaces_catalog.py`.

2. Inject per-simulation OG meta tags into the simulation share page server-side response. In the Flask route that serves the `/sim/{id}` page (likely returning the index.html SPA shell): if the simulation is published, read `signal.json` and template OG tags into the HTML `<head>` before returning: `<meta property="og:title" content="{topic} — MiroShark Simulation">`, `<meta property="og:description" content="Direction: {direction} · {confidence_pct}% confidence · Simulated by {agent_count} agents across {round_count} rounds.">`, `<meta property="og:image" content="https://miroshark.xyz/api/simulation/{id}/og-card.svg">`, `<meta property="og:image:width" content="600">`, `<meta property="og:image:height" content="315">`, `<meta name="twitter:card" content="summary_large_image">`, `<meta name="twitter:image" content="https://miroshark.xyz/api/simulation/{id}/og-card.svg">`. If the simulation is unpublished, fall back to existing generic tags. This requires the Flask route to do a lightweight `signal.json` read before returning the SPA shell — acceptable overhead since published simulations have immutable results.

3. Add 3 unit tests: `GET /api/simulation/{id}/og-card.svg` returns 200 with `Content-Type: image/svg+xml` for a published simulation; unpublished simulation returns 404; the SVG response body contains the simulation topic string. Log to memory: "Open Graph Simulation Share Cards created 2026-08-18. `GET /api/simulation/{id}/og-card.svg` — 600×315 SVG with topic, direction, confidence, stance bars, MiroShark branding. OG meta tags injected server-side into `/sim/{id}` HTML head. Per-simulation `og:image` on every share link. Twitter card: summary_large_image. Enables viral impression every time a simulation is shared on OG-aware platforms."

### 3. Agent Response Transcript API

**Type:** Feature
**Effort:** Small (hours)
**Impact:** MiroShark's simulation data exists as per-platform `actions.jsonl` files — one file per platform, raw lines. There is no unified, chronological view of what every agent said, in order. `GET /api/simulation/{id}/transcript` returns the full simulation as a structured array: `[{round, agent_id, agent_name, platform, action_type, content, stance, timestamp}]` sorted by (round ASC, platform ASC). This is the "story" of the simulation — the complete chronological record of agent interactions. Use cases: reading the simulation narrative programmatically, building downstream analysis (word frequency by stance, most-quoted content, sentiment over time), displaying a chat-style transcript UI, academic citation ("in round 3, Agent-047 posted: '...'"), and export to external analysis tools (Pandas, R). Currently none of these are possible without manually parsing and merging multiple `actions.jsonl` files. Stateless: reads existing files, computes, returns. No new data stored.

**How:**
1. Create `backend/app/api/transcript.py` (~100 LoC, pure stdlib). `GET /api/simulation/{id}/transcript`. Publish-gated. Reads all `actions.jsonl` files from `{simulation_dir}/platforms/`. For each line in each file: parse JSON, extract `round`, `agent_id`, `agent_name` (or equivalent fields depending on the actual actions.jsonl schema — read an example file to confirm field names), `platform` (inferred from the file path), `action_type` (post/reply/trade/etc.), `content`, `stance`, `timestamp`. Build a merged list, sort by `(round ASC, timestamp ASC)` (or by `round ASC, platform ASC` if timestamps are absent within a round). Return: `{"simulation_id": id, "agent_count": N, "round_count": N, "total_actions": N, "transcript": [...]}`. Pagination support: optional `?page=N&limit=M` (default limit: 100, max: 500) — add `"page": N, "total_pages": N` to the response envelope. `Cache-Control: public, max-age=3600`. Register at `GET /api/simulation/{id}/transcript`. Add to `surfaces_catalog.py`. Update `docs/API.md` with field definitions and pagination notes.

2. Add a "Transcript" view to the simulation share page (`Step3Simulation.vue`): a "Transcript" toolbar button that opens a scrollable panel showing agent actions in chronological order. Each row: round badge, platform icon (X/Reddit/market), agent name, action type chip, and content excerpt (truncated to 120 chars, expandable on click). Stance chip with direction color coding. The panel is paginated (load more button, 100 rows at a time). Filter controls at the top: by platform, by round, by stance, by action type. This makes the simulation's internal story accessible in the UI without requiring API access.

3. Add 5 unit tests: published simulation returns 200 with `transcript` array; unpublished returns 404; `total_actions` equals the count of items in `transcript` (without pagination); all items contain `round`, `platform`, `action_type`, and `content` keys; pagination with `?page=1&limit=10` returns at most 10 items and includes `total_pages`. Log to memory: "Agent Response Transcript API created 2026-08-18. `GET /api/simulation/{id}/transcript` returns sorted chronological array of all agent actions across platforms. Fields: round, agent_id, agent_name, platform, action_type, content, stance, timestamp. Pagination: ?page=N&limit=M (max 500). UI: Transcript panel in Step3 with platform/round/stance filters."

### 5. Offline HuggingFace Model Bundle (closes issue #240)

**Type:** DX improvement
**Effort:** Medium (1-2 days)
**Impact:** Issue #240 ("offline huggingface-models for air-gapped environments") has been open for 43 days with 4 comments — the only open issue, and the only request that shows community engagement. Air-gapped environments include enterprise security sandboxes, government networks, academic HPC clusters, and development setups without outbound internet. MiroShark's agent grounding pipeline uses HuggingFace models that are downloaded at runtime — this silently fails in air-gapped environments with no clear error or workaround. The fix has three parts: (1) a pre-download script (`scripts/download-hf-models.sh`) that runs once with internet access and saves models to a local cache directory, (2) a `docker-compose.offline.yml` that mounts the cache and sets `TRANSFORMERS_OFFLINE=1` and `HF_DATASETS_OFFLINE=1` environment variables, (3) a `docs/OFFLINE.md` guide documenting the full setup. This closes the oldest open issue, adds enterprise/HPC viability, and demonstrates that MiroShark's maintainers are responsive — a signal that matters to new stars evaluating whether to contribute. Closing the only open issue resets the issue tracker to zero.

**How:**
1. Create `scripts/download-hf-models.sh` (~50 lines). Reads the list of HuggingFace models used by MiroShark from a config file or by grepping the backend source for `from_pretrained(` calls (likely `sentence-transformers/all-MiniLM-L6-v2` or equivalent for embedding and any reranker models). Downloads each to `./hf-cache/` using either `huggingface-cli download {model}` (if `huggingface_hub` CLI is available) or a Python one-liner `python -c "from sentence_transformers import SentenceTransformer; SentenceTransformer('{model}', cache_folder='./hf-cache')"`. Script header: usage (`bash scripts/download-hf-models.sh`), expected disk usage per model, total (~2-4 GB typical for sentence-transformer models), `set -e` for immediate failure on any download error. Output: `hf-cache/models--{model-name}/` directories with model weights.

2. Create `docker-compose.offline.yml` (~30 lines). Extends the base `docker-compose.yml` (or `docker-compose.override.yml` pattern). Key additions: `volumes: - ./hf-cache:/root/.cache/huggingface` (mounts the pre-downloaded cache into the container's HF cache location), `environment: - TRANSFORMERS_OFFLINE=1 - HF_DATASETS_OFFLINE=1 - HF_HUB_OFFLINE=1` (HuggingFace's three offline-mode environment variables — all three are required; setting only one causes partial offline failures). Comment at the top of the file: "Offline mode — run `bash scripts/download-hf-models.sh` once with internet, then `docker compose -f docker-compose.yml -f docker-compose.offline.yml up` in air-gapped environments." Add `./hf-cache/` to `.gitignore` (model weights must not be committed). Also add a bare-metal offline variant for non-Docker users: add `TRANSFORMERS_OFFLINE=1 HF_DATASETS_OFFLINE=1 HF_HUB_OFFLINE=1` to `.env.example` with a comment "# Uncomment for air-gapped / offline mode (run scripts/download-hf-models.sh first)."

3. Create `docs/OFFLINE.md` (~100 lines). Sections: **Overview** (what "offline mode" means — HF models downloaded once, then served from cache), **Prerequisites** (Docker, or Python 3.11+ with huggingface_hub installed; ~2-4 GB disk for model cache), **Step-by-step: Docker offline setup** (3 commands: clone, download models, run offline compose), **Step-by-step: bare-metal offline setup** (set env vars in `.env`, download models, start normally), **Troubleshooting** (symptoms of a missing model — error messages to look for — and how to re-run the download script), **Supported environments** (Docker, bare-metal Linux/Mac, HPC clusters with Singularity via `export SINGULARITY_CACHEDIR=./hf-cache`). Link from `README.md` pill buttons: add an "Offline / Air-gapped →" link in the docs pill row. Close issue #240 with a comment linking to the PR and `docs/OFFLINE.md`. Log to memory: "Offline HuggingFace Bundle created 2026-08-18. Closes issue #240 (43 days open, 4 comments). `scripts/download-hf-models.sh` — pre-downloads all HF models to `./hf-cache/`. `docker-compose.offline.yml` — mounts cache, sets TRANSFORMERS_OFFLINE=1 + HF_DATASETS_OFFLINE=1 + HF_HUB_OFFLINE=1. `docs/OFFLINE.md` — full setup guide for Docker, bare-metal, and Singularity (HPC). `./hf-cache/` added to .gitignore."

## Selection Rationale

Five ideas targeting utility gaps, social amplification, and the only open GitHub issue.

- **Simulation ZIP Export (#1)** — Research utility primitive. Towards AI coverage and Crucible Sim fork confirm longitudinal research use. Currently requires downloading 5+ files separately. ZIP export at one URL makes simulation results archivable, citable, and attachable in one action. Pure stdlib, ~60 LoC.

- **Open Graph Share Cards (#2)** — Primary viral amplifier in a 42-day social silence. Every shared simulation link becomes a self-contained impression showing topic + direction + confidence. No external services needed — pure-Python SVG + server-side OG meta injection. The fastest path to organic discovery when no human is posting.

The transcript endpoint is the foundation for downstream analysis tools, chat-style UI views, and academic citation of specific agent statements. One stateless endpoint reading existing data.

Directly serves the Towards AI coverage audience who want to try MiroShark but don't know what to simulate. `GET /api/topics/templates` + Step 1 UI integration.

- **Offline HuggingFace Bundle (#5)** — Closes the only open issue (#240, 43 days stale, 4 comments). Enterprise/HPC environments are blocked by the current runtime-download behavior. Pre-download script + offline Docker Compose + docs close the issue formally and add air-gapped viability. Closing the only open issue also signals maintainer responsiveness to new contributors evaluating the project.
