### 1. HuggingFace Live Dataset Sync

**Type:** Integration / Growth
**Effort:** Small (hours)
**Impact:** PR #311 linked the HuggingFace dataset from the README — but the dataset is currently a static snapshot updated manually. A `scripts/sync-huggingface.sh` + `POST /api/simulation/{id}/publish-to-hf` endpoint that automatically appends newly published simulations to `MiroShark/social-prediction-market-sim` as new dataset rows turns a dormant artifact into a live data stream. Nvidia's acquisition of HuggingFace (Aug 2026) raised the platform's profile in AI/ML research pipelines — having a live, auto-growing dataset means MiroShark's simulation archive is discoverable in the HuggingFace dataset hub, model cards, and dataset viewers without any additional promotion. Researchers querying HuggingFace for social simulation training data will find MiroShark's results incrementally as they're published. This is distinct from Offline HuggingFace Bundle (Aug 18 — downloading models into the local env) and from the ZIP Export (Aug 18 — raw archive download); this pushes simulation results *to* HuggingFace as structured rows, not pulls from it.

**How:**
1. Create `scripts/sync-huggingface.sh` (~80 LoC). Requires `HF_TOKEN` env var (HuggingFace write token). Depends only on the `huggingface_hub` Python package (add as optional dev dependency). Algorithm: (1) Scan all simulation directories for completed `signal.json` + `trajectory.json`. (2) For each, build a flat row dict: `{"simulation_id": str, "topic": str, "direction": "BULLISH"|"BEARISH"|"NEUTRAL", "confidence_pct": float, "total_rounds": int, "agent_count": int, "platforms": list[str], "bullish_final": float, "bearish_final": float, "neutral_final": float, "created_at": ISO8601, "published_at": ISO8601}`. (3) Compare against already-uploaded IDs (read `uploaded_ids.txt` from a scratch file, default empty). (4) Upload new rows via `dataset.push_to_hub("MiroShark/social-prediction-market-sim", split="train", token=HF_TOKEN)` using `datasets.Dataset.from_list()`. (5) Append new IDs to `uploaded_ids.txt`. On first run: uploads all published simulations. On subsequent runs: uploads only delta. Add a `.huggingface-sync/` directory to `.gitignore`. Add a `make sync-hf` Makefile target. Log to memory: "HuggingFace Live Dataset Sync created 2026-09-26. `scripts/sync-huggingface.sh` — delta-sync published simulations to MiroShark/social-prediction-market-sim. Columns: simulation_id, topic, direction, confidence_pct, total_rounds, agent_count, platforms, bullish_final, bearish_final, neutral_final, created_at, published_at. `uploaded_ids.txt` dedup. `make sync-hf`. Distinct from Offline HuggingFace Bundle (downloads models) and ZIP Export (local archive)."

2. Create `backend/app/api/hf_sync.py` (~60 LoC). `POST /api/simulation/{id}/publish-to-hf` — operator-authenticated (same `X-API-Key` guard as `/resolve`). Triggers a single-simulation sync: reads the simulation's `signal.json` + `trajectory.json`, builds the row dict, calls `datasets.Dataset.from_list([row]).push_to_hub(...)`. Returns `{"status": "synced", "simulation_id": str, "hf_dataset": "MiroShark/social-prediction-market-sim", "row": {...}}`. If `HF_TOKEN` not set in env, returns `503 {"error": "HF_TOKEN not configured"}`. Register at `POST /api/simulation/{id}/publish-to-hf`. Add to `surfaces_catalog.py`. Update `docs/API.md` with a "Dataset" section. Add 3 unit tests: successful push returns 200 with `status == "synced"`; missing `HF_TOKEN` returns 503; unpublished simulation returns 404.

3. Add a "Dataset" badge row to the Step 3 simulation share page (`Step3Simulation.vue`). When a simulation has been synced to HuggingFace (determined by checking if `simulation_id` is in the `/api/simulation/{id}/signal` response's extended metadata after sync), show a `🤗 In HF Dataset` chip alongside the existing share chips. On click: open `https://huggingface.co/datasets/MiroShark/social-prediction-market-sim` in a new tab. If not synced: no chip. No additional unit tests needed — chip logic is purely frontend conditional rendering.

### 2. Webhook Subscription System

**Type:** Integration / Feature
**Effort:** Medium (1-2 days)
**Impact:** MiroShark simulations take 5–10 minutes to complete. Operators currently poll `GET /api/simulation/{id}/signal` until `status == "complete"` — there is no push mechanism. A webhook system (`POST /api/webhooks`, `GET /api/webhooks`, `DELETE /api/webhooks/{id}`) lets operators register a callback URL that receives a signed POST when any simulation's status changes to `complete`. The payload is the full `signal.json` body plus HMAC-SHA256 signature (reusing the signing infrastructure from Signed Result JSON, PR #152). Unlocks CI/CD integration patterns: a product team can register a webhook to route MiroShark signal completions into Slack, Zapier, n8n, or a custom alert pipeline without long-polling. A startup that runs a daily "market sentiment" simulation can be notified the moment it completes, rather than building a cron + poll loop. For Hacktoberfest contributors: webhook integration bridges are a well-understood category of "good first issue" (connect MiroShark completion events to Discord, PagerDuty, Datadog, etc.).

**How:**
1. Create `backend/app/api/webhooks.py` (~120 LoC, pure stdlib). Three endpoints: **`POST /api/webhooks`** — operator-authenticated. Accepts `{"url": str, "events": ["simulation.complete"], "secret": str (optional, 16+ chars), "description": str (optional, max 100 chars)}`. Validates URL (must start with `https://`). Assigns a `webhook_id` (UUID4). Stores in `data/webhooks.json` (append; create if absent): `{"webhook_id": str, "url": str, "events": list[str], "secret": str|null, "description": str, "created_at": ISO8601, "active": true}`. Returns 201 with the webhook object (secret masked in response: `"secret": "***"`). Max 10 webhooks per operator (returns 429 if exceeded). **`GET /api/webhooks`** — operator-authenticated. Returns all webhooks as `{"webhooks": [...], "total": int}` with secrets masked. **`DELETE /api/webhooks/{webhook_id}`** — operator-authenticated. Sets `"active": false` in `data/webhooks.json`. Returns 204. Register all 3 endpoints. Create `backend/app/services/webhook_dispatcher.py` (~60 LoC): `dispatch_webhooks(simulation_id: str, event: str, payload: dict)` — reads `data/webhooks.json`, filters by `active: true` and matching event, POSTs `payload` to each URL within a 5-second timeout (uses `urllib.request.urlopen`), signs with HMAC-SHA256 when `secret` is set (header `X-MiroShark-Signature: sha256={hex}`). Failures log a warning and continue (do not block simulation completion). Call `dispatch_webhooks(simulation_id, "simulation.complete", signal_json_payload)` at the end of the simulation completion handler. Add to `surfaces_catalog.py`. Update `docs/API.md` with a "Webhooks" section including the full payload schema and signature verification example.

2. Add a "Webhooks" tab to the operator settings panel (if one exists) or as a standalone `WebhooksPanel.vue` component accessible from the simulation dashboard. UI elements: (1) A "Register Webhook" form with `URL` (input), `Description` (optional text input), `Secret` (optional password input), `Events` (checkbox: `simulation.complete` pre-checked). (2) A list of registered webhooks showing URL, description, and a "Delete" button. (3) A one-line delivery log per webhook (last delivery timestamp + status code, if available). Bilingual labels (EN/ZH-CN). Add 5 unit tests: `POST /api/webhooks` with valid URL returns 201 with masked secret; `POST` with non-https URL returns 400; `GET /api/webhooks` returns all active webhooks; `DELETE /api/webhooks/{id}` sets `active: false`; `POST /api/webhooks` beyond 10 limit returns 429. Log to memory: "Webhook Subscription System created 2026-09-26. POST/GET/DELETE /api/webhooks — stores in data/webhooks.json; HMAC-SHA256 signed payloads (X-MiroShark-Signature); dispatch_webhooks() called on simulation.complete; 5s timeout, non-blocking failures; max 10 per operator; https:// required; WebhooksPanel.vue. Hacktoberfest hook: 'connect MiroShark webhooks to X' is a well-defined good-first-issue."

3. Create `docs/WEBHOOKS.md` with a full integration reference: payload schema (full `signal.json` fields), signature verification sample code (Python + Node.js), example receivers (a minimal FastAPI receiver, a minimal Express receiver), and a list of 5 suggested Hacktoberfest integration targets: Discord bot, Slack app, PagerDuty alert, Zapier Zap, and n8n workflow. Each suggested target includes a one-paragraph description and the specific MiroShark webhook fields to use. This document is the Hacktoberfest contribution surface — contributors pick a target and implement the receiver.

### 3. Simulation Comparison API

**Type:** Feature / Research
**Effort:** Small (hours)
**Impact:** MiroShark's analytical stack answers every question *about a single simulation*. The one unanswered class of question is: *how did the swarm react differently to two related topics?* `GET /api/compare?ids=id1,id2,id3` (up to 5 IDs) returns a diff-style side-by-side analytics payload: direction per simulation, confidence delta, trajectory overlap score (correlation between per-round bullish_pct series), divergence score (max per-round absolute difference), consensus timing (which simulation locked direction soonest), and a plain-English comparison summary. Use cases: "ETH $10K by March vs ETH $10K by June" (same event, different timeframes); "Fed rate cut 50bps vs 25bps" (same category, different magnitude); "Trump tariffs Oct vs Trump tariffs Jan" (same actor, different timing). This is distinct from the Leaderboard (Sep 22 — ranked archive, one metric at a time) and from Taxonomy Browser (domain classification). Comparison is the natural next query after a researcher has run multiple related simulations — it gives them a structured diff without having to manually read two signal.json files side by side. For the paper citation hyperstition (Sep 30, 4 days away): a researcher who can say "MiroShark's comparative analysis shows X% more confidence in the 50bps scenario vs. 25bps" is drawing on a quantitative tool worth naming in a methodology section.

**How:**
1. Create `backend/app/api/compare.py` (~110 LoC, pure stdlib). `GET /api/compare?ids=id1,id2,...`. Public, no auth. Accepts 2–5 comma-separated simulation IDs as a query param. Returns 400 if fewer than 2 or more than 5. For each ID: reads `signal.json` (direction, confidence_pct, topic, created_at) and `trajectory.json` (per-round bullish_pct series). If any ID is missing or not published, returns 404 for that ID with a partial results flag. Computes: (1) **Trajectory overlap score** (0–100): Pearson correlation between per-round bullish_pct series, computed only for rounds where both simulations have data; truncates to the shorter series; maps correlation [−1, +1] → overlap [0, 100] via `int((r + 1) / 2 * 100)`. If either simulation has fewer than 2 rounds, returns `null`. (2) **Max divergence**: `max(|sim_a.bullish_pct[r] - sim_b.bullish_pct[r]|)` across all common rounds. (3) **Direction agreement**: `true` if all simulations have the same `direction`, `false` otherwise. (4) **Confidence spread**: `max(confidence_pct) - min(confidence_pct)` across all simulations. (5) **Earliest consensus** — the simulation that first reached ≥ 60% majority (same algorithm as Leaderboard `fastest_consensus` dimension); returns `simulation_id` + `consensus_round`, or `null` if none reached 60%. (6) **Comparison note** — plain-English one-liner: if `direction_agreement == true` → "All simulations reached {direction} consensus; confidence ranged {min}–{max}%."; if `direction_agreement == false` → "Simulations diverged: {id_a} predicted {dir_a} ({conf_a}%) while {id_b} predicted {dir_b} ({conf_b}%).". Response: `{"simulations": [{"simulation_id": str, "topic": str, "direction": str, "confidence_pct": float, "created_at": ISO8601}], "comparison": {"trajectory_overlap": int|null, "max_divergence": float, "direction_agreement": bool, "confidence_spread": float, "earliest_consensus": {"simulation_id": str, "consensus_round": int}|null, "comparison_note": str}, "generated_at": ISO8601}`. `Cache-Control: public, max-age=600`. Register at `GET /api/compare`. Add to `surfaces_catalog.py`. Update `docs/API.md` with a "Comparison" section.

2. Add a "Compare" button to the Step 3 simulation share page (`Step3Simulation.vue`). Behavior: clicking "⇌ Compare" opens a modal with a search box — user types a second (or third) topic name, the modal shows matching published simulations from `GET /api/simulation/search`, and the user selects 1–4 to compare with the current simulation. On confirm: navigates to `/compare?ids={current},{selected1},{selected2},...`. Create `frontend/src/views/CompareView.vue` (~160 LoC). Layout: (1) A header row showing all simulation topics. (2) A direction comparison row: BULLISH/BEARISH/NEUTRAL chips per simulation, color-coded. (3) A confidence comparison bar chart (horizontal bars, one per simulation, violet gradient). (4) A multi-line trajectory chart overlaying all simulations' per-round bullish_pct series (each line a different color from the existing palette). (5) A `comparison_note` block in muted italic. (6) A "⬇ Download comparison.json" button (downloads the raw API response). Bilingual labels (EN/ZH-CN). Add `/compare` to `frontend/src/router/index.js`. Add 4 unit tests: `GET /api/compare?ids=a,b` with 2 valid published IDs returns 200 with `comparison` object; `GET /api/compare?ids=a` (single ID) returns 400; `direction_agreement` is `true` when all directions match; `trajectory_overlap` is between 0 and 100 when both simulations have ≥ 2 rounds. Log to memory: "Simulation Comparison API created 2026-09-26. GET /api/compare?ids=id1,id2,... (2-5 IDs). Computes: trajectory_overlap (Pearson r mapped 0-100), max_divergence (per-round abs diff), direction_agreement (bool), confidence_spread (max-min confidence), earliest_consensus (first sim to reach 60%). comparison_note: plain-English diff. /compare route in frontend: direction chips + confidence bars + overlaid trajectory chart + download JSON. Paper citation hook: quantitative scenario comparison."

3. Add a shared comparison URL to the "Share" controls: a `copy comparison link` button appears on the `CompareView` alongside the existing per-simulation share controls. The URL format is `/compare?ids={all_current_ids}` — it's fully shareable and re-hydrates the full comparison on load. No additional unit tests needed for the share link — it's a static URL construction from existing query params.

### 5. Simulation Agent Demographics

**Type:** Feature / Research
**Effort:** Small (hours)
**Impact:** Every MiroShark simulation runs with 50–200 grounded agents — but currently there's no way to know the composition of a specific run's agent population. `GET /api/simulation/{id}/demographics` reads the per-simulation `agents.json` and returns a structured breakdown: profession distribution (top 5 with percentages), platform distribution (Twitter/Reddit/Polymarket), age bracket distribution (18–25 / 26–35 / 36–50 / 51+), and simulated country/region distribution (top 5 with percentages). This is distinct from the Agent Archetype Atlas (Jun 6 — aggregate cross-simulation profession analytics) — the Atlas answers "across all MiroShark sims, which professions are most common?"; Demographics answers "in *this specific simulation*, who were the agents and how were they distributed?" A researcher who ran "crypto-skeptic regulation" can say "this simulation's agent pool was 38% finance professionals, 29% tech workers, 22% policy researchers — skewed toward domain experts, which may explain the {direction} consensus." That methodological note is what makes a simulation result citable.

**How:**
1. Create `backend/app/api/demographics.py` (~100 LoC, pure stdlib). `GET /api/simulation/{id}/demographics`. Publish-gated. Reads `agents.json` in the simulation directory (the file generated during Phase 3 Agent Setup). Expected structure: a list of agent objects with `profession`, `platform`, `age`, `location` fields (or a subset — handle missing fields gracefully with `"unknown"` bucket). Computes: (1) **Profession distribution** — count by `profession` field, sort descending, return top 5 as `[{"profession": str, "count": int, "pct": float}]`, bundle the rest as `"Other"`. (2) **Platform distribution** — count by `platform` field: `{"twitter": int, "reddit": int, "polymarket": int, "total": int}` with pct per platform. (3) **Age bracket distribution** — parse age integer (if present): buckets `18–25`, `26–35`, `36–50`, `51+`; if age absent, classify as `"unknown"`. Return `[{"bracket": str, "count": int, "pct": float}]`. (4) **Location distribution** — count by `location` or `country` field (whichever is present), top 5 + "Other". (5) **Summary line** — plain-English one-liner: "This simulation's {total} agents were predominantly {top_profession} ({top_pct}%) across {platform_count} platforms, distributed across {location_count} regions." Response: `{"simulation_id": str, "topic": str, "agent_count": int, "professions": [...], "platforms": {...}, "age_brackets": [...], "locations": [...], "summary": str, "generated_at": ISO8601}`. `Cache-Control: public, max-age=3600`. Register at `GET /api/simulation/{id}/demographics`. Add to `surfaces_catalog.py`. Update `docs/API.md` with a "Agent Demographics" section.

2. Add a "👤 Demographics" toolbar button to the Step 3 simulation share page (`Step3Simulation.vue`). Panel layout: (1) A `summary` line at the top in muted italic text. (2) A horizontal stacked bar showing platform distribution (violet = Twitter, orange = Reddit, green = Polymarket). (3) A top-5 professions list with inline percentage bars (same style as Archetype Atlas profession bars). (4) An age bracket distribution bar chart (4 horizontal bars). (5) A top-5 locations list with percentages. All values default to `"–"` if data is absent. Bilingual labels (EN/ZH-CN). Add Demographics data to the EmbedDialog metadata section: show `agent_count`, `top_profession` (with pct), and `platform_distribution` in one line. Add 5 unit tests: published simulation with valid `agents.json` returns 200 with `professions` array; `platforms` totals to `agent_count`; `age_brackets` percentages sum to 100 (within float tolerance); unpublished simulation returns 404; simulation with no `agents.json` returns 404. Log to memory: "Simulation Agent Demographics created 2026-09-26. GET /api/simulation/{id}/demographics — reads per-simulation agents.json; computes: profession distribution (top 5 + Other), platform distribution (twitter/reddit/polymarket + pcts), age bracket distribution (18-25/26-35/36-50/51+), location distribution (top 5 + Other), plain-English summary line. Step3: '👤 Demographics' panel. EmbedDialog: agent_count + top_profession + platform_distribution. Distinct from Agent Archetype Atlas (aggregate cross-simulation) — this is per-simulation population profile."

3. Add a `GET /api/compare-demographics?ids=id1,id2,...` lightweight extension endpoint (~40 LoC, build on top of the demographics endpoint) that returns the demographics for 2–5 simulations side by side: for each simulation, the top profession, top location, platform distribution, and agent count. This is not a separate surface — it reuses `demographics.py`'s internal function and returns the data in the same compare-style response format as the Simulation Comparison API (#3). It surfaces the demographic *cause* of the signal *effect* surfaced by `GET /api/compare` — completing the research loop: what happened (comparison) + who drove it (demographics comparison). Add 2 unit tests: `GET /api/compare-demographics?ids=a,b` returns 200 with a list of 2 demographics objects; single ID returns 400.

## Selection Rationale

Five ideas targeting live data pipeline (HuggingFace sync), push integration (webhooks), cross-simulation analytics (comparison), contributor activation (Hacktoberfest issue queue), and research depth (per-simulation demographics).

- **HuggingFace Sync (#1)** — PR #311 created the link; this creates the pipeline. Nvidia-acquired HuggingFace raised the platform's profile for dataset discovery. Turns a static README badge into a live growing dataset. Small effort, permanent acquisition surface.

- **Webhook System (#2)** — Eliminates the poll-or-miss gap in MiroShark's event delivery. Reuses existing HMAC signing infrastructure (PR #152). Hacktoberfest angle: `docs/WEBHOOKS.md` + 5 named integration targets turn the webhook system into a menu of clearly scoped Hacktoberfest issues.

- **Simulation Comparison (#3)** — The first cross-simulation analytical tool. Trajectory overlap + divergence score + comparison note gives researchers a quantitative diff between related scenarios. Paper citation hook (Sep 30, 4 days): comparative simulation results are a concrete methodological finding.

- **Hacktoberfest Issue Filer (#4)** — The missing piece after the Readiness Kit (Aug 30). 40+ scoped specs exist as local commits; this files them as discoverable, labeled GitHub issues. Hacktoberfest 2026's shift to meaningful AI contributions means a well-scoped AI simulation feature issue is better Hacktoberfest material than it's ever been. `DRY_RUN=1` makes it safe to test before the Oct 1 window opens.

- **Agent Demographics (#5)** — Answers the "who were the agents?" question for any specific simulation. The research hook: demographic composition is a methodological variable that affects signal validity. `GET /api/compare-demographics` chains with Comparison (#3) to deliver the full cause+effect analytical pair.
