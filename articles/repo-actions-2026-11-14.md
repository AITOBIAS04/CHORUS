### 1. Simulation Difficulty Rating

**Type:** Feature
**Effort:** Small (hours)
**Impact:** Every existing analytics metric describes the simulation *outcome* (direction, confidence, controversy, volatility). None measures the *question*. A topic where agents enter 48% BULLISH / 42% BEARISH / 10% NEUTRAL is structurally different from one where 82% enter BULLISH — the first is a contested question, the second is a consensus-seeking scenario. A `difficulty_score` (0–100) based on the initial stance distribution's entropy captures this: high entropy = many agents started conflicted, low entropy = most started aligned. For operators choosing scenarios: "I want to run a genuinely contested simulation" is now answerable. For articles and sharing: "agents entered this simulation nearly split" is a compelling setup hook. For researchers: topic difficulty is an independent variable for cross-simulation analysis. Zero new data sources — derived from round 1 of `trajectory.json` where initial stances are recorded.

**How:**
1. Create `backend/app/services/difficulty_service.py` (~90 LoC, pure stdlib). Accept `sim_id: str`. Load `trajectory.json` → extract round 1 entries → count per-agent initial stances: `{BULLISH: int, BEARISH: int, NEUTRAL: int}`. Compute proportions `p = [count/total for count in counts if count > 0]`. Shannon entropy: `H = -sum(p_i * log2(p_i) for p_i in p)`. Max entropy for 3 classes = `log2(3) ≈ 1.585` bits. `difficulty_score = round((H / 1.585) * 100)`. `difficulty_label`: "High" (≥65), "Moderate" (35–64), "Low" (<35). `initial_stance_distribution: {bullish_pct, bearish_pct, neutral_pct}` (rounded to 1dp). If `trajectory.json` absent or round 1 missing: `{available: false, reason: "insufficient_data"}`. Cache to `storage/simulations/{id}/difficulty.json` (immutable after sim completes — initial stances never change). Merge `difficulty_score`, `difficulty_label`, `initial_stance_distribution` into `signal.json`. Add 5 unit tests: perfectly split 3-way → score near 100; all BULLISH → score = 0; 2-way split → intermediate score; missing trajectory → `available: false`; `initial_stance_distribution` values sum to 100.
2. Add `GET /api/simulation/:id/difficulty` to `backend/app/api/difficulty.py`. Keyless for published sims. `Cache-Control: max-age=86400, public`. Response: `{available: bool, difficulty_score: int, difficulty_label: str, initial_stance_distribution: {bullish_pct: float, bearish_pct: float, neutral_pct: float}}`. Add `difficulty_score`, `difficulty_label` to the OpenAPI `Signal` schema. Add to `surfaces_catalog.py` (type: `analytics`). Add to `docs/API.md` under "Analytics". Add 2 integration tests: endpoint returns 200 with `difficulty_score` for a completed published sim; `difficulty_score` present in `signal.json` after sim completion.
3. Add a "Difficulty" row to the signal card in Step 3 (below direction/confidence): `{difficulty_label} · {initial_stance_distribution short form}`. Add `?sort=difficulty_score` gallery sort option ("Most Contested First" / "Most Consensus-Driven First"). Add `difficulty_score` to the article generator's intro block: "Agents entered this simulation {difficulty_label.lower()}-contested ({initial_bullish_pct}% initially bullish)." Add 2 frontend unit tests: signal card renders "Low" difficulty label for a low-entropy sim; gallery sort option includes "Most Contested First".

### 3. Simulation Checkpoint & Resume

**Type:** Feature
**Effort:** Medium (1-2 days)
**Impact:** Currently, a completed simulation is immutable — the only way to explore an alternative scenario is to start a new simulation from scratch. `POST /api/simulation/:id/checkpoint?round=N` exports the full simulation state at round N as a portable JSON snapshot: all agent beliefs, platform states, event log, and world graph attributes at that point. `POST /api/simulations/resume` accepts a checkpoint JSON + a new director event and launches a new simulation that starts from round N+1 with the imported state. This enables "what if" branching: "What if the Fed had announced an emergency rate cut at round 15 of this simulation?" The operator runs the original to round 24, checkpoints at round 14, injects the new event, and resumes from round 15. The two runs can then be compared using the existing Simulation Comparison View (suggested Nov 6) or the volatility/difficulty metrics. For researchers: the checkpoint format is the standard for reproducibility — any simulation can be forked from any point. No LLM calls required for checkpoint export; the resume launch follows the existing simulation launch path.

**How:**
1. Create `backend/app/services/checkpoint_service.py` (~200 LoC, pure stdlib). `export_checkpoint(sim_id: str, round_number: int) -> dict`: Load `trajectory.json` → filter to rounds ≤ N → extract per-agent beliefs at round N (final entry per agent up to round N). Load `storage/simulations/{id}/config.json` → include `{topic, agents_count, platforms, rounds_total}`. Load `storage/simulations/{id}/world_graph.json` if present → include world graph state. Load `storage/simulations/{id}/events.json` if present → filter to events at round ≤ N. Build checkpoint: `{format_version: "1.0", source_sim_id: sim_id, checkpoint_round: N, topic: str, agent_states: [{agent_id, stance, belief_history: last 3 rounds, influence_score}], platform_states: {X: {bullish_pct, post_count}, Reddit: {...}, Polymarket: {...}}, event_log: [{round, description}], world_graph_snapshot: dict | null, exported_at: str}`. Write to `storage/simulations/{id}/checkpoints/round-{N:04d}.json`. Return the checkpoint dict. `validate_checkpoint(data: dict) -> bool`: check `format_version`, `source_sim_id`, `agent_states`, `platform_states` keys present and non-empty. Add 5 unit tests: checkpoint at round 0 → empty event_log; `agent_states` length equals sim agent count; `platform_states` has entries for each configured platform; validate_checkpoint returns False for missing `agent_states`; checkpoint at round > total_rounds → raises `ValueError`.
2. Add `POST /api/simulation/:id/checkpoint` to `backend/app/api/checkpoint.py`. Session-auth. Query param `?round=N` (required; integer 1 ≤ N ≤ sim's total_rounds). Response: `Content-Type: application/json`, `Content-Disposition: attachment; filename="sim-{id}-checkpoint-round{N}.json"`. Returns the checkpoint JSON directly. Rate limit: max 5 checkpoint exports per session per hour (checkpoints are large; prevent abuse). Add `POST /api/simulations/resume` to `backend/app/api/resume.py`. Session-auth. Request body: `{checkpoint: dict, director_event: str, additional_rounds: int = 12}`. Validate checkpoint via `validate_checkpoint`. Launch a new simulation using the existing simulation launch service: pre-populate `agent_states` from the checkpoint, set `start_round = checkpoint_round + 1`, inject `director_event` as the first event. The new simulation ID is returned immediately; the sim runs asynchronously as normal. Response: `{new_sim_id: str, started_at: str, resume_from_round: int, director_event: str}`. Add both routes to `surfaces_catalog.py` (types: `export`, `create`). Add to `docs/API.md` under "Simulation Lifecycle" with a "Branching Simulations" subsection and example curl workflow. Add 3 integration tests: checkpoint export returns valid JSON with `format_version`; resume endpoint returns `new_sim_id`; resume with invalid checkpoint data returns 400.
3. Add a "Checkpoint" button to the Step 3 timeline view — appears at each round marker when hovered. Clicking exports the checkpoint for that round (triggers the download). Add a "Resume from here" secondary button in the same hover state: opens a dialog with a director event text input and an `additional_rounds` slider (8–48, default 12). Submit button calls `POST /api/simulations/resume` and redirects to the new simulation once it starts. Add a visual indicator on the gallery card for simulations that were resumed from a checkpoint: a small "branched" badge (↗ icon) with a tooltip "Resumed from [source_sim_id] round [N]". The badge links to the source simulation. Add 2 frontend unit tests: timeline hover shows checkpoint button on each round marker; resume dialog submit button is disabled until director_event input is non-empty.

### 4. HuggingFace Dataset Auto-Sync

**Type:** Integration
**Effort:** Medium (1-2 days)
**Impact:** The README has carried a HuggingFace dataset badge (`MiroShark/social-prediction-market-sim`) since launch. The dataset exists. But it is not auto-populated — an operator must manually export and upload simulation data for the dataset to grow. This means the dataset stagnates while the platform runs thousands of simulations. `POST /api/simulation/:id/publish` (the existing publish step) should trigger an async push: append the simulation's `signal.json` + a flattened row from `trajectory.json` to the HuggingFace dataset as a new Parquet partition. The HuggingFace Hub Python client (`huggingface_hub`) is already a likely dependency (or easily added); the `HF_TOKEN` environment variable is the only new secret needed. The dataset grows organically with every published simulation. HuggingFace search surfaces the dataset to ML researchers searching "social simulation", "swarm intelligence", or "market prediction". Each dataset row links back to the simulation share URL — driving organic traffic from HuggingFace Spaces and Papers. Competitor simswarm has no public dataset. This is a durable distribution moat.

**How:**
1. Create `backend/app/services/hf_sync_service.py` (~180 LoC). Import `huggingface_hub` (add to `backend/pyproject.toml` as an optional dependency under `[project.optional-dependencies] hf = ["huggingface-hub>=0.23"]`). Check `HF_TOKEN` environment variable at import time — if absent, the module logs a warning and all public functions become no-ops (graceful degradation; HF sync is optional). `build_dataset_row(sim_id: str) -> dict`: Load `signal.json` → extract `{sim_id, topic, direction, confidence_pct, controversy_score, volatility_score, difficulty_score, total_rounds, total_agents, completed_at, share_url}`. Load `trajectory.json` → compute `{mean_bullish_pct_per_round: list[float], final_bullish_pct: float, platform_count: int}`. Load `config.json` → extract `{platforms: list[str], estimated_cost_usd: float | null}`. Build a flat dict suitable for a Parquet row: all scalar values, arrays as JSON strings. `push_to_hf(sim_id: str) -> bool`: call `build_dataset_row`. Use `huggingface_hub.CommitOperations` to append a new row to `data/simulations.parquet` in the `MiroShark/social-prediction-market-sim` dataset (using `huggingface_hub.HfApi().create_commit`). Handle `huggingface_hub.errors.HfHubHTTPError` → log error, return `False`. On success: write `{hf_pushed: true, pushed_at: str, dataset_url: "https://huggingface.co/datasets/MiroShark/social-prediction-market-sim"}` to `storage/simulations/{id}/hf_sync.json`. Return `True`. Add 4 unit tests: `push_to_hf` returns `False` gracefully when `HF_TOKEN` not set; `build_dataset_row` returns all required scalar fields; `hf_pushed: true` written to `hf_sync.json` on success; `HfHubHTTPError` caught and returns `False` without raising.
2. Hook `hf_sync_service.push_to_hf(sim_id)` into the existing `POST /api/simulation/:id/publish` handler (wherever `published: true` is written to `config.json`). Call it as an async background task (Python `asyncio.create_task` or `BackgroundTasks` if using FastAPI) so the publish endpoint returns immediately — the HF push completes in the background within 5–30 seconds. Add `hf_sync_status` to the `GET /api/simulation/:id` response: `{available: bool, pushed: bool, pushed_at: str | null, dataset_url: str | null}` (read from `hf_sync.json` if it exists). Add `HF_TOKEN` to `docs/INSTALL.md` under "Environment Variables" (optional section): "Set `HF_TOKEN` to auto-push published simulations to HuggingFace. If unset, publishing still works but HF sync is skipped." Add 2 integration tests: `publish` endpoint returns 200 and `hf_sync.json` does not exist when `HF_TOKEN` is unset (graceful degradation); `GET /api/simulation/:id` returns `hf_sync_status.available: false` when `HF_TOKEN` is unset.
3. Add an `hf_sync_status` indicator to the Step 3 share panel: a small "Synced to HuggingFace" badge with the HuggingFace logo (use the existing `huggingface` SVG from the README badge), linking to the dataset URL, shown only when `hf_sync_status.pushed: true`. Show a spinner + "Syncing to HuggingFace…" for 30 seconds after publish if `pushed: false` (polling the sim endpoint at 10s intervals). Add a dataset stats widget below the badge: "Dataset: {N} simulations published" (fetch `https://huggingface.co/api/datasets/MiroShark/social-prediction-market-sim` for `cardData.dataset_info.download_count` or row count). ### 5. Operator RSS Feed

**Type:** Integration
**Effort:** Small (hours)
**Impact:** An operator who publishes 3 simulations per week has no distribution mechanism for followers who want to track new runs without polling the API. RSS is the standard subscription protocol for content producers — it is natively supported by Feedly, NetNewsWire, Reeder, Apple News, and thousands of other readers. `GET /api/users/:id/simulations.rss` returns an Atom 1.0 feed of an operator's published simulations, newest first. Each entry: title = simulation topic, summary = "Direction: BULLISH · Confidence: 73% · 24 rounds · {platform list}", link = share URL, published = `completed_at`. The feed is keyless and cacheable (1-hour TTL) — any reader can subscribe with just the URL. This addresses the distribution gap without requiring a notification channel (Telegram, Discord, Slack). For researchers tracking operators over time: an RSS reader gives a passive stream of new simulations to cite. The HuggingFace dataset push (#4 above) brings ML audience; the RSS feed brings content/analyst audience. No new data sources — built entirely from `signal.json` and `config.json` files in the existing storage layout.

**How:**
1. Create `backend/app/services/rss_service.py` (~120 LoC, pure stdlib). Accept `operator_id: str`, `limit: int = 20`. Scan `storage/simulations/*/config.json` for sims where `operator_id` matches and `published: true` and `status: "completed"`. Sort by `completed_at` descending. Take up to `limit` entries. For each: load `signal.json` → extract `{direction, confidence_pct, total_rounds, controversy_score}`. Load `config.json` → extract `{topic, platforms, completed_at, share_url}`. Build Atom 1.0 XML using `xml.etree.ElementTree` (stdlib): `<feed xmlns="http://www.w3.org/2005/Atom">` root with `<id>`, `<title>`, `<updated>`, `<author>`, `<link rel="self">`. Each `<entry>`: `<id>` = share URL, `<title>` = topic, `<summary>` = f"Direction: {direction} · Confidence: {confidence_pct}% · {total_rounds} rounds · Platforms: {', '.join(platforms)}", `<link href=share_url>`, `<published>` = ISO 8601 `completed_at`. Use `xml.etree.ElementTree.indent` (Python 3.9+) for pretty-print. Return the XML string. Add 4 unit tests: feed with 0 entries renders valid Atom XML with no `<entry>` children (not empty document); feed with 3 entries sorts newest first; `xml.etree.ElementTree.fromstring` parses output without error; `limit` parameter clamps to max 50.
2. Add `GET /api/users/:id/simulations.rss` to `backend/app/api/rss.py`. Keyless. `Content-Type: application/atom+xml; charset=utf-8`. `Cache-Control: max-age=3600, public`. Route also supports `GET /api/users/:id/simulations.atom` as an alias. If `operator_id` is not found (no published sims): return a valid empty Atom feed with `<title>No simulations yet</title>` and `<updated>` = current time — not 404 (the operator exists, they just haven't published). Add `rss_url`, `atom_url` fields to the existing `GET /api/users/:id/profile` response (or create this minimal profile endpoint if absent: `{operator_id, rss_url, atom_url, gallery_url}`). Add to `surfaces_catalog.py` (type: `distribution`). Add to `docs/API.md` under "Operators" with a code example: `curl https://miroshark.xyz/api/users/{id}/simulations.rss > feed.xml` and a note: "Subscribe in any Atom/RSS reader with the feed URL." Add 2 integration tests: feed endpoint returns `Content-Type: application/atom+xml` for operator with published sims; empty-operator feed returns valid Atom XML with 0 `<entry>` children and HTTP 200.
3. Add an RSS subscribe button to the operator gallery page (wherever `?operator=:id` filters the gallery — if the route exists). The button opens a small popover with the feed URL pre-filled in a copyable input + a "Subscribe in Feedly" deep-link (`https://feedly.com/i/subscription/feed/{encoded_url}`) + an "Subscribe in NetNewsWire" deep-link (`netnewswire://add?url={encoded_url}`). Add a `<link rel="alternate" type="application/atom+xml" href="...simulations.rss">` tag to the gallery page's `<head>` when filtered by operator — allows browsers and extensions to auto-detect the feed. Add 2 frontend unit tests: RSS subscribe button renders when gallery is filtered by `operator_id`; `<link rel="alternate">` tag is present in `<head>` for operator-scoped gallery pages.
